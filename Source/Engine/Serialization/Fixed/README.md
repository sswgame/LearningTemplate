# 고정 배치형(B) 코덱 계약

> 질문: 같은 빌드끼리만 읽는 바이트(`FixedLayout`)는 어떤 규칙으로 쓰고 읽는가?
> 독자: 롤백, 넷 스냅샷, 온라인 프로토콜의 메시지 타입을 만들거나 `PROPERTY` 키를 바꾸는 사람.
> 결론: `REFLECT` 타입은 선언 하나에서 자기 기술형(A)과 B 코덱이 함께 생기고, B 의 바이트 배치는 필드 선언 순서와 `Min`·`Max`·`Step`·`MaxCount` 가 정한다. 배치가 바뀌면 스키마 해시가 바뀌어 다른 빌드의 바이트는 거절된다.

생성기(`Tools/ReflectionParser`)가 만든 코덱의 런타임은 `FixedLayout.h`, 생성 코드는 `.gen.cpp` 에 있습니다. 헤더 주석 `FixedLayout.h` 가 호출 방법을, 이 문서가 바이트 규칙을 설명합니다. 이 문서의 절 번호(3.4 등)는 코드 주석이 가리키므로 바꾸지 않습니다.
왜 이 구조인지는 [결정 기록](../../../../docs/09_Decisions.md) 5-4 · 5-9 에 있습니다.

## 2. 두 형식의 역할

기준은 하나입니다. **쓴 빌드와 다른 빌드가 그 바이트를 읽을 수 있는가.** 읽을 수 있어야 하면 A, 같은 빌드만 읽으면 B 입니다.

| 데이터 | 형식 |
|---|---|
| 디스크 세이브, 에셋 · 쿠킹 씬, 핫 리로드 상태 보존, 에디터 복사 · 되돌리기 | A (`BinarySerializer`) |
| 롤백 상태, 결정성 해시용 스냅샷, 장르 스냅샷 · 넷 복제, 온라인 클라이언트 프로토콜 | B |
| 설정(XML) | 텍스트 |

진행 중인 대전을 저장하는 `FightingMatch::writeState` 는 세이브이므로 A, 롤백은 B 입니다. 서버 버스 메시지는 서버 사이에 핸드셰이크가 없어 A 입니다(결정 기록 5-9 "서버 버스는 A").

## 3. 명세

### 3.1 코덱을 받는 타입

생성기는 적격인 모든 `REFLECT` 타입에 B 코덱을 만듭니다. 사용자는 아무것도 더 선언하지 않습니다. 적격이란 `Transient` 가 아닌 모든 `PROPERTY` 의 타입이 3.4 의 표 안에 있다는 뜻이고, 기반 클래스도 적격이어야 합니다.
적격이 아닌 타입은 코덱 없이 등록되고, 그 이유(필드 이름과 타입)는 `.gen.cpp` 주석과 `--dump` 출력에 남습니다. 오류로 멈추지는 않습니다.
B 가 필요한지는 그 타입을 받는 등록 API(롤백, 넷 채널, 온라인 메서드)가 정하고, 이 API 가 기동 때 코덱이 있는지 확인해 없으면 이유와 함께 멈춥니다. `FixedLayout::write` · `read` 는 저수준 진입점이라 게임 코드는 등록 API 를 씁니다.

비용: 새 번역 단위가 없고(기존 `.gen.cpp` 에 덧붙음) 덧붙는 것은 템플릿 없는 직선 코드이며, `.gen.cpp` 만 `FixedLayout.h` · `BitStream.h` 를 include 합니다. 단계 1 전후 Debug 는 `Engine.dll` +153,088 B(+0.7 %), `GameFramework.dll` +81,408 B(+1.0 %)였고 `REFLECT` 타입 454 개 중 적격은 173 개였습니다. 7-a · 7-b 전후 Release 는 `Engine.dll` +12,800 B(+0.08 %), `GameFramework.dll` +5,120 B(+0.10 %), `App.exe` -512 B 입니다. 단계 1 의 Release 전후 값은 재지 않았고, 재려면 단계 1 직전 커밋과 지금을 같은 Release 구성으로 지어 `Bin` 의 파일 크기를 견줍니다.

### 3.2 생성 코드의 위치

- 코덱 함수는 `sw::generated::Registrar<T>` 특수화의 정적 멤버로 `.gen.cpp` 에 있습니다. `REFLECT_BODY()` 가 이 등록기를 friend 로 선언하므로 private 필드도 접근합니다.
- 등록기가 `TypeInfo::_pFixedCodec` 에 코덱 테이블(쓰기, 읽기, 비교, 스키마 해시 함수 포인터) 주소를 넣습니다.
- 중첩 타입이 같은 헤더에 있고 필드가 공개이면 부모 코덱 안에 필드 코드를 펼치고, 그렇지 않으면 FQN 캐시로 코덱을 찾아 간접 호출합니다.

### 3.4 필드 타입별 인코딩

| 필드 타입 | 인코딩 |
|---|---|
| `bool`, `uint8` 플래그 | 1 비트 |
| 정수, `Min` · `Max` 있음 | 범위 비트 수(`BitMath::computeBitsRequired`) |
| 정수, 범위 없음 | `writeVarInt`(부호 있음) / `writeVarUint` |
| `float32`, `Step` 있음 | 칸 번호를 범위 비트 수로 씀(`Min` · `Max` 필수). 칸 수를 넘는 번호는 읽을 때 `OutOfRange` |
| `float32`, `Step` 없음 | 32 비트 원본 비트. `Min` · `Max` 가 있으면 쓰기와 읽기가 범위를 확인 |
| `float64` | 64 비트 원본 비트(`Step` 불가) |
| `float3` 등 수학 타입 | 원소마다 위 규칙 |
| 열거형 | 3.7 |
| `string`, `vector<T>` | `MaxCount` 필수, 개수 + 원소(3.5) |
| `T[N]`, `std::array<T, N>` | 원소 N 개, 개수 없음 |
| 적격 `REFLECT` 타입 | 그 타입의 필드(3.6) |

표에 없는 타입이 하나라도 있으면 적격이 아닙니다(포인터, 참조, 핸들, 접근자 프로퍼티, `unordered_*`, `MaxCount` 없는 가변 길이, 적격이 아닌 구조체). `unordered_*` 는 순회 순서가 비결정적이라 같은 값이 다른 바이트가 되기 때문에 뺍니다.

B 전용 메타데이터는 기존 `PROPERTY()` 키로 적습니다.

| 키 | 뜻 |
|---|---|
| `Min` · `Max` | 허용 범위이자 와이어 범위. 실수 리터럴 또는 필드 이름(쉼표 목록 가능). 인스펙터 슬라이더 범위는 `UIMin` · `UIMax` |
| `Step` | 양자화 간격(새 키) |
| `MaxCount` | 문자열 · 컨테이너 최대 길이(새 키, 1 이상 정수 리터럴 또는 C++ 정수 상수 이름) |

- `Min` · `Max` 는 `float32` 로 보관하므로 정수 경계는 `float32` 로 정확해야 합니다(2e9 는 되고 16777217 은 안 됩니다). 숫자가 아닌 필드의 `Min` · `Max` 는 생성 오류입니다.
- 범위 밖 정수는 쓰기가 실패합니다(자르지 않습니다). `Step` 이 붙은 실수만 손실 인코딩이라 경계로 자릅니다.
- 쓰기 실패는 결함이므로 `FixedLayout::write` 는 `[[nodiscard]] bool` 을 반환하고 등록 API 가 단언하거나 멈춥니다.

### 3.5 가변 길이

- 문자열과 `vector` 는 `MaxCount` 가 있어야 적격입니다. 넷에서 받은 길이로 메모리를 잡기 전에 상한이 있어야 하기 때문입니다.
- 개수는 `[0, MaxCount]` 범위 정수로 씁니다. 쓸 때 `MaxCount` 를 넘으면 쓰기 실패, 읽을 때 넘으면 `OutOfRange`, 잘린 스트림은 `Truncated` 입니다.
- 상한은 정적 값입니다. 런타임 설정이 상한이면 그보다 크거나 같은 정적 상한을 적고 데이터 쪽 검증을 따로 둡니다.
- 같은 상한을 코드도 쓰면 상수 이름으로 적습니다(`MaxCount = kMaxSlotCount`). 생성기(`AstVisitor::resolveMaxCountName`)가 필드가 든 타입, 바깥 타입, 바깥 네임스페이스 순으로 상수를 찾아 값을 계산하고, 그 값이 코덱 · 스키마 해시 · `PropertyMetadata::_maxCount` 에 들어갑니다. 못 찾거나 정수가 아니거나 1 보다 작으면 생성 오류입니다. 상수가 다른 헤더에 있으면 그 헤더를 include 해야 합니다.

### 3.6 중첩 형식과 필드 순서

- 필드는 `PROPERTY()` 가 붙은 멤버를 선언 순서대로 쓰고, 기반 클래스의 필드가 먼저입니다. 크기 접두는 없습니다.
- 다중 상속 타입은 생성 오류입니다(`collectBase`).
- 다른 헤더의 중첩 타입은 열거자 · `ENUM` · `REFLECT()` 표시만 읽고, 실행 시간에 `FixedLayout::findCodec` 으로 그 코덱을 찾아 의존을 확인합니다.

### 3.7 열거형

- 값만 씁니다(이름 해시 없음). 열거자를 바꾸면 스키마 해시가 바뀝니다.
- `ENUM( Count = … )` 가 있으면 `[최소 열거자, Count - 1]`, 없으면 `[최소 열거자, 최대 열거자]` 범위 비트 수로 씁니다. 범위가 32 비트를 넘는 열거형은 생성 오류입니다.
- 읽을 때 등록된 열거자 값이 아니면 `OutOfRange` 입니다. `ENUM( Flags )` 는 기반 타입 폭의 비트로 쓰고, 등록된 비트 밖이 켜져 있으면 쓰기와 읽기가 모두 실패합니다.

### 3.8 런타임 범위 양자화

위치 범위를 같은 스냅샷의 필드가 정하면(`MechArenaSnapshot::_arenaHalfSize`) 그 값도 바이트에 싣고, `Min` · `Max` 가 필드 이름을 받게 해서 표현합니다. 벡터는 원소마다 쉼표로 나눕니다.

```cpp
PROPERTY( Step = 0.01, Min = "-_arenaHalfSize, 0, -_arenaHalfSize", Max = "_arenaHalfSize, _ceiling, _arenaHalfSize" )
float3 _position{};
```

- 이름은 자기 타입의 앞선 필드, 없으면 그 타입을 필드로 가진 바깥 타입의 앞선 필드 순으로 찾습니다. 읽기는 선언 순서이므로 범위 필드가 앞에 있어야 하고, 뒤에 있으면 생성 오류입니다.
- 바깥 타입에서 이름을 찾는 것은 중첩 타입을 부모 코덱 안에 펼칠 수 있을 때(3.2)만 됩니다. 펼칠 수 없거나 같은 중첩 타입을 이름이 다른 두 부모가 쓰면 생성 오류입니다.
- 인스펙터와 읽기 공통 끝(`SerializerUtil::isWithinDeclaredRanges`)은 `PropertyMetadata::computeAllowedRange` 하나로 범위를 풉니다. 같은 타입 안의 필드를 가리키는 경계는 생성기가 읽기 함수(`_pReadMinRange` · `_pReadMaxRange`)를 내므로 이름이 틀리면 컴파일이 안 됩니다.
- `Min` · `Max` 는 리터럴, 필드 이름, C++ 숫자 상수 이름(`Max = LockstepSession::kMaxInputDelay`, `-` 를 앞에 붙일 수 있음)을 받습니다. 생성기가 `MaxCount` 와 같은 함수로 상수를 찾아 값을 풀고(`_` 로 시작하는 이름은 필드), 못 찾았거나 숫자가 아니면 생성 오류입니다.
- 한계: `Step` 은 리터럴만 받습니다(상수와 짝인 곳이 없었습니다). 데이터로 정해지는 범위는 검증 훅(3.10)에 둡니다.

### 3.9 엔디언과 정렬

`BitWriter` 는 낮은 비트부터 채우고 정수는 시프트로, 실수는 `memcpy` 로 얻은 `uint32` 비트를 같은 경로로 씁니다. 호스트 엔디언과 무관하고 비트 단위라 정렬과 패딩이 없습니다.

### 3.10 스트림 구성과 읽기 의미

```
[스키마 해시 64 비트] [최상위 타입의 필드들, 선언 순서, 태그 · 크기 없음]
```

- 해시는 최상위 한 번만 씁니다. 중첩 타입과 컨테이너 원소는 해시 없이 바로 필드입니다.
- 넷 채널은 핸드셰이크가 해시를 이미 확인하므로 메시지마다 싣지 않습니다. 본문만 쓰는 경로는 확인을 마친 `NetMessageChannel` 안에만 있습니다. 온라인 연결은 메시지마다 해시를 싣고, 받는 타입이 바뀐 빌드끼리의 어긋남은 이 해시가 `SchemaMismatch` 로 거절합니다.
- 읽기는 원자적입니다. 대상을 복사한 임시 객체에 읽고 끝까지 성공했을 때만 옮기며, 실패하면 대상은 그대로입니다(B 에 없는 필드를 보존하려고 복사본에서 시작합니다).
- `FixedReadResult` 는 `[[nodiscard]]` 열거형입니다. `Ok`, `SchemaMismatch`, `Truncated`, `OutOfRange`, `ValidateFailed`, `TrailingData`.
- 코덱이 없는 타입을 `write` · `read` · `equals` · `getSchemaHash` 에 넘기면 이유를 로그에 남기고 멈춥니다(대체 값을 돌려주지 않습니다).
- 타입에 `REFLECT( Validate = 함수 )` 가 있으면 읽기 끝에 부르고 오류가 있으면 `ValidateFailed` 입니다. 남은 비트는 바이트 경계까지의 패딩만 허용합니다.

### 3.11 스키마 해시

생성기가 적격 타입마다 정규 문자열을 만들고 FNV-1a 64 로 해시합니다. 정규 문자열에는 다음이 들어갑니다.

1. 인코딩 규칙 버전 `FixedLayout::kVersion`(인코더 규칙을 바꾸면 이 값 하나만 높여 모든 해시를 바꿉니다).
2. 타입 FQN.
3. 필드마다 선언 순서로 이름, 정규화한 타입 이름, B 에 영향을 주는 키(`Min`, `Max`, `Step`, `MaxCount`)와 값, 비트필드 여부.
4. 열거형이면 FQN, 기반 타입, 모든 열거자의 `이름=값`.
5. 다른 `REFLECT` 타입이면 그 타입의 해시(실행 시간에 코덱 테이블에서 얻어 한 번만 계산).

필드 이름을 넣는 것은 같은 타입 필드 둘의 순서 변경을 잡기 위해서입니다. 멤버 초기값, `DisplayName` · `Tooltip` 같은 표시 키, 이름 변경 리다이렉트는 바이트 배치와 무관해서 넣지 않습니다. 단위를 바꾸는 것처럼 해시에 안 잡히는 의미 변경은 넷의 손 버전 상수, 온라인의 `kBaseVersion` 을 올립니다.
생성기는 정규 문자열 목록을 `FixedSchemas.gen.txt` 로 남깁니다. 해시가 왜 바뀌었는지 비교하는 진단용이고 빌드는 읽지 않습니다.

### 3.12 생성 비교

비교는 B 와 같은 필드 집합을 선언 순서로 비교합니다. 실수는 비트 패턴으로 비교하므로 `NaN == NaN` 은 참, `-0.0f == +0.0f` 는 거짓입니다("같은 바이트를 만드는가"와 뜻이 같아야 롤백 불일치 검사에 쓸 수 있습니다). `operator==` 는 생성하지 않고 `FixedLayout::equals( a, b )` 로 부릅니다.

### 3.13 열거형 이름 조회

B 는 열거자 이름을 쓰지 않습니다. 로그용 `getEnumName` 은 FQN 해시로 `TypeRegistry` 를 찾고 없으면 `"Unknown"` 을 반환합니다(표시 전용이라 폴백 금지의 대상이 아닙니다). 빈틈 없는 열거형의 이름은 `EnumInfo::_listDenseName` 에 값으로 보관합니다.

### 3.14 마이그레이션 확장 지점

B 의 기본 동작은 스키마 해시가 다르면 거절입니다. 읽기가 `SchemaMismatch` 를 내기 직전에 변환 레지스트리 (기록된 해시, 대상 타입) → 변환 함수를 볼 자리를 한 곳 비워 두었지만, 변환할 옛 B 데이터가 없어 구현하지 않았습니다. 옛 바이트를 해석하려면 옛 `FixedSchemas.gen.txt` 를 배포본과 함께 보관해야 합니다.

## 5. 호환 정책

- **A 의 스키마 진화는 그대로입니다.** 세이브와 에셋은 태그, 기록 타입 변환(`tryCoerceBinaryPayload`), 버전 머리(판이 정확히 같을 때만 읽음)로 읽습니다. 이관 함수와 옛 판 리더는 첫 출시 전이라 두지 않습니다(결정 기록 5-4).
- **롤백 · 결정성 스냅샷 · 프로세스 안 복제**는 같은 프로세스, 같은 빌드입니다. 해시 불일치는 결함이라 `SW_ASSERT` 와 오류 로그로 멈춥니다.
- **게임 넷 연결**은 정확히 같은 버전만 받습니다. 채널에 등록한 메시지 타입의 스키마 해시를 모두 `NetWireVersion::combine` 에 섞으므로(`NetMessageChannel`) 손 버전을 높이지 않아도 배치가 바뀌면 핸드셰이크가 `VersionMismatch` 로 거절합니다.
- **온라인 서비스**는 접속 핸드셰이크의 첫 필드가 온라인 스키마 해시이고, 서버는 다른 어떤 바이트보다 먼저 비교합니다. 해시는 빌드에 올라온 키트 프로토콜 항목 전부의 영역과 메시지 스키마 해시, `kBaseVersion` 을 섞습니다(`OnlineProtocolRegistry::computeSchemaHash`). 다르면 `kVersionMismatch` 로 거절하고 서버 해시를 실어 보내며, 클라이언트는 "업데이트 필요"로 끝나고 다시 접속하지 않습니다. 이 첫 필드와 거절 응답은 B 가 아니라 해시 64 비트 + 오류 코드의 고정 형식입니다.
- 타입 ID(`TypeInfo::_typeID`)는 실행 순서로 정해지는 로컬 인덱스라 와이어에 싣지 않습니다. 타입을 실어야 하면 FQN 해시를 씁니다.

## 6. 테스트

`Test/ReflectionTest/TestFixedLayout.cpp` 가 이 명세를 확인합니다.

- 왕복(경계값, 빈 컨테이너, `MaxCount` 개)과 `FixedLayout::equals`.
- 스키마 변경 거부: 필드 순서 · 이름, 열거자 추가, `Step` · `Min`, `kVersion` 변경마다 해시가 달라지고 `SchemaMismatch` 가 나야 합니다.
- 적격 판정: 포인터 필드나 `MaxCount` 없는 `vector` 를 가진 타입은 코덱이 없고, 등록 API 에 넘기면 이유를 담아 멈춥니다.
- 잘림 · 범위: 바이트를 하나씩 줄인 모든 접두에서 `Truncated`, 범위 밖 개수와 열거자는 `OutOfRange`, 실패 뒤 대상은 그대로.
- 쓰기 실패: 범위 밖 정수와 `MaxCount` 초과에서 `write` 가 `false`.
- 손 코덱을 지울 때는 같은 시뮬레이션을 손 코덱과 B 로 저장 · 복원해 이후 프레임의 상태 해시를 비교합니다(바이트가 아니라 동작).

## 위험

- 사용자가 B 를 선언하지 않으므로 적격이 아닌 타입을 B 로 쓰는 실수는 빌드 시간이 아니라 기동 시간에 드러납니다. 진입점을 등록 API 몇 개로 모아 이유를 담은 오류로 막습니다.
- `REFLECT` 타입의 필드를 정리하거나 순서를 바꾸면 B 형식이 바뀝니다. 롤백 · 스냅샷은 같은 빌드끼리라 영향이 없고, 넷 · 온라인은 옛 빌드와의 연결이 거절될 뿐 조용히 잘못 읽지는 않습니다.
- `Min` · `Max` 가 와이어 범위가 되므로 허용 범위 밖 값을 쓰던 곳은 B 쓰기 실패로 드러납니다. 의도한 결과입니다.
- 스냅샷 구조체에 `REFLECT` 를 처음 붙이면 `TypeRegistry` 에 등록되고 인스펙터 · A 직렬화 대상이 됩니다.
