1. 동시성 및 멀티스레딩 잠재 결함 (Critical / Concurrency)

1.1 TaskManager 큐 포화 시 무한 스핀/일드 데드락 (Thread Starvation & Deadlock)
- 관련 파일: Source/Core/Task/TaskManager.cpp (L1251~L1278), Source/Core/Concurrency/WorkStealingDeque.h (L53~L58)
- 문제점:
  * scheduleReadyTask에서 메인 스레드 큐(_queueMainThread, 고정 크기 1024) 또는 워커 전용 큐(localQ._queue, 고정 크기 4096)에 작업을 인큐할 때 용량이 초과되면 while (enqueue/push == false) std::this_thread::yield(); 루프를 돕니다.
  * 메인 스레드가 1024개를 초과하는 MainThread 친화도 태스크를 등록하는 경우, 메인 스레드 자신이 while 루프에서 스핀하게 되어 dispatchMainThreadTasks()를 영원히 호출하지 못하는 즉각적인 무한 데드락이 발생합니다.
  * 워커 스레드 또한 자신의 큐가 가득 찼을 때 yield 루프에 갇혀 스스로 큐에서 작업을 꺼내지 못하고 다른 워커의 스틸링에만 의존하게 되어 스레드 기아 상태가 발생합니다.
- 개선 권장안:
  * 고정 용량 초과 시 무한 루프 대신 동적 오버플로우 큐(MPSC 연결 리스트 또는 확장 버퍼)로 폴백하거나, 메인 스레드 등록 중에는 즉시 실행/배치 인큐 방식을 지원해야 합니다.

1.2 부모-자식 태스크 완료 통지 시 동기화 레이스 컨디션 (Dekker's Pattern Race)
- 관련 파일: Source/Core/Task/TaskManager.cpp (L1290~L1308)
- 문제점:
  * onTaskFinished에서 부모 태스크 본문 종료와 자식 태스크 종료 시점 사이에 상태 체크(_activeChildren vs _state)가 원자적으로 묶여있지 않습니다.
  * 부모 스레드가 _state.store(WaitingForChildren)를 수행하고 _activeChildren.load()를 확인하는 순간, 다른 코어의 자식 스레드가 _activeChildren.fetch_sub(1)을 수행하고 _state.load()를 확인하는 과정에서 Store-Load 재정렬(Store-Buffer Delay)로 인해 양쪽 모두 상대방이 완료 처리를 맡을 것으로 판단하고 조기 리턴할 수 있습니다.
  * 결과적으로 부모 태스크가 WaitingForChildren 상태로 영구 정지되어 후속 태스크(Successors)가 트리거되지 않고 waitAll()이 멈춥니다.
- 개선 권장안:
  * 부모의 실행 완료 플래그와 자식 잔여 카운트를 단일 원자적 상태 변수(상위 비트 플래그 + 하위 카운터)로 병합하거나, seq_cst 펜스 또는 락 기반 완료 핸드셰이크를 적용해야 합니다.

1.3 FrameDoubleBuffer와 RenderThread 간 프레임 리셋 레이스
- 관련 파일: Source/Core/Memory/FrameArenaAllocator.h (L150~L188), Source/Engine/EngineLoop.cpp (L505~L507)
- 문제점:
  * EngineLoop::endFrame()에서 _frameDoubleBuffer->swapAndResetPrevious()를 무조건 호출합니다.
  * 게임 스레드(GT)가 프레임 N을 마치고 버퍼를 스왑한 뒤 이전 버퍼(N-1)를 reset()할 때, 별도의 전용 렌더 스레드(RenderThread)가 아직 N-1 프레임 패킷을 렌더링 중이라면 RT가 읽고 있는 메모리가 GT에 의해 즉시 덮어씌워지는 데이터 오염(Data Corruption / UAF)이 발생합니다.
- 개선 권장안:
  * RenderThread의 Triple-Buffering 링 버퍼 완료 펜스 신호와 연동하여, RT가 해당 프레임 렌더링을 완전히 마쳤음이 보장된 슬롯만 reset()하도록 동기화 토큰을 도입해야 합니다.

1.4 hashed_string 풀 셧다운 시 AB-BA 교착 상태 (Deadlock Hazard)
- 관련 파일: Source/Core/String/hashed_string.h (L306~L312, L477~L485)
- 문제점:
  * hashed_string의 intern 풀(AllocationInfo)에서 문자열 등록과 전체 해제 시 뮤텍스 획득 순서가 반대로(Inverted) 되어 있습니다.
    - helper_internal() (신규 문자열 생성 시): 1) shard._mutex (Unique Lock) -> 2) _globalAppendMutex 순서로 락 획득
    - clear() (HashedStringPool::shutdown() 시): 1) _globalAppendMutex -> 2) shard._mutex 순서로 락 획득
  * 엔진 종료(shutdown) 또는 모듈 언로드 시점에 워커 스레드가 새로운 hashed_string을 생성하고 있다면, 두 스레드가 서로의 락을 대기하며 영구적인 AB-BA 데드락에 빠집니다.
- 개선 권장안:
  * clear() 함수에서도 샤드 락들을 먼저 모두 획득한 후 _globalAppendMutex를 잠그거나, clear()가 모든 워커 스레드가 완전히 종료(Join/Drain)된 상태에서만 단일 스레드로 호출되도록 라이프사이클을 보장해야 합니다.

1.5 MulticastDelegate 순회 중 구독 해제 시 Use-After-Free (UAF) 위험
- 관련 파일: Source/Core/Delegate/Delegate.h (L399~L418)
- 문제점:
  * MulticastDelegate::broadcast()는 이벤트 발송 중 델리게이트가 삭제되는 것을 방지하기 위해 _broadcastDepth를 올리고, 삭제 요청을 _listPendingRemove에 지연(Defer)시킵니다.
  * 그러나 루프 내부에서는 _listDelegate[entryIndex]._delegate를 매 반복마다 꺼내어 그대로 호출합니다.
  * 만약 앞선 콜백(A)에서 후순위 콜백(B)의 대상 객체를 파괴하고 remove(handleB)를 호출한 경우, B의 핸들이 _listPendingRemove에 들어갔음에도 루프는 계속 돌아 이미 파괴된 인스턴스의 멤버 함수 델리게이트(B)를 호출하는 Use-After-Free(댕글링 포인터 참조) 크래시가 발생합니다.
- 개선 권장안:
  * _broadcastDepth > 0일 때 remove(handle)가 호출되면 해당 슬롯의 _delegate를 unbind()로 즉시 무효화하여 남은 순회에서 호출되지 않도록 방어해야 합니다.

1.6 LocalizationManager 임시 락 해제 후 내부 버퍼 포인터 반환으로 인한 Use-After-Free
- 관련 파일: Source/Engine/Localization/LocalizationManager.cpp (L504~L531)
- 문제점:
  * LocalizationManager::getString()은 함수 내부에서 std::shared_lock<std::shared_mutex> lock( _mutex );을 획득하여 문자열을 찾은 후, 내부 StringTable의 텍스트 버퍼를 가리키는 원시 포인터(const utf8* pFound)를 그대로 반환합니다.
  * getString()이 리턴되는 즉시 스택 상의 lock이 소멸(Unlock)되므로, 호출부가 반환된 포인터를 사용하고 있는 도중 다른 스레드가 언어 재로드/해제(loadLanguageFile, clear 등)를 호출하면 해당 포인터는 즉시 해제된 메모리를 가리키는 댕글링 포인터가 되어 크래시를 유발합니다.
- 개선 권장안:
  * 내부 버퍼 수명을 안전하게 보장하는 불변 인터닝 스트링 풀을 사용하거나, string 값 복사 반환 또는 호출부 락 획득 스코프를 제공해야 합니다.

1.7 GlobalVariableInfo 다중 스레드 환경에서 비원자적 std::string 쓰기 데이터 레이스
- 관련 파일: Source/Core/GlobalVariable/GlobalVariableManager.cpp (L178~L187, L222~L225)
- 문제점:
  * GlobalVariableInfo::setValueAsString() 및 setValueFromString()은 전역 변수 포인터에 문자열을 대입할 때 어떠한 락 없이 *static_cast<string*>(_pData) = string{val};를 직접 수행합니다.
  * 워커 스레드, 렌더 스레드 등이 전역 문자열 변수(gv_*)를 읽는 도중 메인 스레드나 콘솔에서 값을 수정하면 비원자적 힙 재할당으로 인해 힙 메모리 오염 및 Double Free 크래시가 발생합니다.
- 개선 권장안:
  * 전역 문자열 변수 슬롯에 std::shared_mutex를 도입하거나 atomic<shared_ptr<string>> 기반 원자적 교체를 적용해야 합니다.

1.8 LinearAllocator 멀티스레드 할당 CAS의 느슨한 메모리 오더(relaxed) 및 ABA 레이스 취약점
- 관련 파일: Source/Core/Memory/LinearAllocator.cpp (L73~L75, L87~L97)
- 문제점:
  * LinearAllocator::allocate()는 락프리 할당을 위해 compare_exchange_weak를 std::memory_order_relaxed로 수행하여 Release/Acquire 동기화 펜스를 보장하지 못합니다.
  * 한 스레드가 oldOffset = 0을 읽고 CAS 루프를 도는 도중 다른 스레드가 reset()을 호출하여 오프셋이 0으로 초기화되면, 이미 지나간 이전 크기 계산 값으로 0번 오프셋을 덮어쓰는 ABA 레이스 컨디션이 발생하여 메모리 오염이 발생합니다.
- 개선 권장안:
  * CAS 성공 시 std::memory_order_acq_rel을 적용하고, reset()은 모든 할당 스레드가 완료된 정지점(Quiescent Point)에서만 호출되도록 보장해야 합니다.

1.9 SceneManager::tickTransitions 연속 씬 전환 시 TaskPromise 덮어쓰기로 인한 무한 대기(Hang) 결함

- 개선 권장안:
  * 로드 요청별 독립 Promise 큐를 운영하거나 교체 시 이전 Promise에 명시적으로 취소/null 값을 설정해야 합니다.

2.1 ActionMap 레이어 포인터 캐싱 후 unordered_map 리해싱 시 댕글링 포인터 참조 (Dangling Pointer / UAF)
- 관련 파일: Source/Engine/Input/ActionMap.cpp (L709~L724)
- 문제점:
  * ActionMap::isBindingLayerActive()는 레이어 조회 성능을 위해 _mapLayer(unordered_map<string, LayerDef>) 내부 원소의 메모리 주소를 binding._pCachedLayer에 포인터로 직접 캐싱합니다.
  * 이후 런타임에 registerLayer() / ensureLayer()를 통해 새 입력 레이어가 추가될 때 _mapLayer의 버킷 재할당(Rehashing)이 발생하면 이전에 캐싱된 모든 _pCachedLayer 포인터가 댕글링 포인터가 됩니다.
  * 다음 프레임에 pDef->_bEnabled를 읽는 순간 메모리 오염(Use-After-Free) 또는 프로세스 크래시가 발생합니다.
- 개선 권장안:
  * 원시 포인터 대신 정수형 레이어 ID(uint32 LayerIndex 또는 hashed_string)를 캐싱하거나, 포인터 안정성이 보장되는 고정 핸들 테이블(HandleTable<LayerDef>)을 사용해야 합니다.

2.2 GameModeStateMachine 재진입 전이 시 브로드캐스트 순서 역전 및 상태 불일치 (Re-entrant Desync)
- 관련 파일: Source/GameFramework/Transition/GameModeStateMachine.cpp (L44~L76)
- 문제점:
  * GameModeStateMachine::transitionTo(newMode)는 이전 핸들러 onExit -> 새 핸들러 onEnter -> _onModeChanged 브로드캐스트 순서로 실행됩니다.
  * 새 핸들러의 onEnter()나 _onModeChanged 콜백 내부에서 또 다른 모드로의 전이(transitionTo(ThirdMode))를 재진입 호출하는 경우, 안쪽 전이가 먼저 완료되고 바깥쪽의 이전 전이 이벤트가 나중에 발송되어 외부 리스너들의 상태 동기화가 완전히 깨집니다.
- 개선 권장안:
  * 상태 전이 중 재진입 호출이 발생할 경우 즉시 실행하지 않고 큐에 보관한 뒤 현재 전이가 완료된 후 순차 실행하는 재진입 가드(Re-entrancy Guard)를 도입해야 합니다.

2.3 ModuleHost 모듈 리로드 실패 후 재시도 시 이전 게임 상태(GameState) 영구 소실
- 관련 파일: Source/App/Module/ModuleHost.cpp (L334, L361~L365, L556~L582)
- 문제점:
  * ModuleHost::onBeforeGameReload()는 게임 DLL 언로드 직전 captureGameState()를 호출하여 _listGameSavedState 버퍼에 씬/오브젝트 상태를 백업합니다.
  * 만약 컴파일 에러나 바인딩 실패(poisonLiveReload)로 인해 _game이 nullptr로 남고 restoreGameState()가 호출되지 않은 상태에서, 개발자가 에러 수정 후 다시 리로드하면 onBeforeGameReload()가 _listGameSavedState.clear()를 호출합니다.
  * 이때 _game == nullptr이므로 새로운 직렬화도 불가능하여 이전에 백업해둔 모든 게임 상태 데이터가 완전히 증발(Wiped)합니다.
- 개선 권장안:
  * _game != nullptr일 때만 _listGameSavedState를 덮어쓰도록 보호하고, 이전 리로드 실패로 남은 백업 데이터는 성공적으로 복구될 때까지 보존해야 합니다.

2.4 LiveShaderManager 인클루드 의존성 키 경로(상대 vs 절대) 불일치로 인한 헤더 핫리로드 실패
- 관련 파일: Source/Engine/Graphics/Shader/LiveShaderManager.cpp (L93~L98, L203~L216)
- 문제점:
  * LiveShaderManager::watchShader()는 HLSL 소스 내부의 #include를 파싱하여 _mapIncludeDependency에 등록할 때 engine/shaders/bindless.hlsli와 같은 상대 경로를 키로 저장합니다.
  * 그러나 파일 변경 감지 콜백(onWatchedFileChanged)에서는 OS 파일 감지기로부터 전달된 전체 경로를 합쳐 d:/projects/.../resource/engine/shaders/bindless.hlsli와 같은 절대 경로로 맵을 조회합니다.

2.6 SaveSlot 텍스트 세이브 로드 시 체크섬 불일치로 인한 정상 세이브 오염 판정 (Corrupted Save False Alarm)
- 관련 파일: Source/GameFramework/Save/SaveSlot.cpp (L56~L66, L103~L119)
- 문제점:
  * SaveSlot::saveCommonToTextFile()은 _mapFlag(unordered_map<string, int32>)를 순회하며 텍스트를 만들고 StringUtil::computeHash32로 체크섬을 계산합니다.
  * 반면 loadCommonFromTextFile()은 파일에서 읽은 KeyValueMap(unordered_map<string, string>)을 순회하며 verifySb를 구성하고 체크섬을 검증합니다.
  * unordered_map의 순회 순서는 해시 버킷 분포 및 삽입 이력에 따라 달라지므로, 플래그가 2개 이상인 경우 저장 시의 플래그 기록 순서와 로드 시의 순회 순서가 달라져 체크섬이 완전히 불일치하게 됩니다.
  * 결과적으로 정상적으로 저장된 세이브 파일임에도 로드 시 Checksum mismatch 에러를 출력하며 로드가 거부되는 치명적인 버그가 발생합니다.
- 개선 권장안:
  * 플래그 목록을 체크섬 계산 및 저장/검증 전에 키 이름(std::map 또는 사전순 정렬) 기준으로 정렬(Deterministic Sorting)한 후 순회하도록 통일해야 합니다.

3. 성능 병목 지점 및 락 경합 (Performance Bottlenecks)
--------------------------------------------------------------------------------

3.1 컴포넌트 병렬 틱 시 std::shared_mutex 반복 락 경합
- 관련 파일: Source/Engine/Object/GameObject/GameObjectManager.cpp (L201~L220, L426~L434)
- 문제점:
  * GameObjectManager::tickComponents가 DAG 웨이브 단위로 수십~수백 개의 컴포넌트를 TaskManager::emplaceParallel을 통해 워커 스레드들로 분산 실행합니다.
  * 그러나 각 워커가 실행하는 resolveAndTickItem() 내부에서 매 인덱스마다 resolveComponent() -> findGameObjectById()를 호출하고, 이는 내부적으로 std::shared_lock<std::shared_mutex> lock{ _mutex }를 매번 획득합니다.
  * 코어 수가 많을수록 공유 뮤텍스의 원자적 참조 카운트 수정으로 인한 CPU 캐시 라인 바운싱(Cacheline Bouncing)과 락 경합이 발생하여 병렬화 이점이 크게 상쇄됩니다.
- 개선 권장안:
  * TickExecutionItem 생성 시점에 유효한 컴포넌트 원시 포인터와 오브젝트 활성 상태를 확정해 두고, 병렬 실행 중에는 ID 재검색 및 락 획득 없이 직접 호출하거나 스레드별 읽기 전용 스냅샷 테이블을 사용해야 합니다.

3.2 UI 스레드와 렌더 스레드 간 직렬화 파이프라인 버블 (Frame Stalling)
- 관련 파일: Source/Editor/ImGuiEditor.cpp (L280, L511~L515)
- 문제점:
  * ImGuiEditor::updateUI() 시작 시 waitForDrawSnapshotIdle()을 호출하여 _inFlightDrawSlot이 해제될 때까지 스핀(yield())합니다.
  * _inFlightDrawSlot은 RenderThread가 프레임 렌더링 및 postPresent를 끝마쳐야 비워집니다.
  * 이로 인해 메인/UI 스레드가 렌더 스레드와 동시에 병렬로 다음 프레임 UI를 빌드하지 못하고, 매 프레임 GPU Present 완료 시점까지 블로킹 대기하는 직렬화 버블이 발생합니다.
- 개선 권장안:
  * EditorDrawDataSnapshot 링 버퍼 슬롯 수를 3개(Triple-Buffered Snapshot)로 늘려, 직전 프레임이 렌더링 중이어도 UI 스레드가 다음 슬롯에 독립적으로 UI 커맨드를 기록할 수 있도록 디커플링해야 합니다.

3.3 뷰포트/패널 리사이즈 시 GPU 임시 자원 전면 재생성 (Resource Thrashing)
- 관련 파일: Source/Engine/Graphics/RenderPass/FrameRendererResources.cpp (L180~L223)
- 문제점:
  * FrameRenderer::ensureTransientResources()는 에디터 뷰포트나 도킹 창 크기가 1픽셀이라도 달라지면 releaseTransientResources()를 호출하여 모든 Render Target, Depth Buffer, G-Buffer, Bloom 텍스처 및 Bindless SRV를 완전히 파괴하고 새로 생성합니다.
  * 마우스로 에디터 창을 드래그하여 크기를 조절하는 동안 매 프레임 수십 개의 GPU 텍스처와 디스크립터가 파괴/생성되면서 심각한 프레임 드랍(Stuttering)과 GPU 힙 단편화가 발생합니다.
- 개선 권장안:
  * 실제 렌더 타깃 해상도를 256/512 단위로 상향 패딩(Power-of-Two 또는 Block Allotment)하여 할당하고, 뷰포트 영역만 동적으로 잘라 쓰는 동적 뷰포트 스케일링(Dynamic Viewport Allocation) 구조를 도입해야 합니다.

3.4 SpatialHashGrid2D 쿼리 시 O(N x K) 중복 검사 및 반복 해시 조회 병목
- 관련 파일: Source/Engine/Spatial/SpatialHashGrid2D.cpp (L119~L130)
- 문제점:
  * SpatialHashGrid2D::queryAABB 및 queryCircle은 쿼리 영역에 포함된 모든 버킷을 순회하며 등록된 핸들을 수집합니다.
  * 여러 셀에 걸쳐 있는 엔티티를 검사할 때마다 _mapHandleBound.find(handle)로 바운딩 박스를 해시 검색하고, 중복 방지를 위해 std::find로 출력 벡터 전체를 매번 선형 탐색(O(K))하여 쿼리 반경이 넓을수록 기하급수적으로 성능이 저하됩니다.
- 개선 권장안:
  * 엔티티마다 단조 증가하는 uint32 _lastQueryId 타임스탬프를 부여하여 O(1)로 중복 방문을 체크하거나 쿼리 임시 비트셋을 활용해야 합니다.

3.5 물리 쿼리 및 스윕 테스트 시 매 프레임 힙 동적 할당 (std::vector + std::sort)
- 관련 파일: Source/Engine/Physics/PhysicsWorld.cpp (L249~L268)
- 문제점:
  * PhysicsWorld::queryAabb 및 sweepTest 호출 시마다 로컬 vector<BodyHandle> listCandidateHandle이 힙에서 동적 할당되며, 중복 셀에 등록된 핸들을 제거하기 위해 std::sort와 std::unique를 매번 수행합니다.
  * 레이캐스트, 탄환 충돌, AI 시야 체크 등 프레임당 수백 번 호출되는 핫 패스에서 과도한 힙 할당기 부하 및 메모리 대역폭 낭비가 발생합니다.
- 개선 권장안:
  * 스택 기반 Small-Vector(InlineVector<BodyHandle, 64>) 또는 프레임 선형 할당기(LinearAllocator)를 사용하고, 비트셋(DynamicBitset)을 통한 방문 체크로 O(N log N) 정렬 없이 O(N)으로 중복을 걸러내야 합니다.

3.6 BVHTree3D 동적 오브젝트 이동 시 매 프레임 트리 전면 재구축 (Dynamic Tree Rebuild)
- 관련 파일: Source/Engine/Spatial/BVHTree3D.cpp (L68~L79, L82~L85)
- 문제점:
  * BVHTree3D::update(handle, bounds)가 호출될 때마다 내부적으로 remove(handle) 후 insert(handle, bounds)를 수행합니다.
  * insert는 최적의 노드 삽입을 위해 루트부터 SAH(Surface Area Heuristic) 비용을 계산하며 내려가고, remove는 상위 부모 노드들을 재조정합니다.
  * 매 프레임 조금이라도 움직이는 동적 엔티티가 수백 개 이상일 경우, 매 틱마다 O(N log N)의 무거운 트리 분해/재조정 및 노드 힙 할당이 발생하여 심각한 CPU 병목을 초래합니다.
- 개선 권장안:
  * Box2D/PhysX 스타일의 확장 바운딩 박스(Fat AABB with Margin/Velocity)를 도입하여, 객체가 이전 Fat AABB 영역을 벗어났을 때만 트리를 갱신하고 작은 이동은 비용 0으로 스킵하도록 최적화해야 합니다.

3.7 ReloadFileManager mtime 폴백 모드 활성화 시 매 프레임 전체 디스크 재귀 탐색 병목
- 관련 파일: Source/Engine/Utility/Module/ReloadFileManager.cpp (L133~L135, L226~L244)
- 문제점:
  * 파일 와처 실패 시 mtime 폴백 모드에서 update()가 매 프레임 collectFiles()를 동기 호출하여 전체 디스크를 재귀 순회합니다.
  * 수천 개의 에셋 파일이 있는 프로젝트에서 매 틱마다 50~200ms 단위의 극심한 프레임 스톨이 발생합니다.
- 개선 권장안:
  * 주기적 타이머 스로틀링(1.0초 간격)을 적용하고 비동기 워커 태스크로 디스크 탐색을 분리해야 합니다.

3.8 JsonDocument 및 XmlDocument 대용량 노드 룩업 시 O(N) 선형 탐색 병목

- 개선 권장안:
  * Float2/Uint2/Int2의 경우 기본 정렬을 8바이트로 설정하고, 16바이트 경계(Vector Boundary)를 넘는 경우에만 16바이트로 올림하는 HLSL Cbuffer 패킹 규칙에 맞춰 정렬 로직을 수정해야 합니다.
