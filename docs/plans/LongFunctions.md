# 긴 함수 정리 기준 (2026-10-18, 백로그 C-18)

100 줄이 넘는 함수를 언제 나누고 언제 그대로 두는지 정하고, 목록을 뽑는 도구와 작업 단위를 둡니다.
나누기 자체는 코드 총량을 줄이지 않습니다. 그래서 줄 수는 후보를 고르는 기준일 뿐이고, 나누는 이유는 아래 2절의 구조 문제여야 합니다.

## 1. 측정 도구

### 1.1 지금 상태와 뿌리

함수 길이를 재는 스크립트가 없습니다. 단순 정규식은 여러 줄 시그니처, 람다, 매크로 본문, 주석과 문자열 안의 중괄호에서 틀립니다.

### 1.2 해법

`Scripts/lint/report/RunFunctionSize.py` 를 새로 둡니다. 보고만 하는 도구이고 게이트가 아닙니다.
- 공용 `Scripts/common/CodeText.py` 의 `blankCommentsAndLiterals` 로 주석과 문자열을 지운 글에서, 네임스페이스와 클래스 본문이 아닌 함수 본문의 여는 중괄호를 깊이로 찾습니다.
  함수 이름은 여는 중괄호 앞의 마지막 `이름(` 에서 괄호 짝을 거꾸로 맞춰 얻으므로 여러 줄 시그니처도 맞습니다.
- 출력 열은 파일, 함수, 본문 줄 수, 최대 중첩 깊이, `return` 수, 본문 안 람다 줄 수입니다. 람다 줄을 따로 보이는 이유는 큰 람다가 함수를 길게 보이게 하기 때문입니다.
- 정확도는 clang-tidy `readability-function-size` 와 한 폴더에서 맞춰 봅니다. 두 결과가 다르면 이 스크립트를 고칩니다.

대안: clang-tidy `readability-function-size` 를 전체에 돌리는 방법은 기각합니다. 컴파일 DB 가 필요하고 전체 실행이 수십 분 걸려, 목록을 자주 뽑는 용도에 맞지 않습니다. 대조용으로만 씁니다.

## 2. 나누는 기준

순서대로 봅니다. 앞 기준에서 해결되면 뒤로 가지 않습니다.

1. **중복부터 없앱니다.** `RunDuplicateCode.py` 로 긴 함수 안의 반복 블록을 찾고, 공용 함수나 테이블로 합칩니다. 총량이 줄어드는 유일한 경우입니다.
2. **다시 읽기와 두 번 검사를 없앱니다.** 검사 단계가 읽은 값을 실행 단계가 다시 읽는 함수는 한 번 읽은 타입 있는 값을 넘기게 바꿉니다. 자동화 실행기가 대표 예이고, 데이터 주도 계획 7.3 의 "자동화 단계는 한 번만 읽습니다" 가 이 작업입니다.
3. **단계 경계에서 나눕니다.** 파싱, 검사, 적용처럼 단계가 나뉘고, 앞 단계의 지역 변수가 다음 단계로 넘어가지 않는 함수는 단계마다 함수로 나눕니다. 넘겨야 할 값이 많으면 단계 결과 구조체를 둡니다.
4. **분기 사다리는 테이블로 바꿉니다.** 중첩 깊이가 4 이상이거나 같은 형태의 오류 반환이 반복되면, 경우를 데이터 테이블이나 `switch` 하나로 바꿉니다.

그대로 두는 경우는 다음과 같습니다. 이유를 함수 헤더 주석에 한 줄로 적습니다.
- 순서가 곧 의미인 선형 목록입니다. 초기화 순서, 등록 목록, 프레임 단계 본문이 해당합니다. 나누면 순서를 여러 곳에서 읽어야 합니다.
- 경우마다 짧은 `switch` 디스패처입니다.
- 생성 코드, X-macro 테이블, 테스트 본문, 셰이더 코드입니다.

게이트는 두지 않습니다. 줄 수 상한을 게이트로 두면 이유 없는 기계적 분할이 늘어나고, 그것은 총량을 늘립니다. 결정 기록에 한 줄로 남깁니다.

## 3. 단위

| 단위 | 내용 | 건드릴 폴더 | 선행 | 검증 | 측정 |
|---|---|---|---|---|---|
| L1 | `RunFunctionSize.py` 와 스크립트 테스트, clang-tidy 대조 한 폴더 | `Scripts/lint/report/`, 스크립트 테스트 폴더 | 없음(빌드 없음) | 스크립트 테스트(여러 줄 시그니처, 람다, 매크로, 문자열 속 중괄호), `-L lint` | 없음 |
| L2 | 목록을 뽑아 영역별 수와 상위 함수를 이 문서 4절에 적고, 함수마다 2절의 기준 번호를 붙입니다 | `docs/plans/LongFunctions.md` | L1 | 없음 | 없음 |
| L3 이후 | 영역(폴더)마다 기준 1 ~ 4 를 적용합니다. 영역 하나가 단위 하나이고, 그 폴더를 다른 작업이 건드리는 중이면 미룹니다 | 영역마다 다름 | L2, 그 영역의 다른 계획 단위(예: 자동화는 데이터 주도 D8) | 그 영역의 테스트, 동작 변경 없음 | 핫 패스 함수를 나눌 때만 Release 전후 측정 |

L2 의 영역 분류는 판단이 조금 필요해 `worker` 에 맡기고, L3 의 단순한 중복 합치기는 `mech-worker` 에 맡길 수 있습니다.
