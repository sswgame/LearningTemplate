# 서버 디버깅 계획 — 에디터에서 서버 · 멀티플레이를 손쉽게 보는 길

상태: 계획만 있습니다(2026-10-11). 구현은 시작하지 않았고, 시작하기 전에 아래 "결정할 것" 두 가지를 정합니다.

## 왜 필요한가

서버 버그는 클라이언트 버그보다 보기 어렵습니다. 같은 일을 겪는 흐름이 대체로 다음과 같습니다.

- 서버 프로세스, 클라이언트 프로세스 여럿을 손으로 띄우고 포트와 인자를 맞춥니다.
- 서버에서 중단점에 걸리면 클라이언트가 시간 초과로 끊깁니다. 디버깅하려면 연결이 살아 있어야 하는데, 멈추면 끊깁니다.
- 로그가 프로세스마다 갈라져 있어 한 사건의 앞뒤를 맞추기 어렵습니다.
- "서버에서는 어떻게 보였나"를 클라이언트 화면에서 볼 길이 없습니다.
- 회선이 나쁜 상황은 재현하기 어렵습니다.

상용 엔진의 답은 에디터 안의 재생 모드입니다. 언리얼은 PIE 의 Net Mode(Standalone · Listen · Client) · 플레이어 수 · Net Emulation 프리셋으로, 유니티는 Multiplayer Play Mode 의 가상 플레이어와 Network Simulator 로 푼다. 이 저장소에는 그 바닥이 이미 있습니다.

| 한 프로세스 가상 서버 | `NetSimHarness`(`Source/GameFramework/Kits/Feature/Network/NetSimulation/NetSimHarness.h`) — 결정적, 월드마다 씬 · 물리 | 렌더러 · 에디터 연결(화면 없음) |
| 전용 서버 | `Server`(`Source/Server/README.md`) — 고정 틱, 운영 엔드포인트 | 에디터에서 띄우고 붙는 길 |

## 단위 (위가 아래의 바닥)

### S1 멀티 프로세스 재생 — Net Mode · 플레이어 수

에디터 Play 단추 옆 드롭다운에 **Net Mode**(Standalone · Listen Host · Dedicated Server + Client N)와 **플레이어 수**를 둡니다.

- 에디터가 `Server` 를 자식 프로세스로 띄우고 `App` 클라이언트 N 개를 붙입니다(창 따로, 포트 자동). 각 프로세스에 `-gv_netRole` 같은 인자를 넘깁니다.
- 한 번 정한 구성은 프리셋으로 저장합니다("서버 + 클라이언트 2", "리슨 + 1").
- 모든 프로세스의 로그를 한 Output Log 에 모읍니다. 줄마다 출처 꼬리표(`[Server]` · `[Client1]`)와 서버 틱 번호를 붙이고, 필터로 갈라 봅니다.
- Stop 은 전부를 끕니다. 하나가 죽으면 에디터가 알립니다(종료 코드 · 마지막 로그).
- 이유: 지금 있는 실행 파일만으로 되고(새 엔진 기능 없음), 어느 IDE 든 프로세스에 붙을 수 있습니다. 언리얼의 "Run Under One Process" 끄기와 같은 모양입니다.
- 확인: 에디터 시나리오로 구성을 고르고 Play → 서버와 클라이언트 둘이 접속한 것을 탐침으로 → Stop 뒤 프로세스가 남지 않음.

### S2 중단점 친화 — 멈춰도 끊기지 않기

서버에서 중단점에 걸려도 클라이언트가 끊기지 않게 합니다. 가장 아픈 문제라 먼저 합니다.

- 디버거가 붙어 있으면(`IsDebuggerPresent` 류) 연결 시간 초과 · 하트비트를 **가상 시계로 멈춥니다**. 멈춘 시간만큼 시계가 가지 않아, 재개 뒤 클라이언트는 그 사이를 없던 일로 봅니다.
- 에디터에 "서버 일시정지 · 한 틱 진행" 단추를 둡니다(디버거 없이도 같은 동작). 클라이언트는 지연이 커진 것처럼 보입니다.
- 이유: 상용 엔진은 PIE 가 한 프로세스라 멈추면 전부 멈춰 이 문제가 안 생기고, 따로 도는 전용 서버에서는 그대로 겪는다.
- 확인: 서버 틱을 5 초 멈췄다 재개해도 연결이 유지되는 시나리오.

### S3 서버 검사기 — 실행 중인 서버를 에디터에서 읽기

에디터가 서버(또는 다른 클라이언트)에 붙어 **읽기 전용**으로 봅니다.

- 하이어라키(오브젝트 트리), 선택한 오브젝트의 컴포넌트 값, 서버 개발 콘솔 명령 실행(`SW_DEV_COMMAND` 원격 실행).
- 디버그 채널은 개발 빌드 전용이고 루프백에만 묶으며 토큰을 요구합니다. Shipping 에는 없습니다.
- 이유: 언리얼의 "서버 월드 보기"(PIE 에서 월드 선택)와 같은 자리. 서버 값은 클라이언트에 복제되지 않은 것이 많아 이게 없으면 로그에만 의지한다.
- 확인: 서버에서 오브젝트 값을 바꾸고 검사기에서 그 값이 보이는 시나리오.

### S4 회선 조절 — 실행 중 조건 바꾸기

`NetEmulationConditions` 를 에디터에서 실행 중에 바꿉니다.

- 프리셋(LAN · 와이파이 · LTE · 나쁜 와이파이 · 끊김)과 클라이언트마다 슬라이더(지연 · 흔들림 · 손실 · 대역폭). 올림 · 내림을 따로.
- 버튼: 연결 끊기, 재접속, 몇 초 동안 전부 버리기(스파이크).
- 이유: Unreal Net Emulation, Unity Network Simulator 와 같은 자리. 흉내 자체는 있으니 창구(개발 명령 + 패널)만 더한다.
- 확인: 시나리오로 손실 30 % 를 걸고 탐침이 재전송 · 보정 수치를 보고하는 것.

### S5 네트워크 프로파일러 패널

연결 · 메시지 종류별로 시간축에 그립니다.

- 보낸 · 받은 바이트, 패킷 수, RTT, 손실, 스냅숏 크기, 메시지 종류별 비중, 오브젝트별 복제 빈도.
- 이유: 언리얼 Network Insights, 유니티 Netcode Runtime Stats Monitor 의 자리. 대역폭 문제를 숫자 없이 짐작하지 않게 한다.
- 데이터는 이미 있는 연결 통계와 트래픽 셈을 읽는다(새 수집을 프레임에 더하지 않는다). 디버그 HUD 의 네트워크 섹션과 같은 원천.
- 확인: 부하 봇(`Tools/OnlineLoadBot`)을 붙여 숫자가 오르는 시나리오.

### S6 권위 겹쳐 보기 — 서버가 본 모습을 클라이언트 화면에

클라이언트 게임 뷰 위에 **서버가 마지막으로 알린 자세**를 와이어프레임 고스트로 겹칩니다.

- 예측 오차(내 화면과 서버의 차이), 보간 지연, 랙 보상 기록(히트박스)이 눈에 보입니다.
- 이유: "맞았는데 안 맞았다" 류 버그의 절반은 화면을 보면 끝난다. 언리얼 `p.NetShowCorrections` 와 같은 자리.
- 확인: 일부러 예측을 어긋나게 한 시나리오에서 고스트가 나타나고 차이가 숫자로 나오는 것.

### S7 어긋남 찾기 — 틱별 상태 해시 비교

서버와 클라이언트(또는 롤백 · 락스텝 참가자들)의 틱별 상태 해시를 모아 **처음 어긋난 틱**과 그 오브젝트를 짚습니다.

- 파괴 해시 비교와 롤백 세션의 상태 바이트가 이미 있다. 에디터는 비교 결과를 보여 주는 창만 더한다.
- 되감기: 의도 기록(`.swintent`)으로 그 틱까지 서버를 다시 돌려 서버만 한 틱씩 진행.
- 확인: 일부러 한 쪽 결과를 틀어 놓은 시나리오에서 첫 어긋난 틱이 맞게 나오는 것.

### S8 한 프로세스 가상 서버를 에디터에서 (장기)

`NetSimHarness` 를 에디터 재생에 잇습니다. 서버 월드 + 클라이언트 월드 N 이 한 프로세스에서 돌고 에디터 탭마다 클라이언트 화면이 나옵니다.

- 결정적이고 한 디버거에서 서버 · 클라이언트에 모두 중단점을 걸 수 있다(언리얼 기본 PIE).
- 선행 조건: **다중 월드 · 월드별 렌더**(백로그 1-6 "다중 월드 · 에디터 툴 창"). 지금 엔진은 활성 씬 하나만 틱하고 그린다.
- 이유: S1 로 거의 모든 일이 되므로, 다중 월드가 다른 이유로 들어온 뒤에 얹는다.

## 순서

S2 → S1 → S4 → S3 → S5 → S6 → S7 → S8. S2 는 서버 변경만이라 에디터와 겹치지 않고 가장 아픈 문제를 먼저 푼다. S1 이 되면 나머지는 그 위에서 확인한다. S3 · S5 는 디버그 HUD 의 섹션 등록부와 같은 원천을 쓴다.

## 결정할 것 (사용자)

1. **한 프로세스 vs 여러 프로세스를 먼저.** 권장은 여러 프로세스(S1)를 먼저, 한 프로세스(S8)는 다중 월드 뒤. 한 프로세스가 편하지만 엔진 구조 변경이 선행이다.
2. **디버그 채널 범위.** 읽기 전용(S3 의 기본)으로 시작하고, 값 쓰기 · 명령 실행은 개발 콘솔 명령만 허용할지(권장), 임의 프로퍼티 쓰기까지 열지.

## 지키는 것

- 디버그 채널 · 원격 명령은 Dev 전용이다(Shipping 에 링크하지 않는다). 루프백 + 토큰.
- 서버 코드에 에디터 의존을 만들지 않는다(에디터는 채널의 클라이언트일 뿐).
- 단위마다 "확인 = 자동 시나리오"를 같이 한다(사람 손 확인을 돌리지 않는다).
