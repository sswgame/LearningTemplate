# 증분 쿠킹과 파생 데이터 캐시 계획 (2026-10-18, 백로그 C-42)

리소스를 100MB 이상 들이는 중이라, 에셋이 늘면 매번 전부 굽는 쿠킹이 병목이 됩니다. 쿠킹 결과를 입력의 내용 해시로 찾아 다시 쓰고, 바뀐 입력에 기대는 결과만 다시 굽습니다.
파생 데이터 캐시(DDC)는 쿠킹 결과를 키로 저장하는 폴더입니다. 언리얼의 DDC 에 해당합니다.

## 1. 지금 구조와 뿌리

| 단계 | 어디서 | 다시 쓰는가 |
|---|---|---|
| 셰이더 | `App --cook-shaders`, `ShaderCooker` | 백엔드 폴더마다 `cook.stamp` 가 소스 내용 해시와 도구 지문을 가집니다(결정 기록 5-5). 컴파일 캐시도 있습니다 |
| 씬, 프리팹, GUID 레지스트리, 정점 애니메이션(VAT), 내비메시 | `App --cook-scenes`(`HeadlessSubsystem.cpp:107-139`) | 다시 쓰지 않습니다. 매번 전부 굽습니다 |
| 팩 | `Scripts/generate/CookAssets.py` | 다시 쓰지 않습니다. 매번 `.pack` 을 새로 씁니다 |

뿌리는 쿠커가 자기 입력을 말하지 않는다는 것입니다. 무엇을 읽었는지 모르면 무엇이 바뀌었는지도 판정할 수 없습니다.
셰이더 스탬프는 의존 파일 수집 규칙을 C++(`ShaderCookStamp.cpp` 의 `collectStampedSources`)과 파이썬(`CookAssets.py` 의 `collectStampedSourceHashesInternal`)에 따로 가지고 있습니다. 쿠커마다 의존 목록을 손으로 적으면, 하나를 빠뜨렸을 때 낡은 결과가 조용히 쓰입니다.

## 2. 해법

### 2.1 입력은 적는 것이 아니라 기록됩니다

- 쿠킹 작업 하나(씬 하나, 프리팹 하나, 팩 하나)를 `CookJob` 범위로 감쌉니다. 범위 안에서 일어나는 모든 리소스 읽기는 `ResourceIO`(리소스 읽기의 단일 진입점)가 내용 해시와 함께 그 작업의 입력 목록에 기록합니다.
- 쿠커는 의존 목록을 따로 적지 않습니다. 씬이 프리팹을 읽고 프리팹이 머티리얼을 읽으면, 그 읽기가 모두 씬 작업의 입력이 됩니다. 빠뜨릴 수 있는 손 목록이 없으므로 "의존을 잊은 낡은 결과" 가 형식으로 생기지 않습니다.
- 작업 범위는 스레드 지역 값입니다. 병렬 쿠킹에서도 읽기가 다른 작업에 섞이지 않습니다. 범위 밖 읽기가 쿠킹 중에 일어나면(전역 캐시가 미리 읽은 것을 쓰는 등) 오류입니다. 캐시를 거친 입력도 작업에 기록되도록 캐시 조회가 기록을 남깁니다.

### 2.2 키와 기록

- 작업 키 = 해시(쿠커 이름, 쿠커 버전 상수, 대상 플랫폼과 백엔드, 쿠킹 설정 해시, 기록된 입력의 경로와 내용 해시 목록)입니다.
- 쿠커 버전은 쿠커 소스 옆의 상수입니다. 셰이더 도구 지문과 같은 원칙으로, 바이너리 해시가 아니라 사람이 올리는 버전입니다(결정 기록 5-5). 형식을 바꾸면 버전을 올리고, 그 쿠커의 결과가 모두 다시 구워집니다.
- 작업마다 기록 파일(`Saved/CookRecord/<출력 id>.cookrec`)을 남깁니다. 쿠킹 폴더의 파일은 모두 팩에 들어가므로 기록을 그 옆에 두지 않습니다. 내용은 키, 입력 목록(경로와 내용 해시, 폴더를 훑은 목록), 출력 해시입니다.
- 다음 쿠킹은 기록의 입력만 다시 해시합니다. 내용 해시는 셰이더 스탬프가 쓰는 캐시(파일 크기와 쓰기 시각이 같으면 다시 읽지 않음)를 공용으로 옮겨 씁니다. 모두 같으면 출력을 다시 씁니다. 하나라도 다르면 다시 굽고 기록을 새로 씁니다.
  판정에 파일 시각만 쓰지 않습니다. `git pull` 이 시각을 임의의 순서로 바꾸기 때문입니다(`ShaderCookStamp.cpp` 머리말).

### 2.3 저장소

- 로컬 DDC 는 `Saved/DDC/<키 앞 두 글자>/<키>` 의 내용 주소 폴더입니다. 쿠킹 출력 폴더(`--cooked-dir`)는 DDC 에서 복사해 채웁니다.
- 공유 DDC 는 두지 않고 로컬 층만 둡니다(2026-10-18 사용자 결정, 5절).
- 쿠킹 결과는 바이트 단위로 결정적이어야 합니다. 같은 입력을 두 번 구우면 같은 바이트가 나와야 키로 다시 쓰는 것이 옳습니다. 결정적이지 않은 출력(정렬되지 않은 맵 순회, 시각 기록)은 이 계획의 첫 단위에서 찾아 고칩니다.

## 3. 상용 엔진 비교와 대안

- **유니티 Asset Database v2**: 임포트 결과(아티팩트)를 소스 해시, 임포터 버전, 정적 의존과 임포트 중에 기록한 동적 의존의 해시로 찾습니다 [기억]. 이 계획의 "읽기를 기록" 은 그 동적 의존과 같은 방식입니다.
- **언리얼 DDC**: 쿠커마다 버전 GUID 와 입력 해시로 키를 만들고, 로컬과 공유(네트워크, 클라우드) 층을 차례로 찾습니다 [기억]. 의존은 쿠커 코드가 키에 넣습니다.
- **Godot**: 임포트한 리소스마다 `.import` 파일에 소스 MD5 와 임포터 버전을 기록하고 바뀐 것만 다시 임포트합니다 [기억].

기각한 대안:
- **쿠커마다 의존 목록을 코드로 적는 방법(언리얼식 키 구성).** 기각합니다. 이 저장소의 셰이더 스탬프가 이미 같은 규칙을 두 언어에 적고 있고, 하나를 빠뜨리면 낡은 결과가 조용히 쓰입니다.
- **파일 시각으로 판정하는 방법(make, ninja).** 기각합니다. 쿠킹된 바이너리까지 커밋하는 저장소라 시각이 믿을 수 없습니다.
- **쿠킹 전체를 빌드 시스템(CMake, ninja) 규칙으로 옮기는 방법.** 기각합니다. 씬 하나의 의존(프리팹, 머티리얼)은 쿠킹해 봐야 알 수 있어서 빌드 그래프에 미리 적을 수 없습니다. ninja 의 `depfile` 처럼 실행 후 의존을 남기는 것은 가능하지만, 내용 해시가 아니라 시각으로 판정합니다.

## 4. 단위

동시 빌드는 둘까지입니다. K1(공용 형식: `Engine/Resource/Cook/` 의 `CookJob` · `CookSession` · `CookRecord` · `DerivedDataCache` · `ContentHash`, `ResourceIO` 의 읽기 기록)과 K4(팩 증분, `.packrec`)는 들어갔습니다.
K2(씬 · 프리팹)와 K3(레지스트리, VAT, 내비메시)도 들어갔습니다. `--cook-scenes` 의 모든 쿠커가 쿠킹 세션 안에서 출력마다 `CookStore::cookFile` 을 부르고, 작업은 빈 에셋 캐시로 시작하며, 기록은 `Saved/CookRecord`, DDC 는 `Saved/DDC` 에 둡니다.
레지스트리는 `.meta` 목록을 입력(`CookJob::collectFiles`)으로 남기고, VAT 는 무엇을 구울지 정하려고 목록을 먼저 읽은 뒤 클립 작업마다 다시 읽어 입력으로 남깁니다.
K5 는 셰이더 스탬프를 옮기지 않기로 정했습니다(결정 기록 5-5). 남은 것은 K0(측정)입니다. 공유 DDC(옛 K6)는 하지 않습니다(5절).
팩 증분(K4)은 들어갔습니다. `CookAssets.PackWriter` 가 팩 옆 `<팩>.packrec` 에 키(쿠커 버전, 팩 계약 지문, 압축 · DLC · 디버그 문자열, 항목마다 경로와 내용 해시)와 팩 바이트 해시를 남기고, 같으면 다시 쓰지 않습니다.

| 단위 | 내용 | 건드릴 폴더 | 선행 | 검증 | 측정 |
|---|---|---|---|---|---|
| K0 | 단계별 쿠킹 시간(셰이더, 씬, 프리팹, 레지스트리, VAT, 내비메시, 팩)을 깨끗한 실행과 바뀐 것 없는 실행에서 측정하고, 같은 입력을 두 번 구워 바이트가 같은지 봅니다 | 코드 변경 없음. 결과는 `docs/08_Verification.md` | 없음 | 표가 나옵니다 | 필요합니다. Release App, 3 회, 단계별 초 |

K0 은 측정만 하는 일이라 다른 단위보다 먼저 합니다. 이득이 씬에서 나오는지에 따라 K2 와 K3 의 순서를 정합니다.
