# 콘텐츠 브라우저 감시 지연과 스캔 비용

> 상태: 구현대기 · 선행: 없음 · 영역: editor · 옛번호: 없음 · 진행: 0/2

참조 역색인은 2026-10-23 에 "마지막 변경을 따라왔다"(`ContentBrowserReferenceSearch::isCurrent`)를 준비로 보고 보이는 패널에서 시계를 잡게 고쳤습니다(`assetmanage` 간헐 실패).
같은 모양의 폴더 목록 대기는 [Candidates-editor](Candidates-editor.md) 의 `ContentBrowserAsyncWaits` 에 남아 있고, 여기는 그 나머지 둘입니다.

## 1. 단위

| 단위 | 내용 | 선행 |
|---|---|---|
| CW1 | 감시 지연 울타리: 에디터 밖의 쓰기(`<Scratch>` 복사)는 OS 파일 감시가 알려야 변경 번호가 오릅니다. 알림 전에는 낡은 색인이 맞다고 보입니다(보통 ms, 스캔 하나보다 짧음). 실행기가 사본을 만든 뒤 감시 폴더에 표지 파일을 쓰고 그 사건을 기다리는 울타리를 둡니다. 착수 조건: `assetmanage` 가 한 번이라도 낡은 색인으로 지거나 울타리를 둘 자리가 하나 더 생길 때 | 없음 |
| CW2 | 스캔 비용: 전체 스캔이 Release 2 초, Debug 6~19 초라 보이는 콘텐츠 브라우저에서 파일이 바뀔 때마다 그만큼 시계를 잡습니다. 바뀐 파일만 다시 읽는 증분 갱신(언리얼 에셋 레지스트리)이 줄입니다. 착수 조건: 에디터 체인 시간이 시한에 닿을 때(쿠킹 쪽 에셋 레지스트리는 통째 훑기로 결정 — [결정 기록](../09_Decisions.md) 5-11) | 없음 |
