# 작업 방식

이 저장소는 여러 PC 와 여러 세션에서, 사람과 에이전트가 함께 고칩니다. 이 문서는 그 작업을 나누고, 빌드하고, 검증하고, 내보내는 방식을 적습니다.
한 PC 의 메모리나 세션 임시 폴더에만 있던 규칙을 여기로 옮겼으므로, 다른 PC 에서 일을 시작할 때 이 문서를 먼저 읽습니다.

규칙의 원본은 한 곳씩입니다. 코딩 규칙과 편집 함정은 [AGENTS.md](../AGENTS.md) 목차의 `docs/agents/` 파일, 일을 끝내기 전에 돌릴 것과 측정법은 [검증과 측정](08_Verification.md),
정한 방향과 기각한 안은 [결정 기록](09_Decisions.md), 남은 일은 [계획 문서](plans/Roadmap.md) 에 있습니다. 이 문서는 그 문서들이 다루지 않는 진행 방식만 적습니다.

## 1. 일을 나누는 방식 — 워크트리와 적용 담당

큰 작업 배치는 단위로 나누어 워크트리 하나에 브랜치 하나씩 진행합니다. 워크트리는 main 체크아웃과 같은 저장소를 공유하는 별도 작업 폴더입니다.

```powershell
py -3 -m Scripts worktree-make <이름> --base main      # <드라이브>:\w\<이름>(Windows) · <main 의 부모>/LT-wt/<이름>, 브랜치 wt/<이름>
py -3 -m Scripts worktree-make <이름> --base wt/apply5 # 다른 브랜치에서 갈라 만든다
py -3 -m Scripts worktree-remove <이름>                # 나눠 쓰는 링크를 먼저 끊고 지운다 — 다른 세션이 쓰는 중이면 건너뛴다
py -3 -m Scripts worktree-list                         # 워크트리마다 브랜치와 주인(쓰는 중 · 주인 프로세스 끝남 · 기록 없음)
py -3 -m Scripts shared-lock acquire vcpkg --owner <이름> --purpose "configure"   # vcpkg 를 부르기 전(cmake --preset · --clean-first · 설치) — 쓰는 쪽이 있으면 기다린다
py -3 -m Scripts shared-lock release vcpkg --owner <이름>                          # 끝나면 바로 놓는다(status 로 누가 쓰는지 본다)
```

- **워크트리에는 주인이 있습니다.** `worktree-make` 가 주인 이름 · 프로세스 번호(`CLAUDE_PID`, 사람 셸은 `--pid $PID`) · 세션 · 시작 시각을 워크트리의 git 디렉터리에 적습니다.
  `worktree-remove` 는 주인 프로세스가 살아 있고 내 것이 아니면 지우지 않습니다(`--even-if-owned` 는 사용자가 시킨 때만). 주인 기록이 없는 워크트리(이 기능 전)는 누가 쓰는지 모르므로 지우기 전에 사용자에게 묻습니다.

- **`--base` 를 반드시 줍니다.** 주지 않으면 `origin/main` 에서 갈라지는데, 로컬 main 이 push 전이면 낡은 기준입니다. 지울 때는 `git merge-base --is-ancestor wt/<이름> main` 으로 병합을 확인한 뒤 `worktree-remove` 를 씁니다(브랜치도 지웁니다).
- `.claude/skills` 는 추적하지 않아 새 워크트리에 없습니다. 에이전트가 ponytail · graphify 스킬을 쓰려면 세션을 시작하기 전에 main 체크아웃의 `.claude/skills` 를 워크트리의 같은 위치로 복사합니다. 사용법은 [CLAUDE.md](../CLAUDE.md) "보조 도구" 가 원본입니다.
- 워크트리는 내려받은 도구(LLVM, Ninja, vcpkg)와 vcpkg 설치 폴더를 main 체크아웃과 링크로 나눠 씁니다. 이 링크 폴더(`Tools/*`, `build/vcpkg_*`)는 지우거나 고치지 않습니다.
  그래서 `vcpkg.json`, 포트, `cmake/Modules/Toolchain/Vcpkg/*` 를 바꿔야 하면 워크트리에서 바꾸지 않고 main 에서 먼저 바꿉니다.
- **공유 설치 폴더를 건드리기 전에 쓰는 쪽이 있는지 묻습니다.** `cmake --preset`, `--clean-first` 빌드, vcpkg 설치처럼 vcpkg 를 부르는 일은 먼저 `shared-lock acquire vcpkg` 로 잡고 끝나면 놓습니다.
  의존성 정의가 다른 트리가 같은 `build/vcpkg_installed` 에 설치하면 main 의 라이브러리가 지워져 main 빌드가 `libpq.lib` 같은 링크 오류로 섭니다. 기다려도 안 풀리면 사용자에게 알립니다.
- **적용 담당은 하나입니다.** 적용 담당이 단위 브랜치를 받아 합치고, 빌드하고, 전체를 검증하고, main 에 넣고 push 합니다. 넓게 건드리는 변경(폴더 이동, 헤더, 매크로 철자)을 먼저 넣습니다.
- **도우미는 자기 워크트리 안에서만 일합니다.** 다른 워크트리와 main 체크아웃을 건드리지 않고, push 하지 않습니다. 단위를 끝낼 때마다 최신 main 을 받아 충돌을 스스로 풉니다.
  적용 담당은 충돌을 풀지 않고 되돌려 보냅니다. 셰이더 매니페스트, 쿠킹 바이너리, `import.stamp` 같은 생성 산출물이 충돌하면 한쪽을 고르지 않고 `App --cook-shaders` 나 `--import-models` 로 다시 만듭니다.
- 같은 파일을 건드리는 단위는 한 도우미에게 몰아 줍니다. 끝난 워크트리는 바로 지웁니다.
- 기계적 변경(이동, 이름 바꾸기, 일괄 재작성)은 커밋만 단계별로 나누고 빌드와 테스트는 끝에 한 번 합니다.
- **병렬 작업은 준비된 브랜치부터 통합합니다.** 작업자의 최종 검증은 생략하고 통합이 한 번에 검증합니다. 통합 워크트리에서는 합치고 빌드(Debug `all AllTests` 경고 0)만 하고, main 에 합친 뒤 main 에서 3절의 검증을 돌립니다. 검증이 통과하기 전에는 push 하지 않습니다.
- 결함을 고치는 순서(재현 테스트, 고침, 변이 검사)는 [검증과 측정](08_Verification.md) 1절이 원본입니다.
- `main` 체크아웃에서는 편집하지 않습니다. 빌드는 통합 뒤 검증과 `full-build` 만 합니다. 도우미는 워크트리에서 일합니다.
- vcpkg 가 갑자기 포트 전체를 다시 빌드하면(20 분 넘게) `Tools/vcpkg/packages/*/share/*/vcpkg_abi_info.txt` 의 `triplet_abi` 가 흔들리는지 봅니다. 바이너리 캐시 경로(`VCPKG_BINARY_SOURCES`)는 `Vcpkg.cmake` 가 정하므로 ninja 재구성에서도 빠지지 않습니다. 설치 도중에는 건드리지 않습니다.
- 사용 한도(`rate_limit`)로 도우미가 끊기면 워크트리 작업은 그대로 남습니다. 한도가 풀린 뒤 `SendMessage` 로 이어서 시킵니다.

## 2. 빌드와 CPU

- **동시에 빌드하는 작업은 최대 둘입니다**(적용 담당과 도우미 하나). 나머지 도우미는 코드 적용과 빌드 없는 검사만 합니다. 워크트리마다 빌드 폴더가 따로라 전체를 다시 컴파일하고, 전체 빌드가 겹치면 CPU 가 100 % 에 붙어 테스트 시간 제한이 가짜로 집니다.
- **한도는 빌드 칸 잠금(`build`, 공유 칸 둘)이 강제합니다.** 모든 빌드는 칸을 잡고 돌립니다 — 검증 빌드는 `full-build`(아래 3 절)가 스스로 잡고, 그 밖의 빌드는
  `py -3 -m Scripts shared-lock run build --shared --owner <이름> [--below-normal] -- cmake --build --preset Ninja-Debug --target <타깃>` 으로 돌립니다.
  `run` 은 명령이 지거나 끊겨도 칸을 놓고, 칸의 소유 프로세스가 `run` 자신이라 끝나면 버려진 칸으로 치워집니다. 칸이 비기를 기다리다 시한(기본 30 분)을 넘기면 사용자에게 알립니다.
- 도우미의 빌드와 테스트는 낮은 우선순위로 돌립니다(`--below-normal`). ctest 는 `-j 2` 입니다. 끌 때는 자기 PID 만 끕니다.
  `--target` 없는 빌드는 테스트를 짓지 않습니다. 테스트를 돌릴 도우미는 테스트까지 먼저 짓습니다(ctest · `py -3 -m Scripts test` 가 대신 지으면 칸 없이 보통 우선순위로 돈다).
- **게임 코드는 `Ninja-Debug` 한 빌드가 모두 짓습니다(`SW_GAMES=ALL`).** 게임 실행 확인은 `App.exe -game=<게임>` 으로 합니다. 도우미가 `Ninja-Debug-Lean` 처럼 게임을 줄인 구성으로 지었으면 "게임 빌드 미확인" 으로 보고합니다.
- **GPU 실행은 잠금 모드로 나눕니다.** 결정적 설정으로 기능만 보는 시나리오 · `hostgpu` · 캡처는 `shared-lock acquire gpu --shared`(공유, 동시에 두 프로세스 — 백엔드를 나눠 병렬로 돌린다),
  Release 측정 · 부하 기준선 · 실제 장치 제거(TDR) 실험과 실제 마우스 · 창 포커스에 기대는 시나리오(가상 입력으로 도는지 확인하지 못한 것)는 독점(`--shared` 없이)으로 혼자 돌립니다.
  독점은 공유 보유자가 모두 놓을 때까지 기다리고, 그동안 새 공유는 들어오지 못합니다.
  잠금은 `py -3 -m Scripts shared-lock acquire gpu --owner <이름> --shared`(독점은 `--shared` 없이)로 잡고, 끝나면(실패해도) 같은 모드로 `release` 합니다. 쥔 채 오래 있지 않습니다. GPU 실행만 맡기려면 `gpu-verifier` 에이전트를 씁니다.
- 스크립트로 파일을 고칠 때의 규칙(heredoc 금지 등)은 [EditingTraps](agents/EditingTraps.md) 가 원본입니다. 임시 파일은 scratchpad 에 두고 이름 앞에 에이전트 이름을 붙입니다.
- 컴파일러 경고 전체 조사(`Scripts/lint/report/RunBuildWarnings.py`, 세 프리셋)는 사용자가 요청할 때만 돌립니다. 내 변경이 만든 경고는 그 빌드가 이미 보여 줍니다.

## 3. 검증 단계

어떤 명령으로 무엇을 보는지는 [검증과 측정](08_Verification.md) 이 원본입니다. 여기에는 언제 어디까지 돌리는지만 적습니다.

**검증 빌드는 늘 전체입니다 — `py -3 -m Scripts full-build --owner <이름>`(`all AllTests`, 빌드 칸을 잡는다).** 바꾼 영역의 테스트만 지으면 다른 영역의 테스트가 쓰는
헤더 · 매크로를 바꾼 것이 병합 뒤에야 깨집니다. 고치는 동안의 빌드는 단일 타깃이어도 되지만, "검증했다" 고 보고하는 빌드는 `full-build` 입니다.
`full-build` 는 커밋하지 않은 변경이 없을 때만 짓고, 성공하면 그 커밋의 **빌드 입력**(트리에서 마크다운과 `.claude/` 를 뺀 것)의 증거를 공통 `.git` 에 남깁니다. 문서만 바꾼 커밋은 직전 증거가 그대로 맞아 다시 짓지 않습니다. **main 으로의 push 는 pre-push 훅이 그 증거를 요구합니다**
(`Scripts/setup/InstallGitHooks.py` 가 설치한다 — 훅이 없는 체크아웃은 그 스크립트를 한 번 돌린다). 그래서 병합 결과의 빌드 입력을 `full-build` 하지 않은 main 은 나가지 않습니다.
`full-build` 와 `py -3 -m Scripts test` 는 빌드 · 테스트 출력을 로그 파일(공통 `.git/sw-build-logs/`)에 쓰고 성공이면 끝 몇 줄과 소요 시간, 실패면 원인 줄과 그 주변만 보입니다(토큰 절감). 전부 보려면 `--verbose`.

| 단계 | Debug | Shipping | 그 밖 |
|---|---|---|---|
| 도우미 | `full-build` 경고 0, 고친 스위트(`--test_filter`) 또는 `py -3 -m Scripts test --changed`, 고친 파일의 린트 | — | — |
| 적용 담당(배치마다) | 병합 결과의 `full-build` 경고 0, `-L lint`, `-L nogpu`, `-L race` | 빌드, `-L nogpu`, `-L hostgpu` | 건드린 게임 × 네 백엔드. 배치 끝에 네 백엔드 × 대표 셋(Empty, 에디터, Shooter3D, NileCity) |
| 큰 단계 끝 | 위 + `-L hostgpu` 전체 한 번 | 위와 같음 | 모든 게임 × 모든 백엔드, Release 빌드와 성능 기준, 전용 서버 전체, WSL 리눅스 빌드 |

- **기능 시나리오(`hostgpu`)는 Shipping 이 기본입니다.** Debug 한 바퀴는 같은 검증의 수십 배가 걸립니다. 레이스 검사(`DataRaceDetector`)는 `SW_DEBUG` 에서만 켜지므로 Debug 는 스레드 경로를 지나는 묶음 `race` 만 돕니다(묶음은 `Test/TestPolicy.json` 의 `raceCases`).
- 적용 담당 · 큰 단계의 ctest 는 `-j`(값 없이 — 스레드 수)로 돌리고 도우미는 `-j 2` 입니다. hostgpu 를 뺀 항목은 병렬로 돌 수 있습니다.
- CI 러너는 GPU 가 없어 `nogpu` 만 돕니다. `race` 는 GPU 있는 PC 의 Debug 가 맡고, 리눅스 `CI-Debug-TSAN`(nogpu)이 보조입니다.
- 엔진 런타임 전체를 바꾸는 변경이면 배치 안에서도 큰 단계 끝의 검증을 돌립니다. 의존성을 올렸다면 그 변경에 걸린 기능(TLS, Tracy, 검증 레이어)도 봅니다.
- **에디터 변경은 에디터 시나리오로 확인합니다.** 시나리오 실행기의 에디터 단계(`-EnableEditor`)로 그 흐름을 하나 더하고 AppScenarioTest 로 돌립니다.
- **손 확인을 사용자에게 넘기지 않습니다.** 화면에서 확인할 일은 자동화 시나리오(`Resource/<영역>/automation/*.scenario.xml`)로 만들어 직접 확인합니다. 시나리오로 못 하는 것만 이유와 함께 `Candidates-<영역>.md` 에 후보 절로 씁니다.
- 성능 주장은 Release 측정값으로만 하고, 측정 없이 최적화하지 않습니다. 측정하는 법은 [검증과 측정](08_Verification.md) 2절입니다.

## 4. 내보내기 — push 와 CI

- **검증을 마친 main 은 묻지 않고 push 합니다.** 사용자에게는 결과만 짧게 알립니다. 들어간 것, 검증 수치, 상용 엔진(언리얼, 유니티, Godot)과 비교한 위치와 빠진 것을 적습니다.
- 도우미는 push 하지 않습니다. 검증되지 않은 브랜치가 원격에 가지 않게 하기 위해서입니다.
- main push 가 "전체 빌드 증거가 없다" 로 막히면 그 커밋에서 `full-build` 를 돌립니다. 훅을 우회하지 않습니다.
- 검증이 초록이면 바로 넣고, 뒤에 문제가 드러나면 그 단위를 되돌립니다. 배치 사이에 사용자 확인을 기다리지 않고 다음 배치를 시작합니다.
- **push 뒤 CI 결과를 기다리며 멈추지 않습니다.** 사용자가 실패를 알려 주거나, 세션 시작에 세션 가드가 main CI 실패(잡과 연속 실패 수, `py -3 -m Scripts ci-jobs --summary`)를 알리면 그때 원인을 찾습니다. 며칠 이어진 실패는 다른 일보다 먼저 봅니다. 실패를 읽는 방법(`ci-jobs`, 실패 주석)은 [검증과 측정](08_Verification.md) 4절에 있습니다.

## 5. 결정하는 방식

- **기술 결정은 상용 엔진의 같은 기능과 비교해 정하고, 근거 한 줄과 함께 [결정 기록](09_Decisions.md) 에 남깁니다.** 비교 대상은 언리얼, 유니티, Godot 이고, 온라인 기능은 PlayFab, EOS, Nakama 도 봅니다.
  사용자에게는 결과 요약에서 "정한 것" 으로만 알리고, 결정 표를 올려 고르게 하지 않습니다.
- 사용자에게 묻는 것은 다음뿐입니다. 법과 라이선스, 외부 공개(PR, 게시), 비용이나 계정이 드는 연동, 사용자가 보류로 정한 항목, 되돌리기 어려운 큰 데이터 삭제입니다.
- 게임 리소스는 CC0 급만 넣습니다. 조건과 예는 [결정 기록](09_Decisions.md) 5-1 에 있습니다.
- 이름을 바꿀 때 옛 이름 별칭을 두지 않고 데이터를 다시 씁니다([결정 기록](09_Decisions.md) 5-4).

## 6. 할 일을 다루는 방식

할 일은 아래 네 곳에만 둡니다. 한 사실은 한 곳에만 쓰고 나머지는 링크합니다. 역할 표는 [문서 지도](02_DocumentMap.md) 맨 위에 있습니다.

| 곳 | 담는 것 |
|---|---|
| `docs/plans/<이름>.md` | 착수한 일의 설계, 단위, 계약. 둘째 줄 머리 줄에 상태 · 선행 · 영역 · 옛번호 · 진행(`n/m`)을 둡니다 |
| `docs/plans/Candidates-<영역>.md` | 아직 착수하지 않은 후보. 일마다 `### 이름` 절(이름만, 바로 아래 `제목:` · `옛번호:` 줄)에 왜 필요한가와 착수 조건을 둡니다 |
| `docs/plans/Roadmap.md` | 순서만. 일은 이름 링크로만 가리킵니다 |
| `docs/plans/NEXT.md` | 지금 상태만 |

- 일의 식별자는 이름입니다(`ClusteredLighting`, 단위는 `ClusteredLighting.S2`). 코드 주석 · 결정 기록에 남은 옛 번호(`C-30` 등)는 `py -3 -m Scripts plans --find <옛번호>` 로 새 이름을 찾습니다. 새 일에 번호를 매기지 않습니다.
- 목록은 `py -3 -m Scripts plans`, 링크 점검은 `plans --check` 입니다. 최상단 `README.md` 의 진행 표는 `py -3 -m Scripts status-board --write README.md` 가 만든 생성물이라 손으로 고치지 않습니다.
- **일을 끝낸 사람이 직접 고칩니다.** 단위를 끝내면 그 계획 문서의 단위 절을 지우고 머리 줄 `진행` 을 올립니다. 후보를 착수하면 절을 계획 문서로 옮기고 후보 문서에서 지웁니다. 끝난 일은 `Roadmap.md` 에서 지웁니다. 교훈은 코드 헤더 주석 · 결정 기록 · 검증 문서로 옮깁니다. `NEXT.md` 는 통합 담당만 고칩니다.
- 갱신은 묻지 않고 작업 커밋에 함께 넣습니다. 이 점검은 `plans --check` 와 `status-board --check` 가 맡습니다.
- 여러 PC 에서 고치는 파일이라 작업 중에 pull 과 충돌이 날 수 있습니다. 병합 중이면(`.git/MERGE_HEAD`) 충돌 파일이 내가 만진 것인지부터 봅니다.
  커밋 훅 없이 올라온 커밋은 포맷 위반을 달고 올 수 있으므로, `.clang-format` 과 `Tools/LLVM` 버전이 같은지 확인한 뒤 `py -3 Scripts/lint/fixer/FormatModified.py` 로 정리합니다.

## 7. 커밋 메시지와 글

- **커밋 제목은 `<영역> - <요약>` 입니다.** 본문은 `문제점:`(증상과 원인), `해결방안:`(바꾼 타입, 함수, 파일), `결과:`(통과한 테스트, 동작, 측정값) 세 절이고, 맨 끝에 `Co-Authored-By` 줄을 둡니다.
  병합 커밋 메시지도 한국어로 씁니다(`병합 - main(<해시>)을 wt/<이름> 으로(<무엇이 들어왔나>)`). 모델에 맞는 `Co-Authored-By` 줄을 답니다.
- **커밋 훅의 출력은 요약입니다.** 통과 · 건너뜀 게이트는 한 줄(`게이트 N개: 통과 · 건너뜀 · 실패`)로 접히고 실패한 게이트만 상세가 나옵니다. 전부 보려면 `py -3 -m Scripts lint --verbose`.
- **커밋 훅을 우회하지 않습니다(`--no-verify` 금지).** 훅이 린트를 돌리므로 `git commit -m x` 같은 임시 커밋으로 린트를 시험하지 않습니다. 서식은 `py -3 Scripts/lint/fixer/FormatModified.py` 로 맞춥니다.
- 코딩 규칙은 [AGENTS.md](../AGENTS.md), 해결 원칙(구조로 푼다, 폴백 금지, 근본 원인 보고)은 [CLAUDE.md](../CLAUDE.md) "해결 원칙" 이 원본입니다.
- 커밋 메시지는 프로그래머 용어로 씁니다. "쥔 쪽", "길을 탄다" 같은 문학적 표현을 쓰지 않습니다. 경위와 배경은 커밋 메시지에 쓰고, 주석과 문서에는 현재형의 계약과 주의만 씁니다.
- 사용자에게 보이는 모든 글은 한국어로 씁니다. 답변, 진행 한 줄, 표, 질문, 계획, 에이전트 프롬프트와 보고가 모두 해당합니다. 식별자, 경로, 명령, 로그 문자열은 원문 그대로 둡니다.
- 문서와 주석의 문체는 [문서 쓰기 지침](10_WritingDocs.md)을 따릅니다. 업계에서 굳은 용어를 그대로 쓰고 순우리말 조어를 만들지 않습니다.

## 8. 리눅스 빌드

리눅스는 WSL 안의 별도 클론에서 빌드합니다. Windows 체크아웃에서 `WSL-*` 프리셋을 돌리면 공유 vcpkg 설치 트리를 망가뜨립니다.
클론 위치, gdb 없는 환경의 진단법, 뒤처진 클론을 맞추는 법은 [Scripts/setup README](../Scripts/setup/README.md) "함정 · 계약" 절에 있습니다.
리눅스 분기 코드를 고쳤으면 WSL 에서 빌드하거나, 못 했으면 보고에 적습니다.
