# 작업 방식

이 저장소는 여러 PC 와 여러 세션에서, 사람과 에이전트가 함께 고칩니다. 이 문서는 그 작업을 나누고, 빌드하고, 검증하고, 내보내는 방식을 적습니다.
한 PC 의 메모리나 세션 임시 폴더에만 있던 규칙을 여기로 옮겼으므로, 다른 PC 에서 일을 시작할 때 이 문서를 먼저 읽습니다.

규칙의 원본은 한 곳씩입니다. 코딩 규칙과 편집 함정은 [AGENTS.md](../AGENTS.md), 일을 끝내기 전에 돌릴 것과 측정법은 [검증과 측정](08_Verification.md),
정한 방향과 기각한 안은 [결정 기록](09_Decisions.md), 남은 일은 [백로그](06_Backlog.md) 에 있습니다. 이 문서는 그 문서들이 다루지 않는 진행 방식만 적습니다.

## 1. 일을 나누는 방식 — 워크트리와 적용 담당

큰 작업 배치는 단위로 나누어 워크트리 하나에 브랜치 하나씩 진행합니다. 워크트리는 main 체크아웃과 같은 저장소를 공유하는 별도 작업 폴더입니다.

```powershell
py -3 -m Scripts worktree-make <이름>                  # <main 의 부모>/LT-wt/<이름>, 브랜치 wt/<이름>, 기준 origin/main
py -3 -m Scripts worktree-make <이름> --base wt/apply5 # 다른 브랜치에서 갈라 만든다
py -3 -m Scripts worktree-remove <이름>                # 나눠 쓰는 링크를 먼저 끊고 지운다
```

- 워크트리는 내려받은 도구(LLVM, Ninja, sccache, vcpkg)와 vcpkg 설치 폴더를 main 체크아웃과 링크로 나눠 씁니다. 이 링크 폴더(`Tools/*`, `build/vcpkg_*`)는 지우거나 고치지 않습니다.
  그래서 `vcpkg.json`, 포트, `cmake/Modules/Toolchain/Vcpkg/*` 를 바꿔야 하면 워크트리에서 바꾸지 않고 main 에서 먼저 바꿉니다.
- **적용 담당은 하나입니다.** 적용 담당이 단위 브랜치를 받아 합치고, 빌드하고, 전체를 검증하고, main 에 넣고 push 합니다. 넓게 건드리는 변경(폴더 이동, 헤더, 매크로 철자)을 먼저 넣습니다.
- **도우미는 자기 워크트리 안에서만 일합니다.** 다른 워크트리와 main 체크아웃을 건드리지 않고, push 하지 않습니다. 단위를 끝낼 때마다 최신 main 을 받아 충돌을 스스로 풉니다.
  적용 담당은 충돌을 풀지 않고 되돌려 보냅니다. 셰이더 매니페스트, 쿠킹 바이너리, `import.stamp` 같은 생성 산출물이 충돌하면 한쪽을 고르지 않고 `App --cook-shaders` 나 `--import-models` 로 다시 만듭니다.
- 같은 파일을 건드리는 단위는 한 도우미에게 몰아 줍니다. 끝난 워크트리는 바로 지웁니다.
- 기계적 변경(이동, 이름 바꾸기, 일괄 재작성)은 커밋만 단계별로 나누고 빌드와 테스트는 끝에 한 번 합니다.
- 결함을 고칠 때는 재현 테스트(고치기 전에 지는 것 확인) → 고침 → 변이 검사(고침을 빼면 테스트가 지는가) 순서입니다. 자세한 규칙은 [검증과 측정](08_Verification.md) 1절입니다.

## 2. 빌드와 CPU

- **동시에 빌드하는 작업은 최대 둘입니다**(적용 담당과 도우미 하나). 나머지 도우미는 코드 적용과 빌드 없는 검사만 합니다. 워크트리마다 빌드 폴더가 따로라 sccache 가 거의 맞지 않고, 전체 빌드가 겹치면 CPU 가 100 % 에 붙어 테스트 시간 제한이 가짜로 집니다.
- 도우미의 빌드와 테스트는 낮은 우선순위로 돌립니다. Git Bash 에서 `cmd //c "start /belownormal /wait /b cmake --build --preset Ninja-Debug -j 4"`, ctest 는 `-j 2` 입니다. 끌 때는 자기 PID 만 끕니다.
- **게임별 프리셋(`Ninja-Debug-<Game>`) 빌드는 배치 끝에 적용 담당이 한 번 합니다.** 도우미는 게임 소스를 고쳤으면 "게임 빌드 미확인" 으로 보고합니다.
- 파이썬 조각은 heredoc 이나 `python -` 로 넘기지 않고 파일로 써서 `py -3 <파일>` 로 돌립니다. 그 밖의 편집 함정은 [AGENTS.md](../AGENTS.md) "Editing traps" 에 있습니다.
- 컴파일러 경고 전체 조사(`Scripts/lint/report/RunBuildWarnings.py`, 세 프리셋)는 사용자가 요청할 때만 돌립니다. 내 변경이 만든 경고는 그 빌드가 이미 보여 줍니다.
  빌드 로그의 경고가 이상하면(sccache 가 옛 경고를 재생한 경우) 조사를 돌릴지 사용자에게 묻습니다.

## 3. 검증 단계

어떤 명령으로 무엇을 보는지는 [검증과 측정](08_Verification.md) 이 원본입니다. 여기에는 언제 어디까지 돌리는지만 적습니다.

- **도우미는 단축 검증만 합니다.** Debug 빌드(경고 0), 자기가 만들거나 고친 스위트(`--test_filter`), 고친 파일의 린트입니다.
- **적용 담당은 배치마다 다음을 돌립니다.** Debug 경고 0, `ctest -L lint`, 바뀐 영역의 테스트, `-L nogpu`, Shipping 빌드와 `-L hostgpu`, 그 배치이 건드린 게임 × 네 백엔드입니다.
  배치 끝에는 네 백엔드 × 대표 셋(Empty, 에디터, Shooter3D, NileCity)과 자동화 시나리오를 더합니다. 의존성을 올렸다면 그 변경에 걸린 기능(TLS, Tracy, 검증 레이어)도 봅니다.
- **큰 단계의 끝에만 전체를 돌립니다.** 모든 게임 × 모든 백엔드, Release 빌드와 성능 기준, 전용 서버 전체, WSL 리눅스 빌드입니다. 엔진 런타임 전체를 바꾸는 변경이면 배치 안에서도 전체를 돌립니다.
- **손 확인을 사용자에게 넘기지 않습니다.** 화면에서 확인할 일은 자동화 시나리오(`Resource/<영역>/automation/*.scenario.xml`)로 만들어 직접 확인합니다. 시나리오로 못 하는 것만 이유와 함께 백로그에 적습니다.
- 성능 주장은 Release 측정값으로만 하고, 측정 없이 최적화하지 않습니다. 재는 법은 [검증과 측정](08_Verification.md) 2절입니다.

## 4. 내보내기 — push 와 CI

- **검증을 마친 main 은 묻지 않고 push 합니다.** 사용자에게는 결과만 짧게 알립니다. 들어간 것, 검증 수치, 상용 엔진(언리얼, 유니티, Godot)과 비교한 위치와 빠진 것을 적습니다.
- 도우미는 push 하지 않습니다. 검증되지 않은 브랜치가 원격에 가지 않게 하기 위해서입니다.
- 검증이 초록이면 바로 넣고, 뒤에 문제가 드러나면 그 단위를 되돌립니다. 배치 사이에 사용자 확인을 기다리지 않고 다음 배치을 시작합니다.
- **push 뒤 CI 결과를 기다리며 멈추지 않습니다.** 사용자가 실패를 알려 주면 그때 원인을 찾습니다. 로그와 아티팩트는 관리자만 받을 수 있으므로 공개 API 로 실행, 잡, 실패 주석을 읽습니다.

```powershell
py -3 -m Scripts ci-jobs --runs                    # main 의 최근 실행
py -3 -m Scripts ci-jobs <실행 id> --annotations   # 실패한 잡과 실패 주석
```

## 5. 결정하는 방식

- **기술 결정은 상용 엔진의 같은 기능과 비교해 정하고, 근거 한 줄과 함께 [결정 기록](09_Decisions.md) 에 남깁니다.** 비교 대상은 언리얼, 유니티, Godot 이고, 온라인 기능은 PlayFab, EOS, Nakama 도 봅니다.
  사용자에게는 결과 요약에서 "정한 것" 으로만 알리고, 결정 표를 올려 고르게 하지 않습니다.
- 사용자에게 묻는 것은 다음뿐입니다. 법과 라이선스, 외부 공개(PR, 게시), 비용이나 계정이 드는 연동, 사용자가 보류로 정한 항목, 되돌리기 어려운 큰 데이터 삭제입니다.
- 게임 리소스는 CC0 급만 넣습니다. 조건과 예는 [결정 기록](09_Decisions.md) 5-1 에 있습니다.
- 이름을 바꿀 때 옛 이름 별칭을 두지 않고 데이터를 다시 씁니다([결정 기록](09_Decisions.md) 5-4).

## 6. 백로그를 다루는 방식

- 백로그 갱신은 묻지 않고 작업 커밋에 함께 넣습니다. 새로 알아낸 남은 일과 함정은 더하고, 끝난 항목은 "완료" 표시 없이 그 자리에서 지웁니다.
- 끝난 일의 교훈은 그 영역 README 의 "함정 · 계약" 절에, 결정은 [결정 기록](09_Decisions.md) 에, 검증법은 [검증과 측정](08_Verification.md) 에 옮깁니다. 백로그에 "참고" 절을 다시 만들지 않습니다.
- 여러 PC 에서 고치는 파일이라 작업 중에 pull 과 충돌이 날 수 있습니다. 병합 중이면(`.git/MERGE_HEAD`) 충돌 파일이 내가 만진 것인지부터 봅니다.
  커밋 훅 없이 올라온 커밋은 포맷 위반을 달고 올 수 있으므로, `.clang-format` 과 `Tools/LLVM` 버전이 같은지 확인한 뒤 `py -3 Scripts/lint/fixer/FormatModified.py` 로 정리합니다.

## 7. 커밋 메시지와 글

- **커밋 제목은 `<영역> - <요약>` 입니다.** 본문은 `문제점:`(증상과 원인), `해결방안:`(바꾼 타입, 함수, 파일), `결과:`(통과한 테스트, 동작, 측정값) 세 절이고, 맨 끝에 `Co-Authored-By` 줄을 둡니다.
  병합 커밋 메시지도 한국어로 씁니다(`병합 - main(<해시>)을 wt/<이름> 으로(<무엇이 들어왔나>)`).
- 커밋 메시지는 프로그래머 용어로 씁니다. "쥔 쪽", "길을 탄다" 같은 문학적 표현을 쓰지 않습니다. 경위와 배경은 커밋 메시지에 쓰고, 주석과 문서에는 현재형의 계약과 주의만 씁니다.
- 사용자에게 보이는 모든 글은 한국어로 씁니다. 답변, 진행 한 줄, 표, 질문, 계획, 에이전트 프롬프트와 보고가 모두 해당합니다. 식별자, 경로, 명령, 로그 문자열은 원문 그대로 둡니다.
- 문서와 주석의 문체는 문서 쓰기 지침(docs/10_WritingDocs.md)을 따릅니다. 업계에서 굳은 용어를 그대로 쓰고 순우리말 조어를 만들지 않습니다.

## 8. 리눅스 빌드

리눅스는 WSL 안의 별도 클론에서 빌드합니다. Windows 체크아웃에서 `WSL-*` 프리셋을 돌리면 공유 vcpkg 설치 트리를 망가뜨립니다.
클론 위치, sccache 포트(WSL 은 4227), gdb 없는 환경의 진단법, 뒤처진 클론을 맞추는 법은 [Scripts/setup README](../Scripts/setup/README.md) "함정 · 계약" 절에 있습니다.
리눅스 분기 코드를 고쳤으면 WSL 에서 빌드하거나, 못 했으면 보고에 적습니다.
