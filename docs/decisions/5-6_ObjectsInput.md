# 5-6. 오브젝트, 조종, 입력

> 질문: 5-6. 오브젝트, 조종, 입력 영역에서 이미 정한 것은 무엇이고 근거는 무엇인가?
> 독자: 같은 제안을 다시 하려는 사람, 정한 이유를 찾는 사람.
> 결론: 결정 기록 5 절의 한 영역이다. 번호 체계와 쓰는 법은 [결정 기록](../09_Decisions.md) 5절에 있다.

- **병렬 분배는 항목 수가 아니라 잰 비용으로 고르는 공용 API 를 둔다**(2026-10-16): 고정 임계값 16 은 가벼운 항목(~25 ns)에서 너무 낮아 작은 그룹이 깨우는 비용(~20 us)을 일보다 크게 치렀다(무버 16 개 19 us 대 직렬 1 us). `TaskManager::runParallelByCost`(엔진은 `engine::runParallelByCost`)는 호출 스레드가 앞 항목을 1, 2, 4, … 개씩 직접 돌며 비용을 재고, 경과 3 us 에서 남은 일의 예상 직렬 시간이 16 us 보다 짧으면 이어서 직렬로, 아니면 나머지 구간만 나눈다(저장하는 추정 없음). 씬 틱의 보통 길 · 선행 조건 스테이지가 쓴다. `runParallel(count, threshold)` 는 "임계값 이상이면 나눈다" 계약을 그대로 둔다. 상용 엔진(UE 틱 그룹 · Unity 의 작은 `Update` 목록)도 일이 작으면 깨우지 않는다.
  애니메이션 평가(`AnimationSystem::runPhase`, Release 3 판 중앙값, `GT.Animation.evaluate` p50)는 캐릭터 하나가 직렬로 약 5 us 라 20 개는 깨우는 비용이 더 크고(고정 8 임계 122 us, 직렬 81 us) 100 개부터 병렬이 이겨(직렬 491 → 비용 기반 163 ~ 180 us) 비용 기반으로 옮겼습니다(`kParallelUnitCount` 삭제). 측정한 부하는 걷기 · 대기 클립뿐이고 IK 그래프와 랙돌이 섞인 부하는 재지 않았습니다(NEXT.md).
  실제 게임 부하 확인(2026-10-16, Release · dx12 · 자동 플레이 900 프레임): 틱이 도는 오브젝트 칸이 2 ~ 200 개뿐이라 `GT.Scene.tick.components` p50 이 VoxelCraft 36 → 7 us 로 줄고 나머지 일곱 게임은 같거나 1 ~ 5 us 느렸고 `GT.Frame` 은 같았습니다. 원인은 무거운 디렉터가 앞 항목이라 비용을 재는 동안 호출 스레드에서 직렬로 돌고 워커가 노는 것입니다. 순이득이 프레임 시간의 0.1 % 안쪽이라 **`-gv_tickCostDispatch` 기본은 0(옛 방식)으로 정했다**(사용자가 상용 엔진 기준으로 위임). 스위치와 API 는 남깁니다. AAA 규모로 다시 따져도 같습니다 — 틱 수천 개 씬은 어느 방식이든 바로 나뉘고 갈리는 곳은 무거운 항목이 앞에 올 때인데, 잰 뒤 나누는 방식은 그 항목을 직렬로 돌려 꼬리를 늘리고 고정 임계값은 청크 티켓으로 다른 워커가 나머지를 바로 가져갑니다. 다시 켜려면 프레임 사이에 비용을 기억해 재는 직렬 구간을 없애야 하고 그때 이 스위치로 다시 잽니다. 랙돌 100 + IK 기사 20 군중에서도 틱 분배는 병목이 아니었습니다. 비교 케이스는 `perf-compare --cases tickCostMovers tickCostSmallScene tickCostChurn`.
- **`PostUpdate` 그룹은 서브틱으로 바꾸지 않고 `TickPhase` · 서브틱 우선순위는 유지한다**(2026-10-16, 사용자가 상용 엔진 · AAA 기준으로 위임). `PostUpdate` 사용처 41 개는 "디렉터(`PrePhysics`)가 이 프레임을 끝낸 뒤 읽는다", "앞 그룹이 옮긴 뒤 읽는다" 이고 둘 다 그룹 순서(그룹 사이 장벽 하나)가 정확히 표현하는 의도입니다. 서브틱 선행 조건으로 바꾸면 오브젝트 사이 의존을 핸들로 걸어야 해 복잡하고 속도는 차이가 없습니다(`FollowerOrderingGroupVersusPrerequisite`, 4000 쌍). 서브틱 선행 조건은 같은 그룹 안의 오브젝트 사이 순서(`GameDirectorComponent::_tickAfter`)에 씁니다. `TickPhase` 의 `Early` · `Late` · `Finalize` 와 `priority` 는 제품 코드 사용이 0 이지만 UE · Unity · Godot 이 모두 오브젝트 안의 순서 지정 수단을 두므로 지우지 않습니다(`Component.h` 의 `TickPhase` 주석).
- **선행 조건 스테이지는 말단 오브젝트만 증분으로 끼우고 뺀다**(2026-10-16): 팔로워 4000 에 프레임마다 하나 만들고 지우면 재구축이 프레임당 559 us 였다. 재구축을 평평한 표 · CSR · 오브젝트 순번으로 짓게 해 약 275 us 로 줄였고, 아무도 기다리지 않고 선행 조건이 모두 의존 오브젝트 밖(보통 길)인 오브젝트는 스테이지를 다시 짓지 않고 그 그룹의 레벨 0 스테이지에 끼우고 뺀다(`TickRegistry::applyStageDelta` · `queueStageRemoval`) — 약 69 us. 누군가 기다리는 오브젝트가 바뀌거나 선행 조건이 다른 의존 오브젝트를 가리키면 전체 재구축이다. 기각: 모든 변경을 증분으로 처리(사슬 · 순환은 전체 위상 정렬이 필요). 증분으로 끼운 항목의 자리는 전체 재구축과 같다 — 재구축이 (순서 키, 오브젝트 id) 순이라 끼울 때도 같은 키로 정렬 삽입한다(`IncrementalStageLayoutMatchesFullRebuild` 가 견줌).
- **선행 조건 스테이지의 제거는 요청으로 쌓아 두었다가 `refresh` 끝에서 스테이지를 한 번만 훑어 처리한다**(2026-10-25, `TickRegistry::queueStageRemoval` · `flushStageEdits`). 마이크로 최적화가 아니라 증가 모양을 고치는 구조 정리다: 오브젝트 하나를 뺄 때마다 모든 스테이지의 id 열을 선형으로 훑고 erase 해서 한 프레임에 K 개를 빼면 O(K · S)였고 이제 O((K + S) log K) 다. 끼움도 같은 요청 열에 순서대로 쌓아 순서가 하나씩 처리할 때와 같다(`BulkFollowerRemovalCompactsStagesOnceAndMatchesFullRebuild`). 훑은 횟수는 `getStageCompactCount` 로 센다(`refresh` 당 1). 기각: 오브젝트 id → (스테이지, 위치) 색인(끼우고 빼면 뒤 위치가 밀려 색인을 고치는 일이 O(S) 로 돌아간다). 남은 비용: 끼움은 정렬 삽입이라 항목당 O(S) 이고 배치 병합은 하지 않았다. 스테이지는 `refresh` 직후에만 맞다(그 사이에는 파괴된 오브젝트의 항목이 남는다). [측정: 없음 — 복잡도 모양으로 정했다. 1 만 규모 Release 확인은 `tickCostChurn` 합성 벤치에서 하기 전]
- **`AnimationCrowd` 의 묶음 평가 분배(`kParallelBucketCount` 8)는 비용 기반으로 옮기지 않는다**(2026-10-16, Release · 5 판 번갈아 · 혼자 돌며 잰 중앙값): `GT.Animation.crowdBuckets` p50 이 군중 1000 에서 36 → 49 us, 300 에서 32 → 49 us 로 늘었다. 묶음은 수십 개뿐이고 하나가 수 us 라 비용을 재는 동안 호출 스레드가 앞 묶음을 직렬로 돌고 나머지를 나누는 길이 고정 임계값(8 개 이상이면 바로 나눔)보다 느리다. `GT.Animation.evaluate` p50 은 이득이 없고, 랙돌 300 은 p50 1 us 라 분배가 병목이 아니다. 이 기계의 판 사이 흔들림(프레임 8 ~ 12 ms)이 이득보다 커서 근거는 `crowdBuckets` 구간의 방향(전 판 B 가 높다)이다.
- **프리팹에서 사라진 컴포넌트의 오버라이드는 경고하고 버립니다**(2026-10-06). 언리얼과 같고 유니티는 남겨 둡니다.
- **"그 타입의 컴포넌트 모두" 는 타입별 레지스트리(`ComponentRegistry`)에서 찾습니다**(2026-10-06). 상호작용 대상을 프레임마다 씬 전체에서 찾던 경로가 Release 10k 오브젝트에서 190 us 를 넘었고 레지스트리로 2~6 us 가 됐습니다(언리얼 서브시스템의 등록 목록과 같음). 공간 해시는 두지 않았습니다([후보 문서](../plans/Candidates-gameplay.md) `G-4`).
- **조종 구조**(2026-10-06): 가상 입력은 배타 모드가 기본입니다. 게임플레이 리플레이와 네트워크는 의도(`ControlIntent`)를 싣고 `InputReplay` 는 입력 층의 QA 녹화입니다. 전략과 경영 장르는 폰 없이 디렉터가 명령 조종자가 됩니다. 시나리오는 늘 고정 프레임 시간으로 돕니다. 탑승 중에도 피격을 받고 쓰러지면 강제로 내립니다. 탈것의 의도는 운전석 조종자를 따릅니다.
- **같은 타입이 수천 개 틱하면 타입별 일괄 틱(`TickBatchRegistry`, 등록은 선택)으로 돕니다**(2026-10-13, 사용자 결정 "구조 변경을 한다"). 언리얼 Mass 프로세서 · 유니티 `IJobEntity` 자리입니다. 옮기는 것은 그룹에서 항목이 그 타입의 주 틱 하나뿐인 오브젝트만이라 오브젝트 안의 순서 · 한 오브젝트는 한 스레드 규칙이 그대로이고 정확한 타입만 가서 파생의 `onTick` 을 건너뛰지 않습니다. 모든 컴포넌트를 ECS 저장소로 옮기는 안은 하지 않았습니다(오버라이드 72 곳 · 포인터 모델 전체) — 타입이 데이터를 배열로 옮기는 다음 단계는 측정 뒤에 정합니다.
- **1인칭 카메라는 폰의 부품이라 `Base/Control` 에 둡니다**(2026-10-06, 언리얼 `bUsePawnControlRotation` 자리). 자동 플레이는 몸 안의 분기가 아니라 AI 조종자의 빙의입니다.
- **커서 위치 API 는 `InputManager::getMousePositionNormalized` 하나입니다**(2026-10-06). 게임 쪽 코드는 장치를 직접 묻지 않고 입력 맵 액션을 읽습니다. 패드 스틱 시점은 바인딩마다의 배율 · 프레임 시간 곱(언리얼 Enhanced Input 의 Scale · Scale By Delta Time)으로 넣었습니다(2026-10-13).
- **중첩 프리팹은 쿠킹 때 펼칩니다**(2026-10-13). 배포본이 스폰마다 원본 파일을 열고 원형에 오버라이드를 적용하는 일을 없애려는 것으로 언리얼 Packed Level Actor 와 같습니다. 에디터 · Dev 는 원본을 경로로 가리켜 원본을 고치면 모든 상위에 퍼지고(유니티 Nested Prefab) 순환은 로드 오류입니다.
- **내비 기하에 들어갈 컴포넌트 종류는 종류별 레지스트리(`SW_NAV_GEOMETRY_CONTRIBUTOR`)로 등록합니다**(2026-10-13). Navigation(Object 층)은 Environment(위층)를 include 할 수 없고 인스턴스가 플레이 중에 등록하는 `INavGeometrySource` 는 플레이 전에 도는 쿠킹에 들지 않기 때문입니다. 언리얼 `INavRelevantInterface` 처럼 종류 단위 규칙이라 쿠킹과 런타임이 같습니다.
- **패드 가상 커서는 명령 조종자(디렉터)가 플레이 동안만 켭니다**(2026-10-15). 게임 모듈의 `onInitialize` 가 켜면 에디터에서 편집 중에도 켜져 있고 조종 경계(`CheckControlBoundary`)도 넘습니다(언리얼 `PlayerController` 가 커서 표시 · 입력 모드를 정하는 자리).
- **입력 커맨드 버퍼 둘은 하나로 모으지 않습니다**(2026-10-15, C-26 ⑥). Engine `InputActionBuffer` 는 실시간(초) 액션 이력 · 선입력(에디터 InputMap 패널의 콤보 테스트가 씀)이고 GameFramework `InputCommandBuffer` 는 틱 단위 넘패드 · 버튼 이력이라 롤백에서 다시 돌려도 같은 결과여야 하고 바라보는 쪽을 뒤집습니다. 한쪽으로 모으면 롤백이 깨지거나(실시간) 에디터 · 엔진이 GameFramework 를 알아야 합니다(틱). 언리얼도 Enhanced Input 의 실시간 Combo 트리거와 격투 게임의 프레임 버퍼가 따로 있습니다.

- **큰 클래스는 책임이 따로 서는 묶음을 값 객체로 가르고 소유 객체에 그대로 넘기던 전달 함수는 지웁니다**(2026-10-15, C-26 ⑤). `InputMap` 의 플레이어 설정(감도 · 반전 · 데드존 · 정규화) → `InputPlayerSettings`(언리얼 `UEnhancedInputUserSettings` 자리), `AbilitySystemComponent` 의 태그 개수 → `GameplayTagCountContainer`(언리얼 `FGameplayTagCountContainer`), `UISystem` 의 전달 함수 열다섯 → `getInputRouter()` · `getOffscreenScreens()`, `InputManager` 의 게임패드 전달 함수 다섯(쓰는 곳 없음) 삭제. `GameObjectManager` 는 씬의 얼굴(만들기 · 찾기 · 풀기)이라 그대로 둡니다(언리얼 `UWorld::SpawnActor` 처럼 저장소를 숨기는 자리라 전달이 곧 계약). `InputMap` 의 리바인딩도 바인딩 저장소를 직접 고치는 일이라 가르면 저장소를 밖에 내보여야 해 그대로 둡니다.
- **시나리오의 액션 단계는 액션 값을 직접 넣지 않고 바인딩을 찾아 장치 층에 냅니다**(2026-10-15, `Action` · `ActionAxis`). 언리얼 Enhanced Input `InjectInputForAction` 은 액션 값을 넣어 트리거와 모디파이어 일부를 건너뛰고 유니티 Input Test Fixture 는 장치 키를 누릅니다. 이름은 액션으로 적어 키 배치를 바꿔도 시나리오가 그대로이고 입력은 장치에서 내므로 트리거 · 레이어 · UI 입력 소비의 결함까지 잡습니다. 패드 바인딩을 쓰면 가상 패드를 먼저 연결합니다.
- **게임 로직 단언은 질의 탐침(`target`, `key`, 수 또는 글)과 값 이력(`ExpectVisited`)으로 합니다**(2026-10-15). 기반(일정 시스템 · AI 조종자 · 폰 · 판 상태)이 탐침을 한 번 등록하면 게임은 아무것도 더하지 않고 "10 시에 가게에 있다", "갈기, 심기, 물주기를 차례로 거쳤다" 를 데이터로 적습니다. "N 초 안에 도달" 은 새 단계 없이 `WaitUntil timeoutSeconds` 입니다(언리얼 Functional Test · 유니티 PlayMode 는 코드에서 액터를 직접 읽음).
- **결정적 재생은 `<Record>` 값을 백엔드끼리 비교하고 녹화와 재생의 왕복으로 확인합니다**(2026-10-15). 게임 상태는 고정 틱 위의 CPU 계산이라 백엔드와 무관해야 합니다. 기대값을 시나리오에 적지 않고 같은 실행의 네 백엔드를 서로 비교하므로 해시가 바뀌어도 시나리오를 고칠 필요가 없습니다(Gauntlet 이 여러 장치의 결과를 모으는 방식에 비교 단계를 더한 것). 녹화는 끝 프레임의 탐침 값을 `<Expect>` 로 실어 스스로를 검증합니다.
- **AI 조종자가 블랙보드, 행동 트리 실행기, 상태 이름을 가집니다**(2026-10-15, 언리얼 `AAIController` 의 Blackboard · Brain 컴포넌트와 같음). 그래서 GameFramework 층 테이블에서 `Actor/Control` 이 `Actor/AI` 위(2)로 올라갔습니다. 시계 · 일정 · AI · 빙의 · 탑승을 모두 읽는 자동화 단계와 탐침은 기반 맨 위 `Gameplay/Automation` 에 둡니다.
- **행동 트리 실행기의 잎 이름은 도는 잎이 없으면 그 틱에 마지막으로 성공한 작업입니다**(2026-10-15). 한 틱에 끝나는 작업만 있는 트리(RTS 경제 AI)는 도는 잎이 늘 없어 이름이 비어 있었습니다(언리얼 BT 디버거가 마지막 실행 노드를 보여 주는 것과 같음). `getActiveLeaf()`(번호)는 도는 잎만 돌려줍니다.
- **에디터 입력 단계는 누를 레이블이 그려질 때까지 시나리오 시계를 붙잡습니다**(`EditorClick` · `EditorDrag` · `EditorHover`, 최대 60 프레임, 2026-10-15, A-3). 언리얼 Automation Driver 의 "보일 때까지 기다리기" · Playwright 자동 대기와 같습니다. 고정 프레임 단계는 패널이 프레임을 건너뛰거나 팝업이 늦게 열리면 가끔 졌습니다. 기다림은 `AutomationRunner::holdUntilReady`(붙잡은 프레임은 세지 않고 입력 이벤트를 민다)이고 기다린 프레임은 로그에 남아 다음 실패의 증거가 됩니다.

- **매니저의 타입별 컴포넌트 목록은 정확한 타입마다 버킷 하나이고 버킷은 컴포넌트 풀 항목(FQN 키)에 합칩니다**(2026-10-17, 7-c). 조회는 버킷마다 `isDerivedFrom` 을 한 번 묻습니다. 언리얼 `GetObjectsOfClass` 의 "정확한 클래스 버킷과 파생 열거" 와 같은 계열이고 조상 목록(컴포넌트당 깊이만큼의 위치)보다 메모리가 약 여덟 분의 일입니다. 순서는 약속하지 않습니다. 핸들은 `TComponentHandle<T>` 로 타입을 싣고(7-d) 타입 없는 핸들에서 만들 때만 확인합니다. 찾기의 타입 확인은 Shipping 이 아닌 모든 구성에서 합니다.
- **삭제 대기 오브젝트의 컴포넌트는 항상 삭제 대기이고 컴포넌트 목록을 도는 곳은 컴포넌트 표시 하나만 본다**(2026-10-19, 7-c 측정). 오브젝트 표시는 비공개 하나이며 컴포넌트를 먼저 표시하고, 삭제 대기 오브젝트에 붙는 컴포넌트는 삭제 대기로 시작하며(유니티 `Destroy` 뒤 같은 프레임의 `AddComponent`) 해체 중 오브젝트에는 붙이기를 거절한다(유니티 "being destroyed", 언리얼 `IsActorBeingDestroyed`). 버킷에서 빼는 안은 지연 파괴 전까지 버킷과 목록이 어긋나고 병렬 틱 안에서 배타 잠금이 필요해 버렸다. 버킷 순회 10만 · 말단 8.3 → 3.0 µs.
- **`runParallelByCost` 의 시계는 함수 포인터로 주입하고 선행 조건 스테이지의 순서 키 비교는 한 곳에 둔다**(2026-10-16). 제품은 `MonotonicClock::nowNanoseconds` 를 넘기고(`runParallelByCostWithClock`) 테스트는 가짜 시계로 선점 잡음 없이 직렬 · 분할 판단을 결정적으로 본다. 시계는 청크마다 한 번만 불려 핫 경로에 가상 호출이 없다. `TickRegistry` 의 재구축(`isBefore`)과 증분(`applyStageDelta`)은 `StageOrder` · `isOrderedBefore` 하나를 공유해 두 길의 순서가 어긋날 수 없다.
- **서브틱 입력의 발사는 조종 의도의 선택 칸으로 싣고 발동 순간의 시선은 폰이 지정한 버튼 하나에만 만든다. `GetMessageTime` 과 입력 스레드는 쓰지 않는다**(2026-10-22, 서브틱 입력 B4 · B6). CS2 는 입력에 서브틱 시각을 붙여 서버가 그 순간으로 되감는다. 여기서는 클라이언트가 클릭한 순간의 시선을 의도에 싣는다 — `ControlIntent::_bTriggerLook` · `_triggerYaw` · `_triggerPitch`(없으면 비트 하나)이고 `PawnComponent::_triggerLookButton` 이 어느 버튼의 순간인지 정한다(Shooter3D 는 `Fire`). 순간의 시선은 프레임 시작의 조종 회전에 시선 액션 값 × `InputPressInstant::computeLookFraction`(누름 직전까지의 원시 이동량 ÷ 프레임 전체)을 더해 만든다(감도를 다시 곱하지 않아 액션의 배율 · 반전이 남음). 누름이 이벤트로 오지 않는 바인딩(축 임계 · 길게 누름)은 순간을 지어내지 않고 프레임 끝의 조종 회전을 쓴다. 형식이 바뀌어 `ControlIntentHistory::kVersion` 2 · `NetKitWireVersion::kClientServer` 6 으로 올렸다(옛 `.swintent` 는 거절). 롤백 · 락스텝 키트는 프레임 단위 결정성이 계약이라 이 칸을 쓰지 않는 조종자만 쓴다.
  `GetMessageTime`(`GetTickCount` 계열)의 변화 간격이 15 ~ 31 ms(평균 15.8 ms)로 60 Hz 프레임 하나(16.7 ms)와 같아 프레임 안 자리를 가리지 못한다. 창 스레드가 큐에 넣는 순간의 단조 시계가 더 세밀하고, 입력 스레드로 옮기면 에디터 · 콘솔이 먼저 소비하는 판정을 우회할 위험만 는다. 사건 시각은 `RawInputEvent::_timeMicroseconds`(`InputManager::postRawEvent`)와 `_frameFraction` 이다(입력 리플레이 판 5). `beginFrame` 이 창 [지금 − 델타, 지금] 으로 OS 이벤트의 프레임 안 자리를 채우고 누름마다 `InputPressInstant`(자리 · 그 앞까지의 마우스 원시 이동량 · 시각)를 적으며(시계 주입은 `InputManager::setClock`) `InputMap::tryGetActionPressInstant` 가 바인딩이 완성된 순간(조합 키는 늦은 슬롯, 바인딩 여럿이면 가장 이른 것)을 돌려준다. 넷 입력은 항목마다 틱 스탬프를 싣고(`kInputFormat` 스탬프 켬, `NetKitWireVersion::kClientServer` 5) 서버가 [꺼내는 틱 − `_maxViewLagTicks`, 꺼내는 틱] 으로 자른다. 클릭한 순간의 방향으로 사격이 실제로 나가는지는 시나리오로 보지 못했다(`ShooterPlayerComponent::onTick` 은 게임 모듈이라 `EngineTest` 가 링크하지 않음).

- **타입 핸들 `TComponentHandle<T>` 의 찾기 · 직렬화 · 인스펙터 규칙과 버킷 갱신 규칙**(2026-10-17~19, 7-c · 7-d):
  - 찾기 `resolveComponent<T>` 는 Shipping 이 아닌 모든 구성에서 타입을 확인합니다(맞지 않으면 오류 로그와 Debug 단언 뒤 nullptr). id 는 프로세스 전체에서 한 번만 발급되고 같은 id 를 다시 쓰는 곳은 `ComponentIDRestoreScope` 뿐인데, 그 복원이 짧은 이름으로 맞추면 짧은 이름이 같은 다른 네임스페이스의 타입이 원래 id 를 가져가 핸들이 다른 타입을 가리킵니다. 그래서 복원 키를 FQN 으로 바꿨습니다(`ObjectIdentity::ComponentEntry::_typeFqn`).
  - `executeOrDeferPostTickOnComponent( self, func )` 는 `self` 에서 타입 핸들을 만들어 `getHandle()` 과 템플릿 인자가 어긋나는 일을 형식으로 막습니다. 결함이 숨는 곳은 API 경계를 넘는 핸들(인자 · 대기 항목 · 접근자 반환값)이라 거기를 타입 핸들로 바꿨고(예: `ControlSystem::queuePossess( controller, pawn )` 는 서로 다른 타입의 핸들 둘을 같은 형식으로 받아 인자를 바꿔 넘겨도 컴파일됐음) 여러 타입을 받는 곳(`AnimationNotifyComponent::_animator` 등)은 타입 없는 채로 둡니다. `castTo` 를 `resolveComponent` 로 바꾸면 타입이 다를 때 nullptr 이 아니라 Debug 단언에 걸립니다.
  - 직렬화: `PROPERTY` 로 둘 수 있는 것은 `TComponentHandle<T>` 한 값과 한 겹 시퀀스뿐이고 타입 없는 `ComponentHandle` · 맵 · 중첩 컨테이너는 대상 타입을 확인할 자리가 없어 파서 생성 오류입니다. 파일 형태는 `{대상 오브젝트의 저장 id, 컴포넌트 안정 키(이름#n)}` 이고(오브젝트 자리 0 은 자기 자신, 텍스트는 `0:TestProbeComponent#1`) 스냅샷 · 되돌리기 · 복제는 런타임 id 를 적으며 읽는 쪽이 키 해시의 최상위 비트 표지로 가립니다. 안정 키는 같은 이름의 컴포넌트 순서가 바뀌면 다른 컴포넌트를 가리킵니다(부착과 같은 한계).
  - 확인은 배치가 끝날 때(`ObjectStateBatch::finish`, `[[nodiscard]] bool`)에 합니다. 대상을 못 찾으면 핸들을 비우고 경고(약한 참조), 대상이 있는데 타입이 다르거나 런타임 id 로 쓴 핸들을 파일 id 공간으로 읽으면 로드 오류입니다. 핸들 옮기기는 값 방문(`ReflectedValueWalk`)으로 구조체 · 컨테이너의 모든 깊이를 옮깁니다.
  - 인스펙터: 타입 핸들 필드는 선택기(콤보)로만 그려 잘못된 타입을 넣을 수 없습니다. 판단은 ImGui 없는 `InspectorComponentPicker`, 목록은 편집 대상 씬의 비템플릿 매니저 순회로 채우고 선택 값은 `applyPropertyTextAsEdit` 로 써서 되돌리기가 됩니다. 타입 핸들의 Paste Value 는 막았고 선택기는 삭제 대기 컴포넌트를 따로 거릅니다.
  - 등록형 목록(`ComponentRegistry`)은 버킷으로 옮기지 않습니다(2026-10-19). 타입 대부분이 등록 순서(첫 일치 · 마지막 일치 · 동률 순서)에 기대는데 버킷 순회는 순서를 약속하지 않기 때문입니다. 순서를 형식으로 드러내는 질의(우선순위를 받는 질의)는 아직 없습니다.
  - 버킷 갱신: 추가는 `attachCreatedComponent` 가 오브젝트 목록에 넣는 줄 옆에서, 제거는 `destroyComponentInstance` 맨 앞(`dispatchEndPlay` 보다 먼저)에서 하고 마지막 원소를 빈 위치로 옮깁니다. 모두 저장소 `_mutex` 의 배타 잠금 안이고 조회는 공유 잠금입니다. 순회 콜백 안의 구조 변경은 Debug 단언(`WalkScope`)이 막습니다. 비운 버킷의 벡터 용량은 남겨 같은 이름으로 스폰과 파괴를 거듭하는 게임이 매번 할당하지 않게 합니다. 키는 `TypeInfo` 포인터가 아니라 FQN 입니다(같은 클래스의 `TypeInfo` 사본이 둘이어도 같은 버킷). 측정은 [검증과 측정](../08_Verification.md) "타입별 컴포넌트 질의 벤치"입니다.
