# 5-6. 오브젝트, 조종, 입력

> 질문: 5-6. 오브젝트, 조종, 입력 영역에서 이미 정한 것은 무엇이고 근거는 무엇인가?
> 독자: 같은 제안을 다시 하려는 사람, 정한 이유를 찾는 사람.
> 결론: 결정 기록 5 절의 한 영역이다. 번호 체계와 쓰는 법은 [결정 기록](../09_Decisions.md) 5절에 있다.

- **병렬 분배는 항목 수가 아니라 잰 비용으로 고르는 공용 API 를 둔다**(2026-10-16): 고정 임계값 16 은 가벼운 항목(~25 ns)에서 낮아 작은 그룹이 깨우는 비용(~20 us)을 일보다 크게 치렀다. `TaskManager::runParallelByCost`(엔진은 `engine::runParallelByCost`)는 호출 스레드가 앞 항목을 1, 2, 4, … 개씩 돌며 비용을 재고 남은 일의 예상 직렬 시간이 16 us 보다 짧으면 직렬로, 아니면 나머지만 나눈다(저장하는 추정 없음). 씬 틱의 보통 길 · 선행 조건 스테이지 · `AnimationSystem`(20 개 122 → 81 us, 100 개부터 병렬이 이김)이 쓴다. `runParallel(count, threshold)` 는 "임계값 이상이면 나눈다" 계약을 둔다. 시계는 함수 포인터로 주입해 테스트가 결정적으로 본다(`runParallelByCostWithClock`). 상용 엔진도 일이 작으면 깨우지 않는다.
  **`-gv_tickCostDispatch` 기본은 0(옛 방식)**(사용자가 상용 엔진 기준으로 위임): 실제 게임 틱 칸이 2 ~ 200 개뿐이라 순이득이 프레임 시간의 0.1 % 안쪽이고, 무거운 디렉터가 앞 항목이면 재는 동안 직렬로 돌고 워커가 놀아 꼬리가 늘며 AAA 규모로 따져도 같다. 스위치와 API 는 남기고 다시 켜려면 프레임 사이에 비용을 기억해 재는 직렬 구간을 없앤 뒤 `perf-compare --cases tickCostMovers tickCostSmallScene tickCostChurn` 으로 다시 잰다. **`AnimationCrowd` 묶음 평가 분배(`kParallelBucketCount` 8)는 비용 기반으로 옮기지 않는다**: 묶음이 수십 개뿐이고 하나가 수 us 라 `crowdBuckets` p50 이 36 → 49 us 로 늘었다. [측정: Release · 5 판 번갈아 중앙값 · 2026-10-16]
- **`PostUpdate` 그룹은 서브틱으로 바꾸지 않고 `TickPhase` · 서브틱 우선순위는 유지한다**(2026-10-16, 사용자가 상용 엔진 · AAA 기준으로 위임). 사용처 41 개의 의도("디렉터가 끝낸 뒤 읽는다")는 그룹 사이 장벽 하나가 정확히 표현하고 서브틱 선행 조건으로 바꾸면 오브젝트 사이 의존을 핸들로 걸어야 해 복잡하며 속도 차이도 없다. 서브틱 선행 조건은 같은 그룹 안의 순서(`GameDirectorComponent::_tickAfter`)에 쓴다. `TickPhase` 의 `Early` · `Late` · `Finalize` 와 `priority` 는 제품 코드 사용이 0 이지만 UE · Unity · Godot 이 모두 오브젝트 안 순서 수단을 두므로 지우지 않는다.
- **선행 조건 스테이지는 말단 오브젝트만 증분으로 끼우고 뺀다**(2026-10-16): 팔로워 4000 에 프레임마다 하나 만들고 지우면 재구축이 559 us 였다. 아무도 기다리지 않고 선행 조건이 의존 오브젝트 밖인 오브젝트는 레벨 0 스테이지에 끼우고 뺀다(`TickRegistry::applyStageDelta` · `queueStageRemoval`, 69 us). 누군가 기다리는 오브젝트가 바뀌거나 선행 조건이 의존 오브젝트를 가리키면 전체 재구축이다(사슬 · 순환은 전체 위상 정렬이 필요 — 모든 변경을 증분으로 처리하는 안은 기각). 끼움은 재구축과 같은 (순서 키, 오브젝트 id) 정렬 삽입이고 재구축 · 증분이 `StageOrder` · `isOrderedBefore` 하나를 공유합니다. 제거는 요청으로 쌓아 `refresh` 끝에서 한 번만 훑어(`flushStageEdits`) K 개 제거가 O(K · S) 에서 O((K + S) log K) 가 됩니다(오브젝트 id → 위치 색인은 끼움 때 뒤 위치가 밀려 O(S) 로 돌아가므로 기각). 스테이지는 `refresh` 직후에만 맞습니다. [측정: 없음 — 복잡도 모양으로 정함]
- **프리팹에서 사라진 컴포넌트의 오버라이드는 경고하고 버립니다**(2026-10-06). 언리얼과 같고 유니티는 남겨 둡니다.
- **"그 타입의 컴포넌트 모두" 는 타입별 레지스트리에서 찾습니다**(2026-10-06). 상호작용 대상을 프레임마다 씬 전체에서 찾던 경로가 10k 오브젝트에서 190 us 를 넘었고 레지스트리로 2~6 us 가 됐습니다. 공간 해시는 두지 않았습니다([후보 문서](../plans/Candidates-gameplay.md) `G-4`).
- **조종 구조**(2026-10-06): 가상 입력은 배타 모드가 기본입니다. 게임플레이 리플레이와 네트워크는 의도(`ControlIntent`)를 싣고 `InputReplay` 는 입력 층의 QA 녹화입니다. 전략과 경영 장르는 폰 없이 디렉터가 명령 조종자가 됩니다. 시나리오는 늘 고정 프레임 시간입니다. 탑승 중에도 피격을 받고 쓰러지면 강제로 내리며 탈것의 의도는 운전석 조종자를 따릅니다.
- **같은 타입이 수천 개 틱하면 타입별 일괄 틱(`TickBatchRegistry`, 등록은 선택)으로 돕니다**(2026-10-13, 사용자 결정 "구조 변경을 한다"; 언리얼 Mass · 유니티 `IJobEntity` 자리). 그룹에서 항목이 그 타입의 주 틱 하나뿐인 오브젝트만 옮겨 한 오브젝트는 한 스레드 규칙이 그대로입니다. 모든 컴포넌트를 ECS 저장소로 옮기는 안은 하지 않았고 데이터를 배열로 옮기는 다음 단계는 측정 뒤에 정합니다.
- **1인칭 카메라는 폰의 부품이라 `Base/Control` 에 둡니다**(2026-10-06, 언리얼 `bUsePawnControlRotation`). 자동 플레이는 몸 안의 분기가 아니라 AI 조종자의 빙의입니다.
- **커서 위치 API 는 `InputManager::getMousePositionNormalized` 하나입니다**(2026-10-06). 게임 코드는 장치를 직접 묻지 않고 입력 맵 액션을 읽습니다. 패드 스틱 시점은 바인딩마다의 배율 · 프레임 시간 곱(언리얼 Enhanced Input 의 Scale · Scale By Delta Time)입니다.
- **중첩 프리팹은 쿠킹 때 펼칩니다**(2026-10-13, 언리얼 Packed Level Actor). 에디터 · Dev 는 원본을 경로로 가리켜 원본을 고치면 상위에 퍼지고(유니티 Nested Prefab) 순환은 로드 오류입니다.
- **내비 기하에 들어갈 컴포넌트 종류는 종류별 레지스트리(`SW_NAV_GEOMETRY_CONTRIBUTOR`)로 등록합니다**(2026-10-13). Navigation(Object 층)은 Environment(위층)를 include 할 수 없고 플레이 중 등록하는 `INavGeometrySource` 는 플레이 전 쿠킹에 들지 않아서입니다(언리얼 `INavRelevantInterface`).
- **패드 가상 커서는 명령 조종자(디렉터)가 플레이 동안만 켭니다**(2026-10-15). 게임 모듈의 `onInitialize` 가 켜면 에디터 편집 중에도 켜지고 조종 경계(`CheckControlBoundary`)를 넘습니다.
- **입력 커맨드 버퍼 둘은 하나로 모으지 않습니다**(2026-10-15, C-26 ⑥). Engine `InputActionBuffer` 는 실시간(초) 이력(에디터 콤보 테스트)이고 GameFramework `InputCommandBuffer` 는 틱 단위 이력이라 롤백에서 다시 돌려도 같은 결과여야 합니다. 합치면 롤백이 깨지거나 엔진이 GameFramework 를 알게 됩니다.
- **큰 클래스는 책임이 따로 서는 묶음을 값 객체로 가르고 소유 객체에 그대로 넘기던 전달 함수는 지웁니다**(2026-10-15, C-26 ⑤): `InputMap` 의 플레이어 설정 → `InputPlayerSettings`, 태그 개수 → `GameplayTagCountContainer`, `UISystem` 전달 함수 열다섯 → `getInputRouter()` 등. `GameObjectManager`(언리얼 `UWorld::SpawnActor` 처럼 저장소를 숨기는 씬의 얼굴)와 `InputMap` 리바인딩(저장소를 직접 고치는 일)은 가르면 저장소를 내보여야 해 그대로 둡니다.
- **자동화 입력과 단언**(2026-10-15): 시나리오의 액션 단계는 액션 값을 직접 넣지 않고 바인딩을 찾아 장치 층에 냅니다(언리얼 `InjectInputForAction` 은 트리거 · 모디파이어 일부를 건너뜀 — 이름이 액션이라 키 배치가 바뀌어도 그대로이고 트리거 · 레이어 · UI 입력 소비의 결함까지 잡음). 게임 로직 단언은 기반이 한 번 등록한 질의 탐침과 값 이력(`ExpectVisited`)을 데이터로 적고 "N 초 안에" 는 `WaitUntil timeoutSeconds` 입니다. 결정적 재생은 `<Record>` 값을 같은 실행의 네 백엔드끼리 비교하고(기대값을 적지 않아 해시가 바뀌어도 시나리오 수정 불필요) 녹화 · 재생 왕복으로 확인하며 녹화는 끝 프레임 탐침 값을 `<Expect>` 로 실어 스스로 검증합니다. 에디터 입력 단계(`EditorClick` · `EditorDrag` · `EditorHover`)는 누를 레이블이 그려질 때까지 시계를 붙잡습니다(최대 60 프레임, 고정 프레임 단계는 팝업이 늦으면 가끔 졌음 — Playwright 자동 대기와 같음).
- **AI 조종자가 블랙보드 · 행동 트리 실행기 · 상태 이름을 가집니다**(2026-10-15, 언리얼 `AAIController`). 그래서 `Actor/Control` 이 `Actor/AI` 위로 올랐고 시계 · 일정 · AI · 빙의 · 탑승을 읽는 자동화 단계와 탐침은 `Gameplay/Automation` 입니다. 행동 트리의 잎 이름은 도는 잎이 없으면 그 틱에 마지막으로 성공한 작업입니다(한 틱에 끝나는 트리는 이름이 늘 비었음, `getActiveLeaf()` 는 도는 잎만).

- **매니저의 타입별 컴포넌트 목록은 정확한 타입마다 버킷 하나이고 조회는 버킷마다 `isDerivedFrom` 을 한 번 묻습니다**(2026-10-17, 7-c). 언리얼 `GetObjectsOfClass` 의 "정확한 클래스 버킷과 파생 열거" 와 같고 조상 목록보다 메모리가 약 1/8 입니다. 순서는 약속하지 않으므로 등록 순서에 기대는 `ComponentRegistry` 는 버킷으로 옮기지 않았습니다. 키는 FQN 입니다(같은 클래스의 `TypeInfo` 사본이 둘이어도 같은 버킷). 추가 · 제거는 저장소 `_mutex` 배타 잠금 안에서 하고 순회 콜백 안의 구조 변경은 Debug 단언이 막습니다. **삭제 대기 오브젝트의 컴포넌트는 항상 삭제 대기이고** 해체 중 오브젝트에는 붙이기를 거절합니다(유니티 "being destroyed", 언리얼 `IsActorBeingDestroyed`) — 버킷에서 빼는 안은 지연 파괴 전까지 버킷과 목록이 어긋나고 병렬 틱 안에서 배타 잠금이 필요해 버렸습니다. 측정은 [검증과 측정](../08_Verification.md) "타입별 컴포넌트 질의 벤치".
- **타입 핸들 `TComponentHandle<T>`**(2026-10-17~19, 7-c · 7-d): 결함이 숨는 곳은 API 경계를 넘는 핸들(인자 · 대기 항목 · 접근자 반환값)이라 거기를 타입 핸들로 바꿨습니다(`ControlSystem::queuePossess( controller, pawn )` 은 다른 타입의 핸들 둘을 같은 형식으로 받아 인자를 바꿔도 컴파일됐음). `resolveComponent<T>` 는 Shipping 이 아닌 모든 구성에서 타입을 확인합니다. 컴포넌트 id 복원 키는 FQN 입니다(짧은 이름이 같은 다른 네임스페이스 타입이 id 를 가져가 핸들이 다른 타입을 가리켰음). `PROPERTY` 로 둘 수 있는 것은 `TComponentHandle<T>` 한 값과 한 겹 시퀀스뿐이고 나머지는 파서 생성 오류입니다. 파일 형태는 `{대상 오브젝트의 저장 id, 컴포넌트 안정 키(이름#n)}` 이고 안정 키는 같은 이름 컴포넌트의 순서가 바뀌면 다른 것을 가리킵니다. 확인은 배치가 끝날 때(`ObjectStateBatch::finish`)에 합니다 — 대상을 못 찾으면 핸들을 비우고 경고, 타입이 다르거나 id 공간이 다르면 로드 오류. 인스펙터는 선택기(콤보)로만 그려 잘못된 타입을 못 넣습니다.
- **서브틱 입력의 발사는 조종 의도의 선택 칸으로 싣고 발동 순간의 시선은 폰이 지정한 버튼 하나에만 만든다. `GetMessageTime` 과 입력 스레드는 쓰지 않는다**(2026-10-22, 서브틱 입력 B4 · B6). 클릭한 순간의 시선을 `ControlIntent::_bTriggerLook` · `_triggerYaw` · `_triggerPitch` 에 싣고(`PawnComponent::_triggerLookButton` 이 버튼을 정함, Shooter3D 는 `Fire`) 프레임 시작 조종 회전에 시선 액션 값 × `InputPressInstant::computeLookFraction` 을 더해 만듭니다. 누름이 이벤트로 오지 않는 바인딩은 순간을 지어내지 않습니다. `GetMessageTime`(`GetTickCount` 계열)은 변화 간격이 15 ~ 31 ms 로 60 Hz 프레임 하나와 같아 프레임 안 자리를 못 가리고, 입력 스레드로 옮기면 에디터 · 콘솔이 먼저 소비하는 판정을 우회할 위험만 늡니다 — 사건 시각은 큐에 넣는 순간의 단조 시계(`RawInputEvent::_timeMicroseconds`)입니다. 넷 입력은 항목마다 틱 스탬프를 싣고 서버가 `_maxViewLagTicks` 로 자릅니다. 롤백 · 락스텝 키트는 프레임 단위 결정성이 계약이라 이 칸을 쓰지 않습니다(`ControlIntentHistory::kVersion` 2). 사격이 실제로 클릭 순간 방향으로 나가는지는 시나리오로 못 봤습니다(게임 모듈은 `EngineTest` 가 링크하지 않음).
- **트랜스폼을 따르는 소비자(물리 바디 · 캐릭터 컨트롤러 · 내비 장애물)는 칸의 월드 변경 번호(`SceneTransformPage::_arrWorldVersion`)를 지난번 값과 비교하고, 스텝 뒤 자세는 백엔드가 깨어 있었다고 한 바디(`IPhysicsBodyScene::getMovedBodies`)만 읽는다**(2026-10-27, 감사 SB T1 ~ T3). 번호는 월드를 쓰는 한 곳(`composeWorld`)에서 올라 병렬 틱 경로도 빠지지 않습니다. 알림 리스너(언리얼 가상 `OnUpdateTransform`, Godot `NOTIFICATION_TRANSFORM_CHANGED`)가 아니라 번호인 것은 더티 트랜스폼마다 간접 호출이 붙지 않게 하려는 것입니다([EnginePartition](../plans/EnginePartition.md) 6.3). 깨어 있는 목록은 유니티 · 언리얼 Chaos 의 활성 바디 목록 · Jolt `GetActiveBodies` 와 같은 자리이고, 스텝 앞 · 뒤를 합쳐 이 스텝에 잠든 바디도 마지막 자세를 읽습니다. 정적 · 키네마틱 · 동적 목록을 컴포넌트 쪽에서 따로 나누지는 않았습니다 — 깨어 있는 목록이 같은 일을 하고 종류가 바뀔 때 옮길 일이 없습니다.
