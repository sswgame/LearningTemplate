# 5-5. 그래픽스와 RHI

> 질문: 5-5. 그래픽스와 RHI 영역에서 이미 정한 것은 무엇이고 근거는 무엇인가?
> 독자: 같은 제안을 다시 하려는 사람, 정한 이유를 찾는 사람.
> 결론: 결정 기록 5 절의 한 영역이다. 번호 체계와 쓰는 법은 [결정 기록](../09_Decisions.md) 5절에 있다.

- **RHI 의 완료 · 동기화 계약은 `IRHIDevice` 머리말의 한 표로 두고, 네 백엔드가 같은 테스트로 지킨다**(2026-10-25, 백엔드 감사). `waitIdle` 은 앞서 제출한 모든 GPU 작업이 끝난 뒤 돌아오고, `enqueueGPURelease` 콜백은 그 프레임의 GPU 작업이 끝난 뒤에만 불리며, GPU 는 `kMaxFrameCountInFlight` 프레임보다 더 뒤처지지 못하고, `readReadbackBuffer` 는 읽기 버퍼가 아닌 핸들을 거절한다.
  GPU 확인에서 DX11 비동기 되읽기가 진 원인은 `waitIdle` 이 `Flush` 만 한 것이었고, 점검에서 같은 모양의 약한 구현이 둘 더 나왔다 — DX11 · GL 의 `enqueueGPURelease` 가 프레임 수만 세던 것(Present 없는 반복에서 GPU 가 뒤처진 채 콜백이 돈다), `readReadbackBuffer` 의 읽기 버퍼 검사가 DX11 에만 있던 것.
  고친 방식: DX11 은 프레임 끝 이벤트 쿼리 링, GL 은 프레임 끝 `glFenceSync` 링으로 DX12 · Vulkan 의 펜스와 같은 모양을 만들었고(링이 차면 가장 오래된 프레임을 기다린다), 완료 확인용 쿼리는 디바이스를 세울 때 만들어 못 만들면 초기화를 실패시킨다(폴백 없음).
  언리얼은 RHI 의 `FRHIGPUFence`/`RHIBlockUntilGPUIdle` 이 백엔드마다 같은 뜻이고 DX11 도 이벤트 쿼리로 구현하는 것으로 알고 있다(기억에 의존). 장치 제거 뒤의 `waitIdle` 테스트는 Vulkan 에만 있다(`VulkanLostDeviceStopsWaitingOnTheGPU`) — DX12 의 제거 경로(`debugRemoveDevice`)는 같은 테스트로 걸지 못했다.
- **DX11 도 장치 손실을 `RHITransferSerials` 의 표시 하나로 모으고 `GetDeviceRemovedReason` 은 `isDeviceRemoved` 한 함수만 묻는다. `debugRemoveDevice` 는 표시만 하는 시험용 훅이다**(2026-10-25, 손실 거절 점검의 DX11 몫).
  DX11 은 Present 실패를 로그만 남기고 표시하지 않았고, `waitIdle` · 프레임 링 대기의 `GetData` 실패를 "끝남" 으로 취급하면서 표시하지 않았으며(전송 폴링의 실패만 표시), 제출 진입은 `GetDeviceRemovedReason` 을 직접 불렀다 — 호출 결과를 보는 자리마다 따로 다루는 DX12 · Vulkan 이 고친 것과 같은 모양이다. 고친 방식: 실제 손실의 표시는 `markDeviceLost` 하나(처음 표시한 호출만 로그)이고, 제거 이유를 묻는 `isDeviceRemoved` · 쿼리 읽기 실패를 받는 `reportQueryFailure` 만 부른다. 이벤트 쿼리 대기와 타임스탬프 · GPU 시계 읽기는 `GetData` 가 실패하면 시한까지 돌지 않고 표시한 뒤 끝낸다. 제출 진입(`submitTextureUpload` · `RegionUpload` · `Readback`)은 `isDeviceLost` 를 본다.
  D3D11 에는 `RemoveDevice` 가 없고(D3D12 의 `ID3D12Device5::RemoveDevice` 같은 시험용 API 가 없다) TDR 을 일부러 일으키는 공개 API 도 없어, `debugRemoveDevice` 는 Vulkan 과 같이 손실 표시만 만든다. 그래서 제출 진입 거절은 DX11 에서 확인되지만, 제거된 장치에서 `GetData` · Present 가 실패하는 경로는 확인할 수 없다. 언리얼 D3D11 RHI 도 제거 시험용 훅 없이 `GetDeviceRemovedReason` 을 볼 때 장치 손실 처리를 하는 것으로 알고 있다(기억에 의존).
- **DX12 셰이더 가시 힙은 524288 칸(bindless 32768 + 온라인 블록 960 × 512)으로 둔다**(2026-10-23). 65536 칸(온라인 블록 64)은 미리보기 월드 넷을 그리는 한 프로세스 재생(`editor.netsim`)에서 바닥났다. 언리얼의 온라인 힙 기본도 수십만 칸(`D3D12.OnlineDescriptorHeapSize`)이고, 힙 메모리(16 MB)는 작다.
- **RHI 디바이스 안은 서브시스템으로 만들지 않는다 — 부품은 타입 있는 멤버로 명시 소유하고, 종료 순서는 `IRHIDevice::shutdown` 의 네 단계가 정한다**(2026-10-14, 백로그 C-26 을 닫음).
  언리얼 RHI 도 내부 레지스트리 없이 디바이스가 부품을 명시로 들고 소멸 순서로 정하는 것으로 알고 있다. 해제 큐 · 장부 · 프레임 링 · 타임스탬프는 이미 공용 클래스이고
  핫 패스는 타입 있는 포인터로 부르므로 컬렉션으로 옮겨도 남는 이득은 종료 순서뿐인데, 실제 결함(네이티브 객체와 GPU 완료 사이)은 컬렉션 밖에 있다.
  대신 순서를 어기면 터지게 했다: 2 단계(GPU 대기) 뒤와 4 단계 뒤에 해제 큐가 비었는지, 끝난 종료 뒤에 해제가 쌓였는지를 `shutdown` 이 단언한다
  (`getPendingReleaseCount`, nogpu 테스트 `RHIDeviceShutdownTest`). 점검에서 Vulkan 이 4 단계에서 오프스크린 프레임버퍼를 해제 큐에 넣고 비우지 않던 것을 고쳤다.
- **셰이더 쿠킹 스탬프의 도구 지문은 버전 상수로 만든다 — 컴파일 옵션 판 · Vulkan 타깃 판 · 컴파일러 버전 글(`ShaderCooker::kCompilerVersion`, vcpkg `directx-dxc` 포트 버전)**(2026-10-14).
  컴파일러 라이브러리 파일의 내용 해시로 만들었더니 Windows 에서 쿠킹해 커밋한 스탬프가 리눅스(다른 라이브러리 파일)에서 모두 낡은 것으로 판정돼 리눅스 CI 다섯 잡이 졌다.
  언리얼은 셰이더 DDC 키에 컴파일러 바이너리 해시가 아니라 셰이더 포맷 · 컴파일러 버전 식별자를 넣는 것으로 알고 있다(기억에 의존). 같은 원칙을 따르고,
  사람이 고치는 상수가 실제 설치와 어긋나지 않게 `TestShaderCompilerVersionPin.py` 가 vcpkg 설치 기록과 대조한다.
- **셰이더 쿠킹 스탬프(`cook.stamp`)는 쿠킹 기록(`.cookrec`) 형식으로 옮기지 않습니다**(2026-10-18, C-42 K5). 스탬프는 커밋되는 산출물 곁에 있고 엔진의 판정 하나(`ShaderCooker::verifyCookedShaders` — `App --verify-shaders` · `ShaderCookStampTest`, 2026-10-22 StructureSimplification PK3 에서 파이썬 게이트 `CheckShaderStamps` 를 대신했다)가 보는 계약인데,
  쿠킹 기록은 체크아웃마다의 `Saved/` 캐시이고 판정에 엔진의 읽기 기록이 필요하다. 내용 해시는 이미 같은 함수(`ContentHash`)를 쓰므로 판정 기준은 하나다. 언리얼도 셰이더는 DDC 키를 따로 만들고 에셋 쿠킹과 섞지 않는다 [기억].
- **셰이더 쿠킹은 컴파일 · 리플렉션을 병렬로 돌리고 합치기는 요청 순서대로 직렬로 합니다**(2026-10-25, `ShaderCookDriver::cookRequests`). 단위는 요청 × 포맷 작업이고 작업마다 자기 결과 칸에만 쓴다. 매니페스트 합치기 · 카운터 · 실패 소스 기록 · 매니페스트와 스탬프 쓰기는 직렬이라 산출물은 직렬로 돌 때와 바이트까지 같다.
  같은 바이너리 파일을 만드는 요청은 한 사슬로 한 스레드가 순서대로 돌고, 출력 폴더는 병렬 구간 전에 만든다. 단일 스레드로 요청 × 네 포맷을 차례로 컴파일하던 것이 쿠킹 시간의 대부분이라 보고 나눈다(줄어든 시간은 통합이 `compile` · `reflection` · `total` 로그로 잰다). 언리얼 셰이더 컴파일 워커도 컴파일은 워커 여럿이 하고 결과는 한 스레드가 병합한다 [기억].
  이 일에서 `ShaderReflectionDx` 의 `dxcompiler` 로드가 맨 `static bool` 플래그로 한 번만 찾던 것(동시에 처음 부르면 한 스레드가 빈 함수 포인터를 받아 리플렉션이 빈 채로 매니페스트에 들어간다)을 함수 안 정적 변수로 바꿨다.
- **쿠킹은 최신 바이너리도 매번 읽어 리플렉션을 다시 뽑습니다 — 이전 매니페스트에서 가져오지 않습니다**(2026-10-25, 검토 뒤 하지 않기로 함). ① `isCookedOutputCurrent` 는 소스 내용 해시와 도구 지문(스탬프)만 보고 매니페스트와 바이너리가 같은 쿠킹에서 나왔는지는 보지 않는다 —
  병합이 `reflection.manifest` 를 한쪽 것으로 고르고 스탬프 텍스트는 합쳐지는 경우(작업자 브랜치 둘을 모으는 이 저장소의 흔한 일) 스탬프는 "최신" 이라 하고 매니페스트는 낡아, 재사용하면 다시 쿠킹해도 낡은 리플렉션이 조용히 남는다(런타임은 DEVICE_HUNG 으로 간다).
  ② 매니페스트 형식(`kVersion` 2)은 정점 입력(`_listVertexInput`)을 담지 않아 정점 셰이더의 계약 검사(5번)를 재사용 항목에서 다시 돌릴 수 없다. ③ `ShaderReflection::reflect` 의 의미가 바뀌어도 소스가 그대로면 재사용한 값은 옛 것이다.
  재사용하려면 바이너리 내용 해시를 매니페스트 항목에 넣어야 하고(형식 판과 커밋된 산출물 전체가 바뀐다) 그때 위 셋을 함께 푼다. 언리얼도 DDC 키에 컴파일러 · 리플렉션 판을 넣어 이 어긋남을 키로 막는다 [기억].

- **런타임 UI 를 위해 RHI 에 R8 텍스처, 영역 업로드, 프리멀티플라이 블렌드, 가위 사각형을 더했습니다**(2026-10-06). 사각형 클리핑은 가위로 합니다(Slate, Dear ImGui, Godot 과 같고 배치가 끊기지 않음).
  둥근 모서리 클리핑만 셰이더에서 합니다.
- **머티리얼 XML 과 셰이더 구조체의 필드 불일치는 오류다 — 폴백 없음**(2026-10-23): 셰이더에만 있는 필드(0 으로 채우면 텍스처 인덱스가 Vulkan 의 첫 실제 텍스처가 된다) · XML 에만 있는 필드 · 리플렉션을 얻지 못함은 모두 `Material::syncPropertiesFromReflection` / `ensureShaderLayout` 이 오류(머티리얼 · 필드 · 셰이더 경로)를 남기고 바이트를 비운다. 두 함수는 `[[nodiscard]]` 이고 `MaterialTest.EveryRepositoryMaterialMatchesItsShaderStruct` 가 저장소의 모든 .material 을 한 번에 검사한다.
- **프리멀티플라이 블렌드는 PSO 비트(`_bPremultipliedAlpha`)이고, 머티리얼 블렌드 enum 에는 넣지 않습니다**(2026-10-06). 언리얼도 머티리얼의 `EBlendMode` 와 RHI 블렌드 상태가 따로입니다. 머티리얼이 원하게 되면 그때 enum 에 더합니다.
- **보기 모드는 뷰마다의 설정입니다**(`RenderViewSettings::_viewMode`, 2026-10-10). 에디터 씬 뷰 툴바는 씬 뷰에만 걸고 게임 뷰는 주 출력 모드(Lit)로 그립니다 — 언리얼 뷰 패밀리마다의 View Mode, 유니티 Scene 뷰 Draw Mode 와 같습니다.
  Normals · Depth · Overdraw 는 표면 값을 보이므로 후처리 · 톤맵을 건너뜁니다(언리얼 버퍼 시각화와 같다). Overdraw 는 RHI 에 블렌드를 더하지 않고 알파 0 의 프리멀티플라이로 더하며, 깊이 테스트는 남기고 쓰기만 끕니다(테스트를 끄면 Vulkan 이 깊이 첨부 없는 PSO 로 만든다).
- **디퍼드의 툰은 G버퍼에 칸을 더하지 않고 포워드로 그립니다**(2026-10-21, 옛 D2-6.4, `ForwardOnlyOpaque` · `MATERIAL_FORWARD_ONLY`). G버퍼 패스가 그 머티리얼을 빼고(`RenderPassTypeInfo::_pExcludedMaterialDefine`) 조명 패스 뒤의 포워드 전용 패스가 같은 장면 깊이에 그린다 —
  유니티 URP 디퍼드가 `UniversalForwardOnly` 머티리얼(UniVRM 의 MToon 포함)을 포워드로 그리는 것과 같다(기억에 의존). 셋째 G버퍼 타깃(셰이딩 모델 · 그림자색 · 시프트 · 계단 · 그림자 받기)안은 기각했다 —
  림 · 맷캡 · 발광 · 빛마다 섞는 그림자색은 여전히 담을 수 없어 포워드와 그림이 갈리고, 모든 머티리얼의 G버퍼 PSO 타깃 수 · 대역폭 · 에뮬 백엔드 텍스처 칸이 함께 늘어난다. 대신 툰 표면은 SSAO 의 노멀에 들어가지 않는다.
  define 을 빠뜨린 머티리얼을 쿠킹에서 멈추게 하는 toon.hlsl 의 G버퍼 `#error` 는 셰이더 다시 굽기와 함께 넣는다(계획 GraphicsFormatBundle G2).
- **톤맵을 HDR 씬 컬러로 바꾸는 일은 하지 않았습니다**(2026-10-06). 기본 포워드 파이프라인의 Reinhard 가 흰색을 0.5 로 누르지만, 바꾸면 골든 이미지를 모두 다시 떠야 합니다. 화면이 어두운 게임은 데이터(체력 바 보임 정책 등)로 맞췄습니다.
- **점광 · 스폿 그림자는 큐브 · 배열 텍스처가 아니라 2D 그림자 아틀라스입니다**(2026-10-13). 유니티 URP · Godot 방식이고, RHI 를 바꾸지 않으며 DX11 · GL 의 엔진 텍스처 슬롯 네 개가 그대로입니다.
  방향광 캐스케이드(최대 4)도 같은 아틀라스 안의 타일이고, 추가 뷰는 자기 볼륨 · 그림자 컬링 슬롯을 씁니다.
  칸이 모자라면 주 시점의 화면 크기 대리값(경계 구 반경 / 카메라 깊이)이 큰 빛부터 받습니다(2026-10-17, `ShadowSetupUtil::computeLocalShadowPriority`) — 언리얼이 투영한 화면 반경으로 고르는 것과 같은 기준입니다.
  목록 순서였을 때는 씬에 먼저 놓인 먼 빛이 눈앞의 빛의 그림자를 밀어냈습니다. 화면 크기에 따라 칸 크기를 바꾸는 일은 하지 않았습니다(칸은 한 크기).
- **깊이 패스(그림자 · 깊이 프리패스)는 모양을 머티리얼 코드가 정하는 배치만 머티리얼 셰이더로 그립니다**(2026-10-17, `FrameRendererUtil::drawsDepthWithMaterialShader`).
  알파 컷오프는 두 깊이 패스 모두 머티리얼 셰이더의 깊이 퍼뮤테이션(`SW_PASS_SHADOW` · `SW_PASS_DEPTH_PREPASS`)에 픽셀 스테이지(`clip` 만)를 두고, 정점 변형(바람)은 그림자 패스만 정점 스테이지로 그립니다.
  나머지는 shadowdepth.hlsl 하나를 나눠 씁니다 — 언리얼이 Masked · World Position Offset 머티리얼만 자기 깊이 · 그림자 셰이더를 컴파일하는 것과 같습니다.

  언리얼은 셰이더 타입마다 소스가 (전이) include 하는 파일을 모아 그 해시로 DDC 키를 만듭니다(`GetShaderIncludes` · `GetShaderFileHash`, 기억에 의존). 언리얼은 텍스트를 훑어 include 를 찾고 여기는 컴파일러가 실제로 연 파일을 쓴다는 점이 다릅니다 — 조건부 include 를 잘못 넣지도 빼지도 않습니다.
- **동기 업로드 대기는 "제출 → 티켓 → 폴링" 비동기 계약으로 옮기고, 프레임 경로에는 `waitIdle` 을 새로 만들지 않습니다**(2026-10-25, [RhiAsyncUploads](../plans/RhiAsyncUploads.md), 코드 읽기만 했고 측정 전). 텍스처 업로드 둘과 되읽기의 동기 가상 함수를 RHI ABI 버전을 한 번 높여 지웁니다(백엔드 DLL 이 같은 vtable 을 봐야 해서 쪼갤 수 없고, 옛 함수 위의 기본 구현은 폴백이 되어 두지 않습니다). 동기가 필요한 테스트와 도구는 ABI 밖의 `AndWait` 헬퍼를 씁니다. 새 머티리얼의 GPU 초기화는 렌더 스레드의 프레임 셋업 구간으로 옮기고, 머티리얼과 PSO 는 준비 전 / 준비됨 / 실패 상태를 데이터로 두어 준비 전에는 그리지 않습니다.
  PSO 병렬 생성 기각(9 %, 드라이버가 직렬)과 충돌하지 않습니다. 목적이 생성 속도가 아니라 렌더 스레드의 임계 경로에서 빼는 것이라 생성 스레드는 하나입니다. 언리얼의 `FRHIGPUFence` 폴링과 유니티의 `AsyncGPUReadback` 요청 폴링에 해당한다고 알고 있습니다(기억에 의존, 세부 확인 전).
- **DX11 즉시 컨텍스트는 런타임 다중 스레드 보호(`SetMultithreadProtected( TRUE )`)를 켜고, 백엔드는 같은 임계 구역을 잡는 가드(`D3D11ImmediateContext::lock()`)로만 컨텍스트를 꺼냅니다**(2026-10-25, 코드 읽기만 했고 측정 전). 렌더 스레드의 프레임 스트림은 락 없이, 다른 스레드의 전송 · 폴링 · `waitIdle` 은 백엔드 뮤텍스 안에서 같은 컨텍스트를 써 서로 막지 못했습니다.
  렌더 스레드가 프레임마다 한 번 뮤텍스를 잡는 안은 기각했습니다 — 다른 스레드의 제출과 폴링이 프레임 하나(GPU 백프레셔와 Present 포함)를 통째로 기다리고, 렌더 스레드 자신의 제출에 재귀 잠금이 필요하며, `getNativeContext` 로 나가는 ImGui 백엔드는 막지 못합니다(GL 의 컨텍스트 빌리기가 이 모양이라 비 RT 제출을 프레임 경로 밖으로 제한합니다). 보호의 비용은 즉시 컨텍스트 호출마다 경합 없는 임계 구역 하나입니다.
  언리얼과 유니티의 D3D11 은 즉시 컨텍스트를 렌더(RHI) 스레드 하나만 쓰고 비동기 생성은 스레드 안전한 `ID3D11Device` 로 한다고 알고 있습니다(기억에 의존). 여기는 계약이 "어느 스레드에서나 제출" 이라 그 모양을 따르지 못합니다.
- **DX11 의 큰 텍스처 업로드는 장치가 초기 데이터로 만든 `STAGING` 텍스처로 올리고, 즉시 컨텍스트 잠금 안에서는 `CopySubresourceRegion` 과 이벤트 쿼리 `End` 만 합니다**(2026-10-25, 코드 읽기만 했고 측정 전). `UpdateSubresource` 는 소스 복사(큰 텍스처는 수십 MiB)를 잠금 안에서 해서 렌더 스레드의 `ExecuteCommandList` · `Present` 가 그만큼 기다렸습니다.
  스테이징 풀에 `Map( D3D11_MAP_WRITE )` 로 쓰는 안은 기각했습니다 — `Map` · `Unmap` 은 즉시 컨텍스트 호출이라 잠금을 두 번 잡고(복사는 그 사이 잠금 밖), D3D11 에는 버퍼 → 텍스처 복사가 없어 풀은 크기 · 포맷마다 텍스처여야 해 재사용률을 모릅니다. `CreateTexture2D( pInitialData )` 는 장치 호출(스레드 안전)이라 잠금 없이 복사가 끝나고, 대가는 업로드마다 할당 한 번입니다(측정 전).
  같은 이유로 GL 의 `RHIStagingRing`(오프셋 링 장부)은 맞지 않아 쓰지 않습니다. 스테이징은 기존 전송 큐 항목(`TransferProbe`)이 쥐어 워터마크가 지나면 놓고, 합은 GL 링과 같은 설정 `gv_rhiStagingRingMegabytes`(64 MiB)가 상한입니다 — 차면 끝난 전송을 한 번 모은 뒤 `Busy`, 한 장이 상한보다 크면 `Rejected`(그 크기를 올리던 `UpdateSubresource` 경로는 남기지 않습니다). 장치를 잃으면 예산이 돌아오지 않아 `Busy` 가 끝나지 않으므로 제출 진입에서 `GetDeviceRemovedReason` 을 먼저 보고 `Rejected` 입니다.
  `gv_rhiDirectUploadMaxKilobytes`(256 KiB) 이하는 `UpdateSubresource` 를 그대로 씁니다. 잠금 안의 복사가 수십 µs(메모리 복사 5 ~ 10 GB/s)로 스테이징 생성 · 복사 명령 하나의 고정 비용과 비슷한 자리라는 추정이고, 글리프 아틀라스 구간 갱신(수 KB)이 이 아래입니다. 두 값은 `RhiAsyncUploads` 측정(M1)이 정합니다.
  언리얼 D3D11 의 비동기 텍스처 생성도 초기 데이터를 넘기는 `CreateTexture2D` 를 아무 스레드에서 부르고, 생성 뒤 갱신(`RHIUpdateTexture2D`)은 RHI 스레드의 `UpdateSubresource` 라고 알고 있습니다(기억에 의존).
