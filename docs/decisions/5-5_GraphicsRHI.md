# 5-5. 그래픽스와 RHI

> 질문: 5-5. 그래픽스와 RHI 영역에서 이미 정한 것은 무엇이고 근거는 무엇인가?
> 독자: 같은 제안을 다시 하려는 사람, 정한 이유를 찾는 사람.
> 결론: 결정 기록 5 절의 한 영역이다. 번호 체계와 쓰는 법은 [결정 기록](../09_Decisions.md) 5절에 있다.

- **RHI 의 완료 · 동기화 계약은 `IRHIDevice` 머리말의 한 표로 두고, 네 백엔드가 같은 테스트로 지킨다**(2026-10-25, 백엔드 감사). `waitIdle` 은 앞서 제출한 모든 GPU 작업이 끝난 뒤 돌아오고, `enqueueGPURelease` 콜백은 그 프레임의 GPU 작업이 끝난 뒤에만 불리며, GPU 는 `kMaxFrameCountInFlight` 프레임보다 더 뒤처지지 못하고, `readReadbackBuffer` 는 읽기 버퍼가 아닌 핸들을 거절한다.
  GPU 확인에서 DX11 비동기 되읽기가 진 원인은 `waitIdle` 이 `Flush` 만 한 것이었고, 점검에서 같은 모양의 약한 구현이 둘 더 나왔다 — DX11 · GL 의 `enqueueGPURelease` 가 프레임 수만 세던 것(Present 없는 반복에서 GPU 가 뒤처진 채 콜백이 돈다), `readReadbackBuffer` 의 읽기 버퍼 검사가 DX11 에만 있던 것.
  고친 방식: DX11 은 프레임 끝 이벤트 쿼리 링, GL 은 프레임 끝 `glFenceSync` 링으로 DX12 · Vulkan 의 펜스와 같은 모양을 만들었고(링이 차면 가장 오래된 프레임을 기다린다), 완료 확인용 쿼리는 디바이스를 세울 때 만들어 못 만들면 초기화를 실패시킨다(폴백 없음).
  언리얼은 RHI 의 `FRHIGPUFence`/`RHIBlockUntilGPUIdle` 이 백엔드마다 같은 뜻이고 DX11 도 이벤트 쿼리로 구현하는 것으로 알고 있다(기억에 의존). 장치 제거 뒤의 `waitIdle` 테스트는 Vulkan 에만 있다(`VulkanLostDeviceStopsWaitingOnTheGPU`) — DX12 의 제거 경로(`debugRemoveDevice`)는 같은 테스트로 걸지 못했다.
- **스테이징 링의 할당 결과는 `RHITransferSerials::classifyStagingAllocation` 한 곳이 제출 결과로 옮기고, 장치를 잃었으면 `Rejected` 다. GL 의 버퍼 구간 갱신은 링으로 옮기지 않는다**(2026-10-25, RhiAsyncUploads GL-1 뒤 점검).
  GL 이 장치를 잃으면(펜스 확인 `GL_WAIT_FAILED` → `markLost`) 워터마크가 멈춰 링이 비지 않는데, 링이 찬 업로드가 `Busy` 를 받아 `submitWhileBusy` 와 다음 프레임의 재제출이 끝없이 되풀이됐다(계약 2 는 손실을 `Rejected` 로 둔다). 제출 진입이 `isLost` 를 보고, `Full` → `Busy` 옮기기를 장치 상태를 아는 한 함수로 모아 U5 · U6 의 링이 같은 결함을 갖지 못하게 했다. DX11 · DX12 · Vulkan 의 전송 경로는 지금 `Busy` 를 내지 않아 같은 모양이 없다.
  `updateConstantBuffer` · `updateStructuredBufferRegions` · `updateVertexBufferRegions` 를 링 + `glCopyBufferSubData` 로 바꾸는 안은 기각했다. 프레임 경로 호출자(`RHIConstantBufferSlot` · `ShaderParameterBinder` 의 드로우마다 수백 바이트 상수, `GPUScene` 인스턴스 구간, 정점 · 모프 풀)는 모두 RT 이고 RT 는 프레임 내내 컨텍스트를 쥐므로, 복사를 컨텍스트 밖으로 빼서 줄어드는 점유가 없다. 비 RT 호출(머티리얼 로드의 256 바이트 상수 한 번)은 바로 앞의 `createConstantBuffer` 가 이미 컨텍스트를 빌린다. 반대로 갱신마다 링 장부(뮤텍스 · deque)와 펜스 또는 프레임 시리얼 회수, GPU 쪽 복사 명령이 더해지고, `glBufferSubData` 도 드라이버가 한 번 복사하므로 CPU 복사 횟수는 같다. 언리얼 GL RHI 도 작은 유니폼 갱신은 `glBufferSubData` 계열로 두는 것으로 알고 있다(기억에 의존). 큰 인스턴스 구간에서 드라이버 암묵 동기가 보이면 측정으로 다시 연다.
- **장치를 잃었다는 사실의 저장소는 `RHITransferSerials` 의 손실 표시 하나이고, 전송 제출은 진입에서 `isLost` 를 보고 `Rejected` 를 돌려준다(DX12 · Vulkan 도 GL 과 같다)**(2026-10-25, 손실 거절 점검).
  DX12 는 제출이 `Accepted` 를 주고 폴링에서야 `Failed` 가 됐고, Vulkan 은 자기 `_bDeviceLost` 를 따로 두어 `markLost` 를 부르는 곳이 없었다 — 손실을 표시하는 자리가 호출 결과를 보는 자리마다 흩어져 빠진 자리가 생기는 모양이었다. 고친 방식: Vulkan 은 `_bDeviceLost` 를 지우고 `isDeviceLost` 가 `RHITransferSerials::isLost` 를 읽게 해(`markLost` 는 처음 표시했는지를 돌려준다) 두 상태가 어긋날 수 없게 했고, DX12 는 `GetDeviceRemovedReason` 을 묻는 자리를 `isDeviceRemoved`(묻고 표시) 한 함수로 모았다. 제출 진입은 DX12 `isDeviceLost`, Vulkan `isDeviceLost` 를 본다.
  DX12 는 제거 뒤에도 이미 만든 업로드 슬롯이 있으면 복사를 기록할 수 있어, 진입 검사가 없으면 `Accepted` 가 나온다(GPU 테스트 `RHIDeviceTest.LostDeviceRejectsTransferSubmitsAtEntry` 가 먼저 한 번 올려 둔 뒤 제거한다). 언리얼 RHI 는 제거된 장치에서 명령이 조용히 버려지고 `FRHIGPUFence` 가 끝난 값을 돌려주는 것으로 알고 있다(기억에 의존) — 여기서는 호출자가 잃은 장치를 기다리지 않게 제출 쪽에서 막는다.
- **DX11 도 장치 손실을 `RHITransferSerials` 의 표시 하나로 모으고 `GetDeviceRemovedReason` 은 `isDeviceRemoved` 한 함수만 묻는다. `debugRemoveDevice` 는 표시만 하는 시험용 훅이다**(2026-10-25, 손실 거절 점검의 DX11 몫).
  DX11 은 Present 실패를 로그만 남기고 표시하지 않았고, `waitIdle` · 프레임 링 대기의 `GetData` 실패를 "끝남" 으로 취급하면서 표시하지 않았으며(전송 폴링의 실패만 표시), 제출 진입은 `GetDeviceRemovedReason` 을 직접 불렀다 — 호출 결과를 보는 자리마다 따로 다루는 DX12 · Vulkan 이 고친 것과 같은 모양이다. 고친 방식: 실제 손실의 표시는 `markDeviceLost` 하나(처음 표시한 호출만 로그)이고, 제거 이유를 묻는 `isDeviceRemoved` · 쿼리 읽기 실패를 받는 `reportQueryFailure` 만 부른다. 이벤트 쿼리 대기와 타임스탬프 · GPU 시계 읽기는 `GetData` 가 실패하면 시한까지 돌지 않고 표시한 뒤 끝낸다. 제출 진입(`submitTextureUpload` · `RegionUpload` · `Readback`)은 `isDeviceLost` 를 본다.
  D3D11 에는 `RemoveDevice` 가 없고(D3D12 의 `ID3D12Device5::RemoveDevice` 같은 시험용 API 가 없다) TDR 을 일부러 일으키는 공개 API 도 없어, `debugRemoveDevice` 는 Vulkan 과 같이 손실 표시만 만든다. 그래서 제출 진입 거절은 DX11 에서 확인되지만, 제거된 장치에서 `GetData` · Present 가 실패하는 경로는 확인할 수 없다. 언리얼 D3D11 RHI 도 제거 시험용 훅 없이 `GetDeviceRemovedReason` 을 볼 때 장치 손실 처리를 하는 것으로 알고 있다(기억에 의존).
- **Vulkan 텍스처 전송은 그래픽스 큐에 기다리지 않고 내고(전송 작업 = 커맨드 버퍼 + 펜스, 재사용), 스테이징은 업로드 · 되읽기 영속 매핑 링 둘이다. 전용 전송 큐는 쓰지 않는다**(2026-10-25, RhiAsyncUploads U6).
  B0 는 제출 안에서 일회성 커맨드의 펜스를 기다려 UI 예제가 DX12 만큼 풀리지 않았다. 전송 큐 패밀리를 쓰면 큐 소유권 이전(해제 · 획득 배리어 한 쌍)과 큐 사이 세마포어가 필요하고, 이득은 큰 텍스처 스트리밍 중의 프레임 시간뿐이라 계획 문서 2.2 "전송 큐" 대로 측정 전에는 하지 않는다 — 같은 큐에서는 제출 순서와 첫 · 끝 배리어가 계약 3 을 그대로 만든다. 언리얼 Vulkan RHI 도 기본은 그래픽스 큐의 업로드 커맨드 버퍼이고 비동기 전송 큐는 선택 사항인 것으로 알고 있다(기억에 의존). 펜스를 쓰고 타임라인 세마포어(1.2 코어)를 쓰지 않는 것은 작업마다 완료를 따로 묻고 워터마크는 `RHITransferFenceQueue` 가 앞에서부터만 올리는 기존 부품을 그대로 쓰기 위해서다.
  되읽기 링을 업로드 링과 나눈 이유: 링은 할당 순서로만 회수하므로 가져가지 않은 되읽기 구간이 앞에 있으면 업로드까지 `Busy` 가 된다. 끝나기 전에 버린 되읽기 구간에는 시리얼을 붙여 복사가 끝난 뒤 돌아오게 한다(바로 놓으면 다음 되읽기가 GPU 가 아직 쓰는 자리를 받는다). 전송 중에 파괴한 텍스처의 해제는 시리얼 키 해제 큐에 두었다가 전송이 끝나면 그때의 다음 프레임 펜스 뒤로 넘긴다 — 지금은 같은 큐라 프레임 펜스만으로도 덮이지만, 해제가 큐 공유에 기대지 않게 한다(DX12 의 `releaseTrackedResourceDeferred` 와 같은 규칙). 임시 경로(`issueCompleted`, 제출 안의 펜스 대기)는 지웠다(폴백 없음).
  통합 N 에서 장부가 구간 단위 회수(`RHIStagingAllocator`, glrb2 · glrb3)와 단독 구간(bigup)으로 바뀌어, Vulkan 도 GL 과 같이 되읽기 링은 `gv_rhiReadbackRingMegabytes`, 링보다 큰 한 장은 링이 빌 때 그 크기의 일회성 호스트 가시 버퍼(`VulkanStagingRing::_soloBuffer`, 링마다 하나, `_soloMutex` 가 만들기 · 지우기를 지킨다)로 받는다. 단독 버퍼는 장부가 구간을 돌려받은 뒤 `retireFinishedTransfers` 가 지운다 — 언리얼 Vulkan RHI 의 스테이징 매니저가 큰 요청에 전용 버퍼를 만들고 펜스 뒤에 놓는 것과 같은 자리라고 알고 있다(기억에 의존).
- **DX12 셰이더 가시 힙은 524288 칸(bindless 32768 + 온라인 블록 960 × 512)으로 둔다**(2026-10-23). 65536 칸(온라인 블록 64)은 미리보기 월드 넷을 그리는 한 프로세스 재생(`editor.netsim`)에서 바닥났다. 언리얼의 온라인 힙 기본도 수십만 칸(`D3D12.OnlineDescriptorHeapSize`)이고, 힙 메모리(16 MB)는 작다.
- **RHI 디바이스 안은 서브시스템으로 만들지 않는다 — 부품은 타입 있는 멤버로 명시 소유하고, 종료 순서는 `IRHIDevice::shutdown` 의 네 단계가 정한다**(2026-10-14, 백로그 C-26 을 닫음).
  언리얼 RHI 도 내부 레지스트리 없이 디바이스가 부품을 명시로 들고 소멸 순서로 정하는 것으로 알고 있다. 해제 큐 · 장부 · 프레임 링 · 타임스탬프는 이미 공용 클래스이고
  핫 패스는 타입 있는 포인터로 부르므로 컬렉션으로 옮겨도 남는 이득은 종료 순서뿐인데, 실제 결함(네이티브 객체와 GPU 완료 사이)은 컬렉션 밖에 있다.
  대신 순서를 어기면 터지게 했다: 2 단계(GPU 대기) 뒤와 4 단계 뒤에 해제 큐가 비었는지, 끝난 종료 뒤에 해제가 쌓였는지를 `shutdown` 이 단언한다
  (`getPendingReleaseCount`, nogpu 테스트 `RHIDeviceShutdownTest`). 점검에서 Vulkan 이 4 단계에서 오프스크린 프레임버퍼를 해제 큐에 넣고 비우지 않던 것을 고쳤다.
- **셰이더 쿠킹 스탬프의 도구 지문은 버전 상수로 만든다 — 컴파일 옵션 판 · Vulkan 타깃 판 · 컴파일러 버전 글(`ShaderCooker::kCompilerVersion`, vcpkg `directx-dxc` 포트 버전)**(2026-10-14).
  컴파일러 라이브러리 파일의 내용 해시로 만들었더니 Windows 에서 쿠킹해 커밋한 스탬프가 리눅스(다른 라이브러리 파일)에서 모두 낡은 것으로 판정돼 리눅스 CI 다섯 잡이 졌다.
  언리얼은 셰이더 DDC 키에 컴파일러 바이너리 해시가 아니라 셰이더 포맷 · 컴파일러 버전 식별자를 넣는 것으로 알고 있다(기억에 의존). 같은 원칙을 따르고,
  사람이 고치는 상수가 실제 설치와 어긋나지 않게 `TestShaderCompilerVersionPin.py` 가 vcpkg 설치 기록과 대조한다.
- **셰이더 쿠킹 스탬프(`cook.stamp`)는 쿠킹 기록(`.cookrec`) 형식으로 옮기지 않습니다**(2026-10-18, C-42 K5). 스탬프는 커밋되는 산출물 곁에 있고 엔진의 판정 하나(`ShaderCooker::verifyCookedShaders` — `App --verify-shaders` · `ShaderCookStampTest`, 2026-10-22 StructureSimplification PK3 에서 파이썬 게이트 `CheckShaderStamps` 를 대신했다)가 보는 계약인데,
  쿠킹 기록은 체크아웃마다의 `Saved/` 캐시이고 판정에 엔진의 읽기 기록이 필요하다. 내용 해시는 이미 같은 함수(`ContentHash`)를 쓰므로 판정 기준은 하나다. 언리얼도 셰이더는 DDC 키를 따로 만들고 에셋 쿠킹과 섞지 않는다 [기억].
- **셰이더 쿠킹은 컴파일 · 리플렉션을 병렬로 돌리고 합치기는 요청 순서대로 직렬로 합니다**(2026-10-25, `ShaderCookDriver::cookRequests`). 단위는 요청 × 포맷 작업이고 작업마다 자기 결과 칸에만 쓴다. 매니페스트 합치기 · 카운터 · 실패 소스 기록 · 매니페스트와 스탬프 쓰기는 직렬이라 산출물은 직렬로 돌 때와 바이트까지 같다.
  같은 바이너리 파일을 만드는 요청은 한 사슬로 한 스레드가 순서대로 돌고, 출력 폴더는 병렬 구간 전에 만든다. 단일 스레드로 요청 × 네 포맷을 차례로 컴파일하던 것이 쿠킹 시간의 대부분이라 보고 나눈다(줄어든 시간은 통합이 `compile` · `reflection` · `total` 로그로 잰다). 언리얼 셰이더 컴파일 워커도 컴파일은 워커 여럿이 하고 결과는 한 스레드가 병합한다 [기억].
  이 일에서 `ShaderReflectionDx` 의 `dxcompiler` 로드가 맨 `static bool` 플래그로 한 번만 찾던 것(동시에 처음 부르면 한 스레드가 빈 함수 포인터를 받아 리플렉션이 빈 채로 매니페스트에 들어간다)을 함수 안 정적 변수로 바꿨다.
- **쿠킹은 최신 바이너리도 매번 읽어 리플렉션을 다시 뽑습니다 — 이전 매니페스트에서 가져오지 않습니다**(2026-10-25, 검토 뒤 하지 않기로 함). ① `isCookedOutputCurrent` 는 소스 내용 해시와 도구 지문(스탬프)만 보고 매니페스트와 바이너리가 같은 쿠킹에서 나왔는지는 보지 않는다 —

- **동기 업로드 대기는 "제출 → 티켓 → 폴링" 비동기 계약으로 옮기고, 프레임 경로에는 `waitIdle` 을 새로 만들지 않습니다**(2026-10-25, [RhiAsyncUploads](../plans/RhiAsyncUploads.md), 코드 읽기만 했고 측정 전). 텍스처 업로드 둘과 되읽기의 동기 가상 함수를 RHI ABI 버전을 한 번 높여 지웁니다(백엔드 DLL 이 같은 vtable 을 봐야 해서 쪼갤 수 없고, 옛 함수 위의 기본 구현은 폴백이 되어 두지 않습니다). 동기가 필요한 테스트와 도구는 ABI 밖의 `AndWait` 헬퍼를 씁니다. 새 머티리얼의 GPU 초기화는 렌더 스레드의 프레임 셋업 구간으로 옮기고, 머티리얼과 PSO 는 준비 전 / 준비됨 / 실패 상태를 데이터로 두어 준비 전에는 그리지 않습니다.

- **DX11 의 큰 텍스처 업로드는 장치가 초기 데이터로 만든 `STAGING` 텍스처로 올리고, 즉시 컨텍스트 잠금 안에서는 `CopySubresourceRegion` 과 이벤트 쿼리 `End` 만 합니다**(2026-10-25, 코드 읽기만 했고 측정 전). `UpdateSubresource` 는 소스 복사(큰 텍스처는 수십 MiB)를 잠금 안에서 해서 렌더 스레드의 `ExecuteCommandList` · `Present` 가 그만큼 기다렸습니다.
  스테이징 풀에 `Map( D3D11_MAP_WRITE )` 로 쓰는 안은 기각했습니다 — `Map` · `Unmap` 은 즉시 컨텍스트 호출이라 잠금을 두 번 잡고(복사는 그 사이 잠금 밖), D3D11 에는 버퍼 → 텍스처 복사가 없어 풀은 크기 · 포맷마다 텍스처여야 해 재사용률을 모릅니다. `CreateTexture2D( pInitialData )` 는 장치 호출(스레드 안전)이라 잠금 없이 복사가 끝나고, 대가는 업로드마다 할당 한 번입니다(측정 전).
  같은 이유로 GL 의 `RHIStagingAllocator`(오프셋 링 장부)는 맞지 않아 쓰지 않습니다. 스테이징은 기존 전송 큐 항목(`TransferProbe`)이 쥐어 워터마크가 지나면 놓고, 합은 GL 링과 같은 설정 `gv_rhiStagingRingMegabytes`(64 MiB)가 상한입니다 — 차면 끝난 전송을 한 번 모은 뒤 `Busy`, 한 장이 상한보다 크면 예산 전부를 잡고 혼자 들어갑니다(아래 항목, 그 크기를 올리던 `UpdateSubresource` 경로는 남기지 않습니다). 장치를 잃으면 예산이 돌아오지 않아 `Busy` 가 끝나지 않으므로 제출 진입에서 `GetDeviceRemovedReason` 을 먼저 보고 `Rejected` 입니다.
  `gv_rhiDirectUploadMaxKilobytes`(256 KiB) 이하는 `UpdateSubresource` 를 그대로 씁니다. 잠금 안의 복사가 수십 µs(메모리 복사 5 ~ 10 GB/s)로 스테이징 생성 · 복사 명령 하나의 고정 비용과 비슷한 자리라는 추정이고, 글리프 아틀라스 구간 갱신(수 KB)이 이 아래입니다. 두 값은 `RhiAsyncUploads` 측정(M1)이 정합니다.
  언리얼 D3D11 의 비동기 텍스처 생성도 초기 데이터를 넘기는 `CreateTexture2D` 를 아무 스레드에서 부르고, 생성 뒤 갱신(`RHIUpdateTexture2D`)은 RHI 스레드의 `UpdateSubresource` 라고 알고 있습니다(기억에 의존).
- **DX11 업로드 스테이징 예산보다 큰 업로드 한 장은 `Rejected` 가 아니라 예산 전부를 잡고 혼자 들어갑니다. 텍스처 되읽기는 `Map` · `Unmap` 호출에만 즉시 컨텍스트 잠금을 잡고, 버퍼 구간 갱신은 잠금 안의 `UpdateSubresource` 그대로 둡니다**(2026-10-25, 코드 읽기만 했고 측정 전).
  조사: 저장소 에셋의 가장 큰 업로드는 5.33 MiB(`Resource/game/empty/textures/avatarsample_d` 의 DDS 두 장, 하늘 DDS 는 2.67 MiB이고 `textures_raw` 의 `.hdr` 6.38 MiB 는 쿠킹 입력이라 올리지 않습니다)로 64 MiB 의 1/12 입니다. 코드가 만드는 업로드는 에디터 뷰의 첫 채우기(뷰 크기 RGBA8 — 4K 31.6 MiB, 6K 77.7 MiB, 8K 126.6 MiB)와 렌더 타깃 미리보기 스냅샷(대상 크기 RGBA8 — ultra 그림자 4096² 가 꼭 64 MiB, `gv_shadowMapResolution` 8192 면 256 MiB)이라 화면과 설정에 따라 예산을 넘고, 예전 `UpdateSubresource` 는 이 크기를 받았습니다.
  기본값을 올리는 안은 그 크기에 상한이 없어 같은 회귀가 남으므로 기각했습니다. 한 장을 밉 · 행 구간으로 쪼개 여러 번 내는 안은 앞 조각의 GPU 완료를 제출 안에서 기다려야 해서(제출은 기다리지 않는 계약) 기각했습니다. 혼자 들어가는 업로드는 복사 중인 스테이징이 없을 때만 받고 그동안 다른 업로드는 `Busy` 라 메모리 최고점은 max(예산, 가장 큰 한 장)입니다 — `UpdateSubresource` 도 드라이버가 같은 크기를 복사해 두었으므로 같은 자리이고, 대가는 큰 업로드가 앞선 업로드가 다 끝날 때까지 `Busy` 를 받는 것입니다(측정 전). 언리얼 D3D12 의 업로드 할당자도 풀 블록보다 큰 할당은 전용 자원으로 따로 만든다고 알고 있습니다(기억에 의존).
  되읽기(`takeTextureReadback`): `Map` 이 준 포인터는 `Unmap` 까지 어느 스레드에서나 읽어도 되는 CPU 메모리이고 그 스테이징은 표에서 꺼낸 읽기 하나만 가지므로, 행 복사(4K RGBA16F 면 60 MiB 남짓)를 두 잠금 사이로 뺐습니다. 제출(`submitTextureReadback`)은 이미 잠금 안에서 `CopySubresourceRegion` 과 쿼리만 냅니다.
  버퍼 구간 갱신(`updateStructuredBufferRegions` · `updateVertexBufferRegions`): 호출자(`GPUScene` 의 바뀐 인스턴스 구간, `GPUMeshVertexPool` · `GPUMeshMorphPool` 의 새 메시 정점)가 모두 렌더 스레드이고 렌더 스레드는 그 복사를 어차피 직접 하므로, 잠금 밖으로 빼도 프레임이 줄지 않고 갱신마다 스테이징 생성 · 쿼리 · GPU 복사가 더해집니다. GL 의 같은 함수를 링으로 옮기지 않은 판단과 같은 이유입니다. 잠금 동안 다른 스레드의 전송 · 폴링이 기다리는 시간은 새 메시가 들어오는 프레임의 정점 크기만큼이고, 그것이 보이면 측정으로 다시 엽니다. `readReadbackBuffer`(GPU 해제 콜백 안에서 읽는 작은 버퍼)도 같은 이유로 둡니다.
- **엔진 밖으로 나가는 네이티브 컨텍스트는 잠금 안의 콜백(`IRHIDevice::withNativeContext`)으로만 주고, 스레드끼리 나눠 쓰는 RHI 상태는 그것을 바꾸는 쪽도 같은 락이나 atomic 으로 다룹니다**(2026-10-25, 코드 읽기만 했고 측정 전). 원 getter `getNativeContext` 는 백엔드 안의 protected 훅이 됐고 `RHINativeHandles::_pContext` 는 지웠습니다(판 3). 통합 N 에서 cifixl5 의 종류 확인 결정과 합쳐 `withNativeContext( 기대 백엔드, 콜백 )` 은 `[[nodiscard]] bool` 이고 다른 백엔드이면 콜백을 부르지 않습니다. DX11 은 즉시 컨텍스트 임계 구역을 쥔 채 콜백을 부르고, DX12 · Vulkan 의 프레임 커맨드 리스트와 GL 컨텍스트는 렌더 스레드 전용이라 잠금 없이 넘깁니다.
  DX11 의 ImGui 렌더러는 GL 처럼 텍스처 갱신과 보조 뷰포트 렌더를 렌더 스레드로 옮겼습니다(`requiresRenderThreadContext`). 호출마다의 런타임 보호는 즉시 컨텍스트의 파이프라인 상태(렌더 타깃 · 셰이더)를 지키지 못해, UI 스레드의 보조 뷰포트 렌더가 렌더 스레드 프레임 중간에 렌더 타깃을 바꿀 수 있었습니다. 보조 뷰포트를 그린 뒤에는 백버퍼를 컨텍스트에서 뗍니다(UI 스레드의 `ResizeBuffers` 가 걸린 백버퍼 때문에 실패하지 않게).
  DX12 는 프레임 펜스의 Signal 과 값 올리기를 `_uploadSlotMutex` 안에서 한 덩어리로 합니다. 업로드가 같은 락 안에서 그 값을 읽고 복사를 실행하므로, 락 밖이면 Signal(V) 뒤에 실행된 복사가 V 를 받아 그 펜스를 기다린 얼로케이터 Reset 이 도는 복사를 지울 수 있었습니다. U5 가 락 범위를 줄여도 이 짝은 같은 락에 둡니다. 펜스 대기 이벤트는 장치에 하나를 두지 않고 기다릴 때마다 만듭니다 — 렌더 스레드(링 슬롯)와 업로드 스레드(얼로케이터)가 자동 리셋 이벤트 하나를 함께 기다리면 남의 신호로 깨어나 아직 오지 않은 펜스를 지났다고 믿습니다. 비용은 실제로 기다릴 때만 이벤트 생성 하나입니다.
  다른 스레드가 읽는 플래그(DX11 · DX12 · Vulkan 의 타임스탬프 스위치, DX11 의 쿼리 준비 표시, DX12 의 프레임 펜스 값 · 링 인덱스 · 로그 한 번 래치, Vulkan 의 프레임 슬롯 — 다른 스레드의 `updateConstantBuffer` 가 칸을 고르려 읽는다, GL 의 타임스탬프 스위치 · 쿼리 준비 표시도 같다)는 `atomic` 입니다. Vulkan 의 `_queueMutex` 는 RT 의 `endFrame` 제출 · Present 와 다른 스레드의 일회성 제출 · `waitIdle` 이 모두 같은 락이라 바꾸지 않았습니다. 언리얼은 ImGui 같은 오버레이도 RHI 스레드의 커맨드로 그린다고 알고 있습니다(기억에 의존).
- **스테이징 링 장부(`RHIStagingAllocator`)는 할당 순서가 아니라 구간마다 돌려받고, 빈 자리는 `SpanAllocator` 가 쥡니다**(2026-10-25, [RhiAsyncUploads](../plans/RhiAsyncUploads.md) 2.2 "스테이징 링", 측정 전). 할당 순서로만 돌려받으면 가져가지 않은 되읽기 하나가 링 맨 앞을 막아, 티켓을 쥔 스레드의 `readbackTexture2DAndWait` 가 10 초 시간 초과로 실패했습니다. 시리얼을 붙인 구간은 자기 시리얼이 워터마크(연속으로 끝난 시리얼의 끝)를 지나면 순서와 무관하게 돌아오므로 GPU 가 쓰는 구간을 덮지 않습니다. 쥔 구간들이 남은 자리를 다 차지할 때만 `Busy` 입니다. DX12 · Vulkan 이 붙여도 장부는 이 하나입니다.
  기각: 가져가지 않은 읽기를 프레임 · 시간 상한 뒤 자동으로 버리기(유니티 `AsyncGPUReadback` 의 "그 프레임 안에서만 유효"와 비슷하다고 알고 있음, 기억에 의존)는 티켓 계약을 바꾸고 RHI 에 프레임 시계를 들여야 하며, 실패를 늦출 뿐 쥔 구간이 링을 막는 모양은 그대로입니다. "티켓을 쥔 채 `AndWait` 금지" 를 `ScopedForbidBlockingTransfer` 로 거는 안은 같은 스레드만 막고 다른 스레드가 쥔 티켓이 링을 막는 경우를 못 막습니다. 빈 자리 관리는 새로 짜지 않고 정점 풀이 쓰는 `SpanAllocator`(언리얼 `FSpanAllocator` 에 해당)를 그대로 씁니다.
- **티켓을 쥔 채 제출하는 `...AndWait` 는 `PendingReadback` 이 쥔 수로 Debug 에서 막고, 장치 손실 뒤 로그는 `markLost` 가 처음 표시했을 때만 남깁니다**(2026-10-25, [RhiAsyncUploads](../plans/RhiAsyncUploads.md) 2.2, 측정 전). 쥔 티켓들이 스테이징의 남은 자리를 다 차지하면 `submitWhileBusy` 가 10 초 시간 초과로 실패하는 모양이 남아 있었습니다. `PendingReadback` 이 스레드마다 쥔 수를 세고 업로드 · 읽기 `...AndWait` 가 제출하기 전에 0 인지 단언합니다(소유자는 만든 스레드에서만 놓는다). 한계: 다른 스레드가 쥔 티켓과 `PendingReadback` 에 넣지 않은 날 티켓은 세지 못합니다 — 그 수는 백엔드 표에 있고 헬퍼가 볼 수 없으며, 백엔드마다 세면 호출 쪽 파일이 여러 작업자의 소유와 겹칩니다. `markLost` 는 처음 표시했는지를 돌려주고, 손실 뒤 매 프레임 다시 도는 GL `retireFinishedTransfers` · DX12 `signalExportedTransfers` 의 오류 로그는 그때만 남깁니다. 스테이징 장부 클래스는 링이 아니므로 `RHIStagingAllocator` 을 `RHIStagingAllocator` 로 바꿨습니다(테스트 모음 이름 · 매니페스트 id 는 그대로).
  상용 엔진과의 비교는 확인하지 못했습니다(기억에 의존할 근거가 없음). 기각: 가져가지 않은 읽기의 자동 폐기(위 항목의 기각 사유와 같음).
- **스테이징 링보다 큰 전송 한 장은 장부(`RHIStagingAllocator`)가 링이 비었을 때만 단독 구간으로 내주고, 백엔드는 그 크기의 일회성 버퍼에 받습니다**(2026-10-25, [RhiAsyncUploads](../plans/RhiAsyncUploads.md) 2.2 "스테이징 링", 측정 전). GL 은 링(64 MiB)보다 큰 업로드 · 읽기를 `Rejected` 해, 예전 동기 경로가 받던 에디터 6K+ 뷰 첫 채우기(77.7 MiB), ultra 그림자 스냅샷(64 MiB 이상, 8192² 면 256 MiB)이 회귀했습니다.
  규칙은 장부 하나에 둡니다 — 링 용량보다 크고 단독 상한(`gv_rhiStagingSingleMaxMegabytes`, 기본 512 MiB, 0 이면 받지 않음) 이하인 요청은 링에 산 구간이 0 일 때만 `_bSolo` 구간이 되고, 그 구간이 사는 동안 다른 요청은 모두 `Full`(`Busy`)이라 메모리 최고점은 max(링, 가장 큰 한 장)입니다. 상한을 넘으면 `TooLarge`(`Rejected`)이고 설정 이름을 로그로 알립니다. DX12 · Vulkan 도 이 장부를 쓰면 같은 규칙을 얻습니다. DX11 은 자기 예산 카운터로 같은 조건(복사 중인 스테이징 0)을 이미 쓰며 상한과 예약은 없습니다.
  GL 은 단독 구간마다 `glBufferStorage` 영속 매핑 버퍼를 만들고(할당 때 컨텍스트를 잠깐 빌리고 바이트 복사는 컨텍스트 밖), 장부가 구간을 돌려받은 뒤 컨텍스트를 쥔 `retireFinishedTransfers` 가 지웁니다. 메모리 장부 Staging 에 만들 때 올리고 지울 때 내립니다. 드라이버 비용은 수백 MiB 버퍼 생성 한 번이고, 드문 한 장(뷰 크기 변경, 스냅샷)이라 링을 키워 두는 상주 메모리보다 싸다고 봤습니다.
  굶주림은 예약으로 막습니다 — 링이 비지 않아 `Full` 을 받은 단독 요청은 250 ms 예약을 남겨 그동안 새 링 요청도 `Full` 이고, 다시 올 때마다 연장되며 단독 구간을 내주면 끝납니다. 시간으로 끝내는 이유: 링이 빌 때까지 예약하면 가져가지 않은 되읽기가 링을 비우지 않아 작은 읽기가 영원히 `Busy` 이고, 거절 횟수로 끝내면 호출자 수와 빈도에 따라 뜻이 바뀝니다. 한계: 포기한 단독 요청은 링 요청을 최대 250 ms 막고, 쥔 되읽기가 있는 동안 기다리는 단독 읽기는 그 호출자의 시간 초과까지 다른 읽기를 막습니다.
  기각: 기본 링을 키우기(한도 없는 크기가 남는다), 한 장을 쪼개 여러 번 내기(앞 조각의 GPU 완료를 제출 안에서 기다려야 한다), 호출마다 단독 허용 플래그(지금 모든 호출자가 같은 답이라 백엔드가 `initialize` 에서 한 번 정한다). 유니티의 Async Upload Buffer 는 버퍼보다 큰 텍스처가 오면 버퍼를 그 크기로 늘렸다가 줄이는 것으로 알고 있습니다 **[기억에 의존]**.
- **종류 · 모드를 숫자 코드로 받던 전역 변수는 리플렉션 enum 으로 바꾸고, 명령줄은 열거자 이름만 받는다 — `gv_rhiBackBufferFormat`(0/1 → `RHIBackBufferFormat` RGBA8 · BGRA8), `gv_lightCulling`(0/1/2 → 이미 있던 `LightGridProducer` None · CPU · GPU), `gv_viewMode`(0..11 → 이미 있던 `RenderViewMode`)**(2026-10-25, bbfmt). 전역 변수는 enum 을 이미 지원한다(`GlobalVariableTraits` 의 enum 특수화, 리플렉션 표를 파서로 건 `-gv_rhiBackend=Vulkan`) — `SW_GLOBAL_VARIABLE( 타입, … )` 의 첫 인자만 enum 이면 되고 구조 변경은 필요 없었다. 숫자 폴백을 두지 않으려고 Core 에 `GlobalVariableInfo::setValueFromCommandLine` 을 더했다: 명령줄 글이 enum 변수에 숫자로 들어오면 이유를 담은 오류로 멈춘다(`applyPendingEnumText` 가 기동을 실패시킨다). 영향은 `-gv_rhiBackend=2` · `-gv_vfxSimulation=0` 처럼 enum 이던 변수의 숫자 인자도 같이 오류가 되는 것이다(저장소 안에는 쓰는 곳이 없었다).
  에디터 · 콘솔 · 프리셋 · 사용자 설정 · 자동화의 `setValueFromString` 은 숫자를 계속 받는다 — 값 왕복(`getValueAsString` 이 숫자)과 사용자 설정의 `targetValue` 가 이 글에 기대고, 거기는 사람이 치는 입력이 아니라 프로그램끼리 주고받는 글이기 때문이다. 대신 범위 밖 값은 쓰는 곳이 거른다(`gv_rhiBackBufferFormat` 은 `initialize` 가 오류로 멈추고, `gv_viewMode` 는 `isRenderViewModeIndex` 가 멈춘다).
  언리얼 콘솔 변수(`r.DefaultBackBufferPixelFormat` 은 정수 코드 0~4)는 숫자를 받는 쪽이지만 값의 뜻이 문서에만 있어 순서가 바뀌면 조용히 달라지는 같은 모양이다. 유니티의 명령줄(`-force-d3d11` 같은 이름 플래그)과 Godot 의 `--rendering-driver vulkan` 은 이름으로 고르는 쪽이라 이 결정과 같다고 알고 있다(기억에 의존).
