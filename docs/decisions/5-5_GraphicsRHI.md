# 5-5. 그래픽스와 RHI

> 질문: 5-5. 그래픽스와 RHI 영역에서 이미 정한 것은 무엇이고 근거는 무엇인가?
> 독자: 같은 제안을 다시 하려는 사람, 정한 이유를 찾는 사람.
> 결론: 결정 기록 5 절의 한 영역이다. 번호 체계와 쓰는 법은 [결정 기록](../09_Decisions.md) 5절에 있다.

- **RHI 의 완료 · 동기화 계약은 `IRHIDevice` 머리말의 한 표로 두고, 네 백엔드가 같은 테스트로 지킨다**(2026-10-25). `waitIdle` 은 앞서 제출한 모든 GPU 작업이 끝난 뒤 돌아오고, `enqueueGPURelease` 콜백은 그 프레임의 GPU 작업이 끝난 뒤에만 불리며, GPU 는 `kMaxFrameCountInFlight` 프레임보다 더 뒤처지지 못하고, `readReadbackBuffer` 는 읽기 버퍼가 아닌 핸들을 거절한다.
  DX11 은 프레임 끝 이벤트 쿼리 링, GL 은 프레임 끝 `glFenceSync` 링으로 DX12 · Vulkan 의 펜스와 같은 모양을 만들었다(링이 차면 가장 오래된 프레임을 기다림). 완료 확인용 쿼리를 못 만들면 초기화를 실패시킨다(폴백 없음). 언리얼 RHI 도 백엔드마다 같은 뜻의 `FRHIGPUFence` 를 쓴다(기억에 의존). 장치 제거 뒤 `waitIdle` 테스트는 Vulkan 에만 있다(DX12 제거 경로는 같은 테스트로 걸지 못함).
- **장치를 잃었다는 사실의 저장소는 `RHITransferSerials` 의 손실 표시 하나이고, 전송 제출은 진입에서 `isLost` 를 보고 `Rejected` 를 돌려준다. 네 백엔드가 같다**(2026-10-25). 손실을 표시하는 자리가 호출 결과를 보는 자리마다 흩어져 빠진 자리가 생기던 모양이라 한 곳으로 모았다.
  Vulkan 은 자기 `_bDeviceLost` 를 지우고 `isDeviceLost` 가 `RHITransferSerials::isLost` 를 읽으며(`markLost` 는 처음 표시했는지를 돌려줌), DX12 · DX11 은 `GetDeviceRemovedReason` 을 `isDeviceRemoved`(묻고 표시) 한 함수만 묻는다. DX11 의 쿼리 읽기 실패는 `reportQueryFailure` 가 표시하고 이벤트 쿼리 대기 · 타임스탬프 읽기는 시한까지 돌지 않고 끝낸다. 손실 뒤 로그는 처음 표시한 호출만 남긴다.
  `debugRemoveDevice` 는 표시만 하는 시험용 훅이다(D3D11 에는 `RemoveDevice` 가 없어 제거된 장치의 `GetData` · Present 실패 경로는 확인하지 못한다). 언리얼 RHI 는 제거된 장치에서 명령을 조용히 버리는 것으로 알고 있으나(기억에 의존) 여기서는 호출자가 잃은 장치를 기다리지 않게 제출 쪽에서 막는다.
- **스테이징 링의 할당 결과는 `RHITransferSerials::classifyStagingAllocation` 한 곳이 제출 결과로 옮기고, 장치를 잃었으면 `Rejected` 다. GL 의 버퍼 구간 갱신은 링으로 옮기지 않는다**(2026-10-25). 장치를 잃으면 링이 비지 않아 `Busy` 재제출이 끝없이 돌던 결함을 `Full` → `Busy` 옮기기를 장치 상태를 아는 한 함수로 모아 막았다.
  `updateConstantBuffer` · `updateStructuredBufferRegions` · `updateVertexBufferRegions` 를 링 + `glCopyBufferSubData` 로 바꾸는 안은 기각했다. 프레임 경로 호출자는 모두 RT 이고 RT 는 프레임 내내 컨텍스트를 쥐므로 줄어드는 점유가 없고, 링 장부 · 펜스 · GPU 복사가 더해지며 CPU 복사 횟수는 같다. 언리얼 GL RHI 도 작은 유니폼 갱신은 `glBufferSubData` 계열이다(기억에 의존). 큰 인스턴스 구간에서 드라이버 암묵 동기가 보이면 측정으로 다시 연다.
- **Vulkan 텍스처 전송은 그래픽스 큐에 기다리지 않고 내고(전송 작업 = 커맨드 버퍼 + 펜스, 재사용), 스테이징은 업로드 · 되읽기 영속 매핑 링 둘이다. 전용 전송 큐는 쓰지 않는다**(2026-10-25, RhiAsyncUploads U6). 전송 큐는 소유권 이전 배리어와 큐 사이 세마포어가 필요하고 이득은 큰 텍스처 스트리밍 중의 프레임 시간뿐이라 측정 전에는 하지 않는다(계획 문서 2.2). 언리얼 Vulkan RHI 도 기본은 그래픽스 큐이다(기억에 의존). 펜스를 쓰고 타임라인 세마포어를 쓰지 않는 것은 `RHITransferFenceQueue` 의 앞에서부터 올리는 워터마크를 그대로 쓰기 위해서다.
  되읽기 링을 나눈 이유: 링은 할당 순서로만 회수하므로 가져가지 않은 되읽기가 업로드까지 `Busy` 로 만든다. 끝나기 전에 버린 되읽기 구간에는 시리얼을 붙여 복사가 끝난 뒤 돌려받고, 전송 중에 파괴한 텍스처의 해제는 시리얼 키 해제 큐에 두었다가 전송이 끝나면 다음 프레임 펜스 뒤로 넘긴다(DX12 `releaseTrackedResourceDeferred` 와 같은 규칙). 링보다 큰 한 장은 `gv_rhiReadbackRingMegabytes` 링이 빌 때 그 크기의 일회성 호스트 가시 버퍼(`VulkanStagingRing::_soloBuffer`)로 받고 장부가 구간을 돌려받은 뒤 `retireFinishedTransfers` 가 지운다.
- **DX12 셰이더 가시 힙은 524288 칸(bindless 32768 + 온라인 블록 960 × 512)으로 둔다**(2026-10-23). 65536 칸은 미리보기 월드 넷을 그리는 한 프로세스 재생(`editor.netsim`)에서 바닥났다. 언리얼의 온라인 힙 기본도 수십만 칸이고 힙 메모리(16 MB)는 작다.
- **RHI 디바이스 안은 서브시스템으로 만들지 않는다 — 부품은 타입 있는 멤버로 명시 소유하고, 종료 순서는 `IRHIDevice::shutdown` 의 네 단계가 정한다**(2026-10-14, 백로그 C-26). 언리얼 RHI 도 같은 모양이다. 컬렉션으로 옮겨도 남는 이득은 종료 순서뿐이라, 대신 순서를 어기면 터지게 했다: 2 단계(GPU 대기) 뒤와 4 단계 뒤에 해제 큐가 비었는지, 끝난 종료 뒤에 해제가 쌓였는지를 `shutdown` 이 단언한다(`getPendingReleaseCount`, `RHIDeviceShutdownTest`).
- **셰이더 쿠킹 스탬프의 도구 지문은 버전 상수로 만든다 — 컴파일 옵션 판 · Vulkan 타깃 판 · 컴파일러 버전 글(`ShaderCooker::kCompilerVersion`, vcpkg `directx-dxc` 포트 버전)**(2026-10-14). 컴파일러 라이브러리 파일의 내용 해시로 만들었더니 Windows 에서 쿠킹한 스탬프가 리눅스에서 모두 낡은 것으로 판정돼 CI 가 졌다. 언리얼도 셰이더 DDC 키에 컴파일러 버전 식별자를 넣는다(기억에 의존). `TestShaderCompilerVersionPin.py` 가 상수와 vcpkg 설치 기록을 대조한다.
- **셰이더 쿠킹 스탬프(`cook.stamp`)는 쿠킹 기록(`.cookrec`) 형식으로 옮기지 않는다**(2026-10-18, C-42 K5). 스탬프는 커밋되는 산출물 곁의 계약이고 판정은 엔진의 `ShaderCooker::verifyCookedShaders` 하나가 보는 반면, 쿠킹 기록은 체크아웃마다의 `Saved/` 캐시이고 판정에 엔진의 읽기 기록이 필요하다. 내용 해시는 이미 같은 함수(`ContentHash`)를 쓴다. 언리얼도 셰이더 DDC 키를 에셋 쿠킹과 섞지 않는다.
- **셰이더 쿠킹은 컴파일 · 리플렉션을 병렬로 돌리고 합치기는 요청 순서대로 직렬로 한다**(2026-10-25, `ShaderCookDriver::cookRequests`). 단위는 요청 × 포맷 작업이고 작업마다 자기 결과 칸에만 쓰며, 합치기 · 카운터 · 매니페스트와 스탬프 쓰기는 직렬이라 산출물은 직렬일 때와 바이트까지 같다. 같은 바이너리를 만드는 요청은 한 사슬로 한 스레드가 돌린다. 언리얼 셰이더 컴파일 워커도 같은 모양이다. 이 일에서 `ShaderReflectionDx` 의 `dxcompiler` 로드를 함수 안 정적 변수로 바꿨다(맨 `static bool` 플래그는 동시 첫 호출에서 빈 함수 포인터를 받는다).
- **쿠킹은 최신 바이너리도 매번 읽어 리플렉션을 다시 뽑는다 — 이전 매니페스트에서 가져오지 않는다**(2026-10-25, 검토 뒤 하지 않기로 함). ① `isCookedOutputCurrent` 는 매니페스트와 바이너리가 같은 쿠킹에서 나왔는지 보지 않아, 병합이 둘을 다른 쪽 것으로 고르면 재사용한 리플렉션이 조용히 낡는다. ② 매니페스트 형식(`kVersion` 2)에 정점 입력이 없어 계약 검사를 다시 돌릴 수 없다. ③ `ShaderReflection::reflect` 의 의미가 바뀌어도 소스가 그대로면 옛 값이 남는다. 재사용하려면 바이너리 내용 해시를 매니페스트 항목에 넣고 위 셋을 함께 풀어야 한다.
- **런타임 UI 를 위해 RHI 에 R8 텍스처, 영역 업로드, 프리멀티플라이 블렌드, 가위 사각형을 더했다**(2026-10-06). 사각형 클리핑은 가위로 한다(Slate, Dear ImGui, Godot 과 같고 배치가 끊기지 않음). 둥근 모서리 클리핑만 셰이더에서 한다.
- **머티리얼 XML 과 셰이더 구조체의 필드 불일치는 오류다 — 폴백 없음**(2026-10-23): 셰이더에만 있는 필드 · XML 에만 있는 필드 · 리플렉션을 얻지 못함은 `Material::syncPropertiesFromReflection` / `ensureShaderLayout` 이 오류(머티리얼 · 필드 · 셰이더 경로)를 남기고 바이트를 비운다. 두 함수는 `[[nodiscard]]` 이고 `MaterialTest.EveryRepositoryMaterialMatchesItsShaderStruct` 가 모든 .material 을 검사한다.
- **프리멀티플라이 블렌드는 PSO 비트(`_bPremultipliedAlpha`)이고 머티리얼 블렌드 enum 에는 넣지 않는다**(2026-10-06). 언리얼도 머티리얼 `EBlendMode` 와 RHI 블렌드 상태가 따로다.
- **보기 모드는 뷰마다의 설정이다**(`RenderViewSettings::_viewMode`, 2026-10-10). 에디터 씬 뷰 툴바는 씬 뷰에만 걸고 게임 뷰는 Lit 로 그린다(언리얼 View Mode, 유니티 Draw Mode 와 같다). Normals · Depth · Overdraw 는 후처리 · 톤맵을 건너뛴다. Overdraw 는 알파 0 의 프리멀티플라이로 더하며 깊이 테스트는 남기고 쓰기만 끈다(테스트를 끄면 Vulkan 이 깊이 첨부 없는 PSO 로 만든다).
- **디퍼드의 툰은 G버퍼에 칸을 더하지 않고 포워드로 그린다**(2026-10-21, `ForwardOnlyOpaque` · `MATERIAL_FORWARD_ONLY`). G버퍼 패스가 그 머티리얼을 빼고(`RenderPassTypeInfo::_pExcludedMaterialDefine`) 조명 패스 뒤의 포워드 전용 패스가 같은 장면 깊이에 그린다 — 유니티 URP 디퍼드의 `UniversalForwardOnly` 와 같다. 셋째 G버퍼 타깃안은 기각했다: 림 · 맷캡 · 발광 · 빛마다의 그림자색을 담지 못해 그림이 갈리고 모든 머티리얼의 PSO 타깃 수 · 대역폭이 늘어난다. 대신 툰 표면은 SSAO 노멀에 들어가지 않는다. define 을 빠뜨린 머티리얼을 쿠킹에서 멈추게 하는 toon.hlsl 의 `#error` 는 셰이더 다시 굽기와 함께 넣는다(계획 GraphicsFormatBundle G2).
- **톤맵을 HDR 씬 컬러로 바꾸는 일은 하지 않았다**(2026-10-06). 기본 포워드의 Reinhard 가 흰색을 0.5 로 누르지만 바꾸면 골든 이미지를 모두 다시 떠야 한다. 어두운 게임은 데이터로 맞춘다.
- **점광 · 스폿 그림자는 큐브 · 배열 텍스처가 아니라 2D 그림자 아틀라스다**(2026-10-13). 유니티 URP · Godot 방식이고 RHI 를 바꾸지 않으며 DX11 · GL 의 텍스처 슬롯 네 개가 그대로다. 방향광 캐스케이드(최대 4)도 같은 아틀라스의 타일이고 추가 뷰는 자기 볼륨 · 그림자 컬링 슬롯을 쓴다. 칸이 모자라면 주 시점의 화면 크기 대리값(경계 구 반경 / 카메라 깊이)이 큰 빛부터 받는다(`ShadowSetupUtil::computeLocalShadowPriority`, 언리얼의 투영 화면 반경과 같은 기준). 화면 크기별 칸 크기 변경은 하지 않았다.
- **깊이 패스(그림자 · 깊이 프리패스)는 모양을 머티리얼 코드가 정하는 배치만 머티리얼 셰이더로 그린다**(2026-10-17, `FrameRendererUtil::drawsDepthWithMaterialShader`). 알파 컷오프는 두 깊이 패스 모두 머티리얼 셰이더의 깊이 퍼뮤테이션(`SW_PASS_SHADOW` · `SW_PASS_DEPTH_PREPASS`)의 픽셀 스테이지(`clip` 만)로, 정점 변형(바람)은 그림자 패스만 정점 스테이지로 그린다. 나머지는 shadowdepth.hlsl 을 나눠 쓴다(언리얼도 Masked · WPO 머티리얼만 자기 깊이 셰이더를 컴파일). shadowdepth.hlsl 이 머티리얼 값을 읽게 하는 안은 기각했다 — 머티리얼마다 구조체 배치가 달라 컷오프 값 · 텍스처 칸을 찾을 수 없다. 뎁스 전용 PSO 도 PS 경로가 있으면 픽셀 스테이지를 둔다(`RHIShaderRequest::resolveGraphics`).
- **지형 쓰기는 "사본을 고쳐 사각형만 넘기는" 한 길이다**(2026-10-15, `D2-5` (7), `TerrainComponent::writeHeights` · `writeLayerWeights`). 지형은 읽기용 배열을 내주고(`getHeightSamples` · `readSplatWeights`) 에디터 브러시(`TerrainBrush`)가 고친 배열에서 **바뀐 사각형만** 받는다. 샘플 세터나 브러시 타입은 Engine 에 두지 않고, 되돌리기는 편집 전 사본을 같은 사각형으로 다시 쓰므로 Undo 용 API 가 없다.
  읽는 쪽(병렬 틱 · 배치 계산)과 겹치지 않게 하는 방법은 이중 버퍼나 락이 아니라 **호출 규칙**이다 — 틱 밖(`executeOrDeferPostTickOnComponent`)에서 프레임에 한 번만 부른다(락은 질의마다 비용이 붙고, 이중 버퍼는 높이를 두 벌 들며, 스트로크는 어차피 프레임에 한 번).
  높이를 쓰면 닿는 청크(노멀 때문에 한 샘플 바깥까지)의 메시 · 바운드를 다시 만들고, 청크 세대(`getChunkGenerations`)를 올려 그 청크의 물리 바디만 다시 만든다(언리얼 랜드스케이프 컴포넌트별 충돌과 같다). 내비메시는 `SceneNavigation::invalidateArea` 로 그 타일만, 식생은 지형 세대가 0.3 초 그대로일 때 다시 뿌린다.

  - `SW_MATERIAL_NONE`(머티리얼 없는 사용자 — gbuffer · shadowdepth)은 머티리얼 구조체 · 읽기 · 오프셋 훅이 없고 알파 컷오프는 `#error` 다. 깊이만 쓰는 변형(`SW_MATERIAL_DEPTH_ONLY`)의 정점 → 픽셀 칸은 위치와 등장 디더뿐이다. 사용자 보간 칸 훅에는 읽기 전용 `clipPosition` 을 두고 그 훅에서만 채운다. 스프라이트의 픽셀 스냅은 월드 위치 오프셋이라 세 스프라이트 머티리얼이 `MATERIAL_VERTEX_DEFORM` 을 가진다. 머티리얼 없는 G버퍼 배치와 스프라이트는 보기 모드를 따른다.
  - 림은 `Lighting::computeRimLight` 한 곳이 가지며 디퍼드 값(pow3 × 0.12)이 기준이다.
  - 물은 그림자를 드리우지 않는다(2026-10-23 사용자 결정, 상용 엔진 기준). Unreal Water · Unity 물 모두 반투명 물의 기본이 그림자 끔이고 알파 블렌드 면이 그림자 맵에 불투명하게 찍히면 물 밑이 어두워진다. `water.material` 에 `MATERIAL_SHADOW_CAST_OFF` 를 더했다.
  - 게임 셰이더 하나의 쿠킹 산출물은 백엔드마다 180 파일(네 백엔드 720)이다. 패스 종류 × 머티리얼 퍼뮤테이션(포그 셋)을 모두 굽는다.
- **텍스처 임포트의 형식 이름은 `TextureImportFormatUtil::parse` 한 곳이 풀고, 1 채널은 `R8_UNORM` 으로 낸다**(2026-10-22). 설정 로드가 모르는 `format` 을 거절한다(예전에는 조용히 BC7 이 됨). `r8` 은 원본의 R 채널만 남기고 sRGB 짝이 없어 `srgb` 와 무관하게 UNORM 이다. R8 DDS 는 DX10 머리(`DDS_FLAGS_FORCE_DX10_EXT`)로 쓴다(`DDSLoader` 의 옛 머리 경로가 L8 을 모름, 다른 형식은 바이트가 안 바뀜). 규칙 표에 `Base_Mask` 프리셋과 `Mask_Textures`(`*_mask.*`) 규칙을 더했고 맞는 원본은 아직 없다.
- **셰이더 쿠킹의 "최신" 판정은 모든 `.hlsli` 해시 하나가 아니라 셰이더마다 컴파일러가 실제로 연 헤더로 한다**(2026-10-25). 공유 헤더 전체 해시를 섞던 때는 헤더 하나를 고치면 모든 셰이더가 다시 구워졌다. 컴파일러가 연 파일을 include 처리기(FXC `ID3DInclude::Open`, DXC `IDxcIncludeHandler::LoadSource`)가 컴파일 호출마다 적고(`ShaderCompileResult::_listIncludedFile`, 전이 포함), 쿠커가 소스별 합집합을 `cook.stamp` 5판에 `<해시> <소스>?<헤더 키>` 줄로 적는다. 판정(`isCookedOutputCurrent` · `--verify-shaders`)은 그 소스의 헤더만 다시 해시하고 헤더가 사라졌거나 읽지 못하면 낡음이며 옛 판(4)은 낡음이다.
  컴파일 디스크 캐시와 `ShaderCache` 로컬 캐시는 키가 컴파일 전에 필요해, 항목 옆 의존 기록(`.deps`)을 두고 맞출 때 헤더가 그대로인지 본다(없으면 미스). 인메모리 항목은 `ShaderCooker::computeSourceFingerprint` 로 비교한다. 전역 헤더 해시(`getSharedHeaderContentHash` · `computeEffectiveSourceHash`)는 지웠다.
  한계(코드 주석 `shortcut:`): 앞 순위 루트에 같은 이름의 헤더가 새로 생기는 경우는 최신 판정이 못 잡지만 `findShadowedHeaders` 가 컴파일과 `--verify-shaders` 에서 오류로 막는다. 컴파일 뒤 스탬프를 쓰기 전에 헤더를 고치면 그 변경이 "최신" 으로 들어갈 수 있다(옛 방식과 같은 창). 언리얼은 텍스트를 훑어 include 를 모아 DDC 키를 만들고 여기는 컴파일러가 실제로 연 파일을 쓴다(기억에 의존).
- **동기 업로드 대기는 "제출 → 티켓 → 폴링" 비동기 계약으로 옮기고, 프레임 경로에는 `waitIdle` 을 새로 만들지 않는다**(2026-10-25, [RhiAsyncUploads](../plans/RhiAsyncUploads.md)). 텍스처 업로드 둘과 되읽기의 동기 가상 함수를 RHI ABI 버전을 한 번 높여 지운다(백엔드 DLL 이 같은 vtable 을 봐야 하고, 옛 함수 위의 기본 구현은 폴백이 된다). 동기가 필요한 테스트와 도구는 ABI 밖의 `AndWait` 헬퍼를 쓴다. 새 머티리얼의 GPU 초기화는 렌더 스레드의 프레임 셋업 구간으로 옮기고, 머티리얼과 PSO 는 준비 전 / 준비됨 / 실패 상태를 데이터로 두어 준비 전에는 그리지 않는다. PSO 병렬 생성 기각(9 %, 드라이버가 직렬)과 충돌하지 않는다 — 목적이 렌더 스레드 임계 경로에서 빼는 것이라 생성 스레드는 하나다. 언리얼 `FRHIGPUFence` 폴링과 유니티 `AsyncGPUReadback` 폴링에 해당한다(기억에 의존).
- **프레임 경로의 전송은 기다리지 않고 티켓 + `pollTransfer` 로 끝낸다**(2026-10-25, rhiu9). 글리프 아틀라스(`CanvasRenderer`)와 텍스처 구간 갱신(`TextureCache::flushRegionUpdates`)은 `submit...` 만 내고, 새 아틀라스 페이지는 첫 업로드 티켓이 `Complete` 인 뒤 프레임에 bindless 등록해 그린다(한 프레임 늦게 보임). `Busy` 는 다음 프레임에 다시 내고 `Rejected` · `Failed` 는 오류를 남기고 그 자원을 멈춘다. 두 구간은 `RHITransferUtil::ScopedForbidBlockingTransfer` 로 표시해 `...AndWait` 가 들어오면 Debug 단언이 걸린다(형식이 막지 못한 GPU 왕복을 단언으로 지킴).
- **DX11 즉시 컨텍스트는 런타임 다중 스레드 보호(`SetMultithreadProtected( TRUE )`)를 켜고, 백엔드는 같은 임계 구역을 잡는 가드(`D3D11ImmediateContext::lock()`)로만 컨텍스트를 꺼낸다**(2026-10-25). 렌더 스레드의 프레임 스트림은 락 없이, 다른 스레드의 전송 · 폴링 · `waitIdle` 은 백엔드 뮤텍스 안에서 같은 컨텍스트를 써 서로 막지 못했다. 렌더 스레드가 프레임마다 뮤텍스를 잡는 안은 기각했다 — 다른 스레드가 프레임 하나(백프레셔 · Present 포함)를 기다리고 재귀 잠금이 필요하며 `getNativeContext` 로 나가는 ImGui 백엔드는 막지 못한다. 비용은 호출마다 경합 없는 임계 구역 하나다. 언리얼 · 유니티 D3D11 은 즉시 컨텍스트를 RHI 스레드 하나만 쓰지만 여기 계약은 "어느 스레드에서나 제출" 이라 따르지 못한다(기억에 의존).
- **GL 텍스처 되읽기는 영속 매핑 PBO 되읽기 링 하나로만 받는다**(2026-10-25, RhiAsyncUploads 2.2). 컨텍스트를 빌린 동안에는 `GL_PIXEL_PACK_BUFFER` 오프셋으로 `glGetTextureSubImage` · `glGetCompressedTextureSubImage` 와 펜스 하나만 내고, 바이트는 펜스가 지난 뒤 `takeTextureReadback` 이 컨텍스트 밖에서 매핑에서 복사한다. 장부는 업로드와 같은 `RHIStagingAllocator` 이되 구간은 가져갈 때(`free`)나 버린 읽기의 펜스가 지날 때(`markSubmitted`) 돌아온다. 링보다 큰 읽기는 `Rejected`, 가져가지 않은 읽기로 차면 `Busy`, GL 4.4 가 없으면 읽기는 모두 `Rejected` 이며 동기 `glGetTexImage` 경로는 남기지 않는다. 용량은 `gv_rhiReadbackRingMegabytes`(기본 64 MiB)이고 RHI ABI 를 36 으로 올렸다. 읽기마다 버퍼를 만들면 GL 이름 생성 · 매핑이 컨텍스트 점유에 들어간다(언리얼 GL 은 PBO + 펜스, 유니티 · Godot 은 요청마다 스테이징 + 폴링 · 콜백, 기억에 의존).
- **종류마다 뜻이 다른 `void*` 핸들은 종류 확인과 값 확인이 한 함수에 든 `[[nodiscard]]` 길로만 바깥에 내보낸다 — RHI 디바이스는 `queryNativeHandles( 기대 백엔드, … )` · `tryGetNativeTexturePointer( 기대 백엔드, … )`, 창 이벤트는 `NativeWindowEvent::tryGetWin32Window`**(2026-10-25, cifixl5). `IRHIDevice::getNativeDevice` · `getNativeContext` · `getNativeCommandQueue` · `getNativeTexturePointer` 와 이벤트의 창 핸들은 보호 · 비공개로 내렸다. 백엔드별 함수 대신 기대 백엔드를 인자로 받는 하나로 둔 것은 모듈 경계를 넘는 것이 버전 번호가 든 `RHINativeHandles` 하나라는 계약을 지키기 위해서다(`getBackendType()` 을 넘기면 확인이 없어지므로 호출처가 캐스트할 타입의 상수를 적음). 언리얼은 `GetNativeDevice()` 의 `void*` + `GetInterfaceType()` 두 단계라 같은 결함이 생길 수 있고, 유니티의 백엔드별 인터페이스가 이 결정에 가깝다(기억에 의존).
- **Vulkan 서피스를 만드는 길은 정수 코드가 아니라 `VulkanWsiKind` enum class 로 넘기고, `createSurface` 는 모든 값을 나열한 switch 로 만들며 이 플랫폼에서 못 만드는 값은 오류로 멈춘다**(2026-10-25, vkwsi). `NativeSurfaceKind` 는 X11 안의 xlib · xcb 를 가르지 못해 Vulkan 폴더에 따로 뒀다. 값은 실행 중 상태라 저장되지 않는다.
- **DX11 의 큰 텍스처 업로드는 장치가 초기 데이터로 만든 `STAGING` 텍스처로 올리고, 즉시 컨텍스트 잠금 안에서는 `CopySubresourceRegion` 과 이벤트 쿼리 `End` 만 한다**(2026-10-25). `UpdateSubresource` 는 소스 복사(수십 MiB)를 잠금 안에서 해 렌더 스레드의 `ExecuteCommandList` · `Present` 가 기다렸다. 스테이징 풀에 `Map( WRITE )` 로 쓰는 안은 기각했다 — `Map` · `Unmap` 이 즉시 컨텍스트 호출이라 잠금을 두 번 잡고 D3D11 에는 버퍼 → 텍스처 복사가 없어 풀이 크기 · 포맷마다여야 한다. `CreateTexture2D( pInitialData )` 는 스레드 안전한 장치 호출이라 잠금 없이 복사가 끝나고 대가는 업로드마다 할당 한 번이다.
  GL 의 `RHIStagingAllocator`(오프셋 링)는 맞지 않아 쓰지 않는다. 스테이징은 전송 큐 항목(`TransferProbe`)이 쥐어 워터마크가 지나면 놓고, 합의 상한은 `gv_rhiStagingRingMegabytes`(64 MiB)다 — 차면 끝난 전송을 모은 뒤 `Busy`, 장치를 잃으면 제출 진입에서 `Rejected`. `gv_rhiDirectUploadMaxKilobytes`(256 KiB) 이하는 `UpdateSubresource` 를 그대로 쓴다(글리프 아틀라스 구간 갱신이 이 아래, 두 값은 `RhiAsyncUploads` 측정 M1 이 정함). 언리얼 D3D11 도 생성은 초기 데이터 `CreateTexture2D`, 갱신은 RHI 스레드 `UpdateSubresource` 이다(기억에 의존).
- **DX11 업로드 스테이징 예산보다 큰 업로드 한 장은 `Rejected` 가 아니라 예산 전부를 잡고 혼자 들어간다. 텍스처 되읽기는 `Map` · `Unmap` 호출에만 즉시 컨텍스트 잠금을 잡고, 버퍼 구간 갱신은 잠금 안의 `UpdateSubresource` 그대로 둔다**(2026-10-25). 저장소 에셋의 가장 큰 업로드는 5.33 MiB 이지만 코드가 만드는 업로드(에디터 뷰 첫 채우기 4K 31.6 MiB · 8K 126.6 MiB, 렌더 타깃 미리보기 스냅샷 ultra 그림자 4096² 64 MiB · 8192² 256 MiB)는 화면과 설정에 따라 예산을 넘고, 예전 `UpdateSubresource` 는 이 크기를 받았다.
  기본값을 올리는 안은 상한이 없어 기각, 한 장을 밉 · 행 구간으로 쪼개는 안은 앞 조각의 GPU 완료를 제출 안에서 기다려야 해(제출은 기다리지 않는 계약) 기각했다. 혼자 들어가는 동안 다른 업로드는 `Busy` 라 메모리 최고점은 max(예산, 가장 큰 한 장)다. 언리얼 D3D12 업로드 할당자도 큰 할당은 전용 자원이다(기억에 의존).
  되읽기(`takeTextureReadback`): `Map` 포인터는 `Unmap` 까지 어느 스레드에서나 읽어도 되는 CPU 메모리이고 스테이징은 표에서 꺼낸 읽기 하나만 가지므로 행 복사를 두 잠금 사이로 뺐다. 버퍼 구간 갱신: 호출자(`GPUScene` · `GPUMeshVertexPool` · `GPUMeshMorphPool`)가 모두 렌더 스레드라 잠금 밖으로 빼도 프레임이 줄지 않으므로 GL 과 같은 이유로 둔다. `readReadbackBuffer` 도 같다. 새 메시가 들어오는 프레임에 다른 스레드의 대기가 보이면 측정으로 다시 연다.
- **엔진 밖으로 나가는 네이티브 컨텍스트는 잠금 안의 콜백(`IRHIDevice::withNativeContext`)으로만 주고, 스레드끼리 나눠 쓰는 RHI 상태는 그것을 바꾸는 쪽도 같은 락이나 atomic 으로 다룬다**(2026-10-25). `withNativeContext( 기대 백엔드, 콜백 )` 은 `[[nodiscard]] bool` 이고 다른 백엔드이면 콜백을 부르지 않는다. `RHINativeHandles::_pContext` 는 지웠다(판 3). DX11 은 즉시 컨텍스트 임계 구역을 쥔 채 콜백을 부르고 DX12 · Vulkan 의 프레임 커맨드 리스트와 GL 컨텍스트는 렌더 스레드 전용이라 잠금 없이 넘긴다.
  DX11 의 ImGui 렌더러는 텍스처 갱신과 보조 뷰포트 렌더를 렌더 스레드로 옮겼다(`requiresRenderThreadContext`) — 호출마다의 런타임 보호는 즉시 컨텍스트의 파이프라인 상태를 지키지 못해 UI 스레드가 프레임 중간에 렌더 타깃을 바꿀 수 있었다. 보조 뷰포트를 그린 뒤 백버퍼를 컨텍스트에서 뗀다.
  DX12 는 프레임 펜스의 Signal 과 값 올리기를 `_uploadSlotMutex` 안에서 한 덩어리로 한다. 락 밖이면 Signal(V) 뒤에 실행된 복사가 V 를 받아 그 펜스를 기다린 얼로케이터 Reset 이 도는 복사를 지울 수 있다. 텍스처 전송은 이 락 밖이다 — 전송마다 얼로케이터를 쥔 작업과 전용 전송 펜스, 전용 제출 락(`_transferSubmitMutex`)으로 큐에 바로 내고 해제는 전송 시리얼에 건다(`_transferReleaseQueue`). 펜스 대기 이벤트는 장치에 하나를 두지 않고 기다릴 때마다 만든다 — 자동 리셋 이벤트 하나를 렌더 스레드와 업로드 스레드가 함께 기다리면 남의 신호로 깨어난다.
  다른 스레드가 읽는 플래그(타임스탬프 스위치, DX11 의 쿼리 준비 표시, DX12 의 프레임 펜스 값 · 링 인덱스 · 로그 래치, Vulkan 의 프레임 슬롯, GL 의 타임스탬프 스위치 · 쿼리 준비 표시)는 `atomic` 이다. Vulkan 의 `_queueMutex` 는 이미 모든 제출이 같은 락이라 바꾸지 않았다. 언리얼은 ImGui 도 RHI 스레드의 커맨드로 그린다(기억에 의존).
- **스테이징 링 장부(`RHIStagingAllocator`)는 할당 순서가 아니라 구간마다 돌려받고, 빈 자리는 `SpanAllocator` 가 쥔다**(2026-10-25, RhiAsyncUploads 2.2). 순서로만 돌려받으면 가져가지 않은 되읽기 하나가 링 맨 앞을 막아 `readbackTexture2DAndWait` 가 10 초 시간 초과로 실패했다. 시리얼을 붙인 구간은 시리얼이 워터마크를 지나면 순서와 무관하게 돌아오고, 쥔 구간들이 남은 자리를 다 차지할 때만 `Busy` 다. DX12 · Vulkan 도 이 하나를 쓴다.
  기각: 가져가지 않은 읽기를 프레임 · 시간 상한 뒤 자동으로 버리기(티켓 계약을 바꾸고 RHI 에 프레임 시계를 들이며 막힘은 그대로, 유니티 `AsyncGPUReadback` 은 그 프레임 안에서만 유효, 기억에 의존), "티켓을 쥔 채 `AndWait` 금지" 를 `ScopedForbidBlockingTransfer` 로 거는 안(같은 스레드만 막는다). 빈 자리 관리는 정점 풀의 `SpanAllocator`(언리얼 `FSpanAllocator`)를 그대로 쓴다.
- **티켓을 쥔 채 제출하는 `...AndWait` 는 `PendingReadback` 이 쥔 수로 Debug 에서 막고, 장치 손실 뒤 로그는 `markLost` 가 처음 표시했을 때만 남긴다**(2026-10-25). 쥔 티켓들이 스테이징을 다 차지하면 `submitWhileBusy` 가 10 초 시간 초과로 실패하는 모양이 남아 있었다. `PendingReadback` 이 스레드마다 쥔 수를 세고 `...AndWait` 가 제출 전에 0 인지 단언한다. 한계: 다른 스레드가 쥔 티켓과 `PendingReadback` 에 넣지 않은 날 티켓은 세지 못한다. 손실 뒤 매 프레임 도는 GL `retireFinishedTransfers` · DX12 `signalExportedTransfers` 의 오류 로그는 처음 표시했을 때만 남긴다. 상용 엔진 비교는 확인하지 못했다.
- **스테이징 링보다 큰 전송 한 장은 장부(`RHIStagingAllocator`)가 링이 비었을 때만 단독 구간으로 내주고, 백엔드는 그 크기의 일회성 버퍼에 받는다**(2026-10-25, RhiAsyncUploads 2.2). GL 이 링(64 MiB)보다 큰 업로드 · 읽기를 `Rejected` 해 에디터 6K+ 뷰 첫 채우기(77.7 MiB), ultra 그림자 스냅샷(64 MiB 이상)이 회귀했다.
  링 용량보다 크고 단독 상한(`gv_rhiStagingSingleMaxMegabytes`, 기본 512 MiB, 0 이면 받지 않음) 이하인 요청은 링에 산 구간이 0 일 때만 `_bSolo` 구간이 되고 그동안 다른 요청은 `Full`(`Busy`)이라 메모리 최고점은 max(링, 가장 큰 한 장)다. 상한을 넘으면 `TooLarge`(`Rejected`)이고 설정 이름을 로그로 알린다. DX11 은 자기 예산 카운터로 같은 조건을 이미 쓴다. GL 은 단독 구간마다 `glBufferStorage` 영속 매핑 버퍼를 만들고(할당 때만 컨텍스트를 빌림) 장부가 돌려받은 뒤 `retireFinishedTransfers` 가 지우며 메모리 장부 Staging 에 올리고 내린다.
  굶주림은 예약으로 막는다 — `Full` 을 받은 단독 요청은 250 ms 예약을 남겨 그동안 새 링 요청도 `Full` 이고 다시 올 때마다 연장되며 단독 구간을 내주면 끝난다. 링이 빌 때까지 예약하면 가져가지 않은 되읽기가 링을 비우지 않아 작은 읽기가 영원히 `Busy` 이고, 거절 횟수로 끝내면 호출자 수와 빈도에 따라 뜻이 바뀌기 때문이다. 한계: 포기한 단독 요청은 링 요청을 최대 250 ms 막고, 쥔 되읽기가 있는 동안 기다리는 단독 읽기는 그 호출자의 시간 초과까지 다른 읽기를 막는다.
  기각: 기본 링을 키우기(한도 없는 크기가 남음), 한 장을 쪼개 여러 번 내기, 호출마다 단독 허용 플래그(모든 호출자가 같은 답이라 `initialize` 에서 한 번 정함). 유니티 Async Upload Buffer 는 큰 텍스처가 오면 버퍼를 그 크기로 늘렸다 줄인다(기억에 의존).
- **종류 · 모드를 숫자 코드로 받던 전역 변수는 리플렉션 enum 으로 바꾸고, 명령줄은 열거자 이름만 받는다 — `gv_rhiBackBufferFormat`(`RHIBackBufferFormat` RGBA8 · BGRA8), `gv_lightCulling`(`LightGridProducer` None · CPU · GPU), `gv_viewMode`(`RenderViewMode`)**(2026-10-25, bbfmt). 전역 변수는 enum 을 이미 지원해(`GlobalVariableTraits` 의 enum 특수화) `SW_GLOBAL_VARIABLE` 의 첫 인자만 enum 이면 됐다. 숫자 폴백을 두지 않으려고 Core 에 `GlobalVariableInfo::setValueFromCommandLine` 을 더했다: 명령줄 글이 enum 변수에 숫자로 들어오면 이유를 담은 오류로 멈춘다(`applyPendingEnumText` 가 기동을 실패시킴). `-gv_rhiBackend=2` 처럼 enum 이던 변수의 숫자 인자도 같이 오류가 된다(저장소 안 사용처 없음).
  에디터 · 콘솔 · 프리셋 · 사용자 설정 · 자동화의 `setValueFromString` 은 숫자를 계속 받는다 — 값 왕복과 `targetValue` 가 이 글에 기대고 프로그램끼리 주고받는 글이기 때문이다. 대신 범위 밖 값은 쓰는 곳이 거른다. 언리얼 콘솔 변수는 정수 코드라 순서가 바뀌면 조용히 달라지고, 유니티 · Godot 은 이름으로 고르는 쪽이라 이 결정과 같다(기억에 의존).
- **켜고 끄는 전역 변수는 `bool`, 코드의 "덮어쓰지 않음" 은 `-1` 센티널이 아니라 `std::optional` 이다 — `gv_rhiSoftwareAdapter` · `gv_gpuCulling` · `gv_drawMerge` · `gv_vertexPool` · `gv_textureStreaming` · `gv_gpuUploadQueue`(bool), `FrameDebugOverrides::_drawMerge` · `_vertexPool`(`std::optional<bool>`)**(2026-10-25, gvnum2). int32 는 2 이상의 값도 받아 `!= 0` 으로 읽혔고 -1 센티널은 `>= 0` 비교를 호출마다 되풀이하게 했다. 명령줄 `=0`/`=1` 은 `tryParseBool` 이 받는다. 환경 변수 `SW_RHI_SOFTWARE_ADAPTER` 도 같은 `tryParseBool` 로 읽고 알 수 없는 값은 `IRHIDevice::initialize` 가 이유를 남기고 실패한다(폴백 금지). 남긴 것: 수준 · 개수 값(`gv_validateBindlessIndex`, `gv_textureMipDrop`, `gv_renderViewBudget`)은 그대로, `gv_memoryTracking`(-1 구성 기본/0/1)은 셋째 값이 있어 Core 영역의 후속 후보다. 언리얼 `r.` 변수는 정수 0/1 이고 유니티 · Godot 은 bool 이라 후자를 따른다(기억에 의존).
- **DX11 텍스처 되읽기를 가져올 때(`takeTextureReadback`)는 이벤트 쿼리가 지난 뒤에도 `D3D11_MAP_FLAG_DO_NOT_WAIT` 없이 기다리는 `Map` 으로 읽는다**(2026-10-25, `readReadbackBuffer` 도 2026-10-26 같게). 쿼리가 복사 뒤를 지났는데도 `DO_NOT_WAIT` 가 `DXGI_ERROR_WAS_STILL_DRAWING` 을 돌려 끝난 티켓을 못 읽었다(`RHIDeviceTest.SlicedTexturesTargetUploadAndReadBackPerSlice` 가 Release 1/1 · Debug 3/3 졌고 고친 뒤 Debug 5/5 통과). 런타임 · 드라이버의 자원 추적이 쿼리 완료보다 늦게 풀리는 것으로 본다(추정). 기다리는 `Map` 은 그 추적만 맞추고 곧 돌아오며 장치를 잃으면 오류로 바로 돌아온다. 언리얼 D3D11 의 스테이징 읽기도 쿼리 뒤 기다리는 `Map` 이다(기억에 의존). 한계: `WaitIdleLeavesTheSubmittedCopyReadableOnEveryBackend` 의 DX11 탐침은 기다리는 `Map` 에 가려져 약해진다(내용 검사는 그대로, 다른 세 백엔드 탐침은 그대로).
