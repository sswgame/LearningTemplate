# 5-4. 데이터, 직렬화, 설정

> 질문: 5-4. 데이터, 직렬화, 설정 영역에서 이미 정한 것은 무엇이고 근거는 무엇인가?
> 독자: 같은 제안을 다시 하려는 사람, 정한 이유를 찾는 사람.
> 결론: 결정 기록 5 절의 한 영역이다. 번호 체계와 쓰는 법은 [결정 기록](../09_Decisions.md) 5절에 있다.

- **엔진 데이터에는 별칭을 두지 않습니다**(2026-10-03). 출시한 게임 데이터가 없으므로 이름을 바꾸면 데이터를 다시 씁니다. 옛 `SaveGame` 파일도 읽지 않습니다. 계약은 Serialization README 에 있습니다.
  - 이 결정은 지금 이관할 데이터가 없다는 사실에 기댄 것이지 영구 금지가 아닙니다(사용자 확인, 2026-10-17). 출시한 데이터가 생겼을 때 바로 쓰도록 별칭(`Alias` · `ValueAlias` · `Removed`)은 미리 갖춥니다. 기능은 갖추되 이관할 출시 데이터가 생기기 전에는 제품 데이터 · 게임 코드에 별칭을 두지 않습니다(2026-10-18 사용자 결정).
- **첫 출시 전에는 이관 없이 데이터를 다시 쓰고, 판은 정확히 같을 때만 읽습니다**(2026-10-23 사용자 결정). 형식이 바뀌면 저장소의 데이터를 다시 쓰고, 옛 판 리더 · 이관 함수 · 판 범위 읽기를 두지 않습니다. 판이 다르면 오류로 멈춥니다. 근본 원인은 판 번호를 범위로 받는 API 라서 정확 일치 형식만 남겼습니다(`SW_SCHEMA_MIGRATION` · `SchemaMigrationRegistry` · `deserializeVersioned` · `legacyTypeInfo` · `readHeaderInRange` 등은 지웠고, XML 판은 `AssetXMLFormat::isCurrentXMLVersion` 이 정확 일치만 봅니다).
  - 남긴 것은 호환 분기가 아니라 계약이거나 출시 뒤에도 필요한 것입니다: `BinaryWireVersion`, orphan 정책(`SchemaOrphanPolicy` — 텍스트 Ignore · 바이너리 Reject), 네트워크 `combine` 버전, 서버 레코드 판 거절, SQL 마이그레이션 번호, 팩 형식 거절, 쿠킹 기록의 "옛 형식은 읽지 않고 다시 굽는다", 사용자 설정 `<Upgrade>` 체인. 호환 의무는 출시를 자르는 순간부터이고 그때 판 번호를 기준값으로 굳힙니다.
  - 같은 버전에서 지운 필드를 버려도 되는지는 orphan 정책이라 호출부가 컨텍스트로 정합니다(`setAllowUnknownProperties`, 오브젝트 상태만 켬).
- **설정 파일에는 기본값과 다른 값만 적습니다**(2026-10-06). 언리얼 `Default*.ini` 와 같은 규칙이고 `ConfigFileSchemaTest` 가 기본값을 다시 적은 키를 막습니다.
- **설정 값의 출처는 하나씩입니다**(2026-10-06). 시작 씬은 팩의 `gamesettings.xml`, 창 제목은 `GameConfig::_windowTitle`(언리얼 ProjectName), 고정 스텝은 `EngineConfig::_fixedDeltaTime` 이고 물리는 그 위에 서브스텝 수(`_subStepCount`)만 둡니다(유니티 `Time.fixedDeltaTime` 과 같음). 기본 RHI 도 한 곳에만 적습니다.
- **앱이 다시 쓰는 에디터 상태는 `Saved/Editor/` 에 둡니다**(2026-10-06). `Config/Editor/` 에는 사람이 쓰는 설정만 남깁니다.
- **텍스처와 모델 임포트 설정은 키 테이블입니다**(2026-10-06). 리플렉션 구조체로 만들지 않았고 `PROPERTY( Config )` 메타도 지웠습니다. 엔진 타입에 키트 설정 필드를 두지 않고 키트 설정은 팩 데이터에 둡니다.
- **자체 JSON 로더를 리플렉션 구조체로 옮기는 기준**(2026-10-12). 모듈 매니페스트 · `AnimationLODSettings` · `MemoryBudgetFile` · `FacialRig` · `LipSync` 는 옮겼습니다. 옮기지 않는 것: `TextureImportConfig` · `ModelImportConfig`(적지 않은 값이 부모 프리셋을 따르는 "적지 않음" 의미가 필요한데 리플렉션은 "없음" 과 "0" 을 못 가름), `CrashReportService`(동적 JSON), JWT · Chrome 트레이스 · VRM(외부 형식), `CultureInfo`(부모 문화권을 따름), `LocalizationDocuments`(키가 데이터인 표), `AnimationGraphAsset`(노드 종류마다 필드가 다른 그래프)(2026-10-14 R4 판정).
- **자체 포맷 에셋 로더 넷도 리플렉션으로 읽고 씁니다**(2026-10-17, C-19 R4). `SpriteClipAsset` · `SequenceAsset` · `DialogueGraphAsset` · `Skeleton` 은 키가 PROPERTY 이름이고 저장소 데이터는 새 키로 다시 썼습니다(별칭 없음, 스켈레톤은 `--import-models` 로 다시 만듦). "적지 않음" 을 초기값으로 읽으면 안 되는 칸(스켈레톤 전부, 대화 노드 · 링크 id 와 핀)은 `PROPERTY( Required )` 로 두어 빠지면 오류입니다(`ConfigManager::readConfigJSON` 이 구조체 칸과 목록 원소 안까지 봄). 종류(시퀀스 항목 · 트랙, 대화 노드)는 열거자 이름이고 모르는 종류를 건너뛰거나 Dialogue 로 읽던 폴백은 없앴습니다. 범위 밖 프레임 번호도 오류입니다(스프라이트 구간이 프레임 밖이면 자르고 알림만 남김 — 에디터가 프레임을 지운 뒤 저장할 수 있음).
- **`sw::vector<bool>` 은 쓰지 못하고 불 목록은 `DynamicBitset` 입니다**(2026-10-17, A-18). 같은 이름이 구성마다 다른 의미(바이트 vs 비트 묶음)였고 STL 구성에서 리플렉션 래퍼가 원소 주소를 잡지 못해 컴파일이 멈췄습니다. `VectorElementCheck` 가 두 구성에서 같은 `static_assert` 로 막습니다. 언리얼 `TArray<bool>` 은 바이트 배열이고 비트 묶음은 `TBitArray` 입니다. 리플렉션은 `DynamicBitset` 을 값 하나로 다룹니다(자기 기술형은 '0' · '1' 글, 고정 배치형은 `MaxCount` 가 필요한 `bits`).
- **`SW_ENABLE_STL_CONTAINER` 가 구성마다 바꾸는 것은 컨테이너 기본 할당자 하나입니다**(2026-10-24, `StlContainerConfig`). 목적은 "엔진 할당자 대신 `std::allocator`"(메모리 추적 빼기)로 읽었습니다. `vector` · `array` · `pair` · `map` · `set` · `span` · `unordered_map` · `unordered_set`(밀집 배열 구현, A-20) 은 두 구성 모두 자체 구현이고 `string` · `list` · `deque` 는 두 구성 모두 경합 탐지를 얹은 `std::*` 파생입니다. 바뀌는 것은 `ContainerAllocator<T>`(`Memory.h`)뿐이고 `InlineAllocator` 도 두 구성에서 같은 SBO 구현입니다. 이유: 같은 이름이 구성마다 다른 형식이면 한 구성에서 맞는 코드가 다른 구성에서 달라집니다(`vector<bool>` · 해시 순회 순서). `string` · `list` · `deque` 를 `std::*<T, 할당자>` 별칭으로 줄이지 않은 것은 경합 탐지(디버그)를 잃기 때문입니다. 표준 컨테이너 비교나 디버그 STL 검사가 목적이었다면 되돌립니다 — 사용자 확인을 기다립니다. STL 구성에서만 건너뛰는 테스트는 할당자에 기대는 것(`MemoryTagTest` 둘, `PrimitiveMeshIsTaggedMesh`)뿐입니다. 언리얼 `TMap` 도 밀집 배열이고 표준 컨테이너로 바꾸는 구성이 없습니다.
- **메모리 태그 통계의 해제는 센 블록만 뺍니다**(2026-10-18, A-24). `IAllocationTracker::recordAllocation` 이 `AllocationRecord{ 해시, _bCounted }` 를 돌려주고 할당기는 센 블록 헤더에 기록기 번호(`getTrackerID`)를 적어 그 기록기에만 해제를 넘깁니다. 추적을 켜기 전에 잡은 블록을 켠 뒤 풀면 태그 바이트가 음수로 어긋났습니다. 헤더 크기(48 B)는 그대로이고 해제마다 비교 하나가 늡니다. 언리얼 LLM 도 할당 때 추적한 포인터만 뺍니다.
- **누수는 "창 안에서 태어나 닫힐 때 살아 있는 블록" 으로 잽니다**(2026-10-24, [LeakDetection](../plans/LeakDetection.md)). 기준선 뒤의 살아 있는 양 차이로 재면 창 밖의 오래된 블록을 풀 때 새 누수가 상쇄됩니다. `AllocationRecord` 에 `_windowStamp`(uint32)를 두고 블록 헤더 패딩 6 B 를 `uint8[2] + uint32` 로 나눠 헤더는 48 B 입니다. `Memory` 는 스탬프의 뜻을 모르고 해제 때 돌려주기만 하며 창은 `MemoryProfiler::beginLeakWindow` · `endLeakWindow` 가 맡습니다. 태그별 기준선 배열은 이 창의 한 인스턴스(`TagTotals`)로 합쳤고 짧은 창은 모든 할당의 스택을 잡는 `FullStacks` 입니다. 전수 캡처 비용과 한 씬 로드의 할당 수는 측정으로 정합니다(계획 문서 L2).
- **설정 JSON · 데이터 XML · 세이브가 같은 `Min` · `Max` 를 한 계약으로 지킵니다.** 프리셋 표가 원소마다 따로 부르던 검사는 지웠습니다.
- **범위는 인스펙터와 읽기가 한 함수로 풀고, 소프트 읽기는 실패를 둘로 가릅니다**(2026-10-18, C-56 · C-60 · C-62). `PropertyMetadata::computeAllowedRange` 가 숫자 경계와 필드 경계(`Min = "-_halfSize"`)를 함께 풉니다(필드 경계 읽기 함수는 Shipping 에도 있음). `GameDataXML::readFields` 의 자체 범위 검사는 지웠습니다. `deserializeSoft` 는 `SoftReadResult`(`NotParsed` · `Rejected` · `Read`)를 돌려줍니다 — `bool` 일 때는 범위 밖 값에서 바로 돌아가 같은 파일의 모르는 키를 알리지 않았고 범위 밖 값을 "JSON 이 아니다" 로 알렸습니다. 이제 `NotParsed` 만 바로 돌아가고 `Rejected` 는 orphan 을 모두 알린 뒤 실패합니다. float32 로 보관하는 숫자 경계를 float64 칸과 견주는 어긋남은 그런 칸이 하나(`MemoryBudgetMonitor::_megabytes`, `Min = 0.0`)뿐이라 형식을 바꾸지 않았습니다.
- **이름 읽기(`XMLReadUtil::readOptionalName`)는 글 `none` 을 오류로 알립니다**(2026-10-18, C-59). `hashed_string` 은 언리얼 `FName` 처럼 `none` 을 빈 이름과 같게 보고 빈 이름의 `c_str()` 은 "None" 이라, 열거형 글(`align="none"`)이 "적지 않음" 이 되고 적지 않은 경로가 "None" 이 됐습니다. 이름 형식을 바꾸면 리플렉션이 빈 이름을 "None" 으로 쓴 씬 · 프리팹(100 곳 넘음)과 열거자 `None` 이 함께 바뀌므로 이름 읽기 창구가 그 글을 오류로 막고 그런 속성은 글로 읽습니다. 경로로 쓰는 이름은 비었는지 먼저 봅니다.
- **열거자 이름의 정본은 리플렉션 `ENUM()` 입니다**(2026-10-15, 10-12 의 "enum 이름 테이블 45 곳 유지" 를 뒤집음). 철자가 열거자 이름과 같은 손 이름 표 · `toString( Enum )` 은 지우고 `getEnumName( value )`(`Engine/Reflection/EnumName.h`)로 읽습니다(언리얼 `UENUM` + `UEnum::GetValueAsString`, Godot ClassDB 와 같은 방향). 손 표는 `static_assert` 가 개수만 지키고 순서 · 철자 어긋남은 못 막았고 쓰는 곳이 거의 로그라 인덱스 속도의 이득이 없습니다. 남기는 것: 철자가 다른 와이어 · 데이터 · 지표 문자열(`AdminRole` 의 `"viewer"` 등, `EnumNameTable` 로 읽는 데이터 이름)과 Core 의 열거형(Core 는 리플렉션 아래 티어)입니다. 데이터에 박힌 이름 표를 옮기려면 데이터를 열거자 철자로 다시 씁니다.
- **같은 빌드끼리만 읽는 바이트는 고정 배치형(B) 코덱이고 생성기가 모든 적격 `REFLECT` 타입에 만듭니다**(2026-10-17, [고정 배치형 코덱 계약](../../Source/Engine/Serialization/Fixed/README.md) 단계 1). 사용자는 B 를 선언하지 않고 등록 API 가 `FixedLayout::findCodec` 으로 확인합니다. 세이브와 에셋은 자기 기술형(A) 그대로입니다. 언리얼 `NetSerialize` · Iris 디스크립터처럼 선언(`UPROPERTY`)에서 와이어 형식을 도출하고, 손 버전 상수 대신 정규 문자열 해시가 형식 변경을 잡습니다. 세부:
  - 버전 상수는 `FixedLayout::kVersion`. 읽기 결과에 `TrailingData` 를 더했습니다(남은 비트를 `OutOfRange` 로 부르면 원인이 섞임).
  - `float64` 는 64 비트 원본이고 `Step` 은 float32 에만 붙습니다. 정수 경계는 float32 로 정확히 나타나야 합니다(크기가 아니라 정확성이 기준).
  - 수학 타입은 `ParserDefines.h` `fixedlayout::kArrMathType` 목록으로 정합니다(구조에서 추측하면 핸들처럼 모양만 같은 타입까지 적격이 됨). `vector<string>` 처럼 가변 길이가 두 겹이면 `MaxCount` 하나로 정할 수 없어 적격이 아닙니다. `MaxCount` 는 애노테이션 `count` 로 1 이상의 정수만 받습니다.
  - 다른 헤더의 중첩 · 기반 타입은 실행 시간에 코덱을 찾아 의존을 한 번 확인합니다. 코덱이 없는 타입을 진입점에 넘기면 이유를 로그에 남기고 프로세스를 멈춥니다(0 해시 같은 대체 값은 핸드셰이크 해시에 섞임).
  - 양자화 읽기는 칸 번호가 칸 수를 넘으면 `OutOfRange` 이고 `BitReader::readQuantizedFloat` 도 같은 규칙입니다. `BitWriter::writeInt` · `writeQuantizedFloat` 는 범위 밖이면 쓰지 않고 `false` 입니다.
  기각: 대상 타입을 사용 자리에서 모으는 길(`.cpp` 를 생성기 입력에 넣기, 등록 목록 파일)은 `.cpp` 수정마다 생성기가 다시 돌고 계층이 거꾸로 되며 목록 원본이 둘이 되어서, 필드 속성(`Replicated` 등)에서 도출하는 길은 그 속성이 "어느 필드를 보내는가" 만 말하고 롤백은 모든 필드가 필요해서입니다. 적격은 `REFLECT` 454 개 중 173 개(나머지는 `MaxCount` 없는 가변 길이와 표 밖 타입)이고 Debug 실행 파일은 `Engine.dll` +0.7 % · `GameFramework.dll` +1.0 % 였습니다.
- **이름 변경 리다이렉트는 선언 옆에 적고 리다이렉트 표는 그 이름의 주인이 듭니다**(2026-10-17, R1~R4). 타입 · 열거형의 옛 FQN 은 `REFLECT( Alias )` · `ENUM( Alias )`, 열거자는 `ENUM( ValueAlias = "Old:New" )`, 지운 열거자의 대체는 `ENUM( Removed = "Old:Replacement" )`, 필드는 `PROPERTY( Alias )` 입니다. 유니티 `FormerlySerializedAs` 처럼 이력이 선언 옆에 있고 언리얼 `CoreRedirects` 처럼 호출부는 모릅니다. 다만 표를 전역 하나로 모으지 않고 `EnumInfo::_mapRedirectNameToValue` · `PropertyInfo::_listAlias` · `TypeRegistry` 별칭 표에 둡니다 — 언리얼이 전역인 것은 리다이렉트가 ini 에서 오기 때문이고 여기서는 선언이 등록과 함께 오므로 주인에 붙여야 상속 필드 복사 · 핫 리로드 재등록 · 모듈 해제 묘비를 그대로 따릅니다.

| `WeakInternTable` → `WeakSharedTable` | `Intern` 은 `hashed_string` 과 같은 쓰임 |
| 열거형 `Auto` · `Normal` · `Custom` · `Count` | 열거형 안에서만 뜻이 서고 문맥이 분명하다(`Misc = 0`(`HorrorCatalog.h`) 하나만 `None` 으로 바꿈) |
| 통지 동사(`notify` · `broadcast` · `publish` …) 규칙화 | 추정에 그친다 |

약어 철자 · 어휘표 · 접미사는 docs/agents/NamingCpp.md "Function names" 와 [코딩 규칙 예시](../04_CodingGuidelines.md) 2 절에 있다.

- **저장 목적은 문맥의 필수 값이다**(2026-10-18, C-53). `SerializeContext` 는 `SerializePurpose`(Authoring · Snapshot · SaveGame)를 생성자로만 받고 기본 문맥도 `getDefault( purpose )` 로 목적을 말해야 얻는다. 필드 규칙(`Transient` · `RuntimeState` · `SaveGame`)은 `SerializerUtil::shouldSerializeProperty` 한 곳이 세 형식(XML · JSON · 바이너리)에 같게 정한다. 리플렉션 직렬화기의 문맥 기본 인자는 `getDefault( SerializePurpose::Authoring )`(파일 입출력 도우미라 저작 형식이 계약)이고, 오브젝트 상태(`ObjectStateSerializer`)는 기본 인자 없이 목적을 받는 `ObjectSaveOptions` · `ObjectLoadContext` 로만 쓰고 읽는다. 에디터 되돌리기 · 복사 · 복제 · "시뮬레이션 변경 남기기" 는 Authoring 이다(언리얼 복사도 `TextExportTransient` 를 뺀다). 게임 상태 봉투는 핫 리로드(Snapshot)와 세이브(SaveGame)가 함께 쓰므로 부르는 쪽이 목적을 넘긴다. 컴포넌트 필드에는 `RuntimeState` 만 붙이고 `SaveGame` 을 함께 붙이지 않는다(붙이면 그 타입이 옵트인 세이브가 되어 씬 오브젝트 전체 세이브에서 나머지 필드가 빠짐). 런타임 값이 저작 값에서 시작하면 "남은 수" 가 아니라 "쓴 수" 를 둔다(`GatheringNodeComponent::_usesTaken`).
- **녹화 시나리오는 `saved` 도메인의 id 로 다시 돌린다**(2026-10-22). 시나리오 실행은 `Saved` 를 디스크 도메인 `saved` 로 붙이고(`ScenarioRecorder::mountSavedDomain`) 녹화는 디스크 경로로 쓰고 `makeReplayID` 의 id 로 읽는다. 시나리오 목록에 디스크 입구를 두는 안은 입구가 다시 둘로 갈라져 기각했다(Godot `res://` · `user://` 가르기와 같은 자리).
- **에셋 파일 형식은 XML 이나 바이너리이고 JSON 은 도구 입력 · 설정 · 사용자 상태다**(2026-10-22, 구조 단순화 TX5~TX7). 스켈레톤 · 리그 · 애니메이션 그래프 · 본 마스크 · 스프라이트 클립 · 얼굴 · 비즘 · 대화 · 시퀀스 · 지역화 문서 · VRM 아바타 · SQL 마이그레이션 목록 · 애니메이션 조정 표를 XML 로 옮겼고 옛 JSON 리더는 두지 않았다. 로더는 리플렉션 구조체(`ConfigManager::readConfigXMLElement`)이거나 `XMLNode` 로 손으로 읽는 것(`XMLReadUtil::hasOnlyKnownNames` · `readFloatList`)이다. 형식은 `AssetTypeRegistry::isSuffixFormatAllowed` 로 굳혔다(`.json` 접미사는 쿠킹 입력으로만 등록). **변환한 데이터는 엔진이 다시 쓴 결과와 바이트가 같아야 한다**: 속성값의 `>` 는 이스케이프하지 않고(본문 글은 한다) 120 바이트를 넘는 여는 태그는 속성별로 접는다. 놓치면 `--gather-text` · 재임포트가 파일을 다시 쓰고 `--check-text` 가 낡았다고 한다.
- **셰이더 도메인 목록은 설정 데이터에서 발견한다 — 코드는 include 루트 종류(engine · common)만 안다**(2026-10-23, 머티리얼 셰이더 훅 D1). 정본은 `Config/Engine/EngineConfig.json` 의 `_listResourcePriority` 이고 `game` 토큰은 `game/` 아래 폴더를 훑어 `game/<이름>` 으로 펼친다(엔진은 게임 이름을 모른다). 게임 셰이더의 include 루트는 자기 도메인 + engine + common 이다. 목록이 비었거나 종류가 빠지면 기본값 없이 오류로 멈추고 게임 폴더의 같은 이름 헤더가 include 루트의 헤더를 가리면 컴파일 · 스탬프 쓰기 · 판정이 오류로 멈춘다(`ShaderCooker::collectShaderDomains` · `collectIncludeRootDomains` · `findShadowedHeaders`).

- **기믹 회로 상태는 씬 · 프리팹 · 세이브에는 A, 체크포인트 · 롤백 · 넷 스냅샷에는 B 로 쓰고 둘은 같은 `REFLECT` 선언 하나에서 나옵니다**(2026-10-17~20). 근본 원인은 상태 바이트의 크기를 쓰는 쪽과 읽는 쪽이 따로 손으로 계산했고 회로 해시 하나가 상태 전체의 수용 여부를 정한 것이었습니다. `GimmickNodeState` 는 `_id` · `_kind` · `_stateVersion` · 노드별 실수 · 정수 슬롯 목록을 갖고 `GimmickCircuit::loadState` 는 `GimmickStateMatch`(`Exact` · `NodeSetChanged` · `Mismatch`)를 돌려줍니다. `Mismatch` 는 같은 id 인데 종류 · 종류 상태 버전(`GimmickNodeKind::_stateVersion`, 기본 1) · 슬롯 수가 다르거나 같은 id 가 둘일 때뿐이며 새 노드는 처음 상태로 두고 저장에만 있는 노드는 버립니다. 저장 상태 적용은 `GimmickCircuitComponent::applySavedState` 한 함수(`NodeSetChanged` 는 경고 뒤 이어 가고 `Mismatch` 는 오류를 남기고 회로를 비움)이고 롤백 · 넷은 `restoreState` 로 `Exact` 만 받습니다. 상한은 노드 1,024 · 종류마다 슬롯 32(`registerKind` 가 거절)이고 정본은 C++ 상수 + `PROPERTY( MaxCount = kMaxSlotCount )` 입니다. `GimmickNodeState` 의 뜻이 바뀌는 변경은 종류의 상태 버전을 올리고 데이터를 다시 씁니다. 모르는 XML 요소(옛 `_stateBytes`)는 건너뛰고 로드마다 경고합니다(`SchemaOrphanPolicy::Ignore`). 측정은 [검증과 측정](../08_Verification.md) "기믹 회로 상태", 결정성은 `SameInputsSameStateHash` 로 확인했고 옛 코드 대비 바이트 동일성은 보증하지 않습니다.
- **`isDerivedFrom` 은 조상 디스플레이 테이블을 그대로 두고 DFS 구간 번호는 채택하지 않습니다**(2026-10-17). 디스플레이도 O(1)(원자 로드 네 번과 비교 한 번, 깊이 8 `kAncestorDisplayDepth` 초과나 테이블이 없으면 `isDerivedFromSlow`)이라 구간 번호가 줄이는 것은 원자 로드 두어 번뿐입니다. 구간 번호는 전체 타입 트리를 깊이 우선으로 번호 매겨야 해서 타입 추가(DLL 로드 · 핫 리로드 · 플러그인)마다 다른 번호가 바뀌고 코드 생성기는 모듈 하나만 보므로 전역 번호를 빌드 시간에 못 정합니다. 남은 캐스트 비용의 근본 원인은 타입 없는 핸들과 씬 전체 순회였고 타입별 컴포넌트 목록과 `TComponentHandle<T>` 로 풀었습니다(5-6).
- **엔진 설정 · 게임 프리셋 · 2D 렌더 설정은 정적 활성본(`getActive`)이 아니라 소유 서브시스템이 들고 서비스 표로 읽습니다**(2026-10-25, ArchitectureSeams 3 단계). 언리얼 `GEngine->…Settings`(전역 CDO) · 유니티 `ProjectSettings` 는 전역이지만 여기서는 핫 리로드 · 다중 월드 · 테스트 격리가 목적이라 소유자를 둡니다. `EngineConfig` · `GameConfig` 는 `ConfigManager` 가 생성자에서 자리를 만들어 읽은 값을 담고(다시 읽기도 제자리 — 서비스 표 칸의 주소가 같음) `Render2DSettings` 는 `Render2DSettingsSubsystem` 이 기동에서 읽어 소유합니다. 읽는 쪽은 `engine::getSubsystem<T>()`, 테스트는 `ScopedEngineServiceOverride::bindObject` 입니다. 서비스 표에 못 닿는 에디터 · 게임 프레임워크 호출처는 `GameConfig::getActive()` 전달 창구를 쓰며 `editor::` · `game::` 창구로 옮기면 지웁니다. `CheckServiceAccess` 는 정적 사본의 참조를 돌려주는 `static const T& getActive()` 도 활성 창구로 셉니다(예외 표의 `PendingScopeMove` 는 영구 예외가 아니라 이전 대기).
