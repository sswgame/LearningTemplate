# 입력 맵 묶음

> 질문: 게임의 입력 맵은 어떤 파일로 이루어지고, 액션 이름은 어떻게 짓는가?
> 독자: 게임 · 키트의 입력을 더하거나 고치는 사람과 에이전트.
> 결론: 게임은 `gamesettings.xml` 의 `<inputMap path="…"/>` 줄들로 기본 맵, 공통 파일, 게임 차이를 쌓는다. 같은 뜻은 접두어 없는 한 이름을 쓰고, 한 게임만 쓰는 것만 접두어를 둔다.

## 모양

```xml
<!-- gamesettings.xml - 적은 차례대로 읽는다. 첫 줄이 기본 맵, 맨 끝이 게임 차이다. -->
<inputMap path="common/input/base.input.xml"/>
<inputMap path="common/input/move.input.xml"/>
<inputMap path="game/harvestvalley/data/farm.input.xml"/>
```

```xml
<!-- 게임 차이 -->
<InputMap>
	<action name="Farm.Use" layer="Gameplay" trigger="Pressed"> ... </action>  <!-- 새 액션 -->
	<override name="Status" trigger="Pressed"> ... </override>                 <!-- 바인딩을 통째로 바꾼다. 비우면 눌리지 않는다 -->
	<remove name="Pause"/>                                                     <!-- 액션을 지운다 -->
</InputMap>
```

읽는 차례는 기본 맵 → 키트 맵(id 순) → 나머지 줄이다. 키트는 그 기능의 `.cpp` 에 `SW_INPUT_MAP_EXTENSION( 이름, "id", "경로" )` 한 줄을 둔다. 등록자는 모듈과 함께 오르내리므로 게임 매니페스트가 닿는 키트만 묶음에 든다.

## 규칙

| 규칙 | 까닭 |
| --- | --- |
| 맵 전체 값(시간 · 거리 · 기본 레이어)은 기본 맵에만 적는다 | 파일마다 정하면 이기는 값이 읽는 차례에 달린다 |
| 예외: `virtualCursor` 는 뒤 파일이 적을 수 있고 묶음에 한 번이다(`common/input/virtualcursor.input.xml`) | 시간 값과 달리 게임마다 다른 기능이다. 기본 맵을 둘로 두면 시간 값이 두 벌이 된다 |
| 레이어는 한 파일이 정의하고, 공통 파일은 자기 레이어를 하나 갖는다 | 다른 레이어면 같은 키를 함께 쓸 수 있어 공통 파일이 게임 키를 막지 않는다 |
| 같은 레이어 · 같은 발화 규칙 · 같은 입력을 두 액션이 쓰면 오류다 | 한 번 눌러 둘이 돈다. 다 읽은 맵에 한 번 본다 — 앞 파일끼리의 겹침을 뒤 차이가 풀 수 있다 |
| `<override>` 는 `layer` 를 적지 않으면 덮는 액션의 레이어에 남는다 | 차이는 키만 적으면 된다 |
| 한 액션은 묶음에서 한 번만 덮거나 지운다. 없는 액션을 가리키면 오류다 | 이기는 쪽이 차례에 달리지 않고, 공통 이름이 바뀌면 낡은 차이가 드러난다 |
| 묶음이 깨지면 게임을 띄우지 않는다 | 깨진 맵으로 돌면 키가 조용히 빠진다. 폴백을 두지 않는다 |

검사는 네 곳이 같은 길(`InputMap::loadBundle`)로 돈다: 게임 시작(`GameInstance::applyPackConfig` — 모든 시나리오), 쿠킹(`--cook-*` 가 씬을 굽기 전에 활성 팩), 단위 테스트(`InputMapBundleTest.EveryGamePackBundleLoads` — 모든 게임 프리셋), 입력 맵 패널의 다시 읽기.

## 액션 이름

- **두 게임 이상이 같은 뜻으로 쓰면 접두어 없는 공용 이름 하나다**(`Move`, `Interact`, `Status`). 정의는 `Content/common/input/`, 코드가 적어야 하면 `Engine/Input/Map/CommonInputActions.h` 를 읽는다. 표와 파일이 맞는지는 테스트가 본다.
- **한 게임만 쓰면 게임 접두어를 둔다**(`Farm.Use`, `Skirmish.Stop`). 다른 게임에 같은 뜻이 생기면 그때 공용으로 옮긴다. 묶인 이름이 아니라 뜻이 기준이다 — 말의 질주도 `Sprint`, 마을 사람과 대화도 `Interact` 다.
- **장치 이름공간은 공용 이름에도 쓴다**(`Camera.Pan`). 같은 묶음에 더 얹히는 별도 맵의 이름(`Photo.Move`, `UI.Pause`)은 게임 액션과 다른 일을 하므로 접두어를 유지한다.
- Shooter3D 의 `Fire` · `Reload` · `CycleCamera` · `SwitchWeapon` 은 지금 한 게임만 쓰지만 장르 공용 이름 후보라 접두어 없이 둔다. 두 번째 게임이 쓰면 `common/input/` 으로 옮긴다.
- 게임 코드는 키를 묻지 않는다. 디렉터 둘이 한 게임에서 같은 공용 액션을 읽으면 둘 다 발화한다 — 시계를 미는 디렉터를 하나로 두듯 읽는 쪽을 하나로 정한다.

## 우선순위

공통 파일 < 키트 < 게임 차이 < 플레이어 재배치. 재배치는 묶음을 다 읽은 뒤 사용자 설정이 얹는다(`UserSettingsManager::reapplyAll`). 설정은 id 로 저장하고 스키마 줄이 액션 이름을 가리키므로, 액션 이름을 바꾸어도 `usersettings.json` 은 그대로 읽힌다. 설정의 빈 값(기본으로 되돌림)은 게임 차이까지 합친 키다. 재배치 겹침은 같은 레이어만이 아니라 함께 켜진 레이어까지 본다(`InputMap::canLayersFireTogether`) — 레이어로 나누었어도 게임에서는 함께 돌기 때문이다.

## 입력 맵 패널

경로 칸에 `*.input.xml` 대신 게임의 `data/gamesettings.xml` 을 적으면 묶음을 연다. 파일 목록과 액션마다 정한 파일을 보인다. 저장은 액션을 그것을 정한 파일로 돌려보내고 고치지 않은 파일은 쓰지 않는다. 공통 파일을 고치면 다른 게임도 바뀌므로 게임만의 변경은 차이 파일에 `<override>` 를 적는다. 패널의 새 액션 · 새 레이어는 묶음의 맨 끝 파일로 간다.

## 상용 엔진과 비교

- **언리얼 Enhanced Input:** Input Mapping Context 를 우선순위와 함께 쌓는다. 키 겹침은 우선순위로 소비한다. 여기는 레이어 스택(`blockLower`)이 그 자리이고, 파일 묶음은 컨텍스트 자산 목록에 해당한다. 다른 점은 Input Action 자산이 없고 이름이 정체라는 것, 그리고 같은 레이어 겹침을 소비가 아닌 데이터 오류로 본다는 것이다. 코드를 읽지 않고도 쿠킹에서 잡기 위해서다.
- **유니티 Input System:** Action Asset 하나에 Action Map 을 여럿 두고 켜고 끈다. 자산 하나라 게임 사이 공유는 복사가 된다. 여기는 파일이 나뉘어 한 벌을 공유한다.
- **Godot:** 프로젝트 설정에 입력 맵이 하나고 런타임에 `InputMap.action_add_event` 로 고친다. 기본 액션 이름(`ui_accept`)은 공용 이름 표와 같은 생각이고, 쌓기는 없다.
- 위 내용은 각 엔진 문서를 다시 확인하지 않고 기억으로 적었다.

## 왜 데이터 상속이 아니라 레이어 쌓기인가

프리팹 · 파이프라인 XML 의 공통 상속은 부모 하나에 자식 하나의 사슬이다. 입력은 기능 여럿(이동 · 카메라 · 메뉴)을 게임마다 골라 얹어야 해서 사슬로는 조합이 파일 수만큼 늘고, 키트처럼 게임이 모르는 쪽이 끼어들 자리가 없다. 레이어는 이미 런타임 개념이라(켜고 끄기, `blockLower`, 겹침의 범위) 파일 구조가 런타임 구조와 같아진다. 차이가 필요한 두 동작(덮기 · 지우기)만 원소로 더했다.
