# 에이전트와 토큰

에이전트를 띄우거나 세션의 토큰을 따질 때 읽습니다. 워크트리 · 빌드 · 검증 · push 같은 진행 방식은 [작업 방식](11_Workflow.md) 입니다.

에이전트 정의는 `.claude/agents/` 에 있고, 일에 맞는 가장 싼 모델을 고릅니다.

| 일 | 에이전트(모델) | effort |
|---|---|---|
| 파일 · 호출부 · 지금 값 찾기, CI 로그 · 상태 모으기 | `scout`(haiku) | low |
| 규칙이 정해진 반복 편집(이름 바꾸기 · 이동 · 머리 줄 채우기 · 용어 치환 · 링크 고치기) | `mech-worker`(sonnet) | low |
| 문서 이관 · 정리처럼 항목마다 분류 판단이 드는 일(정본이 이미 지정돼 있을 때) | `mech-worker`(sonnet) | medium |
| 읽기 전용 대조 점검(낡은 문장 · 겹침 찾기, 모르면 "판단 불가"로 표시) | `Explore` 또는 `general-purpose`(sonnet) | medium |
| 범위가 정해진 C++ · CMake · 파이썬 변경, 새 도구 스크립트 + 테스트(변경이 국소적이고 명세가 있을 때) | `worker`(정의의 기본, sonnet) | medium |
| 설계 판단이 드는 C++ · CMake · 파이썬 변경(공개 형식 · 모듈 경계에 닿음) | `worker`(`model: opus` 를 지정해 올림) | medium |
| 설계 · 모듈을 넘는 리팩터 · GPU/스레드 결함 · 배치 통합 | `integrator`(opus) | high |
| GPU · 창을 쓰는 실행과 캡처 확인 | `gpu-verifier`(sonnet) | low |
| 에디터 UI 캡처의 UX 점검(읽기 전용, 기준은 [EditorUX](plans/EditorUX.md)) | `ux-reviewer`(sonnet) | medium |
| 구현 전 설계 · 구조 결정 검토(읽기 전용, 현재 구조 · 유지보수 · 성능 · 상용 엔진과 출시작 선례를 근거 수준과 함께 비교) | `design-reviewer`(opus) | high |
| 병합 전 브랜치 diff 검토(규칙 위반 · 작업자 충돌, 읽기 전용) | `code-reviewer`(opus) | high |

모델과 effort 는 에이전트를 띄울 때 지시문과 함께 정하고(`Agent` 의 `model` · `effort`), 사용자에게 알릴 때 종류 · 모델 · 레벨을 한 줄로 적습니다. `effort` 를 지정하지 않으면 호출한 세션의 레벨을 이어받으므로, 위 표의 값을 항상 지정합니다.

토큰을 아끼는 규칙입니다.

- 지시문에 읽을 문서와 절을 이름으로 적습니다([작업자 규칙](plans/WorkerRules.md) 5절). 찾기만 하는 일은 `scout` 로, 결과는 열 줄 안쪽으로 받습니다.
- **코드를 찾는 지시문에는 `graphify query "<질문>"` 을 먼저 쓰라고 적습니다**(`py -3 -m graphify query ...`, 저장소 루트의 `graphify-out/` 필요. 작업자 워크트리에서는 MCP `query_graph`). 파일 · 심볼 이름을 좁힌 뒤에 그 파일만 읽게 합니다.
  그래프는 `graphify update Source` 로 만든 시점의 코드입니다. **행 번호는 늘 실제 파일에서 다시 확인하게 하고**, 큰 구조 변경 뒤에는 그래프를 갱신합니다. 갱신은 `main` 체크아웃에서 `py -3 -m graphify update Source` 입니다(`graphify` 가 PATH 에 없을 수 있다).
- 같은 에이전트에게 이어 시키는 것(`SendMessage`)은 같은 파일을 계속 만질 때만 합니다. 이어 시킬 때마다 지난 대화가 다시 입력으로 들어가고, 무관한 일이면 새로 띄우는 쪽이 쌉니다.
- 읽기 전용 점검은 Sonnet 이하로 하고, 결론에 닿는 판단(무엇을 지울지, 무엇을 합칠지)은 맡긴 쪽이 합니다.
- 병렬로 띄우는 수는 파일 소유가 겹치지 않는 만큼만 둡니다. 한 일의 보고에는 쓴 토큰 수가 찍히므로, 같은 종류의 일에서 더 싼 조합이 통했는지 다음 배치 때 이 표를 고칩니다.

**세션 자체의 토큰.** 맡긴 쪽 세션은 매 턴 앞의 도구 출력과 에이전트 보고를 다시 입력으로 읽으므로, 에이전트보다 이쪽이 커질 수 있습니다.

- **같은 문서의 수정은 모아서 한 번에 합니다.** 문서 수정마다 워크트리 만들기 · 커밋 · `full-build` · push · 지우기가 한 바퀴 돕니다(호출 약 15번). 같은 문서를 고칠 일이 여럿이면 한 워크트리에서 한 커밋으로 묶습니다.
- **상태 확인 · 진행 보고 턴은 effort low** 로 합니다. 설계 판단 턴만 올립니다.
- **배치가 끝나면 세션을 끊습니다.** 병합 · push 직후에 [NEXT.md](plans/NEXT.md) 에 다음 일과 상태를 적고 새 세션을 권합니다.
- 응답 형식(출력 스타일)이 길어지는 것은 사용자 설정(`/output-style`)이라 에이전트가 바꾸지 못합니다. 학습 목적이 아니면 기본으로 두는 쪽이 쌉니다.

**토큰 측정값.** 쪼개는 조합이 정말 싼지는 숫자로만 압니다. 조각이 끝날 때마다 보고에 찍힌 토큰 수와 도구 호출 수를 아래 표에 한 줄로 적고, 같은 종류의 일을 다음에 맡길 때 견줍니다. 처음 두 줄은 2026-10-19 인스펙터 선택기입니다.

| 날짜 | 일 | 조각 | 에이전트(모델 · effort) | 토큰 | 도구 호출 | 비고 |
|---|---|---|---|---|---|---|
| 2026-10-19 | 인스펙터 선택기 | 위치 찾기 + 설계 명세 | `worker`(opus, medium) | 약 14만 | 39 | `scout` 선행 없이. 대부분 탐색일 것으로 추정 |
| 2026-10-19 | 인스펙터 선택기 | 구현 + 테스트 | `worker`(sonnet, medium) | 약 16만 | 65 | 명세 파일만 읽게 함. 13분. 명세의 사실 하나(`resolveComponent` 의 삭제 대기 처리)가 틀려 구현이 보정함 |
| 2026-10-19 | 인스펙터 선택기 | (참고) 통째로 맡겼다면 | `worker`(opus, high) | 측정 못 함 | | 1분 만에 세워 값이 없다. 위 두 조각 합 약 30만이 기준선 |
| 2026-10-19 | 토큰 줄이기 | AGENTS.md 를 `docs/agents/` 7개 파일로 분할 + 링크 약 60곳 | `mech-worker`(sonnet, medium) | 약 10만 | 24 | 4분. 줄 단위 비교로 내용 불변 확인. 읽는 분량: AGENTS.md 52.7KB 통째 → 목차 4.9KB + 일에 맞는 파일 |

**일을 쪼개서 맡기는 기준.** 한 단위를 통째로 비싼 모델에 맡기지 않고, 일의 성격이 바뀌는 곳에서 자릅니다. 위 표의 한 줄이 한 조각입니다.

1. **판단이 드는 조각만 비싼 모델에 둡니다.** 공개 형식 · 모듈 경계 · 오류 처리 방침을 정하는 일은 `worker`(opus, medium)가 맡고, 결과를 **명세 파일**(스크래치패드)로 받습니다.
   명세는 고칠 파일 · 함수 · 행, 결정과 그 이유, 빈 값 · 오류 처리, 추가할 테스트 이름을 적어서 구현자가 다른 문서를 읽지 않고 일할 수 있게 합니다.
2. **명세가 있는 구현은 `worker`(sonnet, medium)로 내립니다.** 설계 판단이 없으니 모델을 낮춥니다. 명세에 없는 판단이 필요해지면 고치지 말고 맡긴 쪽에 되돌립니다.
3. **찾기와 문서 갱신은 따로 뗍니다.** 위치 찾기는 `scout`(haiku, low), 계획 문서 · 인계 문서 갱신은 `mech-worker`(sonnet, low)입니다. 구현자에게 문서 갱신까지 얹지 않습니다.
4. **너무 잘게 쪼개지 않습니다.** 조각 사이마다 인계(지시문 + 보고)가 한 번 생기고, 이어 받는 쪽은 앞 결과를 다시 읽습니다. 다음이면 한 조각으로 묶습니다.
   - 앞 조각의 결과가 다음 조각의 입력이 아닌 두 일은 병렬로 띄우되 파일 소유를 나눕니다.
   - 조각마다 다시 읽을 코드가 같고 판단이 없으면 하나로 묶습니다.
   - 건드릴 파일이 셋 안팎인 단위는 두 조각(설계 → 구현 + 문서)이면 충분합니다.
5. **실행 중인 작업자를 갈아엎지 않습니다.** 쓴 토큰이 버려집니다. 쪼개는 계획은 띄우기 전에 세우고, 중간에 바꿀 때는 작업자를 세운 뒤 워크트리의 변경이 없는지 확인하고 시작합니다.
6. **조각의 결과는 파일로 넘깁니다.** 대화로 옮기면 맡긴 쪽 입력에 같은 글이 두 번 실립니다. 보고는 다섯 줄 안쪽(파일 경로 + 핵심 결정)으로 받습니다.

- 사용자가 요청을 넘기면, 지금 세션과 다른 모델 · effort 가 맞을 때 한 줄로 권하고 진행합니다. 질문 · 상태 확인 · 진행 보고는 low 로 충분합니다.
- 요청이 이 문서의 규칙과 부딪히거나 한도에 닿으면 실행 전에 한 줄로 알립니다(규칙 이름 · 비용 · 권하는 행동).
- 세션 가드 훅 `.claude/hooks/SessionGuard.py` 는 알릴 것이 있을 때만 출력합니다. 무엇을 알리는지는 훅 파일이 원본입니다.
- **인계 문서는 [docs/plans/NEXT.md](plans/NEXT.md) 입니다.** 대화가 길어지면 배치 경계에서 그 문서에 다음 일과 상태를 적고 새 세션을 권합니다. 새 세션은 그 문서가 있으면 먼저 읽습니다.
- `.gitignore` 는 `.claude` 에서 에이전트 정의 · 훅 · 공유 설정만 추적합니다. 개인 권한 목록은 `.claude/settings.local.json` 에 둡니다.
