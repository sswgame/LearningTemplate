# 설계 백로그(2026-11-07 코드 대조 감사)

> 질문: 지금 코드에서 확인한 결함 · 구조 경계 · 확장 후보와 그 판단은 무엇인가?
> 독자: 이 저장소에서 일하는 에이전트와 사용자.
> 결론: 결함은 바로 고치고, 측정 후보는 재서 정하며, 기능 후보는 수직 슬라이스로 만든다. 판단과 작업 배정은 맨 아래 "통합 담당 판단" 절이 정본이다.

## 동작이 틀린 곳

**1인칭 탄도선이 화면에 안 남을 수 있다.** `ShooterPlayerComponent::findMuzzlePosition`은 1인칭에서 시점 총의 `Muzzle` 소켓을 쓰고, 소켓이나 외형 데이터베이스가 없으면 오류 없이 눈 아래 15cm를 씁니다. 탄도선은 그 점에서 맞은 곳까지 이어집니다. 감시 값 `Shooter3D.TracerWidth`는 두께만 봐서, 선이 총에 가려도 시나리오 `projectilecombo`는 통과합니다.

```852:879:Source/Games/Shooter3D/ShooterPlayerComponent.cpp
float3 ShooterPlayerComponent::findMuzzlePosition()
{
    // ...
    const float3 fallback = getEyePosition() + float3{ 0.0f, -0.15f, 0.0f };
    // 소켓을 못 찾으면 fallback 을 그대로 반환
}
```

**조건식의 `chance`는 식 안에서 굴림을 나누지 않는다.** `GameConditions.cpp`의 `rollChance`는 시드 하나만 봅니다. 한 식에 `chance`가 둘이면 항상 같이 성공하거나 같이 실패합니다.

**빠른 관통탄은 한 걸음에 하나만 맞는다.** `ProjectileSimulation`은 한 스텝에 히트 한 번만 처리하고, 남은 선분은 다음 걸음으로 넘깁니다. 한 프레임에 두 대상을 지나는 탄은 뒤쪽을 놓칩니다.

**슈터 포탑은 쏜 뒤에 생긴 벽을 뚫는다.** `ShooterGimmicks.cpp`는 발사 순간에만 시야를 보고, 비행 중 장애물은 다시 보지 않습니다.

**머티리얼 파라미터 묶음은 핫 리로드가 없다.** `MaterialParameterCollection.h`에 적혀 있습니다. `*.matparams.xml`을 고쳐도 프로세스를 다시 띄우기 전에는 반영되지 않습니다.

## 입력이 조용히 틀어지는 곳

**셰이더 쿠킹 스탬프는 가려진 헤더를 못 본다.** `ShaderCookStamp`는 컴파일러가 먼저 찾은 헤더 하나만 기록합니다. 소스는 그대로인데 더 앞선 루트에 같은 이름 헤더가 생기면 스탬프가 낡았다고 보지 않습니다.

**X11 조합 글자는 UTF-8 로캘이 아니면 깨진다.** `X11InputMethod.cpp`는 조합 중 글을 UTF-8로만 읽습니다. 확정 글은 `Xutf8LookupString`이라 괜찮고, EUC-KR 같은 로캘의 조합 중 글만 깨집니다.

**대기 카메라 화면비는 16:9로 고정이다.** `CameraManagerComponent.cpp`는 대기 카메라가 그릴 뷰의 비를 모르면 이 카메라와 같은 16:9라고 둡니다. 분할 화면·세로 화면에서는 프레이밍이 어긋납니다.

## 테스트가 비어 있는 길

`AccountTicketConnect`(로그인 서비스에서 게임 티켓을 받아 암호화 세션을 여는 경로)는 구현은 `AccountTicketConnect.cpp`에 있고, 단위 테스트 파일은 없습니다. 로그인 암호(`NetSecurityLoginCrypto`)와 PKCE 루프백 클라이언트는 테스트가 있습니다.

인계(`docs/NEXT.md`)에 적힌 Linux 에디터 체인 실패는 이번엔 재현하지 않았습니다. 초점 없는 창에서 `audiomixer`, `graphaddnode`, `viewportselect`, `assetmanage` 등이 입력을 못 받는다는 기록입니다. lavapipe의 `R16G16_SNORM` 블렌드 거부는 코드가 이미 블렌드 비트가 없으면 덮어쓰기로 바꾸므로, 그 기록은 옛 증상일 수 있습니다.

쿠킹된 팩이 코드가 경로를 이어 붙여 읽는 에셋을 빼먹는지는 `-cooked-content`로 확인하지 않았습니다. 서비스 생성 순서가 의존·이름 순이라 생성자 안에서 다른 서비스를 찾으면 깨진다는 위험도, 그런 생성자는 이번 검색에서 찾지 못했습니다.

그래프(`Source/graphify-out/graph.json`)도 조회했다. `ModuleSharedAssetCache.h`는 여러 온라인·장르 카탈로그에서 직접 가져오고, `RHIModuleABI.h`는 RHI 백엔드 등록·진입점에서 가져온다. 그래프의 가져오기 간선은 의존 방향을 찾는 단서이지 런타임 결합이나 결함의 증거는 아니다. 빌드·시나리오는 돌리지 않았다.

### 구조 리팩터링 코드 대조 (2026-11-07)

앞선 표는 서로 다른 커밋의 조사와 패턴 검색에서 나온 가설이었다. 현재 구현을 직접 따라가 보니 일부 주장은 이미 해결됐거나 근거가 부족해 그대로 할 일로 둘 수 없다. 그래프는 관계를 찾는 길잡이로만 쓰고, 아래 판단은 현재 소스 코드로 대조했다. 이 단계는 전체 코드의 완전한 감사를 마쳤다는 뜻은 아니다.

| 우선순위 | 현재 코드에서 확인한 내용 | 개선 방향과 완료 조건 |
|---|---|---|
| 조건부 | **대기 중인 온라인 서버 호출의 조회·회수가 선형이다.** [`OnlineServerCallTable`](../Source/GameFramework/Runtime/Online/Service/OnlineProtocolService.h)의 `isOpen`·`take`가 `_listCall`을 훑고, `take`는 벡터 중간 원소를 지운다. 대기 호출 수를 P라 하면 완료 확인과 제거가 O(P)이고 이동도 생긴다. | 우선 `service_store_pending`의 실제 최대치와 높은 동시 대기 부하에서 완료 처리량·지연을 측정한다. P가 커져 병목이 확인되면 호출 ID 기반 인덱스로 바꾸고, 완료·취소·종료 시 한 번만 제거되는지 테스트한다. 작은 P라면 벡터를 유지한다. |
| 검증 필요 | **엔진 프레임 API에는 뷰 입력이 남아 있지만 렌더 구현 경계는 이미 분리돼 있다.** [`Engine::update`](../Source/Engine/Engine.h)는 `FrameViewports`와 카메라 공급자를 받지만, 제출은 [`IEngineRenderDriver`](../Source/Engine/Graphics/View/IEngineRenderDriver.h)로 전달한다. 따라서 “Engine이 Renderer 구현을 직접 안다”는 이전 주장은 틀렸다. | 서버·쿠커 타깃에서 이 프레임 입력 형식이 실제로 불필요한 의존을 끌어오는지 빌드 타깃·include 그래프로 확인한다. 컴파일 경계 위반이 재현될 때만 뷰 데이터 계약을 분리한다. |
| 점검 보류 | **렌더 확장 두 경로는 확인했으나 중복 결함은 입증되지 않았다.** 기본 씬 수집은 엔진 컴포넌트를 구체적으로 처리하고, 모듈 확장은 [`RenderExtensionRegistry`](../Source/Engine/Renderer/Extension/RenderExtensionRegistry.h)와 프록시 수명 계약을 쓴다. 둘의 입력·수명·스레드 계약은 다르다. | 일괄 통합하지 않는다. 실제 플러그인 기능이 기본 수집 경로에 의존하거나 같은 기능을 두 번 구현하는 사례가 확인될 때만 공통 기여 API를 설계한다. |

| 낮음(생성기 보강 검토) | 생성기는 이름·숫자·라벨 중복을 검사하지만, 프로세스 종료 코드의 플랫폼 표현 범위나 자동화 결과 열거자와의 대응을 전부 검증하지 않는다. 현재 표 값은 POSIX 종료 상태에서 표현 가능한 범위 안이다. | 스키마 검증에 지원 플랫폼의 종료 코드 범위, 고정 예약 코드, 자동화 결과 매핑의 누락/중복 조건을 추가할지 검토하고 생성기 테스트를 둔다. CTest의 skip 코드 77 및 외부 프로토콜/도구가 기대하는 값을 변경할 때는 동작 호환성을 확인한다. |

별도인 [`Scripts/common/ExitCode.py`](../Scripts/common/ExitCode.py)는 스크립트 자체의 `Passed`/`Violation`/`CheckInvalid` 반환 계약으로, App 프로세스 종료 코드 표와 역할이 다르다. 이름이 비슷하다고 두 표를 합치거나 모든 도구에 App 코드를 강제하지 않는다.

### 셰이더 구조와 디퍼드/G버퍼 활용 고도화 (코드 대조 2026-11-07)

**현황:** 디퍼드 렌더링과 G-buffer는 이미 구현되어 있고 선택 파이프라인으로 쓸 수 있다. [`deferredpipeline.xml`](../Content/engine/pipeline/deferredpipeline.xml)은 알베도(`R8G8B8A8_UNORM`), 옥타헤드럴 노멀(`R16G16_SNORM`), 금속도·거칠기·그려짐 표시(`R8G8B8A8_UNORM`)의 세 색 첨부와 깊이를 쓰며, [`deferred_lighting.hlsl`](../Content/engine/shaders/deferred_lighting.hlsl)은 깊이에서 월드 위치를 복원하고 포워드와 공유하는 조명 식으로 라이트를 계산한다. 포워드 파이프라인도 계속 지원한다. 즉 “G-buffer가 없다”기보다 **G-buffer 계약이 현재 PBR 표면 두 속성 중심으로 고정되어 있고 실제 게임 장면에서 그 이점과 비용을 넓게 검증할 필요가 있다.**

- **게임 제작자가 기본 머티리얼을 만들 편집 도구는 있다.** Content Browser에는 `Content/game/<게임>/materials/` 아래 새 `.matgraph.xml` 머티리얼 그래프를 만드는 템플릿이 있고 [`MaterialGraphPanel`](../Source/Editor/Panels/MaterialGraph/MaterialGraphPanel.h)은 노드 연결, 파라미터, 실시간 미리보기, 컴파일 문제를 다룬다. 저장하면 컴파일된 HLSL과 `.gen.material`이 생성되어 런타임/Shipping은 생성물만 읽는다. 생성 머티리얼을 부모로 둔 게임별 `.material` 변형은 [`MaterialPanel`](../Source/Editor/Panels/Material/MaterialPanel.h)에서 색·숫자·텍스처 등 노출된 프로퍼티를 편집하고 구 미리보기/선택 오브젝트 적용을 할 수 있다. 기존 게임에도 이런 변형 에셋이 사용된다(예: `game/wildwest/materials/rider.material`).
- **다만 완전한 게임별 셰이더 저작 플랫폼은 아니다.** 그래프 노드 등록표는 엔진의 고정 등록이며 새 노드는 엔진 C++/HLSL 변경과 쿠킹이 필요하다. 게임 키트/게임 모듈이 자체 노드나 조명 모델을 에디터에 등록하는 확장점은 확인되지 않았다. 현재 노드 그래프는 제한된 표면 출력과 HLSL 조각을 조합하는 저작 도구이지 임의 셰이더를 안전하게 만들고 G-buffer 호환성을 보장하는 범용 도구는 아니다. Material 패널의 구 미리보기는 실제 게임 메시·조명·파이프라인 차이를 모두 검증하지 못한다. 따라서 **기존 노드로 PBR 표면을 조합하고 그 게임의 값/텍스처를 튜닝하는 작업은 가능하지만, 새로운 게임 고유 셰이딩 모델이나 G-buffer 데이터 계약을 아티스트가 단독으로 추가하는 것은 현재 토대 밖**이다.
- **작업자 중심의 다음 단계:** 게임 도메인별 `Material Graph` 노드 복제 대신, 공통 표면 속성/노드 라이브러리를 명확히 지원하고 `_base` 머티리얼 변형으로 게임별 값만 분리한다. 자주 쓰는 조합은 실제 게임 재료(피부·천·금속·젖음·식생 등)별 시작 그래프/재질 템플릿과 검증된 파라미터 그룹으로 제공한다. 미리보기에는 해당 게임의 대표 메시·텍스처·조명/HDR 환경과 현재 Forward/Deferred 경로를 선택할 수 있게 하고, 컴파일 성공뿐 아니라 누락 텍스처·지원 셰이딩 경로·G-buffer/ForwardOnly 분류·쿠킹 상태를 인라인으로 표시한다. 게임별 새 노드는 요구가 반복되고 공통 표면 계약으로 표현할 수 없을 때만 별도 모듈/확장 설계를 검토하며, 코드/HLSL 구현자와 콘텐츠 작업자의 책임을 분리한다. 먼저 기존 `MaterialGraphPanel`, `MaterialPanel`, 에셋 템플릿을 실제 게임 재료 제작 시나리오로 시험해 노드 발견성, 머티리얼 변형, 타깃 메시 미리보기와 쿠킹 확인 중 어느 단계가 제작 병목인지 정한다.
- **현재 표현의 한계:** G-buffer 알파는 셰이딩 여부(Unlit/Lit) 한 비트 역할이고, 머티리얼 첨부의 `a`는 픽셀이 쓰였는지 표시한다. `b`는 미사용이다. 이 약속은 [`binding_output.hlsli`](../Content/engine/shaders/binding_output.hlsli)에서 인코딩하고 [`binding_texture.hlsli`](../Content/engine/shaders/binding_texture.hlsli)에서 복호화하며 C++의 [`RenderPassTypeInfo`](../Source/Engine/Renderer/Pipeline/RenderPassTypeInfo.h) 포맷 표와 XML 첨부가 별도로 맞아야 한다. 새 셰이딩 모델 ID, 표면 속성, 재질 분류를 추가하면 이 여러 계약과 렌더 패스 입력/출력 검증이 함께 바뀐다.
- **이미 있는 우회 경로:** 툰처럼 빛별 단계 셰이딩을 요구하거나 그래프의 Emissive처럼 현재 G-buffer 표면에 담기지 않는 값은 [`MATERIAL_FORWARD_ONLY`](../Source/Engine/Renderer/Pipeline/RenderPassTypeInfo.h)로 G-buffer에서 제외해 `ForwardOnlyOpaque`로 그린다. 이는 표현 불가능한 효과를 정확히 그리는 안전한 경로지만, 기본 PBR 계열 머티리얼까지 실수로 ForwardOnly로 분류하면 디퍼드 조명·타일 라이트 경로의 혜택을 받지 못한다. 반대로 모든 속성을 G-buffer에 넣는 것도 첨부 대역폭·메모리·타일 기반 GPU 비용을 불필요하게 키운다.
- **셰이더 구조 확장 원칙:** 공통 `PixelContext`/표면 평가와 패스별 출력(Forward 색 또는 G-buffer 인코딩)을 분리하고, 표면 모델/필수 입력을 명시적으로 선언·검증한다. G-buffer 레이아웃은 속성마다 임의 define을 늘리기보다 버전이 있는 하나의 명세(속성, 포맷, 인코딩, 클리어 값, 셰이더 모델 ID, 독자)를 기준으로 C++ 패스 계약·XML·HLSL writer/reader·디버그 표시와 맞춘다. 현재 알파에 실려 있는 Unlit/Lit 분류와 픽셀 유효 표시를 그대로 두고 ID를 덧붙일 수 있다고 가정하지 않는다. 포맷 정밀도, 감마/선형 공간, 정규화 범위와 빈 픽셀 동작을 먼저 정하고, 정의되지 않은 필드나 미지원 조합은 쿠킹/파이프라인 검증에서 실패시킨다.
- **확장 우선순위:** 우선 기존 Material Graph/셰이더에서 Lit·Unlit·Emissive·툰·알파 마스크·노멀맵의 패스 분류를 목록화해 지원 계약을 만든다. 다음으로 PBR에서 실제 필요한 추가 정보(예: AO 또는 재질/셰이딩 모델 식별자)가 있는지 대표 게임의 장면과 조명 효과에서 확인한다. 공통 속성 하나가 추가되어야 한다면 기존 남는 비트/채널을 쓸 수 있는지 정밀도와 호환성을 검사하고, 셰이더 모델마다 다른 데이터가 필요하면 데이터 팩/별도 G-buffer 첨부 또는 ForwardOnly 중 측정과 명확한 계약을 근거로 고른다. Emissive는 단순히 모든 그래프를 ForwardOnly로 남기지 말고, 조명과 합성의 의미를 정해 G-buffer 이후의 emissive 합성 경로가 포워드 조명·Bloom·톤맵 순서와 일치하는지 평가한다.
- **G-buffer를 더 적극적으로 쓰는 방법:** 우선순위는 추가 RT보다 먼저 소비자와 관측 가능성을 늘리는 것이다. 기존 Render Targets 패널에서 현재 G-buffer의 각 채널을 선형 값으로 검사하고, 셰이딩 모델/유효 픽셀/노멀·금속도·거칠기 및 실제 포워드 전용 배치를 시각화하는 보기 모드를 제공한다. 화면에서 표면이 어느 경로로 그려졌는지, 왜 그 경로인지(머티리얼 선언/퍼뮤테이션), 픽셀별 값이 무엇인지 알아야 장면 단위로 G-buffer 사용률과 잘못된 분류를 고칠 수 있다.
- **측정과 플랫폼 선택:** Forward와 Deferred는 같은 카메라·콘텐츠·해상도·품질·플랫폼 조건으로 비교한다. 고정된 시나리오에서 GPU 프레임 시간, G-buffer 쓰기/읽기 대역폭과 메모리, 셰이더 변형/PSO 수, 라이트 수에 따른 증가, 투명·ForwardOnly 드로우를 기록한다. 데스크탑 다중 동적 라이트에서 이득이 확인되면 기본 선택 대상으로 삼고, 타일 메모리와 대역폭 제약이 큰 모바일/저사양 GPU에서는 품질별·플랫폼별 포워드 선택을 유지하거나 측정으로 결정한다. 프레임 시간은 반복 측정과 동일 기기 기준선을 사용하고, 단일 측정으로 승격하지 않는다.
- **검증:** writer와 lighting reader가 같은 패킹을 쓰는 왕복/레퍼런스 테스트, 빈 픽셀·역노멀·재질 경계·Unlit/Emissive 값 시나리오, 포워드/디퍼드 동일 장면 이미지 비교, 각 RHI 백엔드의 셰이더 쿠킹/PSO 생성, 모든 G-buffer 첨부의 포맷·샘플 수·역할 검증을 포함한다. G-buffer를 확장하면 저장 대역폭, 동시 컬러 첨부 한도와 Android/Web 등 백엔드의 포맷 지원을 확인하기 전에는 기본 렌더링 경로로 강제하지 않는다.

### Test Framework 고도화 후보 (코드 대조 2026-11-07)

현재 틀은 필터·태그·disabled 사유·픽스처·정적 매개변수 케이스·자식 역할·시한·반복·결정적 샤드·스냅숏·기대 로그·JSON 결과를 이미 제공한다. 에디터 자체 테스트도 같은 `TestRunner`를 쓴다. 이 기능을 중복 구현하거나 별도 프레임워크를 추가할 이유는 확인하지 못했다. Shipping에서는 테스트 구현이 이미 제외되므로 제거할 대상도 지금은 특정하지 않는다.

**실제 게임 루프를 검증하는 시나리오:** 프레임워크 단위 테스트나 한 시스템만 보는 시나리오만으로는 장르 키트가 플레이 가능한 게임 기능을 뒷받침하는지 판단하기 어렵다. 그렇다고 특정 상용 게임을 복제할 필요는 없다. 해당 장르에서 실제 플레이어가 경험할 목표·행동·결과·진행을 담은 작고 독창적인 수직 슬라이스를 만들고, 기존 테스트 게임과 자동화 시나리오를 그 흐름의 회귀 검증에 활용한다.

- **현재 기반을 먼저 재사용한다.** 게임별 자동화 시나리오는 이미 있다: [`Shooter3D autoplay`](../Content/game/shooter3d/automation/autoplay.scenario.xml)는 AI 조준·발사·적중과 플레이어 조종 복귀를, [`HarvestValley actions`](../Content/game/harvestvalley/automation/actions.scenario.xml)는 이동·도구 선택·밭 갈기를, [`StarSkirmish AI`](../Content/game/starskirmish/automation/ai.scenario.xml)는 자원 수집·일꾼 생산·보급 건설을, [`AbilityArena AI`](../Content/game/abilityarena/automation/ai.scenario.xml)는 적 추격·공격을 확인한다. 따라서 “게임 동작을 흉내 내는 테스트가 전혀 없다”는 진단은 맞지 않는다.
- **다만 이 사례들은 완결된 장르 플레이 루프를 모두 검증하지는 않는다.** 현재 확인한 시나리오들은 입력/AI와 개별 상태 전이를 검증하는 데 유용하지만, 예를 들어 전투의 목표 완료와 보상, 농사의 파종→성장→수확→판매와 날짜 진행, RTS의 생산→교전→승패 같은 시작부터 결과까지의 흐름이 각 게임에서 일관되게 자동 검증되는지는 별도 확인이 필요하다. 지원하지 않는 기능을 테스트가 있다고 가정해 빈칸으로 채우지 않는다.
- **고도화는 기존 게임 하나씩의 수직 슬라이스로 한다.** 각 선택 장르에 플레이 가능한 작은 맵, 실제 입력/조작 또는 동일한 게임 입력 추상화를 쓰는 자동 플레이, 유효한 카탈로그/에셋, 명시적인 완료·실패 조건을 갖춘다. 시나리오는 한두 개의 의미 있는 전체 루프를 수행하고 핵심 상태 변화, 저장·재시작이 범위에 포함될 때의 복원, 로그/골든을 판정한다. 자동 플레이는 테스트 전용 치트 경로로 게임 규칙을 우회하지 말고 플레이어와 같은 입력·게임 서비스를 사용하게 한다.
- **검증 층을 나눈다.** 순수 규칙은 단위 테스트, 시스템 간 결합은 게임 수직 슬라이스 시나리오, 렌더링·조작·에디터 UX는 별도 화면/입력 시나리오로 둔다. 한 거대한 시나리오가 모든 조합을 떠맡지 않도록 하며, 고정 델타·시드·초기 상태와 감시 값으로 반복성을 확보한다. 실제 프레임률이나 타이밍이 요구사항인 부분만 벽시계 기반 측정으로 분리한다.

**구조 개선 순서:** 먼저 격리·보고가 필요한 테스트를 몇 개 선정해 현재 실패 산출물의 공백을 확인한다. 그 작업에 맞춰 [`TestRunner.cpp`](../Source/Core/Testing/TestRunner.cpp)의 선택·실행 수명주기·프로세스 격리·보고 직렬화를 책임별로 나눈다. 단순히 파일이 길다는 이유만으로 분리하지 말고, 케이스 상태의 전역 공유를 끊는 실행 문맥과 보고 계약을 명확히 할 때만 구조를 바꾼다. 게임 검증은 현재 자동화 사례와 게임 기능을 먼저 대조하고, 장르의 완결 루프가 비어 있는 게임에만 수직 슬라이스 시나리오를 추가한다.

**이 점검에서 재현하지 않은 것:** WSL 경로 변경, 병렬 생성기 경합, 테스트 크래시 이후 보고 유실은 코드 경계에서 확인한 가능성이다. 실제 실패·데이터 손실을 재현한 것은 아니므로 수정 전 회귀 시나리오로 확정한다.

| 선언형 검사 밖의 참조 | [`AbilityCatalog`](../Source/GameFramework/Runtime/Gameplay/Ability/AbilityCatalog.cpp)는 능력→비용/쿨다운 이펙트를 읽을 때 빠진 이펙트를 경고하고 null 로 둔다. 하지만 이펙트→부여 능력과 AbilitySet→능력/이펙트 ID는 로드 시 연결 검사를 하지 않는다. [`AbilityComponent`](../Source/GameFramework/Runtime/Gameplay/Ability/AbilityComponent.cpp)는 적용 시 조회하고, 세트 적용은 개별 결과를 무시한 채 계속한다. [`SkillTree`](../Source/GameFramework/Kits/Genre/RPG/MonsterHuntRPG/Rule/SkillTree.cpp)는 없는 선행 기술을 경고만 하고 트리를 유지한다. | 데이터 자체가 모두 읽힌 상태에서 연결을 확인하는 규칙이 없는 구간이다. 미등록 ID를 실제 게임에서 조회할 때까지 발견하지 못하거나 해당 효과만 빠질 수 있으므로, 필수/선택 관계와 허용 부분 복구를 먼저 정한 뒤 로드/쿠킹 단계 진단을 추가한다. |
| 중복 ID 정책 경계 | `GameDataXML::addUnique`는 일반 카탈로그의 중복 ID를 오류로 거부하지만, `AbilityCatalog`의 XML 읽기는 공개 코드 추가 API(`addAbility`/`addEffect`/`addAbilitySet`/`addCue`)와 같은 `insert_or_assign` 경로를 써서 같은 키를 교체한다. 공개 API 주석은 코드 추가 시 교체를 명시하므로, XML 중복도 허용할지 별도 계약은 확인되지 않았다. | XML의 같은 종류 ID 중복이 의도인지 테스트로 확정한다. 오류여야 한다면 XML 로드만 `addUnique` 성격으로 읽고 코드 API의 교체 동작은 유지한다. 현재 단계에서는 공개 API 계약이 있어 이를 확정 결함으로 세지 않는다. |
| 자체 카탈로그 내부 연결 | [`RTSCatalog`](../Source/GameFramework/Kits/Genre/Strategy/RealTimeStrategy/RTSCatalog.cpp)의 생산자/선행조건, [`ActionPlatformerCatalog`](../Source/GameFramework/Kits/Genre/Action/ActionPlatformer/Catalog/ActionPlatformerCatalog.cpp)의 패턴 상태 전이, [`QuestCatalog`](../Source/GameFramework/Runtime/Gameplay/Quest/QuestCatalog.cpp)의 다음 단계/분기, [`ScheduleCatalog`](../Source/GameFramework/Runtime/Character/AI/Schedule/ScheduleCatalog.cpp)의 장소·활동·NPC·일정 연결, Conquest의 반격 유닛 등은 각 로더가 직접 검사한다. | 검사 정책이 다르다. **근본적인 경계:** [`XMLCatalogReader::checkReferences`](../Source/GameFramework/Runtime/Foundation/GameData/XMLCatalogTable.h)는 `void`이고 알 수 없는 ID를 로그로만 보고한다. 호출 뒤 `loadRoot`는 항목 수를 반환하며, [`XMLCatalogLoader::isLoaded`](../Source/GameFramework/Runtime/Foundation/GameData/XMLCatalog.h)는 그 수가 0보다 큰지만 로드 성공으로 판정한다. 따라서 이 공통 검사에서 참조 오류가 나도 다른 로드 오류가 없다면 카탈로그가 성공 처리될 수 있다. 일부 자체 검사도 같은 방식으로 로그만 남긴다. 반면 중복 ID·잘못된 필드 등은 정의를 제외하거나 로드를 실패시키는 경로가 있어 데이터 오류별 정책이 다르다.

**개선 방향:** (1) 위의 9개 공통 검사와 별도 로더/자체 검사에서 오류를 보고하는 규칙을 모아, 필수 참조·선택 참조·경고 허용·항목 제외·전체 로드 실패 중 의도된 정책을 각 연결별로 확정한다. (2) 의도적으로 허용된 경고/부분 복구는 유지하고, 필수 연결만 로드 결과에 반영하도록 한다. (3) 같은 루트 안의 연결과 `FighterCatalog`처럼 다른 리소스를 요구하는 연결을 구분해 검증 API를 설계한다. (4) 게임 모듈을 올리기 전에 도는 쿠커에서 검증하려면 모듈 전용 C++ 코드를 호출하는 방식은 쓸 수 없다([`DataCatalogInheritance`](../Source/Engine/Serialization/Inherit/DataCatalogInheritance.h)의 쿠커 경계). 쿠커가 읽을 수 있는 데이터 규칙/선언으로 옮기거나 공용 검증 계약을 생성하는 선택지를 검토하고, 에디터·쿠커·런타임이 같은 참조 결과를 보게 한다. (5) 유효성 오류·선택 참조·상속으로 물려받은 참조·다른 팩/파일 참조의 테스트를 추가한다.

### ReflectionParser · 런타임 Reflection 고도화 후보 (코드 대조 2026-11-07)

Graphify는 관계 탐색에만 사용하고 파이프라인·캐시·호출 경로는 구현과 대조했다. 이미 있는 최적화를 새 과제로 중복 등록하지 않는다. 아래 성능 항목은 병목이 입증된 결함이 아니라 측정 후보이며, 실측 전에는 구조를 바꾸지 않는다.

|---|---|---|
| 조건부(파서 폴백 시 성능·메모리) | [`ReflectionPipeline::parsePending`](../Source/Programs/ReflectionParser/ReflectionPipeline.cpp)은 변경 헤더를 우선 한 TU로 묶는다. 소스 주석의 Release 실측은 공통 헤더 0.52초, Engine 공통 헤더 1.0초, 입력 27개 묶음 1.04초이며, 헤더별 16개 병렬 파싱에서는 한 파싱이 1.0초에서 2.1초로 늘었다고 기록한다. 묶음 파싱 실패 시 [`parseEachInParallel`](../Source/Programs/ReflectionParser/ReflectionPipeline.cpp)는 하드웨어 동시성만큼 워커를 만들며 별도 상한은 없다. | 기존 단일-TU 경로는 유지한다. 대표적인 정상 빌드와 일부 헤더가 실패하는 폴백에서 전체 처리시간·최대 동시 TU 수·최대 RSS를 반복 측정한다. 실제 메모리 압박 또는 처리량 저하가 재현될 때만 워커 수를 제한하거나 실패 입력을 먼저 가려 재파싱 범위를 줄이고, 실패 헤더의 진단 및 나머지 헤더 산출물 보존을 검증한다. |

| 유지(기존 구조 계약) | [`TypeRegistry::populateLookupCaches`](../Source/Engine/Reflection/TypeRegistry.cpp)는 등록 배치가 끝난 단일 스레드에서 상속 프로퍼티 목록, 이름 조회, 세이브게임·검증 여부를 미리 채운다. `StaticType()` 조회는 [`TypeLookupCache`](../Source/Engine/Reflection/TypeLookupCache.h)의 세대 검증 슬롯, 캐스트는 조상 테이블을 사용한다. 그러므로 매 조회가 잠금·맵 조회 또는 상속 사슬 순회라는 전제는 맞지 않는다. | 이 사전 계산을 유지한다. 새 캐시를 추가하거나 등록·언로드 경로를 바꿀 때는 생성·무효화 순서를 갱신하고 모듈 재등록 테스트를 함께 둔다. 일반 `findType`과 열거형 해시 역조회처럼 별도 조회의 비용은 실제 소비자·호출 빈도에서 병목이 확인된 경우에만 다룬다. |
| 테스트 정확성 | 파서 테스트는 내부 함수를 직접 호출하는 단위 테스트는 아니지만, [`Test/CMakeLists.txt`](../Test/CMakeLists.txt)는 8개 헤더 fixture를 실제 파서에 넣어 생성 코드·목록·오류를 대조하고, 알 수 없는 인자와 필수 인자 누락도 검사한다([`RunParserFixture.cmake`](../Test/ReflectionParser/RunParserFixture.cmake)). 런타임 쪽에는 `TestReflectionValidation` 등 단위 테스트가 있다. 현재 파서 성능 기준선이나 단계별 프로파일은 확인되지 않았다. | 기존 fixture를 파서 테스트 부재로 분류하지 않는다. 성능 최적화 전에 변경 없음(incremental skip)·변경된 단일 헤더·다중 헤더 배치·실패 폴백을 같은 입력에서 반복 측정하는 기준선을 만든다. CI의 변동성 있는 시간 문턱은 안정적인 기준과 실행 환경이 마련되기 전에는 추가하지 않는다. |

**범위와 다음 조사:** 현재 코드에는 파서 배치·증분 생성, 타입 조회·캐스트 캐시, 등록 후 사전 계산이 이미 있다. 이번에 확인한 추가 비용 후보는 실패 폴백의 무제한 동시성, 소스 토큰 구성, 검증 중 반복적인 중첩 타입 조회다. 실측 없이 이를 성능 결함으로 단정하거나 전역 캐시를 추가하지 않는다. 같은 반복 조회가 다른 직렬화·에디터 경로에도 있는지는 이 조사에서 전수 측정하지 않았으므로, 위 후보가 병목으로 확인될 때 해당 소비자의 호출 횟수와 함께 좁혀 조사한다.

#### FUNCTION 리플렉션 활용과 호출 경계

- **이미 쓰이는 곳:** 생성된 `FunctionInfo`는 함수명·인자/기본값·반환 타입·invoker와 메타데이터를 보유한다. Inspector는 반영된 메서드의 인자를 기존 프로퍼티 위젯으로 편집하고 호출 결과를 표시하며, `CallInEditor` 인자 없는 메서드는 빠른 실행 버튼으로 보여 준다([`EditorPropertyGrid`](../Source/Editor/Panels/Inspector/EditorPropertyGrid.cpp)). 애니메이터·시퀀서·VFX·대사 컴포넌트의 재생/시험 동작, 대사 라인의 뷰포트 프리뷰([`EditorViewportPreview`](../Source/Editor/Common/Commands/Scene/EditorViewportPreview.cpp)), 반영 생성자 기반 인스턴스 생성 및 함수 API 문서화가 실제 활용 사례다.
- **기반은 있으나 연결이 드문 곳:** [`ReflectionInvoke`](../Source/Engine/Reflection/ReflectionInvoke.h)는 타입 변환/기본 인자 처리, 이름으로 호출, 텍스트 인자 호출, 이벤트를 함수에 연결하는 API를 제공한다. 그러나 이번 호출처 검색에서 `callWithText`와 `bindEventToFunction`의 소비자는 Reflection 테스트뿐이며, 대사 외 범용 `EditorPreview` 소비자도 발견하지 못했다. 따라서 콘솔·비주얼 스크립팅·기믹에 이미 범용 호출/배선이 연결됐다고 간주하지 않는다.
- **메타데이터와 실행 동작을 구분한다:** `Server`, `Reliable`, `Validate`는 파싱되어 메타데이터와 생성 코드에 보존되지만, 조사한 런타임 호출 경로에는 이 값으로 RPC 라우팅·신뢰성·검증을 수행하는 구현이 보이지 않는다. 현재는 호출 정책이 아니라 기록된 선언 정보다. 실제 네트워크 호출을 지원하려면 역할 검사·검증 실패 처리·복제/재접속 의미·서버/클라이언트 테스트를 갖춘 별도 호출 계층이 필요하다. 그 전에는 이 태그만으로 네트워크 보안이나 실행 보장을 제공한다고 문서화하지 않는다.
- **Inspector 경계도 정리해야 한다:** 현재 Inspector는 생성자를 제외한 `_listMethod`를 나열해 `CallInEditor`가 없는 메서드에도 일반 `Invoke` UI를 제공한다. 반대로 `CallInEditor`는 빠른 버튼과 표시 태그에 쓰이지만 함수의 실행 안전성·부작용을 검증하지 않는다. 이를 에디터 작업 API로 확장하기 전, 기본 목록은 명시적으로 허용된 `CallInEditor` 동작으로 좁히고 일반 진단 호출은 별도 개발자 모드/도구로 분리한다. 카테고리는 그룹화에, 표시 이름/설명은 탐색과 툴팁에 일관되게 사용한다.
- **권장 확장 순서:** (1) `CallInEditor` 실행 조건·편집 중 프리뷰 여부·씬 dirty/Undo 영향·취소/실패 결과를 명시하는 최소 계약을 정한다. (2) 인자 없는 버튼에 그치지 않고 기존 타입 위젯과 `ReflectCallResult` 오류 표시를 재사용해 안전한 파라미터 동작을 제공한다. (3) 실사용이 확인된 반복 작업부터 검색 가능한 액션 목록/컨텍스트 메뉴에 연결한다. (4) 콘솔이나 비주얼 배선은 실제 수요가 생길 때 `callWithText`/`bindEventToFunction`를 명시적 허용 목록, 수명 관리, 핫 리로드 검증과 함께 소비한다. 키트 전용 동작은 해당 컴포넌트/키트가 있을 때만 노출한다.
- **완료 기준:** `CallInEditor` 없는 메서드가 의도치 않게 실행 UI에 노출되지 않고, 호출 가능한 메서드는 인자 변환·기본값·오류·반환값·dirty/Undo 결과가 예측 가능해야 한다. 이벤트 구독은 소스/타깃 파괴와 모듈 재로드 후 안전하게 해제·재탐색되고, 네트워크 메타데이터는 RPC 미지원 상태를 UI/문서에서 명확히 표시한다. 현재 테스트의 형식·인자 오류 검증은 유지하고 Inspector 시나리오로 노출 및 실행 가능 범위를 회귀 확인한다.

### 비동기 · 병렬 처리 확장 후보 (코드 대조 2026-11-07)

Graphify로 시스템 간 관계를 찾고 실제 호출 경로와 동기화 경계를 확인했다. 아래 후보는 모두 프로파일링으로 비용을 확인한 뒤 진행한다. 비동기는 대기 시간을 숨기고 병렬 처리는 처리량을 늘리는 서로 다른 도구다. 이미 있는 `TaskManager`와 `engine::runParallel(ByCost)`를 우선 사용하고, 항목마다 무제한 태스크를 만들거나 프레임에서 즉시 기다리는 식의 적용은 피한다.

| 우선순위 | 코드에서 확인한 현재 경로 | 확장 방향과 완료 조건 |
|---|---|---|
| 조건부 높음(에디터 저장 멈춤) | [`SceneManager::writeActiveScene`](../Source/Engine/Scene/SceneManager.cpp)는 호출 중 [`Scene::serializeToDocument`](../Source/Engine/Scene/Scene.cpp)를 실행하고, 활성 오브젝트를 차례로 돌며 상태를 XML로 직렬화한 뒤 XML 또는 상속 차이 파일을 동기 저장한다. 큰 씬 저장은 호출 스레드를 붙잡을 수 있다. | 큰 씬에서 직렬화·델타 계산·파일 쓰기 시간을 나눠 측정한다. 직렬화가 문제면 게임 스레드에서 일관된 `SceneDocument` 스냅숏을 만든 뒤, 그 독립 값의 XML 생성·파일 기록만 워커로 넘긴다. 저장 완료/실패를 비동기로 알리고, 저장 성공 전에 씬의 source path·dirty 상태를 완료 처리하지 않으며, 저장 중 편집이 이어질 때 오래된 스냅숏을 최신 상태로 오인하지 않는 버전 검사를 둔다. `Scene`·오브젝트 매니저를 워커에서 직접 읽게 하지 않는다. |
| 조건부 높음(대형 씬 최초 진입) | [`SceneManager::loadSceneAsyncJob`](../Source/Engine/Scene/SceneManager.cpp)은 파싱과 씬 인스턴스화를 이미 워커에서 수행하며 `Scene.load.parse` · `Scene.load.instantiate` 시간을 따로 잰다. 다만 [`Scene::instantiateNodes`](../Source/Engine/Scene/Scene.cpp)는 엔티티를 한 루프에서 만들고 상태를 적용한 뒤 핸들 연결·부착을 마친다. 등록과 로드 후 처리는 별도 게임 스레드 경로로 나뉘어 프레임당 개수 제한도 있다. | 로그에서 `instantiate`가 우세할 때만 독립적인 상태 디코드·검사 등 순수한 전처리를 병렬화하고, 오브젝트 생성/프리팹 캐시/파일 ID 연결/부착과 등록은 현재 소유권 경계를 유지한다. 완료 순서가 달라도 저장 ID와 계층이 동일한지, 취소·실패 때 부분 씬이 모두 정리되는지, 등록 프레임 예산이 지켜지는지를 대형 fixture로 검증한다. 통째 엔티티 생성의 병렬화는 `GameObjectManager`와 공유 프리팹 상태의 스레드 안전성이 확인되기 전에는 하지 않는다. |
| 조건부 높음(쿠킹 빌드 시간) | [`SceneCooker::cookAllScenes`](../Source/Engine/Scene/SceneCooker.cpp)은 씬 파일을 정렬한 뒤 씬 쿠킹과 해당 프리로드 목록 쿠킹을 순서대로 처리한다. 씬 단위 결과는 서로 독립적으로 보이지만 [`CookStore::cookFile`](../Source/Engine/Asset/Cook/CookStore.h)은 공유 통계·요청 목록·해시 시간을 변경하고, 매 작업의 시작에서 [`AssetManager::clearAssetCaches`](../Source/Engine/Asset/AssetManager.cpp)를 호출한다. `CookJob` 입력 범위는 thread-local 이지만 이 사실만으로 전체 쿠커가 병렬 안전해지지는 않는다. | 실제 씬 쿠킹 시간이 빌드를 지배하는지 먼저 잰다. 병렬화가 필요하면 먼저 에셋 캐시를 작업별로 격리하고 CookStore의 기록/DDC·통계·요청 집합 갱신을 안전하게 분리하거나 결과를 한 스레드에서 병합한다. 그 뒤 씬 단위로 제한된 동시성 작업을 주고, 씬 출력 성공 뒤 프리로드 목록을 처리하는 의존성·실패 집계·결정적 산출물·요청되지 않은 출력 삭제를 테스트한다. 공유 캐시를 그대로 둔 채 씬 루프만 태스크로 감싸지 않는다. |
| 조건부(게임 스레드 에셋 지연) | [`AssetLoadOperation::startLoad`](../Source/Engine/Asset/AssetHandle.cpp)은 안전한 일반 요청을 `AssetManager::launchLoadWork`로 워커에 넘기고, asset streaming은 경로 찾기와 파일 읽기를 비동기로 한다. 반면 `AssetLoadStart::OnCallingThread` 또는 쿠킹 경로는 호출 스레드에서 읽고 완료한다. `AssetLoadProfiler`는 동기/비동기 구분과 IO·decode·upload 단계별 시간을 이미 모은다. | 실제 프레임 스톨 상위 에셋과 그 단계(IO, decode, upload)를 프로파일러로 찾는다. 워커에서 안전하고 호출자가 지연 로드를 허용하는 경로만 비동기로 바꾸며, 즉시 사용할 에셋은 준비 완료 계약과 로딩 UI를 함께 둔다. 쿠킹의 입력 추적상 호출 스레드 읽기가 필요한 경로 및 RHI 스레드 제약은 유지하고, 임의로 모두 비동기화하지 않는다. |
| 조건부(렌더 패스 기록 대기) | [`RenderGraph::executeParallel`](../Source/Engine/Renderer/Graph/RenderGraph.cpp)은 리소스 의존 그래프의 각 레벨 안에서 이미 커맨드 기록을 병렬화하고 레벨마다 합류·제출한다. 같은 레벨의 폭이 좁거나 패스 기록이 짧으면 워커 기상·합류 비용이 이득을 지울 수 있고, 레벨 경계를 없애면 GPU 리소스 순서가 깨질 수 있다. | 기존 `RT.Graph.executeParallel` 및 패스별 비용과 레벨 폭·유휴 시간을 함께 측정한다. 병목이 큰 독립 패스의 CPU 전처리로 확인될 때만 그 준비를 기록과 별개인 작업으로 앞당기거나 합법적인 독립성을 그래프에 표현한다. 패스의 커맨드 리스트 기록과 배리어·레벨 제출 순서는 계속 그래프 의존성의 소유로 둔다. |
| 유지(이미 폭넓게 적용) | 컴포넌트 틱은 오브젝트/배치 단위 fork-join 및 선행 단계, 변환 계층은 더티 루트별 병렬 갱신, 애니메이션은 비용 기반 평가, 프레임 시스템은 접근권 기반 lane, GPU 업로드·수목 배치·환경 식생도 독립 작업을 나눈다. 렌더 그래프와 셰이더 쿠킹은 독립 레코드/포맷을 병렬 처리하고 결과 합치기는 직렬화한다. PackWriter도 항목별 압축·CRC를 병렬로 한다. 틱의 비용 기반 분배 실험은 주석상 8개 게임 중 1개만 이득이고 7개는 같거나 느렸다. | 기존 병렬 경로를 기준선으로 삼고 시스템마다 새 풀/스레드를 추가하지 않는다. 특히 틱은 기본 분배 정책을 무조건 바꾸지 말고 게임별 측정 결과를 따른다. 병렬화 후보에는 작업 수·청크 크기·큐 우선순위·합류 시간과 단일 스레드 결과의 결정성을 함께 기록한다. |

**우선순위 제안:** 사용자가 체감하는 저장 멈춤은 씬 스냅숏을 분리한 비동기 저장을 먼저 실측하고, 처리량 확장은 씬 쿠킹을 다음으로 검토한다. 런타임 씬 생성과 렌더 기록은 이미 일부 비동기/병렬이므로 각 단계별 타이머·프레임 프로파일에서 실제 병목이 드러날 때만 병렬 폭을 늘린다. 현재 문서에 쓴 쿠킹·저장 확장 후보는 정확한 실측 전의 구조 검토 항목이며, 아직 병목으로 확정한 것은 아니다.

### 렌더 스레드와 업로드 전용 스레드 검토 (2026-11-07)

**Unreal과의 용어 구분:** Epic 문서가 설명하는 렌더 스레드 밖의 대표 스레드는 전용 업로드 스레드가 아니라 **RHI Thread**다. Render Thread가 플랫폼 중립 RHI 명령을 만들면 RHI Thread가 이를 플랫폼 API 명령으로 변환·실행하며, 프레임 사이에 작업을 겹치되 GPU 제출 순서는 보존한다([Threaded Rendering](https://dev.epicgames.com/documentation/en-us/unreal-engine/threaded-rendering-in-unreal-engine), [Parallel Rendering Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)). Unreal Texture Streaming은 보이는 정도와 메모리 예산으로 mip 상주를 관리하는 별도 시스템이다([Texture Streaming](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-streaming-in-unreal-engine)). 따라서 Unreal의 이 구조를 “GPU 업로드만 처리하는 스레드”를 추가하는 근거로 그대로 옮기지는 않는다.

| 구분 | 저장소에서 확인한 사실 | 판단 |
|---|---|---|
| 이미 분리된 렌더 실행 | [`RenderThread`](../Source/Engine/Renderer/RenderThread.h)는 게임 스레드에서 받은 패킷을 전용 스레드에서 실행한다. 렌더 그래프는 독립 패스의 커맨드 기록을 이미 병렬화하지만, 레벨 경계에서 합류하고 GPU 제출을 순서대로 진행한다([`RenderGraph::executeParallel`](../Source/Engine/Renderer/Graph/RenderGraph.cpp)). 현재 Unreal RHI Thread와 같은 별도 RHI 명령 소비 스레드는 확인되지 않았다. | RT CPU의 드라이버 호출·커맨드 제출이 병목이면 전용 업로드 스레드보다, RHI 명령 수집과 실행을 분리하는 RHI Thread형 구조가 비교 대상이다. 이는 모든 프레임 명령의 소유권·순서·자원 수명을 바꾸는 큰 변경이므로 프로파일에서 RT CPU 병목과 GT/RT 겹침 부족이 입증되어야 한다. |
| 메시 GPU 생성 | [`GPUUploadQueue::flush`](../Source/Engine/Graphics/Upload/GPUUploadQueue.cpp)는 이번 스냅샷에 보이는 메시의 RHI 생성을 `TaskManager::runParallel`로 나누지만 포크-조인으로 호출 스레드가 완료를 기다린다. 이는 전용 스레드가 아니며, 대기 구간은 `GT.GPUUpload.flush`로 계측된다. 완료 후 스냅샷을 내보내므로 같은 프레임 렌더에서 메시가 빠지는 것을 막는다([`RenderPacketSceneCollector::buildSnapshot`](../Source/Engine/Renderer/Frame/Packet/RenderPacketSceneCollector.cpp)). | `GT.GPUUpload.flush`가 실제 GT 임계 경로라면 먼저 워커 풀의 점유·작업시간과 메시 수를 측정한다. 대기를 없애려면 보이는 즉시 사용 가능한 메시를 보장하는 현재 계약을 바꾸어야 한다(예: 이전 프레임 선요청 또는 준비 전 메시를 잠시 제외). 완료 전에 RT로 넘기거나 임의의 새 스레드에서 같은 Mesh를 만들면 팝인·중복 생성·RHI 수명 경쟁을 일으킬 수 있다. |
| 텍스처 에셋 로드 | 텍스처 파일 읽기·디코드는 로드 작업에서 수행한다. 이후 [`TextureCache::completePendingLoads`](../Source/Engine/Graphics/Texture/TextureCache.h)는 렌더 스레드에서 장치 자원을 만들고 업로드를 제출하며, 제출 수를 프레임 예산으로 제한하고 이미 제출한 업로드는 뒤 프레임에서 티켓으로 폴링한다([`FrameRenderer::executePacket`](../Source/Engine/Renderer/Frame/FrameRenderer.cpp), [`Texture2D::finishUpload`](../Source/Engine/Graphics/Texture/Texture2D.cpp)). 블로킹 acquire·결정적 테스트 경로는 별도로 끝날 때까지 기다린다. | 비동기 IO→디코드→제출→폴링 파이프라인은 이미 있어 “모든 텍스처를 새 스레드로 옮기기”는 중복이다. `AssetLoadProfiler`는 단계별 시간 구조를 제공하지만 [`TextureLoadOperation`](../Source/Engine/Graphics/Texture/TextureCache.cpp)은 현재 `AssetLoadScope`를 열지 않는다. `RT.TextureRegionUpdates`도 구간 갱신·신규 업로드·밉 스트리밍을 한 범위로 묶으므로, 업로드 전용 계측(제출 CPU 시간·바이트·건수·프레임당 대기 수)을 먼저 넣고 RT의 staging 복사나 API 호출이 실제 병목인지 확인한다. OpenGL 컨텍스트 점유와 DX11 즉시 컨텍스트 잠금은 예외·직렬화 경로로 남겨야 한다. |
| GPU 전송 실행 | 업로드 API는 요청 스레드가 스테이징에 데이터를 복사해 전송을 제출하고, 기다리지 않는 경로는 티켓으로 완료를 확인한다. DX12는 전송 전용 펜스를 쓰지만 제출된 복사 리스트는 디바이스의 `_commandQueue`로 실행한다. Vulkan도 전송 커맨드 버퍼를 만들지만 `vkQueueSubmit` 대상은 `_graphicsQueue`다. 따라서 현재 코드에서 전용 CPU 업로드 스레드나 별도 GPU copy queue가 일반 경로로 동작한다고 볼 근거는 없다. | CPU 스테이징 준비와 GPU 전송은 다른 병목이다. CPU 제출을 다른 스레드로 옮겨도 GPU 복사 시간·대역폭은 줄지 않으며, 별도 GPU copy queue를 추가하려면 백엔드별 큐 선택·소유권 이전·동기화·자원 상태 전이와 fallback을 별도로 구현해야 한다. GPU copy/graphics 중첩이 필요한 측정 근거가 없으면 그 작업은 보류한다. |

**결론:** 지금 당장 전용 업로드 스레드를 추가할 근거는 없다. 이미 공유 워커 풀을 이용한 메시 생성과 비동기 텍스처 전송이 있고, 문제 후보는 메시 생성에서 GT가 기다리는 비용 또는 텍스처 제출 중 RT의 CPU 비용으로 서로 다르다. A/B에서는 `gv_gpuUploadQueue`를 켠/끈 경우의 GT/RT 프레임 시간, 메시 생성 수·대기 시간, 텍스처 `IO/Decode/Upload` 비용·대기 텍스처 수를 DX12·Vulkan과 OpenGL에서 비교한다. RT의 RHI 실행이 실제 병목이면 업로드 전용 스레드가 아니라 프레임 명령 순서와 CPU 소유권을 보존하는 RHI Thread형 설계의 작은 프로토타입을 별도 검토한다. 측정 전에는 성능 이득으로 확정하지 않는다.

### 에디터 UI 스레드 분리 검토 (2026-11-07)

Graphify로 호출 관계를 좁힌 뒤 앱 루프, 에디터 ABI, ImGui 플랫폼 백엔드, 뷰 렌더 타깃의 실제 소유권을 코드에서 확인했다. 렌더 스레드 분리는 이미 되어 있지만 UI 프레임 전체를 메인 스레드 밖으로 옮길 수 있는 구조는 아니다.

| 우선순위 | 코드에서 확인한 현재 경계 | 개선 방향과 완료 조건 |
|---|---|---|
| 유지(기존 UI·렌더 병렬화) | [`App::runFrame`](../Source/App/App.cpp)은 게임 모듈 갱신 뒤 메인 스레드에서 [`EditorModuleManager::updateEditorUI`](../Source/App/EditorModuleManager.cpp)를 호출하고, 그 결과로 씬 틱 여부·뷰 렌더 타깃을 확정한 뒤 `Engine::update`를 호출한다. [`IEditor`](../Source/Editor/IEditor.h)의 계약도 `updateUI`는 메인 스레드, `prepareRender`·`render`·`postPresent`는 렌더 스레드로 나눈다. UI가 복사한 [`EditorDrawDataSnapshot`](../Source/Editor/Common/Backend/EditorDrawDataSnapshot.h)은 [`DrawSnapshotHandoff`](../Source/Editor/Common/Backend/DrawSnapshotHandoff.h)를 통해 렌더 스레드가 이전 프레임을 그리는 동안 다음 UI 프레임을 만들게 한다. | 이 UI→렌더 스냅숏 경계는 유지한다. 렌더 스레드가 살아 있는 ImGui 상태를 읽지 않는 현재 보장을 깨지 않는다. |
| 차단(입력·플랫폼 소유권) | [`App::onWindowMessage`](../Source/App/App.cpp)는 OS 이벤트를 동기적으로 에디터에 먼저 전달하고, `processEvent`가 같은 ImGui IO에 입력을 넣은 뒤 반환한 포착 결과로 게임 입력 전달 여부를 정한다([`ImGuiEditor::processEvent`](../Source/Editor/ImGuiEditor.cpp)). `NewFrame`, `Render`, `UpdatePlatformWindows`도 그 컨텍스트와 플랫폼 백엔드를 사용한다. Win32 백엔드는 WndProc 이벤트를 직접 처리하고, X11 백엔드는 전달된 `XEvent`를 즉시 읽는다. | UI 스레드로 옮긴다면 ImGui 컨텍스트와 모든 플랫폼 호출을 한 소유 스레드에 고정하고, OS 이벤트는 순서·프레임 ID가 있는 큐로 전달한다. 입력 포착 응답이 비동기일 때 게임과 에디터 중 누가 키를 받는지, 자동화의 가상 입력과 동기 재생을 어떻게 보존할지 먼저 계약·테스트한다. |
| 차단(씬·엔진 상태 공유) | 프레임 단계는 패널 그리기뿐 아니라 명령·씬 세션·에셋 리로드·제목 갱신을 처리한다([`EditorFrameSteps.cpp`](../Source/Editor/EditorFrameSteps.cpp)). 예를 들어 [`HierarchyPanel`](../Source/Editor/Panels/Scene/HierarchyPanel.cpp)은 활성 `GameObjectManager`를 읽고 선택·재부모화 명령을 실행한다. 반면 [`EditorRenderViews`](../Source/Editor/Common/Workspace/EditorRenderViews.h)는 UI 프레임에서 뷰 상태를 기록하고, 크기 변경 시 `TextureCache`에 렌더 타깃을 요청·교체한다. 프레임 끝에 확정하는 씬 틱/뷰 출력과 원시 `CameraComponent*`도 엔진이 소비한다. | UI와 시뮬레이션을 겹치려면 라이브 `Scene`·오브젝트·컴포넌트·RHI 자원을 양쪽에서 읽고 쓰게 하지 않는다. 메인 스레드가 만든 불변 에디터 입력 스냅숏을 UI에 주고, 편집 명령·선택 변경·뷰 요청을 식별자 기반 출력으로 돌려받아 메인 스레드에서 검증·적용한다. 카메라와 엔진 자원은 원시 포인터를 넘기지 말고 소유 스레드에서 핸들로 다시 찾는다. 프레임 결과가 필요한 `Engine::update`와 Play/Pause/Step 동작은 결정적 순서를 유지한다. |
| 조건부(실측 뒤 UI 계산 분리) | [`ImGuiEditor::updateUI`](../Source/Editor/ImGuiEditor.cpp)에는 `GT.Editor.frameSteps`, 단계별 `GT.Editor.step.*`, 스냅숏 대기 `GT.Editor.waitDrawSnapshot`·게시 구간이 있고, 패널별 시간은 `-gv_editorPanelTimes`로 잴 수 있다. 파일 IO·색인 등은 이미 [`EditorBackgroundTask`](../Source/Editor/Common/Task/EditorBackgroundTask.h) 규약으로 TaskManager 워커에서 계산하고 UI 스레드가 결과를 가져온다. | 먼저 대표 대형 씬·패널에서 UI CPU 시간과 패널별 시간, 스냅숏 슬롯/게시 대기를 따로 측정한다. 대기가 크면 렌더 프레임 지연 문제로 분류하고 UI 스레드 이동 근거로 삼지 않는다. 패널 계산이 병목이면 불변 입력→세대가 붙은 결과를 돌려주는 기존 백그라운드 잡 패턴으로 순수 계산·파일 작업부터 분리하고, UI 위젯 생성과 상태 변경은 소유 스레드에 둔다. |
| 큰 구조 변경(전용 UI 스레드) | 현재 UI 업데이트는 게임 갱신 뒤, 엔진 업데이트 앞에서 동기적으로 한 번 완료되어야 뷰 타깃·틱 상태를 그 프레임에 사용한다. 모듈 리로드·RHI 교체·종료는 에디터와 확장 DLL의 콜백 및 렌더 스냅숏 수명을 함께 다룬다. | UI 전체를 옮기는 것은 가능하더라도 단순히 `updateUI()` 호출을 새 스레드로 감싸는 변경은 아니다. 프레임 입력/출력 큐, UI 컨텍스트·플랫폼 백엔드의 단일 소유권, 씬 명령 커밋, 출력 프레임 지연 계약, 핫리로드·종료 전 UI 작업 drain을 함께 설계해야 한다. 위 프로파일에서 UI 생성이 실제 메인 스레드 임계 경로임을 확인한 경우에만 작은 프로토타입을 만들고, 입력·Play/Pause/Step·뷰 크기 변경·창 닫기·확장 리로드·자동화 결정성 테스트를 통과시킨다. |

**결론과 진행 순서:** 에디터 UI를 별도 스레드로 분리하는 것은 이론상 가능하지만 현재 구조에서는 안전한 즉시 최적화가 아니다. 렌더와의 병렬화는 이미 draw-data 스냅숏으로 이루어지고, `updateUI`를 그대로 옮기면 동기 이벤트 포착·라이브 씬 편집·뷰 렌더 타깃 갱신·프레임 출력의 소유권이 충돌한다. 우선 기존 계측으로 UI 계산과 렌더 대기를 구분하고, 비용이 확인된 순수 계산/IO만 기존 백그라운드 작업 경로로 옮긴다. 전용 UI 스레드는 불변 입력/출력 경계와 명시적인 프레임 지연이 필요하다는 점을 감수할 만큼의 메인 스레드 병목이 입증될 때만 검토한다. 이 문제는 UI 함수 하나가 아니라 에디터가 라이브 엔진 상태를 직접 편집하는 구조에서 비롯되므로, 같은 공유 경계는 새 비동기 패널 작업에도 적용해 점검한다.

### 에디터 기능 · UX 고도화 후보 (코드 · Graphify · 공식 문서 대조 2026-11-07)

코드와 최신 Graphify 그래프에서 실제 패널·서비스·탐색 경로를 확인하고, 상용 엔진 문서는 기능의 존재 여부가 아니라 반복 작업 UX의 비교 기준으로만 사용했다. 결론은 “기능이 거의 없다”가 아니다. `Source/Editor/Panels` 에는 씬·인스펙터·콘텐츠 브라우저 외에도 애니메이션·대화·오디오·머티리얼·UI·렌더·프로파일러·패키징·멀티플레이 도구가 있다. 사용자 단축키, 명령 팔레트, 에셋/오브젝트 Quick Launcher, 다중 선택 인스펙터, Undo/Redo 기록과 명명 레이아웃, Map Check, 에셋 참조 찾기와 파일 이동 시 경로 자동 수정, 비동기 임포트와 진행 상태, 자체 시나리오 테스트도 이미 구현되어 있다. 아래는 이 기반을 중복 구현하지 않고 작업 흐름의 완성도를 높일 후보만 남긴다.

| 우선순위 | 코드에서 확인한 현재 UX와 비교 근거 | 개선 방향과 완료 조건 |

검색 가능한 표/상세와 미리보기(외형·Ability·장비). 각 화면은 런타임이 소비하는 기존 에셋을 직접 편집하고, 유효 데이터와 미리보기 결과를 구별하며, 검증 오류를 해당 요소에 표시한다. 반복해서 같은 선택기·기즈모·검증/Undo 결합이 나타날 때만 작은 공용 위젯/헬퍼를 추출한다. 실제 제작 빈도·오류율이 낮은 데이터는 Inspector/표로 충분할 수 있으므로 “모든 것의 시각화”를 별도 그래프·전용 패널 수로 해석하지 않는다. |

**이미 있는 기능의 확장 우선순위:** Undo/Redo는 이미 데이터 기반 `CommandStack` 과 별도 History 패널을 갖고, 레이아웃은 이름 붙여 저장/복원할 수 있다. 인스펙터 다중 선택과 프로퍼티 편집, 콘텐츠 브라우저의 에셋 생성 템플릿·참조 찾기·Git LFS 배지, Map Check의 대상 선택/초점, 단축키 재지정도 있으므로 같은 기능을 새로 만들지 않는다. 개선은 Undo 트랜잭션 누락·취소 불가 편집을 실제 시나리오로 찾아 보강하고, 검색·컬렉션·복구·문제 해결의 끊긴 연결을 우선한다.

**직접 조작·에셋 배치는 부분적으로 이미 지원한다.** 콘텐츠 브라우저에서 에셋을 고르고 더블클릭해 전용 도구/미리보기를 열 수 있고, 에셋 경로 인스펙터는 형식 제한이 있는 검색 선택기·경로 입력·드래그 드롭·콘텐츠 브라우저에서 보기 기능을 제공한다. 씬 뷰포트는 씬 오브젝트 피킹/선택과 콘텐츠 브라우저에서의 에셋 드롭을 지원하며, 계층 창은 오브젝트 재부모화·형제 순서 이동과 프리팹 자식 배치를 지원한다. 미리보기 뷰포트의 피킹은 그 미리보기 씬의 오브젝트 선택에 연결된다. 그러나 이것이 모든 에셋과 모든 프리뷰에서 통하는 하나의 제작 흐름은 아니다. [`EditorAssetTypeActions`](../Source/Editor/Common/Workspace/Asset/EditorAssetTypeActions.h)에 등록된 뷰포트 배치는 프리팹·메시·텍스처가 각각 오브젝트/스프라이트를 만들고, 씬은 열기 동작을 한다. 다른 에셋 종류는 일반적으로 드롭 대신 열기 동작으로 넘어간다. 배치 위치도 실제 표면 피킹이 아니라 2D Z=0/3D Y=0 평면이며, 교차점을 구하지 못하면 원점으로 떨어진다. 배치 전 고스트, 표면 정렬, 격자 스냅과 프리뷰에서 원본 에셋을 씬으로 끌어오는 공통 경로는 확인되지 않았다. 다음 단계는 종류별 동작 등록을 재사용해 캔버스의 실제 충돌 표면/지형에 배치하고, 놓기 전 미리보기와 스냅·회전 및 실패 위치 표시를 제공하는 것이다. 선택된 종류에서만 유효한 drop target을 강조하고, 지원하지 않는 종류는 원점 배치나 조용한 폴백 없이 허용되지 않는 이유와 가능한 열기 동작을 보인다. 콘텐츠 브라우저, 씬 뷰포트, 인스펙터, 프리뷰 간 에셋/씬 선택 동기화는 임의 전역 선택 하나로 합치지 말고 문맥(활성 문서·메인 씬·프리뷰 씬)을 보존한다. 완료 기준은 프리팹/메시/텍스처 각각의 배치 미리보기·취소·Undo, 표면/평면 교차 실패, Play 중 편집 거절, 그리고 프리뷰 선택이 메인 씬 선택을 오염시키지 않는 자동화 시나리오다.

#### 타일맵과 스프라이트 시트 저작

- **타일맵 편집기가 없는 것은 아니다.** [`TileMapPanel`](../Source/Editor/Panels/TileMap/TileMapPanel.h)은 확대/이동 가능한 캔버스, 브러시·사각형·채우기·픽커·선·지우기, 워프/플래그/데이터 레이어를 제공한다. `.tileset.xml`이 실제 아틀라스 텍스처를 가리키면 팔레트와 맵 셀에 텍스처 타일을 표시하고, 규칙 타일의 이웃에 따른 결과와 애니메이션 타일을 런타임과 같은 규칙으로 그린다. 즉 실제 아틀라스 기반으로 맵을 그릴 토대는 있다.
- **저작 공백은 타일셋과 검증 시나리오다.** [`TileSetAsset`](../Source/Engine/TileMap/TileSetAsset.h)은 아틀라스 경로·균일한 열/행 격자·타일 크기·브러시·규칙 타일·애니메이션·solid·이동 비용을 XML로 읽는다. 하지만 Editor의 에셋 종류/전용 패널 등록에서 타일셋 편집기는 확인되지 않아 브러시 정의와 규칙 패턴을 시각적으로 만들고 고치는 흐름은 부족하다. 실제 기준 에셋 [`town.tileset.xml`](../Content/game/pixeltown/tilesets/town.tileset.xml)과 [`town.tilemap.xml`](../Content/game/pixeltown/maps/town.tilemap.xml)은 실제 픽셀 아틀라스 `engine/textures/pixel/puny_world/puny_world.dds`를 사용한다. 기존 `tilemaptools`는 기본 플래그 레이어의 도구 조작, `tilemapdatalayers`는 데이터 레이어 저장/재로드를 검증하지만, 이 실제 타일셋/텍스처를 사용해 타일을 칠하고 저장 뒤 렌더 결과를 확인하는 시나리오는 아니다.
- **스프라이트 시트는 기본 편집 기능이 이미 있다.** [`SpriteClipPanel`](../Source/Editor/Panels/Animation/SpriteClipPanel.h)은 아틀라스를 격자 이미지로 보여 주고 열/행 수를 정해 셀을 고르거나 전체 셀을 프레임으로 추가한다. 클릭/Shift 클릭, 프레임별 UV·지속 시간·테두리의 숫자 편집, 재생 미리보기와 저장/되돌리기도 제공한다. 다만 격자 분할 중심이며 불규칙 영역을 이미지에서 직접 사각형으로 지정·조정하거나 투명 픽셀 기준으로 여러 프레임을 자동 분리하는 흐름은 확인되지 않았다. 픽셀 경계·패딩이 있는 실제 시트 작업은 수치 UV 수정에 기대게 된다.
- **고도화 순서:** 먼저 기존 런타임 데이터 형식을 그대로 편집하는 `.tileset.xml` 시각 편집을 추가한다. 실제 아틀라스 미리보기/셀 선택을 기반으로 일반·애니메이션 브러시의 프레임, solid/이동 비용, RuleTile 이웃 패턴과 결과를 편집하고, 저장 전 셀 범위·중복 이름·잘못된 규칙을 표시한다. 다음으로 SpriteClip의 기존 격자 슬라이싱을 보존하면서 실물 시트에서 프레임 경계를 드래그해 선택/수정하는 최소 기능을 더한다. 자동 투명 영역 탐색, 회전/패킹된 아틀라스 등은 실제 콘텐츠가 요구할 때 지원 여부와 런타임 포맷을 함께 설계하고, 단순히 UI만 추가해 런타임과 다른 UV 데이터를 만들지 않는다.
- **필수 시나리오:** [`town.tileset.xml`](../Content/game/pixeltown/tilesets/town.tileset.xml)·[`town.tilemap.xml`](../Content/game/pixeltown/maps/town.tilemap.xml)의 실제 픽셀 아틀라스 구성을 테스트용 임시 에셋에서 사용해 브러시 선택, 페인트/채우기/픽커, 규칙 타일 결과, 저장·재로드 및 렌더 결과를 확인한다. 별도 시나리오는 [`hero.sprite.xml`](../Content/game/pixeltown/sprites/hero.sprite.xml)이 쓰는 실제 캐릭터 시트로 셀 선택과 전체 격자 추가, 불규칙 프레임 경계 조정, 재생 프리뷰, 저장·재로드 후 UV/프레임 수를 검사한다. 기존 콘텐츠를 직접 수정하지 않고 테스트용 복사본을 쓰며, 프리뷰와 런타임이 같은 UV/셀 해석을 사용함을 검증한다. 현재 [`spriteclippanel.scenario.xml`](../Content/engine/automation/editor/spriteclippanel.scenario.xml)은 프레임 추가/삭제·애니메이션 구간·저장 왕복을 확인하지만 실제 아틀라스 슬라이싱은 확인하지 않는다.

**시각 저작 적용 시 지켜야 할 경계와 검증**

- **표현은 데이터 의미를 따른다.** 공간 관계에는 뷰포트·기즈모, 계층 영향에는 트리·색 오버레이, 시간에는 타임라인, 분기/연결에는 그래프, 목록성 설정에는 검색 가능한 표·인스펙터를 쓴다. 한 화면에 모든 편집 패턴을 통합하지 않는다.
- **저작 데이터와 런타임 관측을 분리한다.** 편집 UI는 저장될 에셋을 변경하고, 프리뷰는 그 에셋을 격리된 씬/플레이어에서 소비한다. DevTools 런타임 디버거는 실제 실행 상태를 읽기 전용으로 보여 준다. 프리뷰에서만 성공하고 실제 런타임은 다른 규칙으로 해석하는 별도 사본을 만들지 않는다.
- **선택·변경·저장 수명주기를 통일한다.** 선택 대상과 활성 문서가 바뀔 때 이전 드래그를 종료하고, 빠른 드래그는 하나의 Undo 단계로 묶으며, 패널 닫기/재로드 전 dirty 확인을 보장한다. 본/소켓/에셋 참조가 사라지거나 스켈레톤이 바뀌면 기존 값을 조용히 폐기하지 않고 누락·재연결 상태를 표시한다.
- **기즈모를 데이터 편집과 혼동하지 않는다.** 기존 씬 기즈모는 씬 오브젝트를 고친다. 소켓·본 마스크 같은 에셋 값의 직접 조작은 데이터 로컬 공간 변환, 드래그 시작값/끝값, Undo coalescing, 문서 dirty/저장 경로를 해당 모델에 연결해야 한다. 프리뷰 오브젝트만 움직여 원본 에셋이 바뀐 것처럼 보이게 하거나, 원본을 건드리지 않는 preview-only 동작을 저장된 편집으로 표시하지 않는다.
- **검증은 보기 좋은 색칠로 대체되지 않는다.** 마스크는 실제 스켈레톤에 없는 본 이름, 상속과 개별 덮어쓰기의 최종 가중치, 0/1 경계 및 저장 후 재로드를 확인한다. 소켓은 부모 본/종류/변환의 허용 범위, 대칭·후보 연결, hot reload 뒤 같은 배치를 확인한다. 기즈모 조작 후 XML 재로드 결과와 런타임 적용 결과가 모델의 미리보기와 일치해야 한다.
- **첫 두 기능을 공통화의 실측 사례로 쓴다.** 애니메이션 마스크와 소켓 편집을 구현·캡처해 뼈 선택, 픽킹, 뷰포트 상호작용, Undo, 오류 표시에 실제로 공통 코드가 있는지 확인한다. 공통점이 충분하지 않으면 도메인별 UI를 유지한다. 완료는 XML 왕복/모델 테스트, 서로 다른 스켈레톤에서의 마스크 유효성, 소켓을 여러 포즈에서 조정한 뒤 재로드한 배치 일치, `editor/uiaudit.scenario.xml`과 `editor/uicapture.scenario.xml`의 화면 검토로 판정한다.

#### 볼륨 안개 저작·시각화

- **기본 편집은 가능하다.** 씬의 [`FogComponent`](../Source/Engine/Environment/Fog/FogComponent.h)를 선택해 일반 인스펙터에서 색·밀도·높이 감쇠와 볼륨 안개 켜기, 볼륨 거리·산란 배율·이방성을 조정할 수 있다. 효과는 Forward/Deferred 파이프라인에서 공통 fog 패스를 거치고, 별도 컴퓨트 패스가 froxel 볼륨을 만든다([`FrameFog`](../Source/Engine/Renderer/Frame/PostProcess/FrameFog.h)). 즉 기능과 씬 데이터 편집은 있으나 이는 전용 이펙트 저작기와 같은 수준은 아니다.
- **확인한 데모/검증:** `game/empty/maps/fogvolumetric.scene.xml`은 기존 안개 장면을 상속하고 점광원과 볼륨 안개를 추가한다. `fogvolumetric.scenario.xml`은 일반 안개와 볼륨 안개 장면을 연속 캡처해 이미지 차이를 검사한다. 이는 구현 경로가 작동하는지 보는 회귀 테스트이지, 아티스트가 매개변수를 조절하는 전용 프리뷰나 품질/성능 검증 도구는 아니다.
- **전용 도구 공백:** 이번 검색에서는 볼륨 안개 전용 에디터 패널, 산란/밀도 볼륨의 froxel 슬라이스 표시, 설정값을 바꾸며 두 모드를 나란히 비교하는 프리뷰를 찾지 못했다. `FrameFog`의 froxel 결과는 렌더러 내부 구조 버퍼이며 Render Targets 패널의 일반 타깃 표시만으로 이를 바로 시각화한다고 가정하지 않는다. 그러므로 “안개를 설정할 수 없다”가 아니라 **설정은 가능하지만 복잡한 조명 산란을 이해하고 튜닝할 전용 저작·진단 UX가 부족하다**고 구분한다.
- **권장 개선:** 기존 Inspector와 씬 프리뷰를 재사용하는 작은 볼륨 안개 작업 흐름부터 만든다. 실시간 변경 프리뷰, 볼륨 안개 on/off 비교, 거리/높이 단면 및 산란·투과율 froxel 시각화, 주요 광원과 적용 범위 표시, GPU 패스 시간/현재 비활성 사유를 제공한다. 일반 안개 결과와 볼륨 산란을 분리해 보고, 카메라 이동·광원 변경·볼륨 거리 변경에도 같은 프레임 조건으로 비교할 수 있어야 한다. 새 저작 에셋 형식을 만들지 말고 `FogComponent`의 씬 값을 정본으로 유지한다.
- **완료 기준:** 기존 fog 자동화 시나리오를 유지하면서 편집기에서 값을 조정한 결과가 저장/재로드 뒤 같은 장면에 반영되고, 일반/볼륨 비교와 단면 시각화가 렌더러 결과와 일치해야 한다. 컴퓨트 경로가 비활성(기기/셰이더/라이트 조건 등)일 때 평범한 안개로 조용히 폴백하는 화면을 성공으로 오인하지 않도록 이유를 표시하고, 여러 해상도와 품질 설정에서 GPU 비용을 측정한다.

**비교 범위와 제외:** 상용 엔진의 모든 기능을 패리티 목록으로 복제하지 않는다. 코드 에디터/디버거, 마켓플레이스, 클라우드 협업, 원격 빌드, AI 검색은 제품의 주 사용자와 지원 비용이 확인되지 않아 이번 우선순위에서 제외한다. 특히 멀티 유저 편집·외부 서비스·유료 공급자 연결은 비용/운영 책임을 먼저 정한 뒤 별도 판단한다. 이 표는 UI 구현의 완전한 육안 감사가 아니라 코드와 등록된 기능 표면의 구조 검토다. 다음 UI 변경은 프로젝트 규칙 [`EditorUI`](agents/EditorUI.md)의 토큰·접근성·캡처 시나리오 기준으로 실제 화면을 확인한다.

**허용 출처와 적용 규칙**

- **Kenney:** 공식 FAQ는 asset pages의 게임 에셋을 CC0이며 상업 프로젝트에 사용 가능하다고 명시한다([Kenney FAQ](https://kenney.nl/support)). 단, 각 다운로드 묶음에 동봉된 `License.txt`와 실제 사용 파일 목록을 확인하고 보관한다.
- **Poly Haven:** 모델·텍스처·HDRI가 CC0이며 상업 이용·재배포가 가능하다고 명시한다([Poly Haven License](https://polyhaven.com/license)). 에셋별 페이지와 출처도 크레딧에 기록한다.
- **ambientCG:** 다운로드 에셋이 CC0이며 상업 프로젝트에 원본 포함도 가능하다고 명시한다([ambientCG License](https://docs.ambientcg.com/license/)).
- **KayKit 및 현재 저장소의 기존 오디오 팩:** 이미 사용한 개별 팩에 한해 [`common/credits.md`](../Content/common/credits.md)와 [`common/audio.sources.json`](../Content/common/audio.sources.json)의 출처·라이선스 기록을 재사용한다. 새 팩은 같은 제작자라는 이유만으로 기존 팩의 라이선스를 추정하지 않는다.
- **OpenGameArt 등 사용자 업로드 사이트:** 사이트 전체 라이선스로 간주하지 않는다. 개별 항목이 CC0임을 원본 페이지와 내려받은 라이선스에서 확인한 경우만 허용한다. CC-BY는 상업 이용이 가능해도 현재의 “CC0만” 범위 밖이다([CC-BY 4.0 조건](https://creativecommons.org/licenses/by/4.0/)). NC·ND·불명확한 항목은 제외한다.
- **Quaternius:** 현재 공식 QAL은 무료 상업 이용을 허용하지만 원본 에셋 단독 재배포를 금한다([Quaternius QAL](https://quaternius.com/license.html)). 따라서 “무료 상업 이용” 기준에는 맞을 수 있어도 CC0-only 기준에는 맞지 않으며, 원본을 Git/LFS나 공개 템플릿으로 재배포해서도 안 된다. 이미 받은 구버전 묶음은 다운로드 시점의 동봉 라이선스/버전이 확인될 때만 그 기록대로 판단한다. 현재 common 폴더의 Quaternius 원본 디렉터리에는 라이선스/README 파일이 발견되지 않아, 기존 항목은 원본 구매·다운로드 폴더의 증거를 대조하기 전까지 법적 상태를 확정하지 않는다.

**추가 전 체크리스트:** (1) 게임/키트에서 실제로 쓰는 파일과 키트 ID, (2) 원본 다운로드 페이지와 라이선스 원문/버전, (3) 원본 파일 SHA-256 및 받은 날짜, (4) 원본·변환본 경로와 변환 도구/옵션, (5) 재배포·수정 허용 여부를 `credits.md` 또는 형식이 정해진 출처 목록에 남긴다. CC0도 상표·특허·초상/프라이버시 등 제3자 권리를 자동으로 허가하지 않는다([CC0 안내](https://creativecommons.org/publicdomain/zero/1.0/)). 원본에 브랜드·실존 인물·유명 캐릭터가 들어가면 라이선스 표기와 별도로 제외 또는 권리 검토한다. 기존 폴더 규칙(`common` 공유 원본, 게임별 원본, 임포트된 리소스)과 [공용 리소스 구조](ResourceStructure.md)를 유지하고, 원본은 사용되는 파일만 Git LFS에 둔다. 단순히 “무료”라고 표시된 에셋을 자동 다운로드하거나 포함하는 도구는 만들지 않는다.

**실행 순서:** 먼저 이미 있는 각 게임의 `credits.md`와 공용 출처 기록을 키트별로 연결해 중복 구매/다운로드를 막는다. 그다음 기능 시연에 실제로 부족한 리소스만 위 후보에서 골라 팩 단위 CC0 증거와 해시를 남기고, 임포트·게임 화면·출하 패키지에 반영한다. 개별 자산을 확인하지 않고 모든 하위 키트의 리소스가 충족됐다고 간주하지 않는다.

### GameFramework 고도화 후보 (코드 대조 2026-11-07)

GameFramework의 모듈·수명주기·서비스·테스트 경계를 현재 코드와 Graphify로 확인했다. 키트 전반의 기능 구현을 줄별로 감사한 것은 아니며, 아래는 코드에서 확인된 구조와 그에 따른 다음 단계다.

| 우선순위 | 코드에서 확인한 내용 | 개선 방향과 완료 조건 |
|---|---|---|
| 높음 — 시작 실패 정리 | [`GameInstance::initialize`](../Source/GameFramework/Runtime/Foundation/Framework/Flow/GameInstance.cpp)는 게임 범위·서브시스템·네트워크 보안 제공자·세션·사운드·카탈로그·자동 저장을 순서대로 올릴 수 있다. 그런데 공용 [`ModuleInstanceUtil::createInstance`](../Source/ModuleManager/ModuleInstanceUtil.h)는 초기화가 false면 `shutdown` 없이 모듈의 `destroy`만 부른다. [`GameInstance` 소멸자](../Source/GameFramework/Runtime/Foundation/Framework/Flow/GameInstance.cpp)는 현재 게임 범위만 분리한다. 다만 `_gameScope` 멤버가 소멸할 때 소유 서브시스템은 별도로 종료·파괴된다. 이 자동 처리가 `GameInstance::shutdown`의 명시적 정리(오디오 이벤트 해제·네트워크 보안 제공자 제거·파생 `onShutdown`)까지 대신하지는 않는다. | 초기화 단계를 부분 실패에도 안전하게 되돌리는 단일 정리 경로를 만든다. 모든 단계에 상태 플래그를 덧붙이기 전에 먼저 책임별 롤백 경계를 정하고, 정리의 중복 호출도 안전하게 한다. 모듈 공통 유틸리티가 임의로 `shutdown`을 호출하는 것은 다른 모듈 계약까지 깨뜨릴 수 있으므로 피한다. 서브시스템 초기화, 세션 오픈, 오디오/필수 데이터 로드, 자동 저장, 파생 `onInitialize` 실패 각각에서 게임 범위·서비스 제공자·세션·오디오·파생 리소스가 남지 않고 정상 재시작되는 테스트를 추가한다. |
| 높음 — 서비스 충돌 오류 전파 | [`GameInstance::bindScopedService`](../Source/GameFramework/Runtime/Foundation/Framework/Flow/GameInstance.h)는 타입이 이미 등록됐으면 오류만 기록하고 반환한다. `void` 반환이라 [`loadRequiredCatalog`](../Source/GameFramework/Runtime/Foundation/Framework/Flow/GameInstance.h)는 그 등록 충돌을 알 수 없고 성공을 반환할 수 있다. 두 키트가 같은 카탈로그 타입을 서로 다른 데이터로 등록하면 이후 조회가 기존 객체를 돌려줄 수 있다. 현재 일반 호출자는 소수지만, 등록 의미가 키트 조립의 정확성에 직접 닿는다. | 등록 성공 여부를 호출자에게 돌려주고 필수 카탈로그·설정 등록 실패를 게임 초기화 실패로 전달한다. 기본 설정과 게임별 서비스 등록이 같은 타입을 의도적으로 공유하는 사례는 명시적으로 정리한 뒤 API 반환형과 모든 호출부를 함께 바꾼다. 중복 등록·상위 범위 가림·정상 공유 사례를 테스트한다. |
| 중간 — 암묵적 단일 게임 범위 | [`GameService.cpp`](../Source/GameFramework/Runtime/Foundation/Framework/GameService.cpp)의 프로세스 정적 `s_gameServiceState`가 하나의 현재 게임 범위를 들고, [`game::findSubsystem`](../Source/GameFramework/Runtime/Foundation/Framework/GameService.h)는 이를 통해 조회한다. 핫 리로드를 위해 부모 범위를 잇고 떼는 코드도 있다. 따라서 여러 게임 인스턴스의 동시 실행이나 서로 다른 스레드의 독립적인 서비스 조회는 현재 API에서 보장되지 않는다. | 먼저 단일 활성 GameInstance 및 게임 스레드 전용 조회가 의도된 계약인지 문서와 테스트로 확정한다. 에디터 멀티 플레이, 여러 월드 또는 병렬 게임 테스트가 실제 요구가 될 때는 thread-local 폴백이 아니라 명시적 게임 컨텍스트를 호출 경계와 비동기 작업에 전달하도록 설계한다. 핫 리로드 중 구·신 범위와 중첩 테스트의 서비스 조회·해제를 테스트한다. |
| 중간 — GameInstance의 조정 책임 집중 | [`GameInstance.h`](../Source/GameFramework/Runtime/Foundation/Framework/Flow/GameInstance.h)와 구현은 팩 설정·초기화 순서·클라이언트 훅·네트워크 세션·저장/스냅샷·자동 저장·오디오·외형 데이터·프레임 갱신을 함께 조정한다. 인스턴스 서브시스템으로 일부 수명은 나뉘었지만 프레임 순서와 여러 실패 조건은 여전히 한 수명주기 진입점에 모여 있다. | 위 롤백 테스트를 먼저 마련하고, 서로 다른 수명·호스트 대상·실패 정책을 가진 책임만 경계별로 분리한다. 단순히 파일이나 클래스를 쪼개지 말고 초기화/갱신/종료 순서, 소유권, 오류 전달이 독립적으로 검증되는지 완료 조건으로 삼는다. `GameInstance::update`의 순서는 명시적 계약으로 테스트해 키트 메시지·저장 완료·게임 훅 순서 회귀를 막는다. |
| 중간 — 핵심 수명주기 테스트 공백 | GameFramework에는 키트별·기능별 테스트가 다수 있고 온라인 서버 런타임도 의존 순서와 실패 되감기를 테스트한다. 반면 이번 검색에서는 `GameInstance`의 단계별 초기화 실패, `GameService`의 범위 전환, `GameStateSnapshot` 봉투/복원에 대한 전용 테스트를 찾지 못했다. | 게임 인스턴스 수명주기 회귀 테스트를 먼저 추가한다. 이 테스트를 모듈 재생성·핫 리로드 경로와 연결하고, 스냅샷은 잘못된 버전·잘린 버퍼·복원 실패 후 상태 일관성을 확인한다. 기존 키트 단위 테스트를 대체하지 않는다. |

**유지할 기반:** 키트 간 의존성과 모듈 종류는 각 `*.module.json` 매니페스트에 선언되고, [`ModuleManifest.cmake`](../cmake/Engine/ModuleManifest.cmake)는 순환·비활성 의존을 검사하고 의존 순서를 만든다. [`ModuleTargets.cmake`](../cmake/Engine/ModuleTargets.cmake)는 공유 키트, 서버/클라이언트 코드, 에디터 확장을 분리하고 매니페스트 의존이 없는 런타임 키트 링크를 거부한다. 이 경계를 다시 하드코딩하거나 별도 레지스트리로 복제하지 않는다.

**실행 순서:** (1) 초기화 실패 시 생성·정리 호출 순서를 테스트로 고정, (2) 부분 정리의 근본 원인 수정, (3) 서비스 등록 실패 반환과 호출부 전파, (4) 단일 게임 범위 계약 및 핫 리로드 테스트, (5) 필요가 확인된 책임만 수명주기 경계로 분리한다. 전체 장르/기능 키트의 API 일관성·데이터 버전 정책·확장성은 이번 범위에서 완전 감사하지 않았으므로 별도 코드 대조 후 추가한다.

### 오픈월드 액션 RPG 키트: MMO와 싱글플레이 분리 (코드 · 공식 기능 페이지 대조 2026-11-07)

**결론:** 검은사막과 붉은사막을 목표로 기능을 갖춘 게임을 만들려면 현재의 작은 테스트용 게임에 동작 몇 개를 더하는 것으로는 부족하다. 실제 장르 루프를 담은 플레이 가능한 수직 슬라이스와 이를 재사용할 키트 조합이 필요하다. 다만 검은사막은 지속 월드·경제·길드 경쟁이 있는 MMORPG이고 붉은사막은 캠페인·탐험 중심 싱글플레이 액션 어드벤처다. 두 게임을 하나의 “대형 오픈월드 키트”로 합치거나 게임 이름을 그대로 딴 키트로 만들지 않는다.

- **재사용할 기반은 있다.** [`SceneStreamingSubsystem`](../Source/Engine/Scene/SceneStreamingSubsystem.h)은 카메라 및 MMO 관찰자 원점 기반 셀 스트리밍을, [`GF_NetMMO`](../Source/GameFramework/Kits/Feature/Network/NetMMO/GF_NetMMO.module.json)은 관찰자별 관심 영역·우선도·복제를 제공한다. [`GF_ActionAdventure`](../Source/GameFramework/Kits/Genre/Action/ActionAdventure/GF_ActionAdventure.module.json)은 체력/스태미나, 월드 지도, 던전·장치, 요리·무기 내구도 등을, [`GF_OpenWorldWestern`](../Source/GameFramework/Kits/Genre/RPG/OpenWorldWestern/GF_OpenWorldWestern.module.json)은 말 유대·승마·사냥·생존·오픈월드 규칙 일부를 이미 제공한다. 온라인에는 소셜/길드, 거래, 경제 키트도 있다. 다만 이들은 서로 다른 게임 요구를 위한 기반 부품이며, 검은사막이나 붉은사막 수준의 통합 콘텐츠·밸런스·운영 기능이 완성됐다는 뜻은 아니다.
- **기능 범위가 서로 다르다.** 검은사막 공식 기능 소개는 전투/공성, 탐험, 거래, 낚시, 조련, 연금술, 요리, 채집, 사냥을 MMORPG 활동으로 제시한다([공식 기능 소개](https://www.naeu.playblackdesert.com/en-US/GameInfo/Feature)). 이에 맞는 키트 조합은 서버 권위 캐릭터/전투·직업 진행, 장기 성장·장비, 월드 보스/사냥터, 채집·생산·생활 숙련, 마을/작업자·거점, 거래소·경제, 길드·공성/거점전, 파티·대규모 복제와 관전 정책이다. 기존 `NetMMO`, 소셜/거래/경제는 일부 기반일 뿐, 완전한 MMO 서버·경제·안티치트나 이 모든 게임 규칙의 제공으로 간주하지 않는다.
- 붉은사막 쪽은 기존 `ActionAdventure`와 서부극 키트의 개별 부품을 재사용하되, 싱글플레이 캠페인·지역 탐험·보스 전투·캐릭터별 성장·동료/인물 관계·승마와 이동 수단·수집/제작·거점/주거를 연결하는 별도의 게임 키트 조합이 필요하다. 서부극의 법·현상금·사냥 규칙이나 Zelda형 사당/하트 규칙을 공통 오픈월드 규칙으로 일반화하지 않는다.
- **확장 콘텐츠를 위한 실제 요구:** 공식 붉은사막 DLC [Crimson Desert Enhanced: Charting the Unknown](https://crimsondesert.pearlabyss.com/en-US/Game/DLC/charting-the-unknown)은 새로운 육지/해상 위협, 선박으로 바다와 섬 탐험, 잠수·수중 보물/유적, 시설 임대·운영, 확장된 주거 건축, NPC와의 관계, 추가 이야기 흐름을 안내한다. 이 범위는 “DLC 지원”이 단순히 팩을 마운트하는 것보다 넓다. 기존 세이브와 이어지는 퀘스트/지역 상태, 해상·수중 이동/전투, 시설 수익·소유 상태, 건축 변경의 저장·되돌리기, 등장인물별 진행을 호환성 있게 추가해야 한다. 공식 2026-11-05 패치 노트에는 조타, 수중 동굴 입력/잠수, 자유 건축의 방 삭제 확인과 집 보존 관련 수정이 보여, 이 시스템들은 자동화 시나리오가 필요한 경계이기도 하다([공식 패치 노트 2.04.08](https://crimsondesert.pearlabyss.com/en-US/News/Notice/Detail?_boardNo=152)).
- 검은사막은 전통적인 단일 DLC 목록보다 운영 중인 콘텐츠 업데이트로 기능이 누적되는 게임으로 다뤄야 한다. 공식 업데이트 기록에서 확인한 2026-09-23 `Treasure Codex`는 보물·제작 재료·획득처·제작법, 진행도와 최초 완성일을 연결한다([공식 업데이트 기록](https://www.naeu.playblackdesert.com/en-US/Adventure/History)). 이는 수집품 하나를 추가하는 데 그치지 않고 카탈로그, 탐험/획득처 링크, 계정/캐릭터 진행도, UI와 저장 이력을 같은 업데이트로 연결해야 한다는 사례다. 업데이트 명칭과 기능은 계속 변하므로 특정 시점의 콘텐츠 목록을 키트에 고정하지 말고, 버전이 붙은 데이터 카탈로그와 선택 콘텐츠 팩으로 추가할 수 있게 한다.

**권장 구조와 범위**

1. `OpenWorldAction` 계열의 공통 기능 후보는 지역/관심 지점 진행, 퀘스트·발견 기록, 탐험 지도, 전투 조우/보스 계약, 탈것·탑승 인터랙션, 채집/제작/수집 진행도처럼 두 유형에서 실제로 공유될 규칙만 대상으로 한다. 장르 이름을 딴 새 키트는 기존 `ActionAdventure`, `OpenWorldWestern`, `NetMMO`, `Social`, `Trade`, `Economy`를 조합해본 뒤, 중복되는 소유권·저장·데이터 계약이 확인된 경우에만 나눈다.
2. MMO 전용은 `GF_ActionMMO` 같은 선택적 조합 후보로 두고 서버 권위·영속 프로필·구역/샤드·파티/길드·시장 일관성·대규모 전투의 복제/권한 경계를 정의한다. 직업의 기술 연계/자원/재사용 대기, 장비 강화 결과, 경제 거래는 클라이언트가 권위 있게 결정하지 않게 한다. 먼저 단일 테스트 서버와 소규모 관찰자에서 끝까지 도는 루프를 구현하고, 부하/운영 지표가 확인되기 전 월드 전체 규모를 약속하지 않는다.
3. 싱글플레이는 별도 `GF_OpenWorldActionAdventure` 조합 후보로 캠페인 진행·지역 상태·저장/복원·동료 관계·보스/탐험·탈것을 묶는다. MMO 서버/시장/길드 의존성을 포함하지 않는다. 붉은사막 DLC의 해양·수중·주거·시설·관계·추가 이야기는 선택 데이터/시스템 확장으로 취급해 기본 게임의 세이브를 깨지 않게 한다.
4. 두 게임이 공유하는 것처럼 보이는 말·배·전투·퀘스트도 구현을 바로 공유하지 않는다. 현재 [`WesternHorse`](../Source/GameFramework/Kits/Genre/RPG/OpenWorldWestern/Rule/WesternHorse.h)는 코어/겁/유대/능력 해금이 붙은 서부극 승마 모델이다. 공통 탈것 수명·입력·좌석 인터페이스와 게임별 말 진행 규칙이 실제 두 번째 사용처로 검증될 때만 그 경계를 추출한다.
5. 각 게임에 작지만 완결된 수직 슬라이스를 둔다. MMO는 접속→전투/생활 활동→보상·성장→저장 후 재접속, 파티/길드 단위 서버 권위 행동까지 포함한다. 싱글플레이는 지역 진입→탐험/전투/보스→보상/퀘스트 진행→저장·재로드를 포함하고, DLC 확장은 별도 팩 활성화·기존 세이브 승계까지 검증한다. 입력/자동 플레이는 테스트 전용 규칙 우회가 아니라 플레이어와 같은 입력 추상화 및 게임 서비스를 사용한다.

**완료 기준과 순서:** 먼저 기존 Shooter3D/HarvestValley/WildWest 및 온라인 키트가 위 루프의 어떤 부분까지 실제로 이어지는지 대조하고, 없는 동작만 기획된 수직 슬라이스에 추가한다. 렌더링 골든만으로 통과시키지 않고 전투/진행/경제/저장 상태 감시와 의미 있는 완료 조건을 둔다. 콘텐츠 DLC는 기본팩만 있는 상태와 팩이 추가된 상태, 이전 세이브 불러오기, 신규 저장, 의존 데이터 누락/버전 불일치, 해제/복구 동작을 검사한다. 실제 대규모 MMO 부하 목표와 온라인 운영 비용은 별도 설계·측정 대상으로 남기며, 우선은 기능 키트와 테스트 가능한 데모의 완결성을 목표로 한다.

### 하우징 · 주거 건축 키트 (요청 2026-11-07)

**결론:** 선택형 하우징 키트는 가치가 있다. 붉은사막식 자유 건축과 심즈형 가구 배치를 함께 지원할 수 있는 공통 저작·배치·저장 기반을 만들되, 생활 시뮬레이션 규칙 전체를 그 키트에 묶지 않는다. “하우징 키트”는 게임 안의 플레이어 건축/꾸미기 기능이고, 에디터의 씬 제작 도구와는 별도 표면이다.

- **재사용할 수 있는 기반:** [`PlacementRule`](../Source/Engine/Environment/Placement/PlacementRule.h)은 시드 기반 산포 배치 규칙이며, [`CitySimulation`](../Source/GameFramework/Kits/Genre/Strategy/CityBuilder/CitySimulation.h)은 격자 도시의 건물 배치·주거 단계·인구를 시뮬레이션한다. [`ThemePark`](../Source/GameFramework/Kits/Genre/Simulation/ThemePark/ParkLayout.h)은 놀이기구 배치 데이터를 보유하고 키트 전용 에디터 패널도 둔다. 이들은 각각 산포, 도시 타일 규칙, 테마파크 레이아웃으로 범위가 정해져 있어, 집의 방/벽/바닥/가구를 플레이어가 자유롭게 배치하는 범용 하우징 시스템은 아니다. [`GameStateSnapshot`](../Source/GameFramework/Runtime/Foundation/Framework/Save/GameStateSnapshot.h)은 게임 상태 저장 봉투를 제공하고 프리팹 스폰/오브젝트 수명도 재사용할 수 있지만, 이것만으로 부지별 건축 편집 이력·영속 소유권·되돌리기 정책이 정해지는 것은 아니다.
- **권장 키트 경계:** `GF_Housing` 같은 선택적 기능 키트는 부지/구역 소유, 배치 가능한 부품 카탈로그, 배치 검증과 미리보기, 구매·회수, 부지별 저장 데이터를 소유한다. 액션 RPG는 이를 거점/주거 기능으로 조합하고, 심즈형 게임의 욕구·가구 효용·가구 구성원 관계·일정은 별도 생활 시뮬레이션 장르 키트가 소유한다. MMO에서 쓸 때는 소유권과 최종 배치 판정/저장을 서버 권위로 두며, 싱글플레이 전용 키트가 온라인 의존성을 끌어오지 않게 한다.
- **첫 수직 슬라이스:** 한 부지와 벽/바닥/문/가구의 작은 카탈로그를 두고, 화면 조준/지면 투영에 따른 고스트 프리뷰, 격자 및 소켓 스냅, 90도 회전, 배치 불가 이유, 비용 검사, 취소/회수와 Undo/Redo를 끝까지 연결한다. 부품 정의에는 프리팹 참조뿐 아니라 점유 부피, 스냅 지점/방향, 지면·벽·바닥 같은 배치 표면, 허용 규칙과 카탈로그 버전을 둔다. 자유 배치를 지원하더라도 게임/부품별 스냅 정책을 끌 수 있는 하나의 명시적 배치 모드로 다룬다.
- **저장·불러오기:** 씬의 임시 `GameObjectHandle`이나 스폰 결과를 저장 정본으로 삼지 말고, 부지 ID와 안정적인 배치 ID, 카탈로그 부품 ID/버전, 변환, 필요한 변경값만 직렬화한다. 부지 로드 시 같은 입력에서 같은 오브젝트를 재구성하고, 삭제/이동/복제/재로드에서 중복 생성이나 유실이 없게 한다. 기존 게임 저장 봉투와 통합하되 건축 데이터의 스키마 버전, 제거된/교체된 콘텐츠 참조 오류, 세이브 마이그레이션과 팩 의존성을 명시한다.
- **에디터와 인게임 UX를 분리한다:** 인게임 Build Mode는 플레이어 입력, 카메라, 지면/벽 스냅, 충돌, 비용과 즉시 되돌리기를 다룬다. 에디터 키트 확장은 부지 경계/방 앵커/입구, 스냅 지점과 배치 충돌, 카탈로그 프리뷰 및 검증을 콘텐츠 제작자가 저작하도록 한다. 기존 ThemePark 레이아웃 편집기는 특정 키트 소유의 좋은 참고 사례지만, 그 코드를 주거 편집기로 복제하기보다 실제 하우징 스키마와 뷰포트 도구에 맞는 확장으로 만든다.
- **범위 관리:** 첫 단계에서는 구조물의 안정성 시뮬레이션, 임의 메시를 벽/지붕으로 변환하는 절차 생성, NPC가 가구를 자동 이용하는 범용 플래너, 온라인 동시 건축을 넣지 않는다. 심즈류 완성도를 목표로 할 때는 방 인식·문/통로 연결·가구 사용 가능성/효용·가구원 상태/일정이 별도 시스템과 데이터 계약을 요구한다. 붉은사막식 콘텐츠도 게임별 건축 자유도와 부지/시설 경제 규칙을 프로파일/키트에서 정하고 공용 배치 규칙으로 합쳐 버리지 않는다.
- **검증:** 부품 겹침/지지면 오류/잘못된 스냅/부지 경계/재화 부족/콘텐츠 누락을 명시적으로 거부한다. 배치·회전·이동·삭제·Undo/Redo 후 저장/재로드, 카탈로그 업데이트/삭제 후 구세이브, 여러 방과 층, 대량 가구의 프레임·메모리 예산을 자동화 시나리오로 확인한다. 멀티플레이를 지원하는 경우 권한 없는 클라이언트 배치, 동시 편집 충돌과 서버 재접속도 별도 검증한다.

### 핫 리로드와 스크립팅 언어 판단 (코드 대조 2026-11-07)

**결론: 핫 리로드가 이미 있으므로 스크립팅 언어가 불필요하다고 단정할 수는 없지만, 모드 지원 요구가 생겼다고 곧바로 범용 런타임 스크립트 VM이 필요한 것도 아니다.** Lua 도입은 모드가 새 로직을 요구하는지 확인할 때까지 보류한다.

- [`GameModuleManager`](../Source/ModuleManager/GameModuleManager.cpp)는 개발 빌드에서 게임 모듈을 다시 빌드·교체하고, 언로드 전에 상태를 직렬화해 새 인스턴스에서 복원한다. 이 방식은 C++ 로직 변경의 반복 속도를 높이지만 컴파일·링크가 필요하며, 임의의 상태·작업·외부 포인터까지 보존하는 런타임 코드 편집 기능은 아니다. 배포 빌드는 정적 링크라 개발용 동적 리로드가 없다.
- 스크립트 언어가 주는 별도 가치는 빌드 없이 새 동작을 작성·실행하거나, 사용자 모드를 지원하거나, 콘텐츠 제작자가 프로그래머 개입 없이 규칙을 조합하는 것이다. 그런 사용자/워크플로 요구가 없다면 언어 런타임, C++ 바인딩, 디버거·프로파일러, 오류 추적, 패키징, 샌드박스와 버전 호환성을 추가 유지하는 비용이 이점보다 크다.
- 현재 코드에는 제한된 로직을 표현하는 데이터 기반 시스템이 이미 있다: [`BehaviorTreeAsset`](../Source/GameFramework/Runtime/Character/AI/BehaviorTreeAsset.h)의 노드·태스크, [`ConditionExpr`](../Source/Engine/Gameplay/ConditionExpr.h)의 검증·컴파일되는 조건식, [`DialogueGraphAsset`](../Source/Engine/Dialogue/DialogueGraphAsset.h)의 대화 흐름, [`AnimationGraphPlayer`](../Source/Engine/Animation/Graph/AnimationGraphPlayer.h)의 상태 전이. 값·콘텐츠·그래프로 충분히 표현되는 요구는 기존 형식을 확장하고, 일반 프로그래밍 언어를 새로 넣지 않는다.
- 재검토 조건은 구체적인 실제 기능이 기존 API/에셋 형식으로 표현되지 않고, 반복적으로 C++ 변경·빌드를 요구해 제작 병목을 만든다는 근거다. 그때는 먼저 좁은 목적의 데이터 형식/노드/표현식 확장으로 해결 가능한지 본다. 범용 언어가 꼭 필요하면 그때 Lua 등 후보를 평가하고, 서버 권한·네트워크 결정성·시간/메모리 한도·허용 API·스크립트 버전·세이브 호환·툴링을 포함해 별도 설계한다. 임의의 엔진 포인터를 노출하거나 신뢰하지 않는 스크립트를 권한 제한 없이 실행하는 방식은 허용하지 않는다.

**요약:** 핫 리로드는 프로그래머의 C++ 반복을 빠르게 하는 도구이고, 스크립팅은 콘텐츠 제작자/모드 제작자가 새 로직을 런타임에 작성하게 하는 별도 제품 기능이다. 사용자가 모드 지원을 제안했으므로 모드의 범위는 검토 대상으로 올린다. 단, 콘텐츠 모드는 기존 데이터/에셋 형식으로 먼저 지원하고, Lua 등 VM은 모드가 새 로직을 실제로 저작해야 한다는 요구가 확인될 때만 별도 평가한다.

### 모드 지원 키트 (코드 · Graphify 대조 2026-11-07)

**방향:** 모드 제작/사용을 지원한다면 선택 가능한 `Feature/ModSupport` 키트를 두는 것이 타당하다. 모든 게임에 강제하는 엔진 기능이 아니라, 게임이 필요할 때 의존하는 선택 기능으로 둔다. 첫 단계는 **쿠킹된 콘텐츠·데이터 모드**로 한정하고, 임의의 네이티브 코드 DLL을 로드하는 것을 모드 지원으로 간주하지 않는다.

- **재사용할 기반은 이미 일부 있다.** [`PackManager`](../Source/Engine/Content/Pack/PackManager.h)는 우선순위가 있는 `.pack` 마운트/언마운트와 패치 팩을 지원하고, [`AssetPaths`](../Source/Engine/Content/AssetPaths.h)는 임의 도메인 이름과 `mods/pack1` 같은 경로 이름 공간을 인식한다. 다만 기본 우선순위인 [`EngineConfig.json`](../Config/Engine/EngineConfig.json)은 `game`, `common`, `engine`, `editor`뿐이다. 사용자 팩 도메인은 명시적 우선순위/설정 없이 기본 모드 우선순위로 동작한다고 볼 수 없다. [`AssetManager`](../Source/Engine/Asset/AssetManager.h)의 일반 기동 경로는 시작 팩을 마운트하지만, 모드 목록·발견·의존성·활성화 정책과 캐시 갱신을 묶은 모드 수명주기는 확인되지 않았다. 따라서 팩 VFS 기반은 재사용할 수 있지만 현재 구현을 완성된 모드 로더로 취급하면 안 된다.
- [`PackPatchTrust`](../Source/Engine/Content/Pack/PackPatchTrustSource.h)는 패치 사슬의 서명 검증을 위한 것이다. 이를 일반 모드 팩의 제작자 신뢰/허용 목록으로 확대해 해석하지 않는다. 팩의 CRC는 손상을 찾는 무결성 검사이지 제작자 인증이 아니며, 팩 암호화도 신뢰/권한 경계가 아니다. 외부 모드를 허용한다면 서명·출처·권한 정책과 거부 이유를 명시해야 한다.
- C++ 동적 모듈과 핫 리로드는 개발 도구이고 배포 빌드는 정적 링크다([`GameModuleManager`](../Source/ModuleManager/GameModuleManager.h)). 서드파티 바이너리 모드는 ABI/컴파일러/플랫폼 호환과 임의 코드 실행 권한을 요구하므로 첫 모드 키트의 범위에 넣지 않는다. XML/데이터가 호출할 수 있는 동작도 등록된 엔진 액션으로 제한한다. 스크립트가 필요해지면 허용 API, 샌드박스, 실행량 제한, 오류 격리와 버전 호환을 별도 설계한다.

**권장 책임 경계**

1. 엔진의 `PackManager`/VFS는 일반 콘텐츠 팩 기능으로 유지한다. `ModSupport` 키트는 모드 매니페스트, 팩 파일, 버전/엔진 호환 범위, 의존·충돌, 활성 여부와 우선순위를 읽어 검증하고 정해진 순서로 적용하는 게임 프레임워크 계층의 조정자다. 기존 팩 기능을 복제하지 않는다.
2. 처음에는 `ContentOnly` 모드만 허용한다: 허용된 에셋/카탈로그/시나리오 등 기존 데이터 스키마로 표현되는 것만 패키징한다. 모드 전용 도메인·경로 규칙, 기본 게임 에셋 덮어쓰기 허용 범위, 모드끼리 같은 리소스를 제공할 때의 결정적 우선순위, 필수/선택 의존 실패 정책을 정한다. 모드 로드 뒤 이미 캐시에 든 에셋이 오래된 내용을 반환하지 않도록 마운트·언마운트와 캐시 무효화/재로드 경계를 함께 만든다.
3. 모드 활성/비활성은 팩 하나의 마운트 조작만으로 끝나지 않는다. 에셋 핸들·공유 캐시·씬 오브젝트·진행 중 로드 태스크가 해당 팩을 참조하는 동안의 안전 규칙을 정한다. 가장 단순한 1차 정책은 실행 중 토글 대신 다음 게임 시작/세션 시작 때 모드 구성을 고정하는 것이다. 런타임 토글이 실제 요구가 될 때만 안전한 언마운트/에셋 해제를 추가한다.
4. 선택 가능한 `GF_..._ModSupport` Runtime 키트에 모드 검색/검증/적용, 로드 결과와 오류 보고, 활성 모드 목록/구성 해시를 둔다. 제작·활성화 UI가 필요하면 같은 키트의 `Editor/` 확장이나 호스트 도구로 분리한다. 실제 배포 채널(수동 설치/워크숍 등)은 매니페스트와 패키지 계약이 정해진 뒤 어댑터로 추가하고, 특정 스토어 연동을 엔진에 박지 않는다.
5. 모드를 허용하는 멀티플레이 게임은 서버가 허용 모드 목록을 정하고 클라이언트와 콘텐츠/버전 해시를 맞춰야 한다. 서버 권위·치트 방지·저장 호환·네트워크 결정성 정책이 없는 임의 모드 조합은 동기화 불일치를 만든다. 모드가 없는 환경의 기존 세이브와 패키지 실행은 영향받지 않아야 한다.

**완료 기준:** 모드 매니페스트의 잘못된 형식/버전/순환 의존/충돌/누락 팩을 명확히 거부하고, 같은 입력이면 동일한 마운트 우선순위와 구성 해시를 만든다. 기본 에셋 덮어쓰기·모드 간 충돌 정책, 캐시된 참조와 언마운트, 클라이언트/서버 모드 불일치, 제거된 모드가 든 세이브를 테스트한다. 외부 설치 경로는 경로 탈출을 막고 콘텐츠 파서/팩 크기와 복잡도 한계를 검증한다.

**우선순위 판단:** 모드 지원 키트는 유용한 확장 후보이며 모드 제작 요구를 제품 기능으로 다룬다. 먼저 콘텐츠 전용 모드의 패키지/신뢰/충돌/멀티플레이 정책을 정하고, 엔진 팩 계층과의 최소 연결을 구현한다. 네이티브 코드 플러그인과 범용 스크립트 VM, 워크숍 연동은 사용자 요구와 보안·배포 비용이 확인될 때까지 범위에서 제외한다.

### 게임 액션 데이터 저작과 에디터 (코드 대조 2026-11-07)

**방향:** 액션의 매개변수·조합은 XML/데이터로 저작하고, 그래프·프로퍼티 패널로 안전하게 편집한다. XML과 에디터는 대안이 아니다. XML이 저장 형식의 정본이고 전용 에디터는 그 형식을 검증하며 조작하는 UX다. 새 C++ 로직을 XML만으로 자동 생성한다고 약속하지 않는다.

- 용어를 나눠 본다. `GameActionCall`/`ActionRegistry`는 행동 트리·대화·스케줄 등이 공유하는 제한된 이름 있는 동작 어휘다. GAS 형태의 `Ability`는 별도의 실행기·복제·수명 모델을 가진다. 양쪽을 단일 "Action" 실행기로 합치지 않는다.
- **이미 가능한 것:** [`ActionRegistry`](../Source/Engine/Gameplay/ActionRegistry.h)는 이름, 반영된 매개변수 구조체, 실행 함수를 등록한다. 같은 어휘를 텍스트 또는 XML 속성으로 읽고 실행 시 미리 해석한다. [`BehaviorTreePanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/AI/BehaviorTreePanel.h)는 작업 목록을 레지스트리에서 가져와 선택하고, 선택한 동작의 반영된 매개변수를 프로퍼티 그리드로 편집한다. 행동 트리 모델·로더·에디터는 `BehaviorTreeXML`과 `BehaviorTreeNodeParams`를 공유한다. 따라서 “행동 트리 액션을 XML로 쓰거나 편집할 기능이 전혀 없다”는 문제는 아니다.
- **남은 간극:** 등록된 동작은 결국 C++ 함수다. 기존 XML은 어떤 동작을 어떤 값으로 호출할지 표현하지만, 새 동작의 실행 의미나 복잡한 분기·상태를 XML에서 새로 정의하지 않는다. 현재 RTS 액션 7개는 매개변수 없는 C++ 작업으로 등록돼 있어 `<Action task="rts.attack"/>`처럼 호출은 되지만, XML만으로 공격 규칙을 새로 만들 수는 없다.
- **어빌리티 저작은 별도 공백:** [`AbilityCatalog`](../Source/GameFramework/Runtime/Gameplay/Ability/AbilityCatalog.h)는 어빌리티·이펙트·어빌리티 세트·표현 큐를 이미 XML 데이터로 정의하고 반영 메타데이터로 검증한다. 그러나 에디터의 [`AbilityDebugPanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/Ability/AbilityDebugPanel.h)은 실행 중 상태를 읽는 디버거이지 이 카탈로그를 저작하는 편집기가 아니다. 전용 카탈로그 편집 표면은 이번 코드 검색에서 확인되지 않았다. 디버거는 어트리뷰트(base/current), 활성 이펙트(이름·남은 시간·스택), 태그 개수, 어빌리티/쿨다운을 읽기 전용으로 보여 준다. 즉 현재 이펙트 상태를 볼 도구는 있지만, 어떤 공간/상호작용이 어떤 조건으로 이 이펙트를 적용·거부했는지까지 추적하지 않는다.

**권장 고도화 순서**

1. 액션 등록 메타데이터를 보강한다: 편집기에 보일 설명·분류·적용 문맥(행동 트리/대화/스케줄)을 제공하고, 기존 매개변수 `PROPERTY` 메타데이터를 값 범위·선택지·리소스 참조·도움말의 정본으로 쓴다. 에디터에 하드코딩된 별도 액션 목록이나 중복 스키마를 만들지 않는다.
2. 행동 트리 에디터의 기존 동작 선택·매개변수 편집을 발견 가능하게 한다: 분류/검색, 동작 설명과 실행 문맥, 잘못된 작업·매개변수의 인라인 문제 표시, 선택한 동작을 바꿀 때 호환되지 않는 매개변수 값이 어떻게 처리되는지 명확히 한다. 현재 있는 기능을 재작성하지 않고 실제 UX 결함만 개선한다.
3. **Ability Catalog 전용 편집기**를 우선 후보로 둔다: Ability·Effect·Modifier·Execution·AbilitySet·Presentation을 관계가 보이는 목록/상세 편집 흐름으로 다루고, 클래스/이펙트/태그/에셋 참조를 선택·검증한다. 저장은 기존 XML 스키마와 `AbilityCatalog` 로더를 사용하고, 새 파일 형식이나 런타임 구현 중복을 만들지 않는다. 코드 기반 Ability/Execution은 C++ 확장점으로 남긴다.
4. 범용 그래프나 일반 스크립트 실행기를 만들기 전에, 실제 콘텐츠가 어느 표현에 막히는지 사례를 수집한다. 단순 값·분기·반복·기존 노드 조합은 기존 데이터 형식에 노드를 추가하고, 임의 상태/복잡한 로직은 C++ 확장 또는 별도 평가된 스크립팅 요구로 남긴다. XML 파일이 지나치게 길거나 중복되는 경우에만 `_base`/공유 데이터로 공통 부분을 추출한다.
5. 검증 완료 기준: UI 변경은 `.claude` 밖의 프로젝트 규칙 [`EditorUI`](agents/EditorUI.md)에 따라 토큰·다크/라이트/고대비·클리핑·캡처 시나리오를 확인한다. 모델/스키마는 XML round-trip, 잘못된 참조와 범위 값 거부, 저장 후 다시 로드한 동등성 테스트를 갖춘다.

**우선순위 판단:** 기존 행동 트리 액션 에디터는 존재하므로 우선 새로 짓지 않는다. 현재 더 큰 편집 공백은 XML 기반 Ability Catalog의 저작 UX다. 다음 에디터 기능 단계에서 Ability Catalog 편집기와 콘텐츠 제작 사례를 먼저 확인하고, ActionRegistry 검색/설명 개선은 실제 사용성 문제가 확인되면 함께 보완한다.

#### 공간 효과 · 상호작용 제약의 저작과 진단

- **재사용할 런타임 기반:** [`AbilityEffectDef`](../Source/GameFramework/Runtime/Gameplay/Ability/AbilityEffect.h)는 즉시/지속/무한, 주기, 스택, 속성 변경, 부여·차단 태그를 표현한다. AbilityArena의 [`GE_Dash`](../Content/game/abilityarena/data/abilities.xml)는 `MoveSpeed ×3`과 `State.Invulnerable`을 실제 데이터로 적용하며 [`ArenaUnitComponent`](../Source/Games/AbilityArena/ArenaUnitComponent.cpp)는 속성 current와 대시 태그를 이동에 반영한다. 따라서 둔화·기절·이동 금지는 새 독립 버프 체계 대신 이 이펙트/태그 모델을 재사용하는 편이 맞다. 단, 이 이동 연동은 현재 확인한 사례로는 AbilityArena에 국한되며 모든 키트의 이동기가 `AbilityComponent` 속성/태그를 읽는 공통 계약은 확인되지 않았다.
- **공간·기믹 기반의 범위:** [`ActivatorVolumeComponent`](../Source/GameFramework/Runtime/Foundation/Framework/ActivatorVolumeComponent.h)는 태그/거리 판정과 진입 훅을 제공하지만 기본 동작은 한 번 실행하는 볼륨이며 범용 enter/stay/exit 효과 수명 관리자는 아니다. [`GimmickGraphPanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/Gimmick/GimmickGraphPanel.h)은 회로를 시각적으로 편집하고, 회로의 `Volume` 센서와 `Hazard` 액추에이터는 점유자를 대상으로 주기 피해를 준다([`GimmickCircuitComponent`](../Source/GameFramework/Runtime/Gameplay/Gimmick/GimmickCircuitComponent.cpp)). 이는 기믹 배선과 피해 경로이지, AbilityEffect를 적용하거나 둔화/기절을 해제까지 관리하는 공간 이펙트 저작 흐름은 아니다.
- **상호작용 조건의 범위:** [`InteractionDef`](../Source/GameFramework/Runtime/Gameplay/Interaction/InteractionCatalog.h)는 필수/금지 태그, 거리, 각도, 시야, 쿨다운, 권한으로 시작 가능 여부를 제한한다. 예를 들어 `State.Stunned` 태그는 상호작용을 막는 데 쓸 수 있지만, 정의에 시작/완료/취소 시 부여할 이펙트나 이동 제한을 연결하는 필드는 확인되지 않았다. `isAvailableFor`는 최종 참/거짓을 주므로 에디터/디버거에서 실패 원인별 진단도 별도로 필요하다.
- **저작 방향:** 기존 Ability Catalog의 이펙트 정의를 정본으로 삼고, 공간 진입과 상호작용 완료가 동일한 `AbilityComponent` 적용 경로를 호출하게 한다. 우선 대표 사례를 기준으로 재사용 가능한 효과 영역 또는 기믹 액추에이터 중 하나를 정한다. 영역은 씬의 형상/기즈모, 활성 대상·태그 필터, 진입/체류 주기/이탈, 효과 참조, 재적용·스택·종료/이탈 시 제거 정책을 편집할 수 있어야 한다. 상호작용은 효과 적용 시점(시작/완료/취소)을 명시하고, 필요한 경우 지속형 상태 효과의 종료 규칙을 사용한다. 두 경로가 각자 속성 값을 직접 덮거나 별도 디버프 구조를 만들지 않게 한다.
- **이동 제약 계약:** 속도 변경은 기존 이동 속성 효과로 표현하고, 입력 차단/기절은 태그 또는 지속 효과를 이동기와 연결한다. 이동 구현이 제각각인 모든 키트에 전역 플래그를 강제하기 전에, 공용 제어 인터페이스와 키트별 어댑터 중 어느 경계가 필요한지 대표 이동기를 통해 검증한다. 겹친 효과 하나가 해제될 때 다른 효과의 이동 제한까지 풀리지 않도록 태그/효과의 소유 수명으로 합성하고, 종료·영역 이탈·대상 파괴·취소 후 원상 복구를 보장한다.
- **진단 방향:** 기존 Ability Debugger를 확장해 활성 효과의 적용 출처(영역/기믹/상호작용), 적용·거부 시각과 사유, 영향 속성/태그, 중첩/남은 시간, 제거 원인을 볼 수 있게 한다. 별도의 상호작용/공간 진단에는 대상 후보와 점유/진입/이탈 전이, 태그·거리·각도·시야·쿨다운·권한의 판정 결과, 진행 중 상호작용의 취소 사유, 이동이 막히거나 느려진 현재 효과를 연결한다. Gimmick Graph는 저작 도구로 유지하고, 플레이 중 신호/센서 상태와 마지막 전이의 추적은 읽기 전용 런타임 진단으로 분리한다. 서버 권한 게임에서는 최종 판정 주체와 클라이언트 예측 상태를 구분해 표시한다.
- **완료 기준:** 전용 편집 UI에서 저장한 데이터를 기존 카탈로그/씬 로더로 재로드해도 동일해야 한다. 자동화는 영역 진입·체류·이탈·재진입, 겹친 효과/스택, 필터에 의한 미적용, 상호작용 시작·완료·취소 및 각 거부 사유, 이동 제한의 중첩·복구를 확인한다. Ability Debugger 시나리오도 어트리뷰트/어빌리티 수뿐 아니라 활성 효과와 태그를 검증하고, 디버그 정보는 실행 중 상태를 바꾸지 않는 읽기 전용이어야 한다.

### 시퀀서 · 컷씬 저작 고도화 (코드 · Graphify · 공식 문서 대조 2026-11-07)

**결론:** 시퀀서의 기본 제작 부품은 이미 있다. 타임라인 항목을 더하고 지우고 복제하며 구간을 옮기고, 트랜스폼·숫자 프로퍼티·리그 슬롯에 키를 찍어 미리 볼 수 있다. 카메라 컷·블렌드·프리롤·흔들림도 런타임에 연결돼 있다. 다만 현재는 좁은 범위의 단일 에디터와 이름 기반 바인딩이다. 상용 엔진처럼 재사용 가능한 바인딩, 전문 카메라/애니메이션/오디오 트랙, 확장 가능한 트랙 제작 체계까지 준비된 것은 아니다.

- **이미 가능한 것:** [`SequenceAsset`](../Source/Engine/Sequencer/SequenceAsset.h)은 `.seq.xml` 에셋으로 구간 항목과 키 트랙, 프레임 범위, 카메라 인·아웃 블렌드와 프리롤을 저장한다. [`SequencePlayerComponent`](../Source/Engine/Sequencer/SequencePlayerComponent.h)는 자동 재생·루프·재생/정지/일시정지/재개를 제공한다. [`SequenceTriggerComponent`](../Source/GameFramework/Runtime/Character/Camera/SequenceTriggerComponent.h)는 활성 영역에 진입할 때 재생을 시작한다. 이벤트·시나리오 항목은 게임 로직 및 자동화 시나리오를 부르고, 스폰·외형 변경도 지원한다.
- [`SequencerPanel`](../Source/Editor/Panels/Animation/SequencerPanel.h)은 구간 항목의 추가·삭제·복제·시작/끝 편집, 프레임 스크럽과 재생 미리보기를 제공한다. 트랜스폼·프로퍼티·리그 슬롯 키 트랙을 만들고 지우며, 채널 키·커브·자동 키를 편집할 수 있고 문서 되돌리기 스냅숏도 연결돼 있다. 모델 및 에셋 규칙에는 전용 단위 테스트가 있다. 따라서 “항목을 추가/삭제할 편집기가 없다”거나 시퀀서 전체를 새로 만들어야 한다는 평가는 맞지 않는다.
- **이미 연결된 카메라 연출:** [`CinematicCameraComponent`](../Source/GameFramework/Runtime/Character/Camera/CinematicCameraComponent.h)는 카메라 컷, 프리셋 전환, 시네마틱 시작/끝 블렌드, 컷 프리롤의 대기 뷰, 흔들림 신호를 카메라 디렉터·매니저에 전달한다. 일반 [`CameraComponent`](../Source/Engine/Object/Component/CameraComponent.h)는 FOV, 피사계 심도, 렌즈 시프트, 후처리 값을 가진다. 단, `CinematicCameraComponent` 자체는 렌즈를 가진 Cine Camera가 아니라 신호 라우터다. 숫자 프로퍼티 트랙은 직접 숫자 프로퍼티만 대상으로 하므로 중첩된 렌즈 구조체를 촬영자가 쉽게 키프레임하는 전용 UI는 확인되지 않았다.
- **킬캠/탄도 관통 연출은 아직 별도 기능이다.** 발사체 시뮬레이션에는 대상 관통 수와 튕김 수가 있지만(`ProjectileDef::_pierceCount`), 한 스텝에 한 번만 맞아 빠른 탄은 같은 프레임의 다음 대상을 놓칠 수 있다. Shooter3D의 기본 소총탄은 `speed="0"` 히트스캔이며, 현재 확인된 탄 설정·충돌·시퀀서 카메라 신호에는 발사 순간부터 관통·명중·절단까지 궤적을 기록하고 슬로모션 카메라로 재생하는 통합 경로가 없다. 시퀀서 카메라 컷/흔들림과 디렉터 블렌드는 재사용할 수 있지만, 이것만으로 런타임 탄 추적 킬캠이 생기지는 않는다.
- **추가 방향:** 먼저 관통 여부와 관통 지점, 대상/부위, 절단 결과를 한 발의 제한된 이벤트 기록으로 남기고, 단일 관통 장면을 재생하는 수직 슬라이스를 만든다. 카메라는 탄 추적 시점·충돌 지점 클로즈업·게임 시점 복귀를 블렌드하고, 재생 중 게임 입력/피해/물리/네트워크 상태를 중복 실행하지 않도록 기록된 결과를 보여주는 연출 전용 재생으로 분리한다. 서버 권위 게임에서는 판정은 서버가 한 번만 하고 클라이언트는 확정 결과를 연출하며, 스킵·재접속/대전 관전 정책, 프레임 드롭 시 생존, 장면별 재생 길이 제한을 정한다. 관통 탄은 남은 선분을 같은 프레임 안에서 반복 질의해 모든 명중을 순서대로 수집하고, 표면별 관통 가능성/속도·피해 감쇠가 필요할 때에만 해당 데이터 계약을 추가한다. 한 스텝 한 타격 제한은 저사양 프레임에서 명중을 누락시킬 수 있어 연출뿐 아니라 게임 판정의 정확성으로 먼저 고쳐야 한다.
- **바인딩·재사용의 핵심 한계:** 키 트랙과 컷 대상은 씬 오브젝트의 이름 문자열이며 [`SequenceTimelineUtil::findTarget`](../Source/Engine/Sequencer/SequenceTimelineUtil.cpp)은 이름으로 대상을 찾는다. 에셋 데이터와 씬 인스턴스별 대상 바인딩을 별도로 저장하는 구조가 아니다. 오브젝트 이름 변경에 취약하고, 다른 씬/캐릭터에 같은 시퀀스 에셋을 재사용하기 위한 바인딩 대체·수리 UI도 확인되지 않았다. 콘텐츠가 늘면 문자열 입력 실수와 잘못된 대상 연결을 에디터에서 발견하기 어렵다.
- **트랙 종류의 확장 한계:** 구간 종류와 키 트랙 종류는 `SequenceAsset.h`의 열거형·정적 특성 표를 중심으로 정의되고, 적용은 [`SequenceTimelineUtil::applyFrame`](../Source/Engine/Sequencer/SequenceTimelineUtil.cpp), 에디터 UI와 직렬화 검증에 나뉜다. 새 종류는 데이터만으로 추가할 수 없고 엔진·에디터 코드를 함께 고쳐야 한다. 현재 확인한 시퀀서 고유 트랙에는 애니메이션 클립, 오디오, 대사/자막의 전용 트랙이 없다. 이벤트/시나리오에서 외부 코드를 호출하는 것은 가능하지만 타임라인 전용 편집·미리보기·문제 검증을 대신하지 않는다.
- **제작 UX 간극:** 키 트랙은 추가·삭제할 수 있지만 순서 재배치, 키 마름모 직접 끌기, 여러 키/항목 일괄 편집은 찾지 못했다. 카메라 컷도 일반 구간 항목으로 추가하고 대상·프리셋 이름을 문자열로 적는다. 카메라/대상 선택기, 컷 전용 차선, 쇼트/샷 구성 도구, 렌즈 프레이밍 컨트롤은 확인되지 않았다. 시퀀스 중지 때 스폰과 카메라 컷은 해제하지만 다른 대상의 트랜스폼·프로퍼티·활성 상태는 이전 값으로 되돌리는 경로가 보이지 않는다. 최종 포즈 유지인지 시작 상태 복원인지 재생 계약을 명시해야 한다.

**상용 엔진과 비교:** Unreal Sequencer는 Level Sequence 에셋과 레벨의 Sequence Actor를 구분하고 다중 트랙 편집, 카메라 바인딩·컷·섹션 블렌드를 제공한다([공식 개요](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-sequencer-movie-tool-overview), [Camera Cut Track](https://dev.epicgames.com/documentation/en-us/unreal-engine/cinematic-camera-cut-track-in-unreal-engine)). Unity Timeline도 재사용 가능한 Timeline 에셋과 씬 오브젝트를 연결하는 인스턴스 바인딩/Playable Director를 나누며, 필요하면 다른 씬 인스턴스에 같은 에셋을 바인딩한다([공식 에셋·인스턴스 설명](https://docs.unity3d.com/Packages/com.unity.timeline@1.8/manual/tl-overview.html)). Unity Cinemachine은 Timeline과 별개지만 함께 쓰는 카메라 구성·추적·블렌드 시스템이다([공식 개요](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/index.html)). 이 비교에서 우선 참고할 구조는 이름을 그대로 복제하는 게 아니라 **재사용 에셋과 씬 바인딩 분리**, **카메라 제어와 카메라 렌즈/구성 기능 분리**, **트랙을 제작자가 이해하는 다중 차선 UI**다.

**권장 고도화 순서**

1. **씬 바인딩을 명시적으로 만든다.** 시퀀스 에셋 안의 바인딩 ID를 구간/키 트랙에서 참조하고, 플레이어 인스턴스가 해당 ID를 씬 오브젝트 핸들에 연결한다. 에디터에는 오브젝트 선택기, 누락/중복 바인딩 오류, 이름 변경 후 재연결을 제공한다. 이름은 표시용으로만 남긴다. 우선 GUID/안정 ID의 씬 저장·복제·프리팹·직렬화 수명과 핫 리로드 동작을 정한 뒤 채택한다.
2. **촬영자용 카메라 컷 UX를 만든다.** 일반 구간 목록에서 카메라 컷을 고르는 대신 컷 차선과 카메라 바인딩 선택, 컷 구간/전환 편집을 제공한다. `CameraComponent`의 렌즈/피사계 심도/후처리 중 시네마틱에 필요한 값을 직접 키프레임하고 뷰포트에서 즉시 확인할 경로를 설계한다. 기존 프리셋·CameraDirector·대기 뷰와 역할이 겹치지 않게, 실시간 카메라 동작(Director)과 촬영 컷/렌즈 저작(Sequencer)을 분리한다.
3. **재생 종료·중단 계약을 정한다.** 정상 완료, Stop, 씬 전환, 트리거 재진입에서 오브젝트 상태를 복원할지 최종 상태를 유지할지 명시하고, 카메라·플레이어 입력/시선·플레이어 표시의 소유와 원복을 정의한다. 현재 확인된 것은 스폰 및 카메라 컷 정리이고, 나머지 대상 상태의 복원은 확인되지 않았다. 무조건 복원 코드를 추가하기 전에 의도한 정책과 중첩/동시 재생 동작을 테스트로 고정한다.
4. **콘텐츠 수요에 맞춰 일급 트랙을 더한다.** 연출 제작에서 필요성이 확인되면 애니메이션 클립, 오디오, 대사/자막을 각 런타임 시스템과 맞물리는 트랙으로 추가한다(재생·스크럽·중지/원복·에셋 누락 검증까지 포함). 현 이벤트 트랙을 대체하지 않고, 이벤트는 사용자 정의 게임 동작의 확장점으로 남긴다.
5. **트랙 확장 계약과 편집 조작을 고도화한다.** 트랙 메타데이터·런타임 적용·검증·에디터 생성/표시를 한 확장점으로 연결해, 새 트랙 추가 시 종류표·패널의 분산된 분기 수정이 반복되지 않게 한다. 먼저 C++ 등록 기반의 제한된 확장으로 시작하고, 실제 사용자가 데이터만으로 새 로직을 저작해야 한다는 요구가 확인되기 전에는 범용 스크립트 트랙을 만들지 않는다. 이어 키 드래그/스냅, 트랙 재정렬, 다중 선택, 복사·붙여넣기, 확대·축소·스크롤, 카메라/에셋 선택기와 오류 배지를 우선순위로 둔다.
6. **키트가 제공하는 진단 기능은 활성 키트에 묶어 수명주기를 관리한다.** [`ModuleCatalog`](../Source/Engine/Module/ModuleCatalog.h)와 [`ModuleLoaderSubsystem`](../Source/ModuleManager/ModuleLoaderSubsystem.h)는 이미 프로젝트에서 활성화된 키트의 의존성·로드 순서·활성 여부와 모듈 수명주기를 관리하므로 별도의 키트 로더/매니저를 중복 구현하지 않는다. 대신 Dev 전용 Sequencer 진단 매니저/레지스트리가 엔진 공통 재생 정보와 선택된 키트의 진단 제공자를 합친다. 공통 영역은 현재 프레임·활성 항목·지나간 이벤트·카메라 신호/블렌드 상태를 제공하고, 키트 제공자는 자기 이벤트의 의미, 조건식 판정 이유, 게임플레이 결과를 선택적 섹션으로 해석한다. 제공자는 키트 모듈이 활성일 때만 등록·표시하며, 모듈 언로드/핫 리로드 전에 등록과 구독을 해제해 함수 포인터·객체가 내려간 DLL을 가리키지 않도록 한다. 현재 SequencerPanel의 재생은 편집 중 미리보기이고, 런타임 [`SequencePlayerComponent`](../Source/Engine/Sequencer/SequencePlayerComponent.h)의 정보를 통합해 보여 주는 컷신 디버거는 확인되지 않았다. 런타임 플레이어를 골라 타임라인 플레이헤드와 활성 클립/컷/스폰, 최근 발화 이벤트와 대상·결과, 바인딩 누락, 트랙 샘플 값 및 적용 실패를 표시한다. 카메라는 컷 대상과 컷 전환, 설정된 블렌드 시간뿐 아니라 실제 전환 진행량/가중치도 연결한다. 시퀀서에 없는 범용 조건/전이 모델을 새로 가정하지 않고, 조건 판정은 해당 키트 제공자가 보고한다. 패널은 읽기 전용으로 두고 이벤트 기록은 고정 용량으로 제한한다.
7. **검증:** XML 왕복·기존 에셋 호환, 바인딩이 다른 두 씬에서의 재사용, 대상 삭제/이름 변경, 시퀀스 완료·중단·되감기·루프, 카메라 컷/블렌드/렌즈 키, 에셋 누락, 이벤트 중복·누락 및 루프 경계, 트랙 추가와 Undo/Redo를 모델 테스트 및 자동화 시나리오로 검증한다. 에디터 UI 변경은 [`EditorUI`](agents/EditorUI.md) 규칙과 시퀀서 UI 캡처 시나리오를 따른다.

**우선순위 판단:** 지금 있는 항목 추가/삭제·키 편집기를 다시 만드는 것이 아니라 (1) 안정적인 씬 바인딩과 선택 UI, (2) 컷씬 종료/원복 정책, (3) ModuleCatalog/ModuleLoaderSubsystem 수명주기를 재사용하는 진단 제공자 매니저와 재생 중 이벤트·대상·실제 카메라 블렌드 진행량 패널, (4) 카메라 컷·렌즈 저작 경험을 먼저 개선한다. 키트 전용 디버깅은 해당 키트가 활성일 때만 붙이고, 엔진 공통 시퀀서에 키트별 의존을 넣지 않는다. 오디오·애니메이션·대사는 실제 게임 컷씬 사례를 기준으로 일급 트랙 우선순위를 정한다. 새 트랙을 쉽게 추가하는 목적은 확장 계약으로 풀되, 데이터 전용 플러그인이나 Lua 도입으로 성급히 일반화하지 않는다.

### VFX 저작 · 캐릭터 잔상/분신 연출 고도화 (코드 대조 2026-11-07)

**결론:** 이펙트 제작과 미리보기의 기본 토대는 있다. 방출기 설정·수명 커브·색 커브를 데이터로 편집하고 파티클을 재생할 수 있으며, `Ribbon`은 꼬리·칼 궤적에 바로 쓸 수 있다. 그러나 캐릭터의 애니메이션 포즈를 복제해 잔상으로 남기거나, 독립된 분신을 만들고 페이드/동기화하는 전용 런타임·에디터 워크플로는 확인되지 않았다. 따라서 붉은사막과 같은 캐릭터 중심의 잔상·분신 연출을 현재 VFX 시스템만으로 작업자가 편하게 저작할 수 있다고 보기는 어렵다.

- **이미 가능한 것:** [`VFXEffectDef`](../Source/Engine/VFX/VFXEffectDef.h)는 CPU/GPU 방출기, 빌보드·Ribbon·메시 렌더, 생성률/버스트, 수명·크기/색 커브, 충돌, 파티클 라이트와 사용자 파라미터를 정의한다. [`CatalogPanel`](../Source/Editor/Panels/Catalog/CatalogPanel.h)은 `.vfx.xml`을 포함한 카탈로그 XML을 표로 편집하고 실제 로더로 검증한다. 중첩된 크기/색 커브에는 키 추가·삭제와 시간/값/보간 편집, 곡선 그래프 및 색 그래디언트 미리보기가 있다([`CatalogTableEditor`](../Source/Editor/Panels/Catalog/CatalogTableEditor.cpp)). 별도 [`VFXPreviewPanel`](../Source/Editor/Panels/VFX/VFXPreviewPanel.h)은 효과를 재생·재시작·정지하고 방출기 정보를 보여 준다. 즉 기본 에셋 편집기는 있으나 전문 노드 그래프 편집기는 아니다.
- **잔상에 재사용할 수 있는 것과 없는 것:** `VFXRenderMode::Ribbon`은 순서대로 생성된 파티클 위치를 이어 꼬리·칼 궤적을 그리므로 독립적인 마법 궤적은 가능하다. 메시 방출기는 정적 메시를 입자마다 그린다. 반면 VFX 파티클 데이터에는 스켈레탈 포즈/스킨 팔레트 스냅숏이나 이미 그려진 캐릭터의 시점을 보존하는 기능이 없고, `SkeletalMeshComponent`와 VFX 메시 방출기 사이에 포즈 복제 경로도 확인되지 않았다. 따라서 캐릭터의 현재 포즈를 여러 시점에 고정해 반투명으로 페이드시키는 잔상은 단순히 Ribbon이나 메시 파티클 설정만으로 해결되지 않는다. 애니메이션을 계속하는 분신도 같은 이유로 VFX 파티클과 별개의 스켈레탈 외형/포즈 수명 관리가 필요하다.
- **저작 UX의 간극:** 카탈로그 커브 창은 키를 숫자로 편집하고 곡선을 표시하지만 키를 그래프에서 직접 끌어 편집하는 전문 VFX 커브 도구는 아니다. VFX 미리보기는 읽기 전용이고, 카탈로그 저장 후 별도 창에서 다시 읽어 재생하므로 편집·미리보기 간 왕복이 있다. 미리보기에서 캐릭터 애니메이션 타깃, 잔상 포즈 간격/지속시간, 재질 투명도, 효과 단계별 on/off를 함께 조정하는 기능도 확인되지 않았다.
- **권장 고도화 순서:** (1) 기존 VFX 에셋의 곡선 편집과 미리보기 왕복을 실제 제작자 시나리오로 점검하고, 먼저 저장 후 자동 갱신·방출기 격리/단계 재생·타깃 씬 프리뷰를 보강한다. (2) 캐릭터 잔상은 VFX에 본 스냅샷을 억지로 넣기보다, 스켈레탈 렌더링이 소유하는 제한된 `PoseAfterimage` 기능으로 포즈/메시/머티리얼 참조를 고정 시간 동안 보존하고 투명도 곡선으로 그리는 최소 수직 슬라이스를 만든다. 포즈 버퍼 수, 캡처 빈도, 화면 밖/LOD, 재사용 풀과 메모리 상한을 명시하고 원본 캐릭터 애니메이션·물리 상태를 복제하지 않는다. (3) 분신이 실제 게임플레이에서 필요하면 별도의 캐릭터 프리팹/애니메이션 인스턴스로 구현하고, 복제 포즈 재생형인지 AI/전투가 가능한 독립 개체인지 요구를 구분한다. (4) 그런 연출을 반복 제작하는 사례가 확인된 뒤에만 전용 VFX/캐릭터 연출 패널을 확장한다. 임의 그래프/모듈 시스템을 먼저 도입하지 않는다.
- **검증:** 정지 포즈와 빠른 애니메이션, 체형/메시 변경, 여러 겹 잔상, 투명 정렬·그림자, 저사양 제한과 반복 스폰/해제를 자동화 시나리오와 GPU/CPU 메모리 측정으로 확인한다. 잔상은 미관만이 아니라 포즈 캡처 비용과 투명 드로우 호출을 늘리므로 품질 단계/예산에 따라 명시적으로 제한한다.

### DevTools 개발 도구 고도화 (코드 · Graphify 대조)

**결론:** DevTools는 단순한 콘솔/HUD가 아니다. 배포 빌드에서 분리된 공유 모듈로, 파일 감시·설정 및 셰이더 리로드·네트워크 회선 흉내·RenderDoc·HUD·콘솔 등을 이미 제공한다. 에디터에는 별도 프로파일러와 버그 리포트 도구가 있고, 프레임 트레이스 저장/느린 틱 자동 캡처도 있다. 따라서 기능을 더 늘리기 전에 **기존 도구 사이의 상태·결과 연결**과 **재현 가능한 진단 자료**를 보강하는 편이 가치가 크다.

- **현재 기반:** [`DevTools/CMakeLists.txt`](../Source/DevTools/CMakeLists.txt)는 DevTools를 공유 DLL로 두며 엔진이 이 모듈을 알지 못하도록 확장점에 연결한다. App·Server·EditorModule·GameFramework가 같은 개발 도구를 쓰고, Shipping은 DevTools를 링크하지 않는다. [`DevCommandRegistry`](../Source/Engine/Console/DevCommandRegistry.h)와 `SW_DEV_COMMAND`는 여러 모듈의 명령 등록/해제, 도움말 및 자동완성 기반을 제공한다. [`DevConsole`](../Source/DevTools/Console/DevConsole.h)은 에디터 Output Log와 게임 창 오버레이가 공유하며 표준 입력 명령 채널도 있다.
- **이미 있는 관측·캡처:** [`DebugHUD`](../Source/DevTools/DebugHUD/DebugHUD.h)는 등록형 섹션을 제공하고 FPS/프레임 시간, CPU·GPU 구간, 드로우, 메모리, 씬 오브젝트, 물리, 오디오, 입력, 카메라 정보를 표시한다. [`ProfilerPanel`](../Source/Editor/Panels/Profiler/ProfilerPanel.h)은 구간·GPU 패스·타임라인·호출 트리·메모리·GPU 메모리를 다루고 Tracy와 RenderDoc 연결을 제공한다. 프레임 구간 및 Chrome Trace/Perfetto 내보내기, 느린 틱 자동 캡처, 메모리 예산 감시도 존재한다. [`BugReport`](../Source/Engine/Renderer/Capture/BugReport.h)는 메모, 스크린샷, 로그, 씬 사본, 카메라 위치, RHI/빌드 정보, 재현 명령과 가능한 경우 최근 트레이스를 모은다.
- **이미 있는 개발 루프:** [`DevToolsHost`](../Source/DevTools/DevToolsHost.cpp)는 설정 리로드, 콘텐츠 폴더 감시 서비스, 수동 셰이더 재컴파일, [`RenderDocCapture`](../Source/DevTools/RenderDoc/RenderDocCapture.h), [`NetLineEmulationSubsystem`](../Source/DevTools/Net/NetLineEmulation.h), 서버 포즈 오버레이, 프레임 스톨 검증, 오래된 Saved 산출물 정리를 호스트 생명주기에 연결한다. `ConfigReloadSubsystem`은 실패한 설정 파일의 기존 값을 유지하고 오류를 남긴다. 이 범위를 고려하면 기본 콘솔, HUD, 프로파일러, 회선 흉내를 처음부터 다시 만들 필요는 없다.

**확인한 간극과 권장 순서**

1. **버그 리포트를 재현 자료로 확장한다.** `BugReport.h`는 입력 녹화기가 전역으로 없어서 현재 리포트에 입력 스트림을 담지 않는다고 명시한다. 첫 단계는 사용자가 직접 시작/정지하는 제한 시간 입력 기록과 시각 정보를 리포트에 추가하고, 씬/설정/에셋 버전 또는 해시와 활성 모듈 구성을 함께 남기는 것이다. 전체 결정론 재생을 약속하지 말고, 먼저 기록된 입력을 동일 빌드/콘텐츠 조건에서 재생할 수 있는 범위를 정의한다. 로그·씬·설정은 민감한 값이 들어갈 수 있으므로 공유 전에 포함 항목을 검토하고 제외할 수 있게 하며, 자동 업로드는 별도 동의·정책 없이는 추가하지 않는다.
2. **리로드 결과를 한 곳에서 추적한다.** 설정, 에셋 캐시, 셰이더는 서로 다른 경로에서 감시/갱신되고 일부는 에디터 전용이다([`AssetHotReload`](../Source/Editor/Common/Workspace/HotReload/AssetHotReload.h), [`ConfigReloadSubsystem`](../Source/DevTools/AssetReload/ConfigReloadSubsystem.h), [`ShaderRecompiler`](../Source/DevTools/Shader/ShaderRecompiler.h)). 경로별 마지막 요청·성공/실패·실패 원인·현재 적용 버전을 모아 Output Log와 에디터에서 조회할 진단 뷰를 추가하면, 이전 값이 유지되는 상황이나 오래된 리소스를 빠르게 식별할 수 있다. 기존 리로드 소유자와 오류 처리를 대체하지 않는 읽기 전용 집계로 시작한다.
3. **성능 측정을 자동 회귀 판정에 연결한다.** 현재 측정은 수동 패널/명령과 텍스트 보고·트레이스 중심이다. 기존 `-gv_profileFrames`/`-gv_profileSeconds`, 성능 모델, 자동화 시나리오를 재사용해 시나리오별 측정 구간과 기기/빌드/RHI/콘텐츠 메타데이터를 기계 판독 가능한 산출물로 남기고, 동일 조건의 기준선과 명시적 예산을 비교하는 경로를 검토한다. 기기 편차가 큰 전체 CPU/GPU 시간은 초기 CI에서 절대 실패 기준으로 쓰지 말고, 고정된 자동화 환경과 안정적인 카운터부터 판정한다. 기존 Tracy/Perfetto 분석 기능은 유지한다.
4. **게임/키트별 도구는 등록 확장점을 통해 제공한다.** HUD 섹션과 개발 명령은 이미 엔진·키트·게임에서 등록할 수 있다. 게임별 임시 패널을 DevTools 코어에 넣기보다 등록된 섹션/명령을 이용해 월드 상태, 네트워크 권위 차이, AI/액션 상태 등 해당 게임에서만 의미 있는 진단을 보탠다. 실제 반복 사용이 확인된 진단만 공통화한다.
5. **시각화 도구는 있는 것을 연결하고, 비어 있는 런타임 진단만 보충한다.** 씬 Hierarchy의 텍스트 검색과 개별 뷰포트 시각화 토글(물리 형상, NavMesh, 카메라 절두체, 디버그 선 등)이 이미 있다. Scene 뷰에는 `LODLevel`/`LODFadeCode` 색상 모드가 있어 거리 변화에 따른 LOD 전환을 볼 수 있지만, 머티리얼 셰이더 메시만 색을 읽고 다른 셰이더 경로는 회색이다. Animation Graph 미리보기, 리그/본 디버거, Behavior Tree의 실행 노드 표시, 선택 오브젝트의 Ability 런타임 상태 패널도 각각 존재한다. Render Targets 패널 역시 타깃 이름·포맷 검색, 미리보기, 채널/깊이 보기, 픽셀 값 확인을 제공한다. 그러므로 이 도구들을 다시 만드는 대신 다음 공백을 좁힌다.
   - Quest에는 카탈로그/로그 런타임 기반은 있으나 진행 중 상태를 보여 주는 전용 디버거는 확인되지 않았다. [`QuestLog`](../Source/GameFramework/Runtime/Gameplay/Quest/QuestLog.h)는 퀘스트 상태·단계·목표별 개수·선택 대기와 시작/진행/완료/실패 이벤트를 제공하므로, 이를 이용해 활성 퀘스트·단계·목표 달성도·전이 및 실패/대기 이유를 읽기 전용으로 표시한다.
   - **기믹 그래프 편집기와 기믹 런타임 디버거는 역할이 다르다.** [`GimmickGraphPanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/Gimmick/GimmickGraphPanel.h)은 그래프 구성·배선·매개변수를 편집하고 검증하는 저작 도구다. 회로는 노드별 센서 값, 출력 비트와 상태 슬롯을 이미 유지·저장하지만, 실행 중 각 노드의 입력/출력 변화, 활성 경로, 해당 액추에이터 대상과 변화 원인을 연결해 보여 주는 전용 런타임 뷰는 확인되지 않았다. 편집 패널은 그대로 두고, 선택한 회로에서 단계별로 노드 상태와 선의 신호를 강조하고 최근 전이 기록 및 대상 오브젝트 변화를 읽기 전용으로 추적한다. 일시정지/단계 진행은 기존 플레이 제어에 연결하고 별도 실행 상태를 만들지 않는다.
   - **퀘스트·아이템·해금은 개별 값 조회가 아니라 진행 조건 추적으로 다룬다.** [`SessionStateComponent`](../Source/GameFramework/Runtime/Gameplay/SessionState/SessionStateComponent.h)는 플래그·퀘스트 로그·인벤토리를 한 세션 상태에 보관한다. [`Inventory`](../Source/GameFramework/Runtime/Gameplay/Inventory/Inventory.h)는 슬롯과 아이템 수량, [`GameFlags`](../Source/GameFramework/Runtime/World/Query/GameFlags.h)는 조건식이 읽는 이름별 정수 값을 제공하지만, 이 값들을 한곳에서 보고 퀘스트/아이템 조건이 왜 달성되거나 해금되지 않았는지 추적하는 도구는 확인되지 않았다. 세션/플레이어별로 퀘스트 목표 진행과 완료, 인벤토리 보유량, 플래그·조건식 결과, 해금 결과를 모아 표시하고, 가능한 경우 이를 바꾼 게임 이벤트나 기믹/액션까지 연결한다. 카탈로그 정의값과 플레이어별 런타임 상태는 구분하고, 테스트용 강제 변경은 읽기 전용 디버거와 섞지 않는다.
   - Ability Debugger는 어빌리티 전용이며, 임의 Action의 호출·실행·완료·실패를 추적하는 범용 Action 런타임 뷰는 확인되지 않았다. 우선 실제 실행 경로가 보유한 데이터를 확인하고, 액션 종류와 키트의 확장점을 등록할 수 있는 공통 실행 추적을 마련한다. 저장된 액션/그래프 저작 패널과 런타임 상태 디버거는 분리한다.
   - **NPC 일정·행동 디버깅은 부분적으로 이미 있다.** [`ScheduleDebugPanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/Schedule/ScheduleDebugPanel.h)은 NPC별 오늘 일정 타임라인과 현재 행동 설명을 제공하고, [`ScheduleSystem::explainNPC`](../Source/GameFramework/Runtime/Character/AI/Schedule/ScheduleSystem.cpp:612)는 지금 구간, 일정 출처, 끼어들기 스택, 후보 루틴/행사와 실패한 조건 절을 보여 준다. [`BehaviorTreePanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/AI/BehaviorTreePanel.h)은 선택한 오브젝트/실행기의 활성 노드를 트리에서 강조한다. 하지만 NPC 한 개체에서 일정·조건·현재 Behavior Tree/실행 Action·블랙보드 값을 한 흐름으로 연결하는 디버거는 아니다. 기존 두 패널을 새로 만들지 말고, NPC 선택을 연동하고 활성 트리/노드 및 블랙보드 값을 표시하며 일정 조건·끼어들기에서 현재 행동으로 이어지는 근거를 묶는다. 범용 AI 상태 패널을 추가하기 전에는 스케줄 없는 NPC와 다른 AI 실행기도 같은 인터페이스로 조회할 필요가 있는지 확인한다.
   - **캐릭터 상태·스킬은 Ability Debugger의 현재 스냅샷을 확장한다.** [`AbilityDebugPanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/Ability/AbilityDebugPanel.h)은 선택 오브젝트의 어트리뷰트 기본/현재 값, 활성 이펙트, 태그 개수, 부여 어빌리티와 쿨다운을 읽기 전용으로 보여 준다. 하지만 체력/상태머신·경험치와 레벨·스킬 랭크 및 포인트·해금 조건·아이템 획득 이력을 통합하지 않고, 값 변화의 시간순 원인도 기록하지 않는다. [`SkillTreeState`](../Source/GameFramework/Kits/Genre/RPG/MonsterHuntRPG/Rule/SkillTree.h)는 특정 키트의 스킬 트리 상태이므로 공통 Ability Debugger가 자동으로 볼 수 없다. 우선 캐릭터별 런타임 요약에서 기존 컴포넌트의 상태·스킬/레벨/퀘스트/인벤토리 데이터를 모으고, 스킬 해금은 요구 랭크·레벨·사용 점수와 판정 결과를 설명한다. 그다음 제한된 이벤트 기록으로 체력/상태·능력치·스킬·획득 데이터의 변화와 출처(피해/보상/퀘스트/아이템 사용)를 연결한다. 키트 전용 스킬 시스템은 등록형 제공자로 붙이며 상태 조회는 읽기 전용으로 둔다.
   - **물리 진단은 셰이프 와이어프레임과 시뮬레이션 상태를 구분해 확장한다.** 현재 Physics Shapes 시각화는 정적/키네마틱/동적, 수면, 트리거를 색으로 나눠 2D·3D 충돌 셰이프를 그리며, 게임 뷰포트에는 물리 씬의 바디 셰이프 디버그 선을 그리는 경로와 물리 HUD 통계가 있다. 이는 형상·전체 수치 확인에는 유용하지만 접촉점/법선/충격량과 트리거 진입·이탈, 관절 연결·축·한계/모터, 충돌 레이어 필터를 공간에서 추적하는 도구와는 다르다. 접촉 이벤트는 물리 씬에 존재하므로 첫 단계는 선택 개체와 시뮬레이션 스텝에 연결된 접촉·트리거 오버레이 및 짧은 이벤트 기록을 제공하고, 그다음 Joint/Ragdoll의 연결 상태·축·제약 한계, 충돌 레이어 행렬과 질의 결과를 시각화한다. Jolt/Box2D 백엔드 간 진단 의미를 맞추고, 비활성 시 기록·그리기 비용이 들지 않게 한다.
   - **캐릭터 이동 디버깅은 별도 진단 축으로 추가한다.** 2D/3D Character Controller에는 실제 속도, 접지 여부·바닥 법선·딛고 있는 바디 등의 상태가 이미 있고, NavMesh Agent에는 목적/경로 상태, 희망 속도와 회피 후 속도, 다음 코너, NavMesh/오프메시 링크 상태가 있다. 다만 캐릭터 전용 뷰포트 디버거는 확인되지 않았고 컨트롤러가 받은 이동 요청 속도도 읽기 전용 상태로 공개되어 있지 않다. 선택 캐릭터에 캡슐, 접촉/접지 법선, 지지 바디, 이동·속도 벡터를 그리며 요청 속도→NavMesh 희망/회피 속도→컨트롤러 실제 속도와 위치 차이를 한눈에 비교한다. 3D 계단 높이·최대 경사, 2D 접지/경사 판정, 점프·공중·움직이는 바닥/루트 모션 전환, NavMesh 모서리와 오프메시 링크를 상태와 함께 표시하고, 실패 전후의 짧은 스텝 기록으로 미끄러짐·벽 걸림·뜀/낙하 판정 오류를 추적한다. 요청 속도 계측을 추가한다면 기본 비활성 및 저비용으로 유지하고, 2D/3D와 두 물리 백엔드에서 같은 의미를 보장한다.
   - **플랫폼·지형 저작은 이미 있으므로 별도 지형 편집기를 중복하지 말고, 표면 의미와 이동 진단을 잇는다.** [`TerrainBrushTool`](../Source/Editor/Viewport/TerrainBrushTool.h)은 높이·레이어 가중치·구멍을 브러시로 편집하고 크기 조정과 Undo/Redo 및 저장을 지원하며, [`TerrainColliderComponent`](../Source/Engine/Environment/Terrain/TerrainColliderComponent.h)는 렌더 청크와 대응하는 정적 충돌 메시를 만들고 높이 변경 시 영향받은 청크만 다시 만든다. [`TileMapPanel`](../Source/Editor/Panels/TileMap/TileMapPanel.h)은 2D 타일·워프·플래그·데이터 레이어를 편집하고 [`TileMapRendererComponent`](../Source/Engine/TileMap/Component/TileMapRendererComponent.h)는 단단한 타일에서 충돌 바디를 생성한다. 일반 물리 셰이프 편집/시각화도 있어 플랫폼 충돌 형상과 높이장 편집의 기반은 갖춰져 있다.
     - **저작 데이터의 분절:** [`PlatformerMotor2D`](../Source/GameFramework/Runtime/Character/Movement/PlatformerMotor2D.h)의 Solid/OneWay/Ladder/Hazard 격자는 타일맵 에셋·에디터와 별도의 모델이다. 한쪽 발판·무너지는 발판·점프대·컨베이어·오르기 구역과 움직이는 발판 기믹도 각각 존재하지만, 높이장 스플랫 레이어·물리 재질·타일 데이터와 캐릭터 이동 반응을 잇는 공통 표면 계약은 확인되지 않았다. `computeLayerWeightsAt`은 서버에서도 읽을 수 있는 표면 질의 기반이지만, 현재 캐릭터 이동/발소리에서 이를 소비하는 호출 경로는 찾지 못했다. 그러므로 타일맵·높이장·충돌 메시를 한 포맷으로 합치기보다, 캐릭터가 지지 표면에서 읽을 표면 종류/식별자, 법선, 표면 속도, 이동 계수와 발소리·효과 분류를 좁은 공통 질의로 제공하고 기존 형식별 데이터를 어댑터로 연결한다. 실제 게임이 필요로 하는 속성만 채택하고 물리 마찰과 게임 이동 계수는 같은 값이라고 가정하지 않는다.
     - **디버깅 연결:** 앞의 캐릭터 이동 디버거를 확장해 접지한 바디/컴포넌트와 좌표(타일 또는 지형 청크), 표면 분류·레이어 가중치, 접촉 법선과 경사 한계, 지지체가 전달한 속도, 입력/요청 속도와 실제 이동 결과를 한 화면에서 비교한다. 기존 Physics Shapes·NavMesh 시각화를 재사용하고 새 전용 툴은 상태 연결에 집중한다. 지형 브러시 변경 후 충돌 청크가 갱신됐는지, 타일의 충돌 분류와 이동 판정이 일치하는지, NavMesh와 실제 충돌 경계가 어긋나는지도 표시한다. Terrain은 현재 위치·방향·크기 처리 제약(회전·크기는 반영하지 않음)을 편집 UI에서 분명히 알린다.
     - **검증:** 높이장 경사·구멍·브러시 수정, TileMap 경계와 OneWay/사다리/위험 타일, 정적·움직이는 발판 및 컨베이어 위 승강/이탈을 자동화 시나리오로 재현한다. 시각 높이·충돌·내비/이동 판정과 표면 질의가 같은 영역을 가리키는지, 지지체가 움직일 때 속도 전달과 충돌이 안정적인지 확인한다. 먼저 현재 에셋과 각 키트에서 실제로 쓰는 표면 속성을 목록화하고, 공통 계약은 필요한 최소 항목으로 시작한다.
   - Hierarchy 검색, Render Targets 검색, 패널별 실행 상태는 서로 독립적이다. 우선 통합 런타임 탐색/필터에서 이름·유형·컴포넌트·상태·태그 같은 기존 데이터를 대상으로 필터링하고, 선택한 결과를 Hierarchy/Inspector의 같은 개체로 연결한다. LOD 모드에는 적용 경로를 넓히고, 개체별 선택 단계·화면 크기/임계값을 확인할 수단을 추가한다. Render Targets 패널은 재사용하면서 패스와 첨부의 생산자·소비자, 실행 순서, 크기·포맷 및 수명 정보를 연결해 그래픽스 문제의 원인을 추적할 수 있게 한다.

**경계와 완료 기준:** 원격 명령 실행 서버는 현재 확인된 필요가 아니며, 인증·권한·네트워크 노출을 설계하지 않은 상태로 추가하지 않는다. 진단 수집은 비활성일 때 런타임 비용이 거의 없어야 하고, 캡처 크기/기간·보존 정책을 제한하며 개인 데이터를 기본 포함하지 않아야 한다. 검증은 Dev Client·전용 Server·Shipping에서의 컴파일/기능 분리, Windows/Linux 파일 감시, 리로드 실패 시 이전 유효 상태 보존, 캡처 취소/저장 실패, 입력 기록 누락과 빌드/콘텐츠 불일치, 성능 산출물의 반복 측정 편차를 포함한다.

**우선순위 판단:** 가장 먼저 기존 `BugReport`에 제한된 입력 기록과 재현 환경 정보를 연결하고, 그다음 리로드 결과를 읽기 전용으로 통합한다. 시각화는 기존 LOD·Render Targets·Animation·Ability·Behavior Tree·NPC Schedule·물리 셰이프 기능을 보존하면서 기믹 실행 추적, 퀘스트/아이템/해금 조건, 캐릭터 성장·스킬 변화와 출처, NPC 일정-행동-블랙보드 연동, 범용 Action 런타임 상태 및 물리 접촉과 캐릭터 이동 진단의 최소 수직 경로를 보충하고, 반복 사용이 확인되면 통합 탐색/필터를 확장한다. 진행 시스템 디버깅은 우선 읽기 전용의 현재 상태와 이벤트 원인 추적부터 만들고, 임의 값 변경은 별도 테스트 제어로 분리한다. 성능 예산은 자동화 환경의 반복성 자료를 확보한 뒤 좁은 범위에서 시작한다. 근본 원인은 개별 도구의 부재보다 진단 흐름이 서로 다른 소유자에 분산된 점이며, 같은 단절은 설정·에셋·셰이더 리로드 결과와 프로파일링 결과에도 나타날 수 있으므로 각 시스템을 새로 만드는 대신 공통 진단 산출물로 연결한다.

### 날씨·캐릭터·지면 표면 상호작용 (코드 대조 2026-11-07)

**결론:** 날씨 변화와 캐릭터의 젖음 표현을 처음부터 새로 만들 필요는 없다. 날씨는 `StatBlock` 값과 전환 보간을 제공하고, 캐릭터에는 `Wet` 등 표면 채널·감쇠·머티리얼 바인딩 기반이 있다. 하지만 날씨 상태가 캐릭터 표면 상태를 갱신하는 연결은 확인되지 않았다. 발자국 알림은 물리 재질에 따른 소리만 재생하며, 눈 누적·발자국 흔적·눈 표면 변형은 확인되지 않았다. 즉 필요한 것은 이 기존 데이터 경로들을 연결하고, 지면 반응의 표현 및 수명 정책을 추가하는 것이다.

- [`WeatherSystem`](../Source/GameFramework/Runtime/World/Environment/WeatherSystem.h)은 임의 이름의 날씨 값을 보간하고 저장 상태를 제공한다. [`WeatherCatalog`](../Source/GameFramework/Runtime/World/Environment/WeatherSystem.cpp)는 `<Values>`를 읽지만 날씨 값을 렌더러나 캐릭터 외형에 자동 적용하지 않는다. 현재 [`prairie.weather.xml`](../Content/game/wildwest/data/prairie.weather.xml)은 기온 값만 정의하고, 해당 키트는 이를 생존 규칙의 체감 온도 계산에 사용한다. 눈/강수 종류나 눈 표면 상태의 공통 계약은 발견되지 않았다.
- [`CharacterSurfaceState`](../Source/Engine/Character/Fit/SurfaceState.h)와 [`default.surfacechannels.xml`](../Content/engine/character/default.surfacechannels.xml)은 영역별 `Wet`·`Dirt`·`Blood` 값, UV 마스크, 감쇠를 이미 제공한다. [`CharacterSurfaceBinding`](../Source/GameFramework/Runtime/Gameplay/Appearance/CharacterSurfaceBinding.cpp)은 이를 머티리얼 파라미터와 마스크 텍스처로 전달한다. 다만 상태를 바꾸는 것은 게임플레이 호출자의 책임이며, 전체 코드 검색에서 날씨에 따른 `Wet` 갱신은 찾지 못했다. 표면 상태는 Appearance의 채널 경로가 설정된 캐릭터에만 활성화된다.
- [`WaterBodyComponent`](../Source/Engine/Environment/Water/WaterBodyComponent.h)는 파도 포함 수면 높이와 한 지점의 수중 여부/깊이를 질의할 수 있고, [`BuoyancyComponent`](../Source/Engine/Environment/Water/BuoyancyComponent.cpp)는 강체 폰툰의 잠긴 비율을 계산한다. 그러나 이 침수 판정은 캐릭터 의복/몸 표면 상태에 연결되지 않았고, 사람 캐릭터의 전신 침수율이나 부위별 노출 상태를 제공하지 않는다. 물 표면에 들어갔다는 참/거짓만으로 젖음량을 정하지 말고, 우선 대표 신체 지점의 침수 깊이/비율과 표면 상태를 정해 점진적으로 올린다.
- [`Footstep` 애니메이션 알림](../Source/Engine/Character/AnimationNotify/AnimationNotifyHandlers.h)은 발 소켓 아래를 질의해 물리 재질별 소리를 고르고 기록한다. 현재 핸들러에는 지면에 발자국을 남기거나, Terrain의 레이어 가중치를 사용해 표면 반응을 고르는 처리가 없다. [`TerrainComponent`](../Source/Engine/Environment/Terrain/TerrainComponent.h)의 CPU 레이어 가중치 질의와 높이장 수정 경로는 재사용 후보지만, 발자국마다 지형 높이/충돌 메시를 직접 변형하는 방식은 충돌·내비게이션 갱신 비용과 게임플레이 표면을 오염시키므로 기본 접근으로 삼지 않는다.
- **사구·개미지옥 같은 위험 지형:** Terrain 레이어 및 재질로 모래 지형을 표현하고 브러시로 형태를 편집할 수 있으며, [`GimmickGraphPanel`](../Source/GameFramework/Plugin/Editor/GameplayTools/Gimmick/GimmickGraphPanel.h)과 [`GimmickSensorComponent`](../Source/GameFramework/Runtime/Gameplay/Gimmick/GimmickSensorComponent.h)은 시각 회로와 점유자 감지를 제공한다. 그러나 내장 `Hazard`는 정해진 주기의 피해를 주는 액추에이터이며, 모래에 빠지는 정도, 이동 저항, 탈출 입력, 구조/실패 조건을 제어하지 않는다. 모래 레이어나 정적 사구 메시만으로는 그런 효과가 생기지 않는다.
  - **저작 방향:** 첫 수직 경로는 기존 Terrain/재질로 만든 모래 표면과 별도의 환경 상호작용 구역을 결합한다. 구역은 경계, 모래 표면 종류, 진입 후 가라앉는 속도/한계, 이동 저항, 탈출 또는 구조 조건을 데이터로 설정한다. 매 캐릭터마다 Heightfield나 충돌 메시를 파내는 대신, 제한된 런타임 상태로 효과를 계산한다. 일반 모래의 보행 감속과 실제 함몰/탈출 기믹은 다른 설정 모드로 분리해 단순 효과에 복잡한 상태가 강제되지 않게 한다. 편집은 우선 기존 Inspector와 볼륨/기믹 배치 흐름을 재사용하고, 씬 제작에서 반복되는 작업이 확인된 후에만 경계 페인트·프로파일 미리보기를 위한 전용 패널을 만든다.
  - **물리·표현 일치:** 이동 제어기는 요청 속도를 받지만 현 코드에서 환경별 이동 저항을 공통 적용하는 입력은 확인되지 않았다. 영향을 받는 캐릭터의 이동 속도와 빠져드는 시각 표현은 같은 고정 스텝 상태를 기준으로 갱신하고, 표현만 지하로 내려가 충돌 캡슐이 지상에 남거나 반대로 충돌체만 사라지는 불일치를 막는다. 시작/완료/탈출에 따른 전이, 점프·대시·넉백·사망·씬 전환 시 상태 정리와 멀티플레이의 서버 권위도 명시한다. 동적 지형 변형이 실제 게임 요구라면 별도 선택 기능으로 두고 NavMesh·충돌 갱신 비용을 측정한다.
  - **디버깅·검증:** 기존 이동/물리 시각화에 구역 경계, 현재 점유자, 캐릭터별 침강 단계·체류 시간·이동 계수·탈출 진행도와 진입/이탈 원인을 연결한다. 고정 경로로 안전한 모래와 위험 구역을 왕복하고, 경계 모서리·빠른 이동·점프/대시 진입·겹치는 구역·상태 제거/복원·반복 탈출을 시나리오로 검증한다. 뷰포트에서 보이는 침강량과 컨트롤러/충돌 위치가 정의된 오차 안에서 일치하는지, 재진입 시 상태가 중첩되지 않는지, 전용 서버가 같은 게임플레이 판정을 내리는지도 확인한다. 현재 [`gimmickgraph.scenario.xml`](../Content/engine/automation/editor/gimmickgraph.scenario.xml)은 노드와 배선 편집 및 Undo를 확인할 뿐, 실행 중 구역 점유나 환경 반응은 검증하지 않는다.
- **최소 구현 방향:** 공통 표면 질의가 정착된 뒤 발걸음 이벤트가 접촉 위치·방향·표면 분류와 캐릭터/신발 정보를 한 번 전달하고, 표면 반응 계층이 눈/진흙/물 등 지원 표면에서만 발자국 효과를 만든다. 눈 자국은 먼저 고정 용량·공간 타일 기반의 시각 마스크/흔적과 제한된 감쇠·정리 정책으로 구현한다. 실제 눈 깊이가 이동 속도·저항에 영향을 주는 게임만 별도 게임플레이 값을 사용하고, 매 발걸음마다 Heightfield 충돌 형상을 다시 만들지 않는다. 강수와 물 침수는 서로 다른 입력으로 `Wet` 채널에 반영한다. 침수 깊이/지속시간에 따라 젖음이 증가하고, 물 밖에서는 채널의 건조 감쇠를 재사용한다. 캐릭터 전체가 같은 속도로 젖는 간단한 시작점으로 충분하며, 전신/부위별 침수와 의복 방수 차이는 표현·게임플레이 요구가 생길 때 확장한다. 실내/지붕 아래 강수 차단은 노출 데이터가 준비된 경우에만 적용하고, 일시정지·시간 배율과 일관되게 게임 시간을 쓴다.
- **오염·데칼 세척:** `Dirt`와 `Blood` UV 마스크는 표면 상태의 국소 표시로 쓸 수 있고 각 채널의 자연 감쇠도 있지만, 물에 닿았을 때 감쇠를 빠르게 하는 규칙은 없다. 코드에서 범용 런타임 Decal 컴포넌트/프로젝터는 찾지 못했다. 그러므로 현재는 “데칼이 물에 씻긴다”고 가정하지 않는다. 먼저 물이 `Wet`뿐 아니라 씻김 가능한 `Dirt` 등 지정 채널의 감소율에만 영향을 주도록 하고, 상처/찢김처럼 유지해야 하는 채널은 보존한다. 후에 실제 투영 데칼 시스템을 추가한다면 모든 데칼을 일괄 제거하지 말고, 씻김 여부와 물/시간에 따른 수명을 데칼 데이터가 명시하게 한다. UV 표면 마스크와 월드 공간 데칼은 저장·머티리얼·수명 경로가 다르므로 같은 구현으로 섞지 않는다.
- **저작·진단:** 기존 날씨 카탈로그와 캐릭터 채널·머티리얼을 재사용하고, 지면 반응을 위한 표면별 발자국 유형/효과와 강수·눈 매개변수는 실제 게임 에셋에서 필요한 최소 데이터로 저작한다. 에디터/DevTools에서는 선택 캐릭터의 날씨 입력, 표면 분류, 접촉 위치, `Wet` 값과 눈 흔적 생성/만료를 확인할 수 있게 한다. 별도 범용 날씨 편집기보다 날씨 값 미리보기와 표면 상호작용 검증을 기존 카탈로그/시나리오 경로에 연결한다.
- **검증 시나리오:** 제어된 비·눈·맑음 날씨와 야외/실내, 눈·흙·단단한 지면, 호수/강 테스트 씬에서 캐릭터를 정해진 경로로 이동시킨다. 비에 노출된 캐릭터의 `Wet` 값/머티리얼 반응이 올라가고 비가 그친 뒤 마르는지 확인한다. 발목/허리/전신 침수 단계에서 젖음 증가량이 깊이·노출 시간에 따라 달라지고, 물 밖에서 건조되는지 검사한다. 물 진입 시 `Dirt` 등 씻김 대상으로 지정된 채널만 감소하고, 상처/찢김·비대상 채널은 보존되는지 확인한다. 실내 강수 차단은 노출 데이터가 적용된 경우만 검사한다. 눈 위에서 양발이 올바른 위치·방향·간격으로 발자국을 만들고 지면 밖/실내/다른 표면에서는 잘못 생성되지 않는지, 흔적이 정해진 수명에 따라 줄고 반복 주행에서도 고정 용량을 넘지 않는지 확인한다. 날씨 전환·시간 배율·일시정지·반복 실행과 전용 서버에서의 게임플레이 상태 일관성도 확인한다. 실제 눈 지형 변형이나 투영 데칼이 요구되는 경우에만 렌더 표현, 충돌/이동 영향, 세척·저장 및 네트워크 권위를 별도 범위로 검증한다.

**우선순위 판단:** 먼저 날씨/침수→`Wet` 채널과 발걸음→표면 반응을 잇는 최소 시나리오를 만들고, 눈 흔적은 제한 용량의 시각 효과로 시작한다. 사구 함몰은 고정 경계·고정 스텝 상태·이동 및 표현 연동을 갖는 테스트 기믹으로 수직 검증한 다음 재사용성을 판단한다. 눈이나 모래가 실제 이동/충돌 형상을 바꿔야 한다는 요구가 확인되기 전에는 Heightfield 변형이나 범용 동적 지형 시스템을 추가하지 않는다. Graphify 그래프 파일은 현재 작업 폴더에서 찾지 못해 이 조사는 직접 코드 검색으로 대조했다.

## 통합 담당 판단(2026-11-08)

위 감사를 코드 규칙(구조로 푼다 · 폴백 없음 · 미사용은 쓰게 · 대기를 쌓지 않음)에 맞춰 정했다. "요구가 확인될 때만" 으로 적힌 항목 중 상용 엔진과 비교해 지금 정할 수 있는 것은 정했고, 측정이 필요한 것은 측정을 일감으로 넣었다(재지 않고 미루지 않는다).

**바로 고칠 결함(7 차 S1).**
- 1 인칭 총구: 소켓 · 외형 데이터가 없을 때 눈 아래 15 cm 로 가는 폴백을 지운다. `Muzzle` 이 없으면 오류로 멈추고, 데이터에 소켓을 채운다. 탄도선은 시점 총 앞에서 시작해 화면에 보이게 한다.
- `chance`: 식 안의 호출마다 굴림 차례를 섞는다(시드 + 호출 순번). 결정성은 유지한다.
- 관통탄: 한 걸음 안에서 남은 선분을 다시 질의해 모든 명중을 차례대로 모은다(언리얼 `SweepMulti` 와 같은 자리).
- 포탑: 쏜 뒤 생긴 벽을 탄이 비행 중에 맞게 한다(발사 순간 시야만 보지 않는다).
- 머티리얼 파라미터 묶음 핫 리로드, `ShaderCookStamp` 가 컴파일러의 실제 의존 목록(가려진 헤더 · 탐색 경로 포함)을 기록, X11 조합 중 글을 로캘 변환(UTF-8 가정 제거), 대기 카메라가 실제 뷰 종횡비를 받게, `InteractionSession` 을 `DepletingValue::take` 로.
- 종료 코드: `InitializationFailed` 를 표에 더한다(초기화 실패와 크래시를 가른다 — 언리얼도 초기화 실패 코드를 따로 낸다). `requestQuit` 은 `ProcessExitCode` 만 받는다.
- `LinuxScenarios.py` 의 WSL 경로를 `wslpath -a` 로 구한다. `AssetReferenceFields.generated.json` 갱신은 잠금 + 원자 교체. 리플렉션 파서 폴백의 동시 파싱 수에 상한을 둔다.

**계약을 형식으로 고정(S2).** 프로세스당 Engine 하나 · GameInstance 하나를 계약으로 정하고 중복 바인딩을 시작 오류로 막는다(테스트 포함 — 다중 엔진 요구가 생기면 그때 컨텍스트로 옮긴다). `GameInstance::initialize` 부분 실패의 단일 되감기 경로, `bindScopedService` 가 성공 여부를 돌려 필수 카탈로그 충돌을 초기화 실패로 전파, 수명 · `GameService` 범위 전환 · `GameStateSnapshot` 봉투 테스트. 카탈로그 참조: `checkReferences` 가 결과를 돌려 필수 참조가 깨지면 로드 실패, 선택 참조는 선언으로 표시, Ability 카탈로그의 이펙트 → 능력 · 세트 → 능력 연결 검사, XML 중복 id 는 오류(코드 API 의 교체 동작은 유지). 쿠커가 같은 규칙을 데이터 선언으로 읽게 한다. 테스트 틀: 케이스 옵션의 프로세스 격리, CTest 마다 JSON 보고, 매개변수 케이스의 안정 이름. 서버 서비스 서술자 `Server` · `Reliable` · `Validate` 메타데이터는 실제 RPC 경로로 쓰게 한다(2 차 묶음).
