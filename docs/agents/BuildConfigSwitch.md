> 질문: 개발 · 배포(· 플랫폼 · 타깃) 차이를 코드에서 어떻게 가르는가?
> 독자: 구성마다 다르게 동작해야 하는 코드를 쓰는 사람.
> 결론: 차이의 크기로 고른다 — 값뿐이면 `build::` 상수, 갈래 하나가 다른 구성에 없는 헤더 · 모듈을 쓰면 그 자리 `#if`, 기능 전체가 없으면 CMake 가 구현 파일을 고른다. 몇 줄짜리 차이로 파일 짝을 만들지 않는다.

## Build configuration switches

Pick the smallest form that fits the difference. The goal is the same in all three: one decision point, and code that is compiled in every configuration whenever possible so the configuration you did not build cannot rot.

| The difference is ... | Use | Example |
| --- | --- | --- |
| A value only — both branches use symbols every configuration has | `build::kShipping` (or `kWithClientCode` · `kWithServerCode`) from `Core/Foundation/BuildInfo.h`, read with plain `if` or `if constexpr`. Both branches compile everywhere; the dead one is dropped, and functions it calls need no definition in that configuration | the render diagnostics policy (`RenderDiagnostics::get` returns the constant default when `build::kShipping`), `GameSelection::select`, `ConfigManager::initializeSubsystem` (disk vs baked JSON) |
| A few lines, and one branch needs a header, type or module the other configuration does not build | `#if defined( SW_SHIPPING )` at that spot, in the one file. `if constexpr` cannot help: a discarded branch outside a template is still parsed and name-checked | Logger sink selection, the dev-command and automation registration macros (`DevCommandRegistry.h` · `AutomationWatch.h`) |
| A whole feature the configuration does not have (automation runner, DevTools host, module reload, server debug console, editor module) | The feature registers itself (`SW_MODULE_SUBSYSTEM` publishing an interface) from its own folder, and CMake excludes that folder. The host only looks the interface up; when it is absent and the run asked for the feature (`-scenario`, `-EnableEditor` …), startup fails with the reason | Unreal: a Developer/Editor module the shipping target does not link |

Rules:

- Platform chains end in `#else` + `#error "Unsupported platform"`. Name the platform in every branch: `SW_PLATFORM_WINDOWS` · `SW_PLATFORM_LINUX` · `SW_PLATFORM_ANDROID` · `SW_PLATFORM_WEB`, or `SW_PLATFORM_POSIX` for the three non-Windows platforms. Never `#if Windows #else`, never `!defined( SW_PLATFORM_* )`: a new platform must fail to compile at each decision, not run the wrong branch (Unreal `PLATFORM_*`). `py -3 -m Scripts lint platform-chains` checks it; exemptions and reasons are in `Config/Rules/Lint/PlatformChains.json`. CMake follows the same rule: a chain whose first condition is only platform tests (`WIN32`, `UNIX`, `CMAKE_SYSTEM_NAME STREQUAL`, `sw_platform_name STREQUAL`, host `CMAKE_HOST_*`) ends in `else()` + `message(FATAL_ERROR …)`, and `if(NOT WIN32)` is only a guard that returns or stops. Scripts read the host OS only from `Scripts/common/HostPlatform.py` (`isWindowsHost`, `kHost`, `executableName`), which stops on an unlisted host. Modules run on every platform unless `_listExcludedPlatform` in the manifest says otherwise.
- No file-name switches. Never exclude a file from a configuration by its name suffix (`*DevCommands.cpp`, `*Reload.cpp`, `*Shipping.cpp`). Dev-only code that registers itself (dev commands, dev online stand-ins) stays in the feature's `.cpp`; the registration macro does not register in Shipping and holds the handler in a `[[maybe_unused]]` constant, so the body compiles everywhere and is dropped from the shipped binary. Code that needs headers or libraries Shipping does not build lives in a `Dev/` folder — the only dev-only source patterns are `Tests/` and the `Dev/` folders listed in `Config/Rules/Layers/DevFolders.json` (`SW_DEV_ONLY_SOURCE_PATTERNS`; a `Dev/` folder outside that table stops configure).
- Do not split one class across files to make files shorter. A long file means the class holds several jobs: extract the job into its own class, or keep one file.
- No stub implementation files. A `<Name>Shipping.cpp` / `<Name>Off.cpp` that implements the same declaration with empty bodies keeps the host calling a feature that does not exist — the dependency points the wrong way. Invert it: the feature attaches to the host, not the host to the feature.
- Do not create a file pair for a difference of a value or a few lines — use the first two rows.
- Never re-derive the configuration from other macros (`#if !defined( _DEBUG )` and so on). `SW_SHIPPING` and `SW_TARGET_NAME` come from `cmake/Engine/BuildLayout.cmake`; `BuildInfo.h` mirrors them as constants. Client/server has no macro at all — read `build::kWithClientCode` · `kWithServerCode` and split client-only work by folder (`Client/`) or module (`_listTarget`).
- Client and server split symmetrically by folder name: a Server target builds no `Client/` folder (`SW_CLIENT_ONLY_SOURCE_PATTERNS`, gate `serverbuild`), a Client target builds no `Server/` folder (`SW_SERVER_ONLY_SOURCE_PATTERNS`, gate `clientbuild`; both in `[gatefolder]` of `TargetLayers.toml`). Shared code reaches the other side only through a published seam (`IGameClientPartFactory`, `IOnlineLocalServerFactory`) and gets an error when it is absent. A shared type does not live in a folder named after one side (`Engine/Config/ServerConfig.h`, not `Config/Server/`).
- No alias macros for a configuration. Dev-only code reads `SW_SHIPPING` itself (`#if !defined( SW_SHIPPING )`): an alias that means "not Shipping" makes a reader look up every definition. A switch that CMake turns off behind the code's back is the same problem: say the condition where the sources are excluded (`Source/Engine/CMakeLists.txt` excludes the automation runner for Shipping and the dedicated server).
- Test and dev hooks stop at Release. Shipping holds no automation runner, no automation registrations, no test global variables (`SW_TEST_GLOBAL_VARIABLE` is a folded constant there) and no dev counters on runtime classes — dev features live in `DevTools` / `Dev/` and observe the runtime through standard instrumentation (`SW_PROFILE_COUNT`). `py -3 -m Scripts shipping-check` fails when a test variable name is left in a shipping binary.
- Engine and Core still hold no editor-only function (`AGENTS.md`, Source/Editor row) — this file is about dev vs shipping behaviour of runtime code, not about `WITH_EDITOR` regions.
